> v4.1 是對 v4 的校正文件，不新增功能。內容來源：對照說明文件.md（v3.1.0）、Inter-Agent Protocol v1、claude-pilot-suite、gemini-cli-subagent 四份文件交叉分析。

## 一、移除的錯誤擔憂

### ❌ 誤判一：Gemini 雙倍 Token 消耗

**v4 分析曾指出：** gemini-reviewer 透過 Inter-Agent Protocol 接收程式碼內容，可能造成雙倍 Token 消耗（Claude 先讀 + 再傳 Gemini）。

**實際情況：**

說明文件.md 的 diff-only review 原則：

```bash
REVIEW_FILE=$(mktemp /tmp/review-XXXXXX.txt)
git diff --no-color HEAD~1 > "$REVIEW_FILE"
cat $REVIEW_FILE | gemini --model gemini-2.5-flash -p "..." 2>&1
```

Team Lead 從未讀取原始碼，只產生 git diff。三個 reviewer 共用同一份 diff 檔案，Gemini 直接接收，沒有中間層轉譯。

`gemini-cli-subagent` 的「傳路徑不傳內容」規則適用於大型檔案摘要情境，不適用於 code review——review 本來就需要看 diff 內容本身，無法用路徑代替。

**結論：** 此擔憂不成立，從 v4 分析中移除。

---

### ❌ 誤判二：違反「子任務只能向下委派」原則

**v4 分析曾指出：** Team Lead（Claude Sonnet 4.6）委派 copilot-developer 使用 GPT-5.3-Codex，違反 Pilot Suite 的「Opus 是天花板，子任務只能向下委派」規則。

**實際情況：**

Pilot Suite 的「只向下委派」是單一工具生態（Claude Haiku/Sonnet/Opus）內的成本控制機制，防止貴的模型被便宜模型指揮去做更貴的事。

AI-Pair 是跨工具異構架構，Team Lead 的角色是：
- 決定任務邊界
- 提供清晰的 task context（TASK_FILE）
- 驗收輸出是否符合規劃

實作者能力比指揮者強不是問題——現實軟體團隊也是如此，Tech Lead 不需要比每個工程師都會寫程式，需要的是計劃夠清楚、驗收夠嚴格。重點是**最終輸出是否符合規劃**，而非能力層級是否向下。

**結論：** 此擔憂不成立，從 v4 分析中移除。

## 二、從說明文件.md 新發現的實作缺口

### ⚠️ 缺口一：settings.local.json 未涵蓋 v4 新模型（🔴 高優先）

v3.1.0 目前的 `.claude/settings.local.json` 只允許：

```json
"Bash(copilot --model gpt-4.1:*)",
"Bash(copilot --model gpt-4.1-mini:*)",
"Bash(copilot --model claude-sonnet-4.6:*)",
"Bash(gemini --model gemini-2.5-flash:*)",
"Bash(gemini --model gemini-2.5-flash-lite:*)"
```

v4 新增的所有 tier 模型都未列入，autopilot 執行時會跳出確認對話框，中斷自動化流程。

**更新 SKILL.md 前需補充的權限項目：**

```json
"Bash(copilot --model gpt-5-mini:*)",
"Bash(copilot --model gpt-5.4-mini:*)",
"Bash(copilot --model gpt-5.3-codex:*)",
"Bash(copilot --model gpt-5.4:*)",
"Bash(gemini --model gemini-3-flash-preview:*)",
"Bash(gemini --model gemini-3.1-flash-lite-preview:*)"
```

> **注意：** 這些 model ID 的準確格式仍是 v4 Phase 1 待驗證事項之一，以實測結果為準再寫入設定。

---

### ⚠️ 缺口二：TASK dispatch 協定未說明模型傳遞方式（🟡 中優先）

v3 的 dispatch 協定：

```
TASK:{file_path}   → copilot-developer 固定用 claude-sonnet-4.6
```

v4 引入動態 tier 後，Team Lead 在規劃階段決定 developer 模型，但目前的 Inter-Agent Protocol v1 沒有傳遞 tier 資訊的欄位。

**可能的解法（待決定）：**

選項 A：在 TASK_FILE 內容中加入 `MODEL_TIER:` 欄位
```
MODEL_TIER:{simple|standard|complex|security}
TASK:{file_path}
```

選項 B：在 Bash 呼叫層直接由 Team Lead 根據評估結果帶入 `--model` 參數，不改 Protocol

選項 B 實作較簡單，但 Protocol 格式對 developer subagent 不透明。建議討論後確認再寫入 SKILL.md。

---

### ⚠️ 缺口三：gemini-3-flash-preview 壓縮格式為解析相容性問題（🟡 中優先）

說明文件.md 已有記錄：「`gemini-2.5-flash-lite` 可能用 `/` 分隔 findings，Team Lead 需容錯解析」

v4 新增 `gemini-3-flash-preview` 作為 Level 3 的 gemini-reviewer，這個模型的輸出分隔符格式尚未驗證。這不只是能力問題，是 Inter-Agent Protocol 解析的相容性問題——如果格式不符，Team Lead 的彙整邏輯會靜默出錯（不報錯，但 findings 遺漏）。

**Phase 1 驗證應加入：**

```bash
echo "int x = 1" | gemini --model gemini-3-flash-preview \
  -p "Review. Output ONLY:
SRC:gemini-3-flash-preview
C|test.dart:1|issue|fix
VERDICT:PASS" 2>&1
```

確認輸出是否嚴格使用 `|` 分隔，而非 `/` 或其他格式。

---

### ⚠️ 缺口四：移除 Claude Haiku 4.5，Level 1 fallback 改用 GPT-4.1（🔴 高優先）

v4 Copilot Tier 表中 Tier LOW developer 使用 `Claude Haiku 4.5`（0.33x），Level 1 fallback chain 也包含它：`GPT-5 mini → Claude Haiku 4.5 → FAIL`。

**問題：Claude Haiku 4.5 在這裡不合理。**

| 問題 | 說明 |
|------|------|
| 成本矛盾 | Haiku 4.5 via Copilot CLI 是 0.33x，GPT-5 mini 是 0x（FREE）。Fallback 反而更貴，違反 v4「能用免費就用免費」的設計核心 |
| 套用錯誤 | 從 Pilot Suite 的 Haiku/Sonnet/Opus 階層直接搬過來，沒考慮到 Copilot 生態已有 GPT-5 mini（FREE）和 GPT-4.1（FREE）|
| 未驗證 | v3 從未透過 Copilot CLI 呼叫 Claude Haiku 4.5，Phase 1 也未列入測試 |

**建議修正（寫入 v4 SKILL.md 時適用）：**

v4 原始 Tier 表：
```
Tier LOW: Developer=Claude Haiku 4.5（0.33x）, Reviewer=GPT-4.1（FREE）
```
→ 移除 Tier LOW，簡單任務統一用 Tier FREE（GPT-5 mini）

v4 原始 Level 1 fallback：
```
Level 1 developer: GPT-5 mini → Claude Haiku 4.5 → FAIL
```
→ 改為：
```
Level 1 developer: GPT-5 mini → GPT-4.1（FREE）→ FAIL
```

同時從 settings.local.json 需求清單中移除 `"Bash(copilot --model claude-haiku-4.5:*)"`，Phase 1 驗證也不再需要測試此路徑。

---

### ⚠️ 缺口五：Level 1 靜默從 1 reviewer 變 2 reviewer（🟡 中優先）

v3 Level 1 定義（說明文件.md）：

```
Level 1 | --quick | Gemini only
```

v4 Level 1 定義：

```
Level 1 — 快速掃描（--quick）
  copilot-reviewer: GPT-5 mini（FREE）  ← 新增
  claude-reviewer:  跳過
  gemini-reviewer:  gemini-3.1-flash-lite-preview
```

v4 在 Level 定義中加入了 copilot-reviewer，但「變更三：更新 Level 定義」沒有明確標註這是行為變更。

**影響：**
- `--quick` 耗時估算（~20s）可能需要上修（現在要等兩個 reviewer 而非一個）
- 兩個 FREE reviewer 對品質有利、對成本無影響，方向正確
- 但說明文件.md 和 SKILL.md 更新時需明確記錄此變更，避免使用者預期落差

## 三、維持不變的 v4 擔憂

### ⚠️ Team Lead Sonnet 高信心偏誤（🟡 中優先）

來源：claude-pilot-suite

Sonnet Pilot 存在的理由之一是「Sonnet 的高信心偏誤容易跳過前置檢查」。Team Lead 是 Claude Sonnet 4.6，負責在任務開始時評估複雜度並決定 developer tier 和 review level。

風險：低估複雜度 → 分配到 FREE/LOW tier → 執行品質不足，但升級機制在 reviewer 發現問題後才觸發，已浪費一輪執行成本。

**可能的緩解方式：**
- 在 Team Lead Planning Protocol 加入強制複雜度確認步驟（類似 Sonnet Pilot 的 6 步驟前置檢查）
- 或在 SKILL.md 明確說明「評估時偏向高估而非低估」

此項不影響 Phase 1 驗證，但建議在 v4 SKILL.md 實作時一併處理。
