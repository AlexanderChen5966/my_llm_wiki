## 核心論點

Boris Cherny（Claude Code 負責人）提出的開發者五種原型，最好的用法不是貼在人身上的職種標籤，而是**診斷「這個專案現在缺哪一種工作能力」的框架**。問題該從「你屬於哪一種」換成「這個專案現在缺哪一種」。

## 重點整理

- 五原型與職責：①**原型開發者**——大量嘗試新想法，多數不正式發布 ②**建造者**——把想法推進到可上線品質 ③**整理者**——刪除、簡化、加速 UI／程式碼／系統 ④**成長推進者**——反覆改善產品提高 PMF ⑤**維運者**——維持成熟系統的安全性、可靠性、效能與效率
- Anthropic 分析約 40 萬筆 Claude Code 工作階段：人類約 70% 負責「要做什麼」的規劃判斷，Claude 約 80% 負責「怎麼實作」；且**任務特定專業性越高，工作階段成功率越高**（專業性指「是否理解這個任務該達成什麼」，不是一般寫程式能力）
- 各原型對應的人類端必答問題：試什麼／交付什麼品質到正式環境／保留刪除什麼並簡化到什麼程度／改善什麼才能提高 PMF／保護什麼、接受哪些風險、如何偵測與復原
- 產品階段對應：PMF 前＝原型開發者+建造者+整理者；找 PMF 並成長中＝建造者+整理者+成長推進者+部分維運者；已建立強 PMF＝整理者+成長推進者+維運者+部分建造者
- 建造者的能力轉向：從「自己寫大量程式碼」轉為「規格／驗收條件 → 架構／限制 → 測試／驗證標準 → 委託 AI 實作 → 審查」的迴圈設計與監督；批判指出「能運作的軟體」與 production-grade 仍有很大距離，實作變快後設計、審查與治理反而成為新瓶頸
- 整理者反而更重要：Anthropic 內部 8.6% 的 Claude Code 任務用於重構等 papercut fixes；批判認為整理不該是建造完才收尾的後段作業，而應從設計實作階段就納入
- 成長推進者最難 AI 化（需要真實使用者這個外部世界），但也是邊界最模糊、塞進最多能力的一類（客戶研究／市場選擇／定位／產品策略／渠道／定價／業務）
- 維運者的問題是不易被評價：「沒有發生故障」「避免了事件」很難被看見，角色固定化還可能被誤認為職涯死胡同
- 主要批判：Kun Chen（前 Meta／Microsoft）指分類固化會讓人停止自我提問，Cherny 回應同意「角色會隨時間與專案改變」；Vivek Bharadwaj 指偏矽谷產品組織，建議把前四類合併為廣義建造者、保留成長推進者，再補上 **Handler**（推動複雜組織運作，如 Chief of Staff／事業營運）與 **Grown Ups**（法務、財務、風險管理）
- 作者方法論註記：他刻意要求 GPT-5.6 蒐集資料時「也納入批判性意見」，只加這一句，調查視角就差很多

## 可用之處

「加一句『也納入批判性意見』」是可直接複用的研究 prompt 技巧，適合本庫的 research 與 wiki-health-check 流程。五原型當診斷軸線也可以往內用：檢視自己的知識庫工作是不是全押在「建造者」（一直寫新條目），而缺少「整理者」（合併、刪除、精粹）。
