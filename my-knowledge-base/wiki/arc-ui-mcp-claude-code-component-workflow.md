## T（核心論點）

**Arc UI 解決的是「元件選擇與實作一致性」：讓 Claude 先透過（唯讀）MCP 查詢有哪些元件、再取得安裝命令，而不是自己亂寫一套按鈕。** 它不替你決定內容順序、視覺方向與使用者要完成的動作，也不保證每個網站都會變好看——元件庫讓技術規格一致，不會自動產生獨特的視覺概念。

## B（適用場景）

**適用：**
- 已有 React 19 + TypeScript 專案，想補表單、對話框等互動元件，並讓 AI 生成的 UI 與既有規格不分叉
- 內容清楚、功能有限的單頁（如課程報名頁）作為第一個試點
- 已有設計系統的團隊：當作**補充**（先找出原系統缺少的互動，如複雜表單、確認對話框），而非一次替換全站

**不適用 / 注意：**
- Arc 文件以 React 19、TypeScript、CSS modules、共用樣式變數與 `@/*` 路徑別名為核心；其他框架不能直接複製 React 元件，單純活動頁原有模板可能已足夠
- 不要誤以為必須另裝 Tailwind，以 Arc 實際依賴為準
- 授權：免費元件依官方說明為 MIT（聲明要保留）；Pro 元件適用另一套商業授權。**「終端產品使用」≠ 可把元件重新包裝成模板庫／元件庫／轉售資源**；使用者席次與來源碼存取也是獨立問題。若交付物本身是網站模板商品，購買前先確認
- 免費帳號也涉及驗證；登入成功不代表含所有 Pro 元件、也不代表整個團隊可共用一個帳號
- 官方未載明的部分（實際可得元件清單、價格方案細節）本條目不補

## R（操作步驟）

1. **先看專案條件**：請 Claude 讀套件清單與共用 CSS，列出要新增哪些檔案、原因、是否影響既有頁面；首次試用在可回復的分支或副本
2. **接上 MCP**（官方文件提供的遠端命令，執行前核對當下文件與 Claude Code 版本）：
   `claude mcp add --transport http arc https://uiarc.dev/api/mcp`
   遠端 MCP 在官方文件中描述為**唯讀**，只提供元件資訊；真正改檔案的仍是 Claude Code 在你的目錄執行安裝／編輯，兩階段應**分別檢查**（先確認選對元件，再確認改動符合原架構）
3. **先查詢、不改檔**：請它列出「適合報名頁的表單、按鈕、成功提示：元件名稱、用途、免費／付費限制、安裝命令」；產物應是一張選擇表，若只丟大段新程式碼而沒說用哪個元件，要求重新查詢文件。官方列出的工具涵蓋搜尋元件、列出元件、取得元件內容、安裝命令與技能內容
4. **安裝走 shadcn CLI + registry**（核對來源域名與寫入目錄後再執行；不要用社群留言的不明連結）：
   - 無 `components.json` 先 `pnpm dlx shadcn@latest init`；已有則合併欄位勿覆蓋
   - 加 registry：`{"registries":{"@uiarc":"https://uiarc.dev/r/{name}.json"}}`
   - `pnpm dlx shadcn@latest add @uiarc/arc-foundation`，再 `add @uiarc/button @uiarc/dialog`（作者標明為起步示範，表單仍依實際欄位選）
   - 在應用入口（Next.js `app/layout.tsx` 或 Vite `src/main.tsx`）**引入一次** `@/components/arc/foundation.css`
   - 也可依官方頁面用完整元件網址安裝（免設 registry）
5. **安裝後檢查檔案變更**：按鈕位置、共用 CSS 只引入一次、路徑別名可解析、暗色模式有對應的新色彩變數
6. **把需求寫具體**：保留既有字體與品牌色、頁面只放哪些內容、使用 Arc 既有元件不新增其他元件庫、表單送出前顯示欄位錯誤與成功確認訊息
7. **Pro token 管理**：依官方方法管理，不寫進公開程式碼或聊天範例；可請 Claude 檢查變更是否含帳號資料，但**不要要求它印出完整 token**
8. **三輪驗收**：
   - 內容：不用捲很久就看到適合誰、何時、費用；重要資訊不要藏在展開區塊
   - 表單：空白、格式錯誤、正確填寫、重複送出；錯誤提示說明如何修正；成功訊息區分「報名已送出」與「付款已完成」；未接後端要明示僅為介面示意
   - 鍵盤與手機：Tab 走過欄位按鈕、對話框焦點合理、長中文課名不把價格推出畫面、無橫向捲動
   - 最後請 Claude 列出新增依賴、修改的共用樣式、尚未接上的功能；不要把「AI 寫完了」當成可對外收款的證據
9. **修改要求寫成可觀察的問題**（「手機版日期比按鈕不明顯」優於「不夠高級」），每輪只改一組；建議新增套件時，先要它說明 Arc 現有元件為何不夠
10. **視覺參考與產品內容分開**：指明借用哪一部分（標題大小、表單分組、留白節奏），參考圖少而清楚（一張排版、一張色彩），照片／文案／品牌識別不直接混入

## C（關鍵行動）

- [ ] 在可回復分支試一個按鈕＋一個欄位＋一種提示訊息，確認桌機與手機皆正常、新舊元件可共存
- [ ] 採用前把「參與開發人數、客戶交付形式、是否轉售模板」寫成三行，對照官方授權條款
- [ ] 團隊留簡短使用紀錄（元件名稱、來源文件、安裝日期、授權種類、採用理由），與專案放一起
- [ ] 用接近正式長度的中文文案測試換行與行高（別全用「測試」兩字）
- [ ] 完成標準設小：查到正確元件、安裝來源可追溯、頁面可建置、一位同事能獨立走完報名測試；四項成立才擴到下一頁

## 原始摘要

作者以「課程報名頁」為情境，說明 Arc UI MCP 如何接進 Claude Code：先唯讀查詢元件，再以 shadcn CLI／registry 安裝，區分免費 MIT 與 Pro 商業授權，最後以內容、表單、鍵盤與手機、建置結果四輪檢查驗收。重點在可追蹤的元件選擇與可維護性，而非首頁截圖。作者未實測，也未提供授權或價格的量化數據。
