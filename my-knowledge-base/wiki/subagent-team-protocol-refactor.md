2025-11 寫的 Claude Code subagent 團隊定義：8 個角色、12,069 行。2026-08 重寫：同樣 8 個角色、**1,239 行**。少了 90%，但它現在才真的能用。

## T（核心論點）

> **真正的教訓不是「文件要精簡」，是「規則不能有兩份」。**

12K 行本身不是問題，**同一條規則在 6 個地方有 6 個版本**才是。抽出 `_PROTOCOL.md` 之所以有效，是因為它讓每條規則只有一個定義位置——**跟寫程式時把重複邏輯抽成函式是同一件事**。（同一手法用在規則檔上：[[claude-md-design-patterns]]、[[apple-claude-md-teardown]]）

第二個更深的論點是關於「怎麼寫規則給模型」：

> **寫給 AI 的規則不是寫得越嚴越有效。你要先分清楚哪些是它「結構上會遵守」的（欄位、層級、清單），哪些是它「行為傾向壓得過規則」的（開場白、語氣、先講什麼）。前者用規則管，後者要順著設計，或者在讀取端容錯。**

## B（適用場景）

**適用：**
- 已經在用 subagent 但苦於「交件格式每次不一樣、順手多做事、停在半路等你、說測試過了其實沒跑」
- 想跨專案共用同一套 agent 定義（本套是 `~/.claude/agents/` 全域安裝）
- 規則檔／角色檔膨脹到你自己也不確定哪條是最新版

**不適用 / 注意：**
- ⚠️ **這是文件工程，不是程式**。沒有測試套件能驗證一份 prompt 是否「正確」；唯一驗證方式是實際派工、看產出、發現問題就改協定。作者明說**所有結論都是單一使用者的經驗，不是實驗結果**
- ⚠️ **v2 只跑了一個多月，樣本不夠**，且無法排除「同時也變會派工了」這個混淆因素
- ⚠️ **效果會隨模型版本變動**：有些規則（如下方的 ✅ 預設值）是為了繞過特定模型的行為傾向而寫，模型換代後可能不需要
- 🔴 **它預設你有一套流程**（PRD → 技術設計 → issue → 分支 → 實作 → 審查 → 部署）。只是想快速改個 bug 的話，整套過重
- 作者本人的建議：**不要照抄**，很多是他的個人偏好（繁中 commit、GitHub Issues、產出路徑），Fork 一份換成自己的規範

## R（三層決策 + 一份協定 + 8 個角色）

### 三層角色

- **PM = 使用者** — 需求方與最終決策者。預算、範圍、方向、不可逆操作只有人能拍板
- **主 agent** — 讀需求、拆任務、派工、整合回報、決定何時開 PR
- **subagent** — 一次性執行者。**只跟主 agent 對話，不能聯絡其他 subagent，也不能直接找 PM**

🔑 這個限制強迫所有跨角色協調都走主 agent，**資訊流是一棵樹而不是一張網**。

### 檔案結構

```
~/.claude/agents/
├── _PROTOCOL.md          ★ 派工協定（140 行）：任務書格式、統一回報格式、DoD、
│                           阻塞協定、scope 鎖、一次性回覆、產出路徑、git 規範
├── product-manager.md    PRD
├── tech-lead.md          架構／技術選型／schema／任務拆解／ADR
├── research-analyst.md   技術、資料源、市場、競品調研
├── backend-engineer.md   所有非 UI 程式碼
├── frontend-engineer.md  UI 層（web、儀表板、TUI、通知模板）
├── qa-code-reviewer.md   實跑測試＋逐檔審查，只審不修
├── devops-engineer.md    容器化、CI、部署、排程、密鑰、備份、監控
└── risk-manager.md       專案健康度與風險
```

角色檔第一句話一律是：**先完整閱讀 `_PROTOCOL.md`；本檔只描述你這個角色與眾不同的部分**。衝突時**專案 `CLAUDE.md` 優先於全域協定**——這樣同一套 agents 才能跨專案共用。

| | v1（2025-11） | v2（2026-08） |
|---|---|---|
| 8 個角色檔總行數 | 12,069 | **1,239** |
| 單一角色檔 | 712 ~ 2,518 行 | 150 ~ 169 行 |
| 共同規則 | 散在 8 檔，版本不一致 | 集中在 `_PROTOCOL.md`（140 行） |
| 技術棧預設 | web／電商／K8s | 無（由專案 `CLAUDE.md` 帶入） |

### 三個 v1 症狀

1. **context 被自己的定義吃掉**——subagent 開工先讀 2,000 行自我介紹，真正該讀的設計文件排在後面、權重被稀釋
2. **角色重疊導致派工錯誤**——同一條規則（分支怎麼開、commit 訊息怎麼寫）在 6 個檔案各寫一次而且**寫得不一樣**。🔑 **Claude 讀到互相矛盾的規則時不會報錯，它會挑一個**
3. **預設了你沒有的技術棧**——一堆 web／電商／K8s 範例，讓它在純 Python 資料管線專案裡建議加 Ingress

### 統一回報格式（狀態只有三種）

```markdown
## 回報：<角色> — <任務一句話>
<選填：一段不超過五行的摘要>
### 狀態
DONE                          ← 只能是 DONE / PARTIAL / BLOCKED
### 產出
- <路徑>：<說明>（commit：<hash> on <branch>）
### 驗證
- 測試：<指令> → <N passed / N failed，或「未執行：原因」>
### 假設
### 待決事項（需主 agent／PM 拍板）
### 發現與建議（scope 外，未動手）
### 未完成
```

⚠️ **「用不到的欄位寫『無』，不要刪欄位」也要明寫**，否則它會整段刪掉，主 agent 就沒辦法機械式地讀。

## C（關鍵行動）

- [ ] 檢查自己的 agent／skill 檔：有沒有同一條規則在多處各寫一份且版本不一致？抽成一份共同協定
- [ ] 在協定第 0 節明寫「你是一次性的」，並全域搜掉「請確認後我再繼續」「回報進度 60%」這類指令
- [ ] 回報／文件範本一律**留空**，並加一條明規則禁止預填假數字
- [ ] 對「模型行為傾向壓得過規則」的部分（開場白、語氣）改成順著設計 + 讀取端寬鬆解析，不要硬對抗

## 補充資料

### 🔑 subagent 是一次性的——這是 v1 最致命也最不明顯的 bug

subagent 是**一次派工、一次最終回覆，中間沒有對話回合**。v1 角色檔裡大量「完成第一階段後回報進度並等待確認」「若需求不明確請先詢問 PM」——**這些指令在 subagent 身上完全不成立**。它照著模板寫了「請確認後我再繼續」然後就結束了，那次派工什麼都沒產出。

> 寫這些模板時腦子裡想的是「跟 Claude 對話」的體驗。但 subagent 不是對話，它比較像**送出一個 job 然後拿回一份 report**。

協定第 0 節：

```markdown
你是**一次性**的：這次任務只有一次最終回覆，沒有中途對話。
不要寫「請確認後我再繼續」「回報進度 60%」「等待指示」
——那些永遠不會有人回。能做的做完，不能做的說清楚，一次交齊。
```

配套是把「不確定怎麼辦」講死：**不腦補需求。任務書不清楚時，先做不依賴那個答案的部分，其餘選一個保守假設完成，把假設寫清楚。只有在「任何假設都會讓工作作廢」時才停下來，交出 partial 產出＋明確問題。**

### 🔑 結構上會遵守 vs 行為傾向壓過規則——格式改三版的實測

第一版把狀態寫成標題正下方的裸行 `**狀態**：DONE | PARTIAL | BLOCKED`。**它不聽**：同一份任務書派兩次，第一次改成「## 摘要」，第二次改成「## 結論」加一句「完成。」。作者特地加了三條**逐字要求**，明寫「不要寫成『完成。』」——

**結果三條裡只有一條生效。** 管欄位層級的那條（一律 `###`、名稱照抄、額外欄位附加在後）一次就聽，連空的 `### 未完成` 都會乖乖寫「無」；管開頭那兩行的兩條，寫得再白都沒用。

> **模型在開口的第一句服從「先講結論」的習慣，那是它最強的行為傾向之一，一段散文規則蓋不過去。但只要進到「欄位」這個結構裡，它就照做。**

所以改成順著它設計：狀態**搬進 `### 狀態` 欄位**且內容限一個字；**明文允許**標題後放一段五行內摘要（給它一個合法位置）；主 agent 端改成**寬鬆解析**（抓 `### 狀態` 後第一個出現的詞，不要求逐字相符）。第三次派工全數符合。

（此區分在庫內尚無對應條目，值得日後升級為概念層框架，與 [[agents-md-guide]]「寫不可推斷的隱性知識」互為印證）

### Claude 會把回報範本裡的 ✅ 當成預設值

v1 為了「讓它知道長什麼樣」，範本直接寫了填好的範例 `- 測試：pytest tests/ → ✅ 18 passed`。然後就開始收到「✅ 18 passed」的回報——**在一個根本沒有 18 個測試的專案裡**。

🔑 **它不是在說謊，它是在照抄範本。你給它看的是一個已填好的表格，它理解成這是輸出的樣子。** 同樣的事發生在 PRD 與調研報告上：範本裡的假數字、假結論會原封不動出現在產出裡。

解法：**範本一律留空**，加明規則「不偽造結果。測試要真的跑、數字要真的量。沒跑就寫『未執行』，失敗就貼失敗輸出。**回報範本裡的 ✅ 是要你填的，不是預設值**」；文件類產出的 DoD 加一條「沒有預填的假數字、假結論、佔位符」。

配套**阻塞協定**：同一個問題最多嘗試 **3 次**不同做法，仍失敗就停，交出目前產出＋失敗紀錄。**阻塞不代表交白卷**。

### 四個刻意的設計選擇

- **`model: inherit`** — 角色檔不寫死模型，派工時由主 agent 決定（規劃／審查吃重推理，機械性任務用便宜的）。寫死會讓你每次改主意都要編輯檔案（與 [[fable5-subagent-model-routing-design]] 同一考量）
- **文件角色給 tools 白名單** — product-manager／research-analyst／risk-manager 限制成 `Read, Glob, Grep, Write, WebSearch, WebFetch`，**沒有 Bash、沒有 Edit**。理由很現實：**PM agent 一旦能動程式碼，它就會忍不住去動。權限限制比在文件裡叮嚀「你不要寫程式」有效得多**
- **產出路徑總表** — 協定裡寫死每種產出去哪，並明寫「工作項目、bug、風險一律用 GitHub Issues，不要自建 markdown 追蹤表」。不寫這條，每個 agent 都會熱情地幫你生一個 `TODO.md`，然後你有五份互相矛盾的待辦清單
- **qa-code-reviewer 只審不修** — 讓「修」一定回到工程師角色、走一樣的測試與 commit 規範。**審查者順手修掉的東西不會有測試**

### 派工長什麼樣

```
請用 backend-engineer 實作 issue #12。
目標：新增 FinMind 台股價量 provider
範圍外：不要動既有的資料清洗流程
必讀：docs/architecture/data-pipeline.md
分支：feature/12-finmind-provider
```

作者認為真正值得帶走的只有三個結構性決定：**共同規則抽一份，角色檔只寫差異**／**明寫「你是一次性的」**／**範本留空，明禁預填**。
