## T（核心論點）

在 Mac mini M4（16G RAM）上使用 Ollama 自架小型 LLM，將簡單低複雜度任務交給本地模型處理，複雜任務才用付費 AI 服務，以節省 API 成本。Apple Silicon 的 Unified Memory 架構讓 CPU 和 GPU 共享記憶體，適合跑 14b 以下模型。

## B（適用場景）

**適用：** 預算有限的個人開發者、需要離線環境或資料隱私的場景、n8n 自動化流程中的簡單 AI 任務
**不適用 / 注意：** 16G RAM 跑 20b 模型很慢，無法取代雲端的大算力模型

台大計資中心電子報文章，作者柚子哥以社畜工程師視角分享完整安裝流程。涵蓋：硬體選擇（Mac mini M4 教育價 16,400 元）、Ollama 安裝與移除、模型標籤含義（b 參數量 / Turbo / Vision / Thinking / Tools / Embedding）、CLI 與 UI 兩種使用模式、不同模型對比（llama3.2:3b vs gpt-oss:20b vs gemma3:12b）、REST API 串接（Postman 測試）、stream 參數差異。Tools 與 Agent 的概念區分表格值得參考。

## 補充資料：完全本機 RAG 疑難排解與 48GB 運用（2026-08-03 併入）

來源：〈在 Mac mini（M4 Pro/48GB）上嘗試建置「完全本機」的 LLM + RAG 環境〉。Ollama 入門教學（另一篇同批素材）核心概念已被本條目與 `ollama-2026-complete-guide` 完整涵蓋，僅補此篇獨有的實測疑難排解。

### 常見錯誤

| 錯誤 | 原因與處理 |
|---|---|
| `Connection refused` | Ollama 沒啟動——用 `ollama list` 確認；若同時有 LM Studio，確認是 Ollama 那邊啟動 |
| `address already in use` | Ollama 已在執行（常見於 GUI 版已常駐）——不需再跑 `ollama serve` |
| 第一次執行異常慢 | `bge-m3` 正在把全文向量化，時間與文件量成正比，**非異常**——先用少量檔案測試 |
| PDF 無法讀取 | 需 `pip install pypdf` |
| 載入模型時記憶體不足 | `sudo sysctl iogpu.wired_limit_mb=40960` 提高 GPU 記憶體上限（**重開機會重設**）|

### 充分運用大記憶體的三個重點

1. **優先選 MLX 格式**——針對 Apple Silicon 最佳化，參數量相同時通常比 GGUF 更快更省記憶體；選模型時看到 `-mlx` 標示優先選
2. **注意生成模型與嵌入模型同時佔記憶體**——想常駐 32B 級生成模型，嵌入端選較輕量的 `bge-m3` 會更有餘裕
3. **先從輕量模型開始**（如 14B）——一開始選太大模型，很難分辨「沒跑成功」還是「只是很慢」

### 不寫程式的替代方案

**AnythingLLM**（拖放文件建知識庫）與 **LM Studio**（GUI 搜尋/下載/執行模型，較容易找到 MLX 格式）都能在底層搭配 Ollama，可與程式建置的環境並用。


## 補充資料：模型級距、量化與「哪些工作值得留在本機」（2026-08-17 併入）

來源：《觀察 AI，也觀察自己》Day 17。⚠️ 該篇作者用的正是 **Mac M4 Pro 48GB Unified Memory**，與本庫硬體一致，數據可直接參考。

### 模型級距的粗略地圖

| 模型級距 | 常見 Q4 版本大小 | 建議整機記憶體起點 | 適合感覺 |
|---|---|---|---|
| 3–4B | 約 2–4GB | 8–16GB | 快速分類、短摘要、簡單工具 |
| 7–9B | 約 5–7GB | 16GB | 日常聊天、翻譯、資料整理 |
| 12–14B | 約 8–10GB | 16–24GB | 品質與速度較平衡 |
| **27–32B** | **約 17–20GB** | **32–48GB** | 較好的推理、翻譯與專業工作 |
| 70B 左右 | 通常 40GB 以上 | 64–96GB 以上 | 高記憶體工作站較實際 |

🔴 **這張表只能當「先去哪一區找模型」的地圖，不是硬體保證書**：作業系統、一次輸入的文字長度、圖片輸入，以及「同時開著的 Chrome 那 66 個分頁」都要吃記憶體。

> **「模型 20GB、RAM 48GB，因此還剩 28GB」不是精確公式——電腦的會計制度沒有那麼單純。**

⚠️ 另外**不存在「32GB 記憶體一定只能跑 14B」的絕對公式**；少數 MoE 模型每次生成只啟用部分參數，但**載入時仍得考慮整體權重**，不能只看「這次有幾個參數上班」。

### 量化：為什麼同樣 27B 大小差很多

量化**不是把參數刪掉，也不只是把檔案丟進 ZIP 壓縮**，而是把模型拿來算數的數字換成較省空間、精度較粗的表示法（把 `0.1374` 記成 `0.14`）。單看一個數字差異很小，但模型裡有數百億個數字。

Ollama 官方給的粗略比例：**`q8_0` 約使用 `f16` 一半的記憶體，`q4_0` 約四分之一**。

🔑 **類比很傳神：像圖片壓縮——適度壓縮通常看不太出來；壓得太狠，整張臉開始像 Minecraft。**

**Q4 對一般個人電腦是務實起點**（放得下、速度合理，品質損失未必會破壞摘要、翻譯這類可驗收任務）。⚠️ 但 Q4／Q8／MLX 哪個適合仍要拿自己的工作測——**不必為追求最高精度而讓每產生一個 Token 的時間都可以去泡一杯咖啡**。

### 🔑 48GB M4 Pro 的實際定位（與本庫硬體相同）

作者實裝的 `gemma4:26b-mlx` 與 `qwen3.8:27b` **都約 18GB**——這個級距對 48GB Unified Memory 通常還能留空間給 macOS、執行程式與輸入內容。

🔴 **但這裡有另一個坑**：Qwen3.8 27B 標示支援 **262K 脈絡**，這不代表應該直接把脈絡拉到上限。Ollama 官方特別提醒：

> **脈絡長度拉得越長，需要的記憶體就越多。**

🔑 **「模型支援很長的脈絡」與「你的電腦適合每次都開到上限」是兩件不同的事**——這與 [[context-engineering-stacking]]、[[agent-context-management]] 的「Context 不是越大越好」在硬體層再次交會。

### 四個問題篩選「什麼工作值得留在本機」

本機模型最適合的**不一定是最重要的工作**，而是符合以下多數條件者：

1. **會重複做很多次**
2. **輸出格式相對固定**
3. **可以用原文、規則或人工快速驗收**
4. **不需要剛剛發生的最新資訊**

作者的兩個實例都與本庫的素材處理高度相關：

- **YouTube 影片摘要**：`URL → 取字幕 → 切分 → 本機模型 → 摘要/重點/時間線 → 存成 Markdown`。🔑 取字幕仍需網路，但**真正反覆消耗大量 Token 的「整理逐字稿」可以留在本機**（兩萬字的影片只要整理論點、案例、名詞，不必每次都呼叫最強的雲端模型）
- **學術文章翻譯**：PDF 先轉乾淨 Markdown → 按段落／章節切開 → 交本機模型翻譯並固定規則

⚠️ 對本庫的直接啟示：`raw/` 的字幕（`.srt`／`.vtt`）與長 PDF 前處理，正好符合這四個條件，是可考慮下放本機的環節；但**條目撰寫需要跨篇比對與判斷，屬於不該下放的那一類**。

### Fine-tune 的界線（常見誤解）

🔴 **fine-tune 不是用來「讓模型知道我公司 2026 年最新 SOP」**（那是知識更新，該用 RAG 或把資料放進 Context），而是讓**模型「怎麼回答」變得比較像你要的方式**——語氣、格式、風格與領域習慣。
