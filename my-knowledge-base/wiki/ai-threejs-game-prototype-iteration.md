兩篇從兩端看同一件事：Riven 自己用 ChatGPT＋Codex＋Blender 做完一款 Three.js 競速遊戲《歐兜賣尬車》；aiposthub 拿 Meticulai 的 Lost Marbles（50 顆彈珠淘汰賽）談「AI 寫出程式之後，怎麼知道它好不好玩」。結論一致：**程式交給 AI 寫，真正花時間的是把「怪怪的」翻成可檢查的條件，一輪只修一件事。**

> ⚠️ **來源性質**：Riven 篇是單一作者單一專案的自述，遊戲數值（小噴 0.65 秒、氮氣 2.5 秒等）**只適用該專案**；aiposthub 篇是解讀他人公開示範影片與官網，作者明說沒打完一場、不判斷整體平衡，X 互動數（約 956 讚、6 萬瀏覽，查詢時）只代表有人關注。ChatGPT 桌面版整合 Codex 的操作路徑為 2026-09 快照。

## T（核心論點）

> **AI 能把「寫程式」的門檻拿掉，但拿不掉「看出哪裡不對、講清楚要改成什麼」——把每輪縮成一個能驗收的目標，回饋拆成四句話，自己打開玩過才算完成。**

回饋四句話（Riven 稱整個專案最值得帶走的技巧）：

| 要說的事 | 範例 |
|---|---|
| 哪裡有問題 | 從背後看，右手袖口和手掌之間有縫 |
| 在什麼情況發生 | 選 Vbike、向左轉時特別明顯 |
| 哪些要保留 | 保留臉型、長袖配色和目前的鏡頭 |
| 怎樣才算修好 | 三台車、左右轉向、正背面都沒有斷裂或穿模 |

aiposthub 從玩家測試端講同一件事：「到第二段斜坡時，向左輸入後畫面仍向前」比「很難玩」好處理——**包含情境、輸入與結果，能用相近條件重做一次**。

## B（適用場景）

**適用：**
- 用 AI 做瀏覽器 3D 互動作品（Three.js 遊戲、互動網頁、3D 展示）的原型到可玩版本
- 任何「AI 說做完了、但看起來怪怪的」的視覺／互動任務——四句話回饋可直接套用到 UI 修正
- 要給別人試玩、收測試回饋的獨立開發

**不適用 / 注意：**
- 想「輸入一次描述就得到完整商業遊戲」——兩篇都說公開資料不支持這個期待
- 能操控的 3D 角色躲不掉建模：漂亮的三視圖離可操控角色還很遠，Riven 的角色是在 Blender 用腳本建、匯出有命名部件的 GLB；不能假設任何 GLB 都套得上同一套骨架控制
- 「AI 做遊戲」≠「遊戲裡有 AI 對手」：Lost Marbles 的 49 個電腦對手是一般遊戲程式，不能推算語言模型用量

## R（操作步驟）

### 1. 先分工：每個工具交出能檢查的東西

| 工具 | 交出什麼 |
|---|---|
| ChatGPT | 美術規格、參考圖分析、概念圖與宣傳圖 |
| Codex | 能執行、能檢查的檔案（改程式、接素材、開預覽、除錯） |
| Blender | 能載入遊戲的 GLB 模型 |
| Three.js | 玩家實際看到的畫面（場景、相機、渲染器）——**不含遊戲規則**，碰撞、淘汰、排名、重開要自己建 |

- 專案資料夾分 `references/`、`assets/models/`、`assets/audio/`、`src/`、`docs/`；AI 工作範圍越清楚，越不會動到不該動的東西
- 參考圖每張配一句用途（「這張看比例」「這張看後腦髮型」），**圖跟圖衝突時寫清楚誰說了算**
- 把「更精緻」翻成看得到的條件，存成 `docs/art-direction.md` 當每輪依據（髮型精緻＝髮束前後重疊、髮根接合自然）

### 2. 第一輪只做「能跑完一圈」

- 封閉道路＋代用車、基本操控、第三人稱鏡頭、邊界碰撞、檢查點、三圈完賽與重開；**先不做城市和精細角色**
- 要求 Codex「先檢查現有檔案和環境再決定啟動方式」「完成後實際開啟預覽，說明哪些功能已驗證」
- 「完成了」不代表完成：自己起跑、過彎、擦牆、跑完一圈
- 載入 GLB／JS 模組要開本機伺服器；直接雙擊 HTML 常只看到空白；`localhost` 不能丟給朋友玩

### 3. 每輪一個目標、最小範圍修正

> 請先讀取這次相關程式，找出問題原因，再做最小範圍修正。保留已經正常的操控、車款選擇與計時。完成後請列出：修改內容、實際驗證方式、仍未驗證的部分。若只做了程式檢查，請不要宣稱已完成整場實玩。

- 頭髮、車子、地圖同時大改，變差了就找不出原因
- 功能分段加：甩尾＋胎痕 → 能量條 → 小噴與音效
- 驗收寫成「不能發生」：只按 Shift 不轉向不能刷能量、按住 Space 不能無限氮氣、一直按油門不能自動小噴（關鍵：程式要分「正在按住」與「這一刻剛按下」）
- 邏輯測試（氮氣不重複觸發）和視覺檢查（尾流沒擋住彎道）**誰也取代不了誰**；有 Git 可用 Codex `/review` 檢查未提交變更
- 先把**一個完整回合**做穩（進入 → 操作 → 勝負 → 再開始一次），再加賽道或模式；否則同一個基本問題會被帶到每個場景（aiposthub）

### 4. 從玩家實際看到的角度驗收

- 追車視角下玩家大多看到後腦、背、手肘和車尾——**背面品質比正面海報更影響體驗**；另做角色檢視頁，同一問題固定同一角度比較
- 場景越漂亮越要保留操作回饋：玩家要找得到自己、看得到前方障礙；效能跟不上會被感受成「難度」
- 靜態截圖只能檢查外觀，**連續操作才看得出視角、碰撞與規則是否一致**
- 調光固定同一鏡頭逐項開關（主光與曝光 → 反射與陰影 → 發光與模糊）
- 保留一份設定固定的基本版本，把場景、對手、效果逐步加回去，掉幀時才知道是誰造成的

### 5. 收測試回饋與交付

- 試玩回饋請對方記：瀏覽器、裝置、出問題的位置，最好附一小段錄影
- 桌面鍵盤與手機觸控是兩套輸入，提示要跟目前裝置連動；分清「操作角色」和「操作視角」
- 多人模式另一個設計題：誰過線、誰淘汰、何時下一輪要大家一致；裝飾物擺動與勝負排名對同步正確性的要求不同；要處理斷線重進
- 交付檢查表（Riven）：啟動、選車、操作、比賽（逆向與重複過線不能刷圈）、完賽、視覺、效能（目標裝置跑完一場）、版本（保留修改前版本、記下未驗證項）、分享（公開版沒夾帶私人素材、帳號、開發設定）
- 生成配樂與宣傳圖：記清音檔來源、不拿其他商業遊戲配樂；封面縮到手機縮圖大小再看，生成文字逐字檢查，標示「宣傳圖非實機畫面」

## C（關鍵行動）

- [ ] 下次請 AI 改視覺／互動問題時，用四句話（哪裡／什麼情況／保留什麼／怎樣算修好）取代「再精緻一點」
- [ ] 提示詞結尾固定加「列出修改內容、驗證方式、仍未驗證的部分；只做程式檢查不可宣稱已實玩」
- [ ] 做 3D 作品時，驗收清單分「邏輯測試」與「連續操作的視覺檢查」兩欄

## 補充資料

**2026-11-19 補充（來源：aiposthub〈Perplexity Roadster 遊戲亮相：Computer 做出的 AI 原型，離正式作品還差什麼？〉，https://www.aiposthub.com/perplexity-computer-roadster-browser-game-prototype/ ，2026-10-19）**：Perplexity 執行長公開以 Perplexity Computer 製作的瀏覽器駕駛＋飛行遊戲；製作過程、人工修改、費用均未公布，以下驗收建議是站方觀點，不是該作品的實際流程。

- **展示能證明與不能證明的分開**：有可玩連結與影片 ≠ 正式商業遊戲完成、≠ 全程無人修改、≠ 所有裝置流暢、≠ 固定時間與費用
- **先定義「最小可玩迴圈」**：玩家反覆做什麼、得到什麼回饋、為何想再做（例：加速、轉彎、回到起點）；需求寫成可觀察結果——「按住方向鍵持續轉向、放開後停止增加轉向」比「真實的操控感」好對焦
- **驗收要讓第一次接觸的人自己走一遍**：入口與載入狀態是否清楚、按鍵與畫面回饋是否對應、視角會不會讓人以為轉向顛倒、**刻意走錯路**（離開道路、卡住、翻車有沒有返回方法）
- 🔑 **「重新開始」要寫清楚重設哪些東西**：只把車放回起點，和把速度、分數、場景狀態一起重設，是不同結果；狀態切換（地面↔飛行）同一按鍵用途改變要有提示
- 測試紀錄寫「操作＋結果」（「降落後仍無法轉向」而非「手感怪怪的」）；問題分「阻擋遊玩」與「影響美感」兩類，先讓最小迴圈走完
- 效能在目標裝置上量、包含不同路線與切換視角後的表現，不能用宣傳影片代替；無法使用某項圖形功能時要明確告知
