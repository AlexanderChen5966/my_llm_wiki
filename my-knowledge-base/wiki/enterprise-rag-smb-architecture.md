一個 Spring Boot + Vue3 中小企業級 RAG 系統的完整工程實作：8 個領域拆分的後端 Package、6 容器基礎設施、段落優先分塊、向量+關鍵字混合檢索+可選 Rerank（含降級設計）、鄰居 Chunk 補全、三層參數覆蓋（請求＞知識庫＞全域）。核心命題：**企業級 RAG 的工程複雜度不在 LLM，在檢索**——「RAG = 向量資料庫 + 大模型 API」只是 Demo 公式，真正的工程量在文件入庫/分塊/召回/精排/可觀測這「前 99 公里」。

## T（核心論點）

Demo 版 RAG 公式忽略了真正決定「能用」與「好用」的工程細節：文件怎麼入庫、長文件怎麼切、中文檢索關鍵字怎麼抽、向量召回 20 條哪 5 條該進上下文、rerank 掛了怎麼辦、使用者怎麼知道回答引用了哪些原文、檢索參數怎麼調且怎麼驗證調對了。這篇文章把整個專案骨架攤開，示範一條可從 0 到 1 落地的企業級 RAG 鏈路長什麼樣。

## B（適用場景）

中小企業想自建知識庫問答系統（一個團隊用一個知識庫，不需要多租戶）；評估 RAG 系統該拆成哪些模組、哪些容器；需要參考「能用」到「好用」之間的具體工程落差（分塊策略/混合檢索/降級設計/參數可調）。

## R（架構重點）

**明確劃邊界**（第一版刻意不做的事）：多租戶與權限體系（中小企業場景通常一團隊一知識庫）／複雜文件前處理（先用 Apache Tika 通用解析，表格擷取/OCR/層級結構留待第二階段）／自研 Embedding 模型（直接對接 OpenAI 相容介面，模型可換）。

**8 個領域拆分 Package**（按領域非按層拆分，一個 Package 內含 Controller/Service/Entity，改功能只在一個包裡跳）：`document`（上傳/非同步索引/狀態機）／`parser`（Tika 解析）／`chunk`（段落優先切分）／`embedding`（OpenAI 相容 API 呼叫）／`vector`（Qdrant 讀寫）／`retrieval`（混合檢索編排）／`rerank`（精排，掛了自動降級）／`chat`（問答編排+引用）／`evaluation`（檢索評測）／`knowledgebase`（參數配置）／`audit`（問答日誌）。前端路由與後端 Package 一一對應。

**6 容器基礎設施**：MySQL（結構化資料）／Qdrant（向量最近鄰搜尋，MySQL 做不到）／MinIO（原始文件儲存）／Embedding 模型容器／Reranker 模型容器／Nginx（幫模型容器套 Bearer Token 驗證，因為模型容器本身無認證機制）。產品化細節：埠號非標準（減少掃描機率）、模型容器不直接暴露、資料持久化到本機目錄、敏感資訊走 env 檔。

**文件入庫：5 狀態非同步流水線**：`UPLOADED → PARSING → CHUNKING → INDEXING → INDEXED`（任意節點失敗→`FAILED` 並記錄原因）。上傳只做「落 MinIO + 建資料庫記錄 + 丟執行緒池」三件事，不同步等大文件解析完成。每個狀態切換即時寫庫，讓前端能輪詢顯示進度。

**分塊：段落優先而非無腦切**：以段落為最小單位拼塊，只有單一段落超過 maxChars（預設 1000 字元）才滑窗切分（重疊 150 字元）。原因：段落有天然語意邊界，硬拼會讓向量「兩頭不像」，檢索時兩邊都討不到好。

**混合檢索的核心洞察——純向量檢索對專有名詞/編號不敏感**：兩條腿並行——向量召回（語意層，topK 預設 20）+ 關鍵字召回（字面層，MySQL 全文索引，沒命中降級 LIKE）。中文關鍵字抽取用 4 字 n-gram 視窗切分彌補中文無空格分詞邊界的問題。兩路結果依各自分數（向量 cosine / 關鍵字固定弱分 0.2）融合排序。

**Rerank 是增強路徑非主鏈路**：Cross-Encoder 把 question 與候選 chunk 拼在一起打分，精度顯著高於向量相似度，但呼叫失敗時**自動降級回融合排序**（try-catch 包裹，warn log 後繼續），不影響問答可用性——這是生產系統對「外部服務可能掛」的防禦性設計範例。

**鄰居 Chunk 補全**：命中 chunk 向前後各擴展 N 個鄰居（預設各 1 個），解決「知識跨兩個 chunk」問題（如步驟說明分在相鄰兩段）。補全後按 context-max-chars（預設 8000）截斷，先到先得確保最相關 chunk 排最前。上下文組裝格式明確標註「引用 N，文件：X，片段：Y」，讓 LLM 回答時能帶引用編號。

**三層參數覆蓋**：`請求參數 > 知識庫配置 > application.yml 全域預設`。這個設計把「調參」從「改程式碼→重新部署」變成「前端 Settings 頁面調滑桿→即時生效→Chat 頁面直接試效果」，是評測閉環（不同參數組合跑同一評測集）得以成立的前提。

**三種問答呼叫方式**：同步問答（一次性返回）／流式問答（SSE，Java 21 虛擬執行緒，交易用 TransactionTemplate 手動管理避免 SSE 長交易鎖表）／僅檢索（只跑檢索不調 LLM，供除錯用）。每次問答記審計日誌（question/answer/命中 chunk IDs/模型名/延遲），不記 IP/user——中小企業第一版不需要。

## C（關鍵行動）

- [ ] 自建 RAG 系統前先明確劃邊界（做什麼/不做什麼），避免範圍漂移
- [ ] 中文內容檢索務必做關鍵字補召回（n-gram），不能只依賴向量語意召回
- [ ] 外部服務（Rerank/Embedding）務必設計降級路徑，不能讓單點故障拖垮主鏈路
- [ ] 檢索參數做成可調（三層覆蓋機制），而非寫死在程式碼裡，才能支撐評測閉環
- [ ] Chunk 補全與引用來源標註是「好用」與「能用」的分水嶺，不是可有可無的細節
