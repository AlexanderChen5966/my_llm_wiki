整合〈Tedium Is Stability〉系列 01–03（iThome 連載，**系列進行中**，04 預告談 harness）。

## T（核心論點）

一個「功能」水面下藏著一組**沒說出口的隱形義務**（稽核／權限／機敏／外部／容錯／多台安全…），它們不是無限多，而是**固定、會反覆出現、可以被清點的**——本質就是軟體工程的老概念「橫切關注（cross-cutting concerns）」。既然可清點就能寫下來，於是**把義務也當成 Code（Obligations as Code）**；而讓清單真正被落實的，是把協作方式從「調 prompt」改成「**設計循環**」，並且每條義務都接上一個**機器能判定**的檢查。

**最關鍵的翻轉**：過去「逐條補齊十幾條義務」的繁瑣是**出錯的來源**（人會累、會趕、會默默跳過）；交給 AI agent 後，跑一遍清單的成本趨近於零，繁瑣就從出錯的來源**翻轉成安定的來源**。

## B（適用場景）

**適用：**
- 與 AI agent 協作開發，卻總覺得「功能寫完了但還是不放心」
- 團隊的開發規矩靠資深工程師直覺與 code review 口頭提醒維繫（人一走、換個 session、換個沒踩過坑的 AI 就漏）
- 想把 CLAUDE.md／AGENTS.md 從「規則清單」升級成「可驗證的義務清單」

**不適用 / 注意：**
- 文中的「八個面向十幾條」**只是給感覺、不是聖旨**——每個產品要依自家習慣加上對自家程式碼的分析，長出專屬的那一組
- **系列尚未完結**（03 預告 04 談 harness），完整落地方法還在連載中
- 若驗證步驟不可判定，整個循環會空轉（見下方陷阱）

## R（三層遞進）

### 01 → 命名那份不安

「AI 幫你把功能寫完了，你為什麼還是不放心？」——先替這種結構性的不安取名字。

### 02 → 隱形契約是可清點的老朋友

**橫切義務約十幾條、收攏成八個面向**：稽核與紀錄／系統健康與告警／審核與狀態管理／權限／個資與機敏／外部系統與容錯／排程／資料庫結構與復原／回歸測試／負載／多台機器安全。

**走一遍「匯出訂單報表 API」，會點亮這些**：

| 義務 | 具體怎麼「做到」（可檢查的動作）|
|---|---|
| **稽核** | 治理良好的系統有**統一寫入口**——grep 該寫入口的呼叫點，看新路徑在不在裡面。⚠️ 背景排程常預設「只留執行足跡、不進使用者可見的異動紀錄」，這是設計不是 bug |
| **權限** | **`scope` 管角色能不能，`license` 管客戶買沒買**——是兩件事，兩個都要問 |
| **機敏** | 報表欄位有無身分證號、電話需遮罩。**最容易被漏，因為不遮功能照樣會動** |
| **外部** | 對外呼叫要落紀錄，鐵律：**永遠不要把密碼、授權 token 放進紀錄的 request 內容** |
| **容錯** | 外呼可能失敗 → 想清楚重試還是補償，別讓它默默消失；重試要考慮**冪等** |
| **多台安全** | 每月自動匯出的排程，正式環境跑兩台時只能在其中一台跑，否則報表和信都來兩份——**用集中協調的排程機制** |

### 03 → 設計循環，不是設計 prompt（Design the Loop, Not the Prompt）

> 「把跟 AI 的協作想成寫一句夠好的 prompt，彷彿咒語夠精準就會一次做對做全——**這是這個時代最貴的錯覺之一**。」

**循環骨架（任何任務都一樣）**：
```
蒐集（讀懂這任務點亮哪些義務）→ 動手（實作）→ 驗證（每條義務跑可判定檢查）
   ↑                                                    ↓
   └────────────── 紅燈回頭重來 ／ 綠燈才收工 ←──────────┘
```

**關鍵洞見：骨架不變，唯一隨領域改變的是「怎麼算對」——只有 verifier 換題目。**（寫程式跑測試／接資料比對筆數／改流程走端到端）

### 🔴 致命陷阱：verifier 必須「可判定」

> 如果驗證只是自己回頭看一眼、覺得「嗯，應該有做吧」，**這個循環是空轉的，跟咒語思維沒兩樣，只是多繞了一圈**。

**每條義務接上機器能判定的檢查**：

| 義務 | 可判定的檢查 |
|---|---|
| 有沒有記稽核 | **grep** 統一寫入口的呼叫點，看新路徑在不在裡面 |
| 端點有沒有過授權 | **負向測試**——拿沒權限的身分去打，期望被擋 |
| 改 A 有沒有壞 B | **回歸測試**，且斷言「**最終狀態**」而非「這次跑出來的差異」|
| 欄位跟資料庫對不對得上 | **結構檢查**，讓它在啟動時就紅燈 |

**咒語思維 vs 循環思維**：前者射出去對就對錯就錯，漏了什麼當下不知道，等三個月後帳單來才發現；後者每輪都有驗證把關，**把「會不會漏」從運氣變成可設計的機制**。

## C（關鍵行動）

- [ ] 盤點自家專案真正的那一組橫切義務（別直接抄八個面向，要加上對自家程式碼的分析）
- [ ] 把義務清單寫成人和 AI 都讀得懂、**可逐項打勾**的檔案，並像程式碼一樣版控
- [ ] **為每一條義務配一個「機器能判定」的檢查**——沒有可判定驗證的清單等於沒有
- [ ] 回歸測試記得斷言「最終狀態」，不是「這次的差異」
- [ ] 把身分從「操作聊天機器人的人」換成「設計迴圈的工程師」——不要再花時間雕 prompt
