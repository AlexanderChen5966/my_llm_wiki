同系列 Day 02–04 見 [[claude-code-api-request-reverse-engineering]]、Day 05–10 見 [[hand-coding-agent-file-tools]]、Day 11 見 [[handcraft-agent-shell-tool]]、**Day 12 見 [[agent-loop-stop-conditions]]**。前十二天造零件，這一天不加功能，把一個埋了 bug 的專案丟給它做隨堂考——**跑五次，含出包的那一次全部記下來，連帳單都附上**。

## T（核心論點）

> **測試會過也不代表任務成功，還要看它是怎麼讓測試過的。**

真正的驗收就三件事：**測試綠燈、改動範圍合理、需求沒被誤解**。🔑 **前兩件機器可以幫你看，第三件目前還是得人類來做。**

以及那次失敗給出的第二個結論：

> **手上沒有可以跑的驗證，模型最後只能猜——猜錯了還會很有自信地告訴你沒問題。**

## B（適用場景）

**適用：**
- 設計自建 agent 的驗收方式（為什麼要印 diff 而不是只印 pytest 最後一行）
- 理解「為什麼驗收測試要放在 agent 改不到的地方」的具體理由
- 估算 coding agent 單次任務的實際成本結構
- 作為最小 eval case 的範本

**不適用 / 注意：**
- 🔴 作者自己聲明**這不是嚴格的對照實驗**：工具清單變了、模型生成也有隨機性，不能把失敗只算在「看不到結果」頭上；五次樣本也不足以證明用字差異的因果
- ⚠️ 成本數字為 KeSi（自製 agent，七個工具）實測，非 Claude Code 本體

## R（考題設計與三次成功實測）

### 考題刻意設計的三個難點

會員訂單試算專案，bug 是 `tier_discount()` 裡的 `if amount > threshold` 應為 `>=`（經典 off-by-one：買 1001 有折扣，剛好 1000 反而沒有）。

1. **bug 不在測試指到的檔案裡** — 失敗的是 `test_pricing.py`、測的是 `pricing.checkout()`，但錯在 `rules.tier_discount()`，要**跨兩層**才追得到
2. **錯誤訊息看不出原因** — `assert 1000 == 900` 只說少折 100，可能是折扣沒算／運費多算／折扣表寫錯，**必須讀 code**
3. **旁邊還有干擾** — `utils.py` 與 `test_utils.py` 完全無關但就躺在那裡。🔑 **「一個會亂讀檔案的 agent，帳單會比較貴」**

題目只給一句話、不指定檔名也不指定工具：「跑一下測試，有一條過不了，幫我找出原因並修好」。

### 七步路線全部由它自己排

`list_files` → `run_command(pytest -v)` → 讀 `test_pricing.py` → 讀 `pricing.py` → 讀 `rules.py` → `edit_file` → 再跑一次測試。

兩個值得注意的細節：

- ✅ **它自己選了 `-v` 而不是 `-q`**，作者沒教任何參數——因為它要的是「哪一條測試掛了」而不是一句摘要
- ✅ `edit_file` 的 `old_string` **把整個函式包進去只換一個字元**（那行其實是唯一的，直接帶也會過，但多帶上下文比較保險）
- ✅ **`utils.py` 與 `test_utils.py` 連開都沒開**

### 三次的帳單

| | 圈數 | 牆上時鐘 | input | output | 成本 |
|---|---|---|---|---|---|
| 第一次 | 6 | 16.2s | 31,967 | 1,095 | $0.0374 |
| 第二次 | 7 | 16.8s | 37,110 | 1,151 | $0.0429 |
| 第三次 | 8 | 78.5s※ | 42,961 | 1,215 | $0.0490 |

※ 第三次的第 1 圈就花 61 秒，是連線卡住不是模型在想事情。

三次都修對同一行、改法一模一樣，但**圈數 6/7/8、花費差了三成**——沒辦法靠重跑得到完全相同的重播。

🔑 **但有一個數字三次完全相同：第 1 圈的 input 都是 4,162。** 那一圈送出去的只有工具說明書（4,130 token）加同一句題目，一個 byte 都沒差。**會浮動的是模型決定做什麼，不是我們送出去的東西。**

其他成本觀察：

- 題目本身只有二十幾個字，但第 1 圈就要付 4,162 token——**七份工具說明書的錢，還沒開始做事就先付**
- input 從 4,162 一路爬到 6,673，**每一圈都把前面所有工具往返重念一次**（日記越寫越厚）
- 第 4 圈 output 特別高（466）因為是 `edit_file`，`old_string` 與 `new_string` 兩份幾乎一樣的函式都要重新生成；**output 比 input 貴五倍，所以這是全場最貴的一圈**
- 工具紀錄有七行但帳單只有六圈：**parallel tool use**，模型一次回應可開多張單（第 3 圈 output 184 是隔壁幾圈的兩倍半，就是三個 `read_file` 一次開出去那圈）

## C（關鍵行動）

- [ ] 驗收一律印 **diff** 而不是只印測試最後一行——「7 passed」只說這七條過了，沒說它是怎麼過的
- [ ] 把驗收測試放在 **agent 改不到的地方**（SWE-bench 就是這樣做的）
- [ ] agent 收尾說「**應該**可以通過」時提高警覺：那代表它手上沒有驗證證據

## 補充資料

### 🔴 拿掉 `run_command` 那次：改壞測試，還講得很有自信

同一份專案、同一句話，只把 `run_command` 移出工具清單（`--no-shell`）：

**好消息**：它靠讀 code 一樣找到那個 `>` 並改成 `>=`，**完全正確**。

**代價與翻車**：它把整個專案幾乎讀了一遍（連無關的 `utils.py`、`test_utils.py` 都讀了，還多開一次 `glob`），然後**動了測試檔**：

```diff
-    # 滿千折百：1000 - 100 = 900，900 大於 800 所以免運
-    assert checkout([(1000, 1)]) == 900
+    # 滿千折百：1000 - 100 = 900，900 小於 800 所以加運費 60
+    assert checkout([(1000, 1)]) == 960
```

**900 明明大於 800。** 程式已經被它修對了（`checkout` 真的回傳 900），但它把答案改成 960，於是這條測試從頭到尾沒綠過。花了 $0.0399 繞一大圈，專案回到原點。

三個結論：

1. **模型會犯很蠢的錯，而且講得很有自信** — 900 跟 800 誰大誰小不是複雜推理，但它寫錯了，還**順手把註解一起改成錯的**。官方對 honest 的定義是「該承認極限時承認」，那是**訓練出來的傾向，不是保證**
2. **注意用字從「都通過了」變成「應該都能通過了」** — 前三次它剛親眼看到 `7 passed`，這次只能說「應該」。⚠️ 作者謹慎聲明五次樣本不足以證明用字因果，**但可以確定的是：它手上沒有測試結果，卻仍宣稱結果應該會過**——這正是 grounding 缺席的風險
3. 🔴 **改測試讓它變綠，是最好走的一條路** — 這次它不是為了作弊，是真心認為測試寫錯了（只是算錯）。**但你可以想像另一種情況：一個修不好 bug 的 agent，把測試改成 `assert True`，畫面上照樣全綠燈**

⚠️ 同樣拿掉 `run_command` 再跑一次，這次它沒動測試檔就收工、七條全過（$0.0279）——**改壞測試不是每次都會發生**，但兩次的收尾都用了「應該」。

🔴 **KeSi 目前對這種事一點意見都沒有：它可以改測試、刪測試、在你沒看到的地方偷偷把標準放寬，沒有任何一道關卡會問你一聲**——而它的權限跟前十二天那個只會讀檔的版本一模一樣，全部放行。

### 為什麼「綠燈」證明不了什麼

要讓那七條測試變綠，至少有這些做法：把 `DISCOUNT_TABLE` 門檻從 1000 改成 999／在 `checkout()` 裡加 `if goods == 1000: return 900`／**把那條測試刪掉**。三種都能變綠，也都不是我們要的。

承接 Day 09 的那句「編輯成功也不代表任務成功」，本篇再加一句：**測試會過也不代表任務成功**。

### 模型會憑空生出參數（grounding 反例）

第二次跑的時候它下了 `cd /tmp/a1eec5c2-df1b-4078-8b99-ce68c7b7c0c9 && python -m pytest -v`——**那個 UUID 目錄不存在，是它自己掰的**（呼應 Day 05「表格是它填的，值是它猜的」）。指令失敗後它下一步就改成直接跑 pytest，成功了。

作者提出一條線索但**明確拒絕下結論**：Day 11 的工具說明書寫著「需要換目錄時請在同一行用 `cd x && ...`」，它下的指令跟這個句型很像，只是 `x` 被憑空填值。**「工具說明可能影響模型的行為，要確定是不是說明書造成的，還得固定其他條件多跑幾次對照。」**

另外第三次它沒用 `list_files`，改用 `find . -name "*test*.py" ... | head -20` 走 shell——說明書裡「讀寫檔案請優先使用 read_file、edit_file、write_file」這句，**看得出來只是個建議，不是規則**。（同 [[handcraft-agent-shell-tool]] 的「工具說明書寫規則到底有多少強制力」）

### 這就是一個最小的 eval case

準備有 bug 的專案 → 確認一開始是紅的 → 交給 agent → 跑測試看有沒有變綠 → **檢查它改了什麼**。這是一個 case 的其中一次 trial。

Anthropic 的 eval 設計建議三件事：評測要 **mirror your real-world task distribution**、別忘了 edge case、題目寧可多不要少。

**SWE-bench 對照**（Princeton 團隊，arXiv 2023 → ICLR 2024）：2,294 個問題，來自 12 個熱門 Python 專案的真實 GitHub issue 與對應 PR。關鍵差異是 🔑 **模型看不到用來評分的測試，也不能像 KeSi 一樣直接改掉驗收標準**——交出 patch 後由外面另一支程式套上去再跑測試。每題帶兩組清單：

- **FAIL_TO_PASS** — 原本紅的要變綠
- **PASS_TO_PASS** — 原本綠的不准弄壞

兩組都滿足才算解題成功。⚠️ 本篇那次失敗**不屬於** `PASS_TO_PASS`（它改的是這題的目標測試）；真要對上 `PASS_TO_PASS`，情況會是修 bug 時順手把原本會過的 `test_utils.py` 弄紅。**這個差別正好說明為什麼驗收測試要放在 agent 改不到的地方。**

**分數史**：2023 年論文剛上 arXiv 時最好成績是 Claude 2 的 **1.96%**（100 題解不到 2 題）→ 2024-08 人工重審留下較乾淨的 500 題成為 **SWE-bench Verified**，分數一路衝到八成以上 → 🔴 **2026-02 OpenAI 宣布不再用它評估前沿寫程式能力**，理由是資料污染，加上題意與測試的問題還沒清乾淨，建議改用 **SWE-bench Pro**。
