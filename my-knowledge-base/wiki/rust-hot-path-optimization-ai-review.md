開源鍵盤音效 App KeyEcho 重構到 1.0，用四招讓音訊熱路徑快 27 倍（最大切片 38 倍）且零位元組複製。全程大量交給 AI agent 產碼，Rust 借用檢查器是第一道審查；但作者拒絕了一個「看似乾淨卻會靜默降版」的 AI 修正——決定何時停止與整合，仍是人的工作。

## T（核心論點）

熱路徑優化的本質是「把每次按鍵都要付出的成本移出路徑」（解碼、配置、取樣複製、鎖）。而 AI 產碼時代最重要的教訓不是速度，而是判斷：**綠燈只證明測試通過，不證明測試涵蓋了你即將失去的功能**。每個 pin / hack / 魔術數字都要就地寫明「為什麼」，因為 agent 對你的專案毫無上下文。

## B（適用場景）

**適用：**
- 對延遲敏感的熱路徑（音訊 / 即時事件）優化
- 大量使用 AI agent 產碼、需要建立人類把關準則的專案
- 想理解 Rust 型別系統為何是 AI 產碼的安全網

**不適用 / 注意：**
- 不是通用效能指南，四招針對「短而高頻的路徑」
- 微基準數字是查找路徑，非端到端延遲（取決於 OS / 硬體）

## R（四招重構 + 兩條人類把關規則）

### 讓熱路徑快 27 倍的四個動作

1. **選取音效包時一次性預先解碼**：按鍵時不再做任何解碼（把前置工作換成記憶體用量）
2. **去重相同切片**：用 `(start_ms, duration_ms)` 當 key，每個唯一切片只解碼一次並共用
3. **零拷貝播放**：解碼後取樣存在 `Arc<[f32]>`，查找只複製 Arc（引用計數 +1），每次按鍵複製成本 0 位元組
4. **移除全域 mutex**：目前音效放 `ArcSwapOption`、音量放 `AtomicU32`，查找是無鎖讀取

預解碼需兩道保護：有界佇列（大量輸入形成反壓，記憶體不無限成長）+ 10 MiB 已解碼取樣預算（超過就拒絕載入）。

| 路徑 | v0.0.5 | v1.0 | 變化 |
|---|---|---|---|
| 快取查找（平均切片）| 1184 ns、複製 66.84 KiB | 43.5 ns、0 位元組 | 快 27.2 倍 |
| 快取查找（最大切片）| 1638 ns、複製 98.88 KiB | 43.1 ns、0 位元組 | 快 38.0 倍 |

**Rust 為何讓這件事又快又安全**：把共享緩衝改 `Arc<[f32]>` 並移除 mutex，正是出錯就會變成別名或 `Send`/`Sync` 錯誤的改動，借用檢查器會在編譯階段就攔下——agent 參與越多，這道防線越有價值。

### 那個看似乾淨、卻不能合併的 AI 修正

CI 在 QEMU 下建置失敗，agent 提出把音訊 crate 的 git pin 拿掉改用 crates.io release，CI 立刻變綠。但作者**拒絕**：那個 pin 把 `cpal` 鎖在 0.18（提供拔耳機 / 切藍牙時聲音跟隨的裝置重導向），改回會靜默降到 0.17.3 失去該功能，而且沒有任何測試涵蓋這行為。真正的修正是 `cargo vendor` 離線建置，pin 從頭到尾沒動。

### 兩條規則

1. 每個 pin / hack / 魔術數字旁都要寫「為什麼」（註解或專案 AI 規則檔）——agent 不記得當初為何放它
2. 不接受你沒要求的相依版本變更，即使 CI 變綠也不行

**agent 沒有沉沒成本概念**，放任它會永遠優化某個建置目標；決定何時停止是人的工作（作者直接刪掉跑兩小時、無明顯使用者的 armv7 建置）。

## C（關鍵行動）

- [ ] 熱路徑優化先問：哪些工作可以移到「選取 / 初始化」時一次做完
- [ ] 共享大型 buffer 用 `Arc<[T]>` 做零拷貝，讀多寫少的狀態用 `ArcSwap` / `Atomic` 去 mutex
- [ ] 在 CLAUDE.md / AI 規則檔記錄每個 pin 與 hack 的理由
- [ ] Review AI 修正時，別讓 CI 綠燈取代「這是否悄悄改了相依版本或砍了功能」的人工判斷
