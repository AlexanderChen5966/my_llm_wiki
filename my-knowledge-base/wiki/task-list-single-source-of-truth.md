## T（核心論點）

大規模開發不能只靠「長 Prompt」管理——AI 沒有跨對話的記憶，前一次對話決定的方針，到下一次對話就會消失。解法是把 **`docs/task-list.md` 當成任務管理的唯一正本（Single Source of Truth）**：即使 Slack、GitHub Issue、聊天內容與 AI 完成報告的記載不同，**正式狀態一律以這個檔案為準**。

## B（適用場景）

**適用：** 中大型開發任務、多個 AI 工具協作同一個 repo、需要第三方（人類 reviewer）能追蹤進度的場景

**不適用 / 注意：**
- 個別任務的目的與完成條件**不該塞進長期規則檔**（AGENTS.md/CLAUDE.md），那裡只放「每次都要用到的規則」
- 與知識庫既有 [[claude-code-dynamic-workflows]] 是**不同主題**——那篇談 Claude Code 內建動態工作流功能，本篇談**任務清單管理方法論**，兩者互補

## R（六個核心機制）

### 一、`task-list.md` 的表格結構

```markdown
| ID | 任務 | 狀態 | 進度 | 相依性 | 完成條件 | 證據 |
|---|---|---:|---|---|---|---|
| DEV-001 | 建立文章草稿 API | 完成 | 100% | - | API 測試成功 | Test #18 / PR #12 |
| DEV-002 | 防止重複建立 | 進行中 | 70% | DEV-001 | 相同 ID 不會增加投稿 | 等待驗證 |
```

至少包含：**ID**（唯一識別）、**任務名稱**、**狀態**、**進度**（補充狀態看不出的中間過程）、**相依性**、**完成條件**、**證據**（連結測試/PR/log/畫面確認）。

### 二、🔴 任務 ID 途中不可重複使用

一旦發行過的 ID，即使任務已刪除，**也不要拿去用在別的用途**——重複使用會讓過去的 commit、PR、測試結果、對話裡提到的 ID **變成另一個意思**。

> 任務不做了，**不要刪掉那一列**，把狀態改成「中止」或「非對象」，並保留理由。

### 三、新問題一律登錄為新任務，不塞進目前任務

作業中發現其他 bug 或改善項目時，先判斷屬於哪一類：
1. **為了滿足目前完成條件而必須處理** → 在目前任務內處理
2. **雖有關聯，但不屬於目前完成條件** → 登錄成新任務
3. **無關的既有問題** → 登錄成新任務

> 不這樣切分，一個任務就會**無限膨脹，永遠無法完成**。

### 四、🔑 進行中任務原則上限定為 1 件

**正因為是大規模開發，才要限制進行中只有 1 件**——AI 能快速處理多個工作，但同時修改多個任務，**人類要檢查的組合會暴增**：若 3 個任務同時動同一支 API，很難判斷哪個變更是 bug 原因、該在哪個測試發現、規格變更從哪來、回退要回到哪裡。

**標準流程**：① 決定下一個任務 → ② 確認開始時 Git 狀態 → ③ 只實作該任務 → ④ 測試與 review → ⑤ 更新文件與證據 → ⑥ 建 commit/Draft PR → ⑦ 標記完成或等待驗證 → ⑧ 進下一個任務。

> 要平行化，僅限**不會寫入相同檔案或資料**的獨立調查與測試；多個實作平行進行則要分 branch 或 **Git worktree**。

### 五、任務指示模板（可直接複製）

```markdown
# 目標任務
DEV-002 防止重複建立

## 開始前確認
- 確認目前 branch、HEAD、git status
- 閱讀 task-list.md 與相關規格文件
- 確認前置任務 DEV-001 已完成
- 若工作樹中已有既有變更，則停止

## 目的 / 變更範圍 / 禁止事項 / 完成條件 / 完成時要做的事 / 停止條件
（各自條列明確定義）
```

**三層放置原則**（避免重複規則）：

| 放置位置 | 內容 |
|---|---|
| `AGENTS.md` / `CLAUDE.md` | 測試指令、禁止事項、Git 運作、review 標準（**每次都用到的規則**）|
| `task-list.md` | 任務狀態、相依性、完成條件、證據 |
| 個別任務指示 | 這次的目的、對象範圍、特定確認事項 |
| 設計文件 | 系統整體規格、資料結構、判斷理由 |

> Codex 用 `AGENTS.md`、Claude Code 用 `CLAUDE.md`——**若兩者都要用，共通規則集中一處，另一方引用**，減少重複。

### 六、🔴 分開「已實作」與「已完成」（本文最關鍵洞察）

**只有程式碼存在，不代表功能就正確。**

| 狀態 | 意義 |
|---|---|
| 未著手 | 調查與實作都還沒開始 |
| 調查中 | 正在確認規格或既有程式碼 |
| 實作中 | 正在修改程式碼 |
| **本地已驗證** | 自動測試等已成功 |
| **實際環境等待驗證** | 還剩部署端或真實資料的確認 |
| 完成 | 已滿足定義的完成條件與必要驗證 |
| 保留 | 等待外部回覆、權限、規格決定 |

> 沒有這種區分，**AI 可能寫完程式就回報「完成」**，人類會誤以為已能在實際環境使用。還有只能在實際環境確認的項目，**別硬把進度設 100%**，標示「實作完成・等待實際環境驗證」。

### 完成報告要以「證據」為中心，不是「做了什麼」

❌ 不足以作為完成確認：「已實作防止重複建立的功能。也新增了測試，運作沒問題。」

✅ **第三方能追蹤的資訊**：
```markdown
## 結果
- 第一次請求：建立投稿 ID 120
- 使用相同外部候選 ID 的第二次：重用投稿 ID 120
- 不同的候選 ID：新建立投稿 ID 121

## 測試
- 目標測試：12 件成功、0 件失敗
- 相關回歸測試：48 件成功、0 件失敗
- 實際環境確認：未執行

## Git
- 開始時 HEAD：abc1234 / 結束時 HEAD：def5678
- branch：feature/DEV-002-idempotency
```

## C（關鍵行動）

- [ ] 建 `docs/task-list.md` 當任務唯一正本，任何分歧一律以此為準
- [ ] 任務 ID **一旦發行絕不重複使用**，作廢的任務改標「中止」不刪列
- [ ] 新發現的問題先判斷「是否屬於目前完成條件」，不屬於就登錄新任務
- [ ] **進行中任務限定 1 件**，需要平行時用獨立 branch/worktree
- [ ] 狀態拆成「本地已驗證」與「實際環境等待驗證」兩級，別讓 AI 一寫完就回報「完成」
- [ ] 要求完成報告用**證據格式**（結果數據 + 測試通過數 + Git hash），拒絕「已實作、運作沒問題」這類空話
