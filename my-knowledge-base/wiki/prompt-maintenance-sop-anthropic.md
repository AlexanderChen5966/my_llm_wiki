## T（核心論點）

AI 系統效能下降，多數人第一反應是換模型、調參數，或把提示詞越寫越長。但真正的問題往往是**提示詞本身積累了太多歷史包袱**——多人維護、舊模型補丁、混雜業務規則。Anthropic 應用 AI 工程師 Margot van Laar（Code w/ Claude 2026 演講）的核心命題：「我們很少從頭寫提示詞，我們大多數時候是在除錯一個舊的。」

## B（適用場景）

**適用：**
- 長期維護生產 AI 系統的工程師（提示詞有多人修改歷史）
- 發現 AI 表現退步，但不確定問題根源在模型還是提示詞
- 從頭建構新代理，需要選擇架構策略

**不適用：**
- 全新的一次性提示詞（不需要「除錯舊的」）
- 效能問題確定是模型能力不足（這時提示詞優化是徒勞）

## R（4 步驟維護 SOP）

### 步驟 1：先建評估清單，再動提示詞

**在任何修改之前**，先定義測試案例：

| 類型 | 目的 |
|------|------|
| **控制組（Control cases）** | 模型本來就能正確處理的問題，確保改動不造成退步 |
| **邊緣案例（Edge cases）** | 過去曾失敗的情境，改後應持續通過 |
| **能力邊界案例** | 應轉人工 / 應拒絕回答的情境 |

**評估清單的兩個作用：**
1. 區分「提示詞問題」（可修復）vs「模型能力不足」（需換模型/引入工具）
2. 防止優化變成「對著錯誤的鏡子調整」

> 沒有評估清單，所謂的優化不過是憑感覺。

### 步驟 2：先清理提示詞結構，再針對具體問題

典型提示詞腐化症狀：
- 角色設定矛盾（「你是一位人類客服」→問 AI 是否是 AI 時混亂）
- 直接複製貼上官網文字（包含 hero image 說明、cookies 提示）
- 結構完全扁平（政策/語氣/角色全擠一起）

**修正方式：XML 標籤分區**

```xml
<role>...</role>
<guidelines>...</guidelines>
<policy>...</policy>
<tone_of_voice>...</tone_of_voice>
```

僅做這一步（不針對任何具體失敗案例），van Laar 示範中 5 個測試案例就有 1 個明顯改善。

**輸出契約（額外最佳實踐）：**
```python
# API 參數加上
stop_sequences=["</response>"]
# 提示詞加上
# "把回應包在 <response> 標籤內"
```
防止模型輸出結束後繼續生成多餘內容，對複雜結構化輸出（巢狀 JSON）特別有效。

### 步驟 3：一次只處理一個失敗案例（三個關鍵教訓）

**教訓 1：別讓舊補丁變成新詛咒**

舊模型的防禦性指令（「絕對不要告訴客戶方案資訊，引導去官網」）在新模型被過度執行——即使有正確答案，模型也不敢回答。

解法：明確說明**何時**應該直接回答、**何時**才需要引導，取代籠統的禁止指令。

> 建議用版本控制記錄每條補丁的**新增原因**，以便日後追蹤和移除。

**教訓 2：Instructions don't add capability**

「指令不能取代能力。」要求模型「精確計算按比例費用」，但讓模型靠心算處理帳單本就不可靠。

解法：給模型真正的計算工具（定義 schema + 實作邏輯），而不是加強語氣要求它算準。

**教訓 3：只告訴模型代價，它會做出單面的決策**

「轉接客服費用 $8，且計入快速解決率」→ 模型優化了轉接成本，忽視了「處理不當造成客戶流失」的另一面代價。

解法：補上反面資訊，讓模型判斷完整的取捨框架，而不是只告訴它你想要什麼結果。

### 步驟 4：架構比模型更重要（新代理建構）

van Laar 測試了五種策略組合，**三段式代理架構最優勝**：

| 策略 | 結果 |
|------|------|
| Sonnet 4.6 + 簡單提示詞 | 全部失敗，違規數高 |
| Opus 4.7 + 相同提示詞 | 仍失敗，違規數減少 |
| Opus 4.7 + 動態思考 | 全部通過，但 token/延遲增加 3 倍 |
| Sonnet 4.6 + 含自我檢查指令 | 部分通過（輸出長度限制） |
| **三段式代理（生成→評估→修復）** | **全部通過，token 用量和延遲最低** |

**三段式代理架構：**
```
Generator（生成器）：生成第一版草稿
    ↓
Evaluator（評估器）：逐條核對規則，列出違規項目與具體證據
    ↓
Repairer（修復器）：接收違規清單，針對性修正草稿
```

**關鍵設計優點：**
- 三個提示詞各自簡單，每個只做一件事
- 軟性需求（「Harry 和 Sally 盡量不要排同班」）直接加入 Evaluator，不動 Generator 的硬性規則
- 比「讓最強模型硬撐整個任務」更高效

**注意事項：**
- 加入工具需後端工程支援（非純提示詞工程師可單獨完成）
- 三段式代理多兩個 LLM 呼叫，延遲敏感場景需評估
- 評估清單品質決定一切：邊緣案例覆蓋率直接決定改善上限

## C（關鍵行動）

- [ ] 對現有提示詞建立評估清單（控制組 + 邊緣案例 + 能力邊界）
- [ ] 審查所有舊補丁：加了這條的原因是什麼？新模型還需要嗎？
- [ ] 遇到計算/查詢類問題，先評估是否需要給模型工具，而不是強化語氣
- [ ] 複雜生成任務考慮三段式架構（生成→評估→修復）取代單一強模型
