## T（核心論點）

Anthropic 為 Claude 5 世代刪掉 Claude Code **逾 8 成系統提示詞、內部編碼評測零可測量下滑**——證明過去為判斷力不足的舊模型設計的「大量範例＋嚴格禁令」正在扯新模型後腿。核心轉向是**從「防呆」到「授權」**：減少過度約束（overconstraining）、少堆範例改為設計清楚介面、用漸進式揭露取代全塞前面，把判斷權還給模型。

## B（適用場景）

**適用：**
- 使用 **Claude 5 世代模型**（Opus 5 / Fable 5 等）時檢討既有 CLAUDE.md 與提示詞
- CLAUDE.md 或工具描述已塞滿「絕不」「一律禁止」與大量範例、想瘦身的人
- 設計 Skills / 工具介面時取捨「寫多細」

**不適用 / 注意：**
- **前提是新模型**——舊模型少了這些護欄，註解等輸出在很多情境會出錯，貿然刪光等於拆掉防翻車護欄
- **「讓模型判斷」≠ 什麼都不寫**：官方為「高度重要領域」（安全、關鍵約束）保留嚴格約束空間，哪些領域不能交給判斷力仍需人決定
- 守則本身有保鮮期——提示詞技巧的折舊速度就是新常態，下一代模型可能再翻案

## R（六組對照 → 4 條可套用守則）

| 構面 | 舊做法 | 新做法 |
|------|--------|--------|
| 行為約束 | 給 Claude 立規矩 | 讓模型用判斷力 |
| 工具示範 | 給大量範例 | 設計清楚、有表達力的工具介面 |
| 資訊載入 | 全塞在最前面 | 漸進式揭露，需要時才載入 |
| 指令強調 | 重要指令重複講 | 只寫在工具描述，講一次就好 |
| 記憶維護 | 用 CLAUDE.md 手動存記憶 | 自動記憶分擔手動保存 |
| 規格描述 | 寫成簡單文字檔 | 高保真參照物：測試碼 / HTML 原型 / Rubric |

**4 條新守則：**
1. **別立死規矩，留判斷空間**：把「絕對不要」挑出來問「有沒有例外」，有就改成描述原則。官方示範：註解規則從「絕不寫多段註解」改為「跟隨周圍程式碼的註解密度、命名與慣用寫法」。
2. **與其堆範例，先設計好介面**：大量範例會把模型鎖在單一路徑。改讓參數名稱/選項本身就清楚（如待辦工具狀態只開放「待處理/進行中/已完成」+「同時只保留一項進行中」，不必舉例）。但範例輸出、格式參照、特殊案例示範仍有用途。
3. **漸進式揭露**：把資訊拆成檔案樹，需要時才載入。驗證流程/程式碼審查從系統提示詞拆成獨立 Skills（甚至延遲載入，模型須主動搜尋才取得完整定義），CLAUDE.md 只留一行指路。
4. **規格可加高保真參照物**：一份規格可以是完整測試碼、現成函式、HTML 原型——**HTML 排版原型的效果通常好過文字描述或截圖**；也可把品味寫成 rubric 讓模型生驗證代理自我把關。

## C（關鍵行動）

- [ ] 掃描 CLAUDE.md 的「絕不 / 一律禁止」措辭，逐條問「有例外嗎」，有就改成描述原則
- [ ] CLAUDE.md 瘦身至 200 行內：**凡 AI 翻專案就能發現的一律刪**，只留特殊慣例、限制、常見陷阱與持續性規則（建置/測試指令、命名、架構）
- [ ] 把多步驟驗證流程拆成獨立 Skill，CLAUDE.md 只留一行指路
- [ ] 用 `/doctor` 體檢：它會找出 CLAUDE.md 中模型可自行推導的內容並提修剪建議（經確認才套）
- [ ] 確認自己在用 Claude 5 世代模型；舊模型不要貿然刪護欄

## 原始摘要

Anthropic 技術團隊 Thariq Shihipar 於 2026-07-24 官方部落格發文（〈The new rules of context engineering for Claude 5 generation models〉）。核心診斷是「過度約束」（overconstraining）：內部員工紀錄常見同一請求塞互相打架的指令（「留下文件說明」vs「不准加註解」），模型雖能猜出意圖但須耗更多推理處理衝突。CLAUDE.md 自動記憶功能（Claude Code 2.1.59+ 預設開啟）從除錯經驗與被糾正偏好自行累積筆記，與手動 CLAUDE.md 互補而非取代。Skills 定位為「輕量指南」，最有價值的是編入個人/團隊/產品獨有觀點。（bnext 業配與延伸閱讀段落已略）

## 補充資料：三篇媒體轉述的獨有內容（2026-07-30 併入）

同一則官方發文的三個中文轉述版本，各自補上官方原文與 bnext 版沒有的角度。三篇皆已 `.processed`，不另建條目。

### 一、四層 Context 架構（cyberq.tw / blocktempo 皆有）

官方對「每一層該管什麼」的分工，是原本 4 條守則沒有的結構視角：

| 層 | 定位 | 要點 |
|---|---|---|
| **System Prompt** | 與產品情境高度綁定 | 用 Claude Code 的人幾乎不會動；**自建 agent harness 才該在這裡投入大量時間** |
| **CLAUDE.md** | 保持輕量 | 簡短描述 repo 用途，**大部分 token 花在「陷阱（gotchas）」**（如型別全集中在單一檔案這類反直覺組織）；Claude 讀檔案系統就能知道的事不要寫 |
| **Skills** | 輕量指南 | 除非高度關鍵領域，避免寫成強約束；長 Skill 拆多檔案；**最適合承載你／團隊／產品的特定觀點與知識** |
| **References** | 以 `@` 提及檔案 | **優先用程式碼形式**（模型最熟悉的語言）；HTML mockup 通常勝過文字描述或截圖 |

### 二、單一來源原則與資訊放置對照表（aiposthub 獨有）

同一條規則同時出現在多層，看似加強提醒，實際造成兩個問題：**改的時候容易只改一份**、**不同層句子有差異模型還要判斷誰優先**。

| 資訊類型 | 建議放置位置 |
|---|---|
| 產品角色、所有任務都適用的行為 | System prompt |
| 專案架構、build 指令、團隊慣例 | `CLAUDE.md` |
| 特定檔案或目錄才適用的要求 | Path-scoped rules |
| 可重複執行的多步驟流程 | Skills |
| Claude 從工作中累積的專案經驗 | Auto-memory |
| API、規格、mockup、測試、長篇資料 | References |
| **絕對禁止／必須強制執行的限制** | **Permissions、hooks、sandbox**（非自然語言）|

> 200 行的意義釐清：**不是超過就失效**，而是提醒「檔案持續變長，很可能混進只適用特定任務的流程」，該拆成 rules 或 Skills。

### 三、CLAUDE.md vs auto-memory 的分工（填補本條目原缺口）

原本 V 層記為「官方只說互補、沒給判準」——這兩篇給出了具體清單：

| 留 `CLAUDE.md`（人撰寫、團隊共同） | 交給 auto-memory（Claude 自行累積）|
|---|---|
| 用哪個套件管理工具 | 某個測試在特定環境失敗的原因 |
| 測試與 lint 的正式指令 | 除錯經驗、架構筆記 |
| API handler 固定放哪個目錄 | 個人偏好與被糾正的習慣 |
| 團隊共用的命名與 review 規則 | — |

判準：**「團隊共同遵守」寫 CLAUDE.md，「工作中學到」交給 memory**——避免 CLAUDE.md 變成雜亂的專案日記。

### 四、🔴 不能刪的安全界線（填補本條目最大缺口）

原本 V 層記為「判斷權該讓多少沒有可操作判準」——aiposthub 給出了明確的分界原則：

> **「讓模型自行判斷」不等於把高風險決策也交給模型。**

以下**不應只放在自然語言指令中**：
- 禁止存取 secrets 或個人資料
- 禁止寫入 production
- 禁止執行特定破壞性指令
- 財務、醫療、法規流程中的強制審核
- 只能修改指定目錄或特定資源

**判準：違反一次就造成不可接受損失的 → 用權限／隔離環境／allowlist／deny rule／`PreToolUse` hook 攔截。**

> **自然語言適合引導判斷；安全控制負責保證邊界。把兩者混在一起，才是最危險的 context engineering。**

### 五、三步驟盤點法（aiposthub 獨有的可操作流程）

不需一次重做，先整理最常用的一個專案：

1. **先盤點，不要立刻刪**：用 `/context`（確認實際載入什麼）、`/memory`、`/skills`、`/doctor`（診斷設定、schema、Skill description 是否因預算不足被截短）
2. **分成四類**：① 所有任務都需要 → 留精簡 CLAUDE.md ② 只有特定目錄／流程需要 → 移 path-scoped rules 或 Skills ③ 可由程式／測試／hook 強制 → 改確定性工具 ④ 重複／過時／模型能自行判斷 → 刪除候選
3. **用真實任務做刪除測試**：建 10–20 個代表性任務，記錄完成率、人工修正次數、token 用量，**一次移除一組規則**再比對

> ⚠️ **這一步最容易被忽略**：官方敢刪大量 system prompt 是因為背後有 coding evaluations，**不是靠團隊覺得「看起來更簡潔」**。別一口氣刪 80%。

### 六、⚠️ 反面評論：三個必須保留的懷疑（cyberq 獨有，最有價值）

1. **樣本數問題**：X 貼文與官方部落格**出自同一人、同一篇內容**——是「一位位置絕佳的工程師對單一產品演進的自述」，**不是兩個獨立驗證來源**。「80% 可刪」是 Claude Code 在 Anthropic 自家評測集上的結果，未必能外推到你的法遵審核 agent 或客服 agent
2. **研究結論並不一致**：普林斯頓 10 repo／124 個已合併 PR 對照實驗顯示 AGENTS.md 有幫助；但另一組研究發現**LLM 自動生成的 AGENTS.md 反而略降任務成功率、成本增約 23%**，人工撰寫版才有約 4% 改善；ETH 研究指出架構總覽式內容會增加推論成本並誘使模型廣泛巡覽檔案，卻未提升成功率
   → 共同結論不是「寫多寫少」，而是**寫的是不是模型自己推不出來的東西**——這與官方對 CLAUDE.md 的建議一致
3. **治理與資安的張力**：讓模型自行判斷 vs 可稽核可解釋存在結構性衝突。RSA 2026 共識：**上下文視窗本身就是 AI agent 的主要控制點與新的安全邊界**（模型無法區分系統提示、使用者輸入與檢索內容，每個 token 都可能是指令或攻擊面）。真正不能刪的是**法遵邊界、資料存取範圍、稽核紀錄要求**，且 EU AI Act 2026-08 進入執法階段後只會更硬

**🔴 數字可信度的第三方指認**：cyberq 明確指出，社群流傳的「系統提示詞由 **800 token 縮減至 164 token**」以及不同發布日期等具體數字**並未經官方確認**——官方唯一給出的量化說法只有「移除超過 80%」與「評測無可測量的損失」。
> 這與本知識庫 2026-07-27 的獨立查證結論一致（當時追查該數字來源未果，故未寫入條目），現有第三方明確指認，**確認該數字不可引用**。

## 補充資料：第四來源與一個實測後續（2026-08-19 併入）

這一篇的價值在**兩個既有條目沒有的東西**：六條規則的「舊寫法 vs 新寫法」逐條對照，以及**作者照做之後的實測與反向驗證**。

### 🔑 照做之後：砍掉 1473 行 harness（約 2 萬 token）

> **「昨天按照 Anthropic 官方對他們五代模型的兩個建議，把整套四時代建構起來的 harness 削減了 1473 行，大約 2 萬個 token。」**
> **「目前用 5 起來的確少了過度思考鑽牛角尖的感覺，也都能遵循得不錯。」**

🔑 **最有價值的是他做了反向驗證**：

> **「我故意切回 4.6，果然發現舊一代模型開始胡亂放飛自我。」**

⚠️ 這條反向驗證把本條目的核心主張從「官方說法」升級成「使用者可複現的觀察」——
**同一套精簡後的 harness 在 5 上表現好、切回 4.6 就失控**，說明「刪 80% 系統提示」的前提確實是模型世代能力，
而不是「規則本來就沒用」。**引用本條目的任何精簡建議時，必須標明模型世代。**

### 六條規則的舊 / 新寫法對照

| # | 規則 | 舊寫法 | 新寫法 |
|---|---|---|---|
| 1 | **少給規則，讓 Claude 用判斷** | 「預設不寫註解。不要建立多段註解或分析文件。」 | 「寫出**像周邊程式碼**的 code：匹配註解密度、命名與 idiom。」 |
| 2 | **少給範例，改設計介面** | 給三條使用範例 | 設計**表達力強的工具**：Todo 用 `status: pending/in_progress/completed`，並規定**一次只允許一項 `in_progress`** |
| 3 | **不要一次塞滿，改循序揭露** | 所有說明都放最前面 | 發現 → 載入 → 使用三步（ToolSearch／Skills／CLAUDE.md 子檔按需載入）|
| 4 | **別重複自己** | system prompt 提工具、工具描述再講一次 | **「怎麼用工具」集中寫在 tool description**，system prompt 保持精簡 |
| 5 | **從 CLAUDE.md 記憶到自動記憶** | 用 `#` 快捷鍵或手動寫進 CLAUDE.md | Claude **自動保存**工作與偏好相關 memory 並跨 session 重用；**CLAUDE.md 回到輕量說明** |
| 6 | **從簡單規格到豐富參照** | 只有 markdown 計畫檔 | 也能有效使用 **HTML artifacts、程式碼、測試、其他 codebase、rubrics** |

🔑 **規則二的洞察最容易被忽略：「參數設計本身就是提示」**——給太多範例反而會限制 Claude 的探索空間，
**結構清楚的介面比範例更泛用**。（這與 [[agent-skill-design-patterns]] 的 description 寫法、
[[html-as-ai-output-interface]] 的「HTML artifact 比文字描述更高保真」都對得上）

### 落地做法：四個位置各放什麼

| 位置 | 放什麼 |
|---|---|
| **System Prompt** | 產品環境與代理角色、任務目標、輸入輸出格式、限制條件——**建立一致的行為基準** |
| **CLAUDE.md** | **簡述 repo，把 token 留給 gotchas**：專案結構、開發與測試指令、依賴與慣例；**細節與陷阱留給 References** |
| **Skills** | 團隊特有知識與流程**模組化**，含觸發條件、步驟與產出格式 |
| **References** | 用 `@` 檔案帶入 spec、mockup、codebase，作為事實依據 |

最後一步是**簡化**：刪多餘與重複、優先循序揭露，可用 `/doctor` 檢查。

（⚠️ 「CLAUDE.md 把 token 留給 gotchas」正是 [[claude-code-hooks-memory]] 併入的 Day 19 那條「規則檔不是雜物抽屜」
與 OpenAI「巨大 AGENTS.md 效果不好」的同一結論——**三個獨立來源收斂到同一點**）

## 補充資料：三種舊 Prompt 習慣該退場（第五來源，2026-08-28 併入）

來源：bnext／經理人〈2026提示詞進階方法：怎麼對AI下指令？3種舊Prompt習慣該退場〉（2026-08-26，作者羅秀如）。
本頁既有內容偏工程／CLAUDE.md 視角，此來源補上**一般職場使用者**的三個具體舊習慣，與本頁「從防呆到授權」是同一轉向的另一面。

**該退場的三種寫法**

| 舊習慣 | 為什麼失效 | 改成什麼 |
|---|---|---|
| 每次都加「請一步一步思考」 | 新一代推理模型本身已具備拆解任務與規畫步驟的能力，逐次加上未必提高品質，**還可能增加處理時間** | 交代**判斷條件**：比較 3 個行銷方案時給預算上限、目標受眾、這次最在意的成果 |
| 「請扮演一位有 20 年經驗的行銷總監」 | 只指定了大致領域，沒說明處理什麼產品、市場狀況與限制；**單純堆年資與頭銜幫助有限，背景寫太多還會分散注意力** | 角色可留，但要與任務直接相關：給產品特色、溝通對象、讀者看完後該採取的行動 |
| 🔴「絕對不要出現幻覺」「不要提供錯誤資訊」 | **禁止指令無法取代資料與查核標準**——AI 仍不知道哪些資料可信，也不知道遇到不確定資訊時該怎麼辦 | 提供可參考的資料 + 說明查核方式，並要求它**標出無法確認的內容、不要自行補寫** |

**動工前先回答兩個問題**（作者的「把 AI 當剛加入團隊的同事」框架）

1. **這項工作為什麼要做？** 同樣整理產業資料，給主管會議要集中在決策與風險，給新同事則要補基礎背景。只說「幫我整理」，AI 無從判斷哪種內容更重要。交代目的不必寫成企畫書，說明成果的使用者、使用場合與要解決的問題即可。
2. **什麼樣的成果才算合格？** 「寫得專業一點」無法當驗收標準。合格標準要落在**可以檢查的內容**上——以電子報為例：文章的篩選條件、每篇摘要長度、哪些資訊需保留來源。目的與標準說清楚後，指令不一定變長，但更貼近真正需求。

🔑 **與本頁既有內容的關係**：第三條「禁令換成資料與查核標準」正是本頁「減少過度約束、把判斷權還給模型」在一般使用場景的翻譯——**光下禁令不會產生能力，只有補上可查核的依據才會**。這也呼應 [[prompt-maintenance-sop-anthropic]] 的「Instructions don't add capability」。

⚠️ 本篇為媒體轉述兼課程宣傳文，三條規則本身無一手數據支撐；硬證據仍以本頁原有的官方 ablation（刪 8 成系統提示詞、內部編碼評測零可測量下滑）為準。另引黃仁勳「用 AI 處理你本來就會做的事是一種算力浪費」，屬觀點非數據。
