`allenai/olmocr`（Allen Institute for AI 開發，Apache 2.0）：基於 7B 參數視覺語言模型（VLM）的開源 PDF/圖片轉 Markdown 工具，用多模態模型理解整個頁面版面（而非逐字辨識），輸出保留標題階層/表格/公式/多欄閱讀順序的結構化文字，成本低於 $200 美元/百萬頁，官方 olmOCR-Bench（7000+ 測資、1400 份文件）v0.4.0 綜合分數 82.4，在同類開源方案中名列前茅。

## T（核心論點）

傳統 OCR 只解決「圖片轉文字」，但 LLM/RAG 真正需要的是「文件結構」——標題階層、段落順序、表格邊界、公式語意、正確閱讀順序（含多欄版面）。OLMOCR 用 VLM 整頁理解取代逐字辨識，並提供**可重現的 benchmark 分數**而非空泛宣稱，這是它相對於一般「工具介紹型」文章描述更值得信賴之處。

## B（適用場景）

建置 RAG 知識庫前的 PDF 前處理；學術論文/技術報告/掃描教材批次數位化（含公式與多欄排版）；需要百萬頁級批次轉換（支援 AWS S3 工作佇列 + 多節點協調）；企業內部文件管理系統轉 AI 可搜尋格式。**不適合**：只是偶爾辨識單張圖片文字的輕量需求；沒有 GPU 且不想用付費推論服務的場景（見下方硬體需求）。

## R（重點整理）

- **核心功能**：PDF/PNG/JPEG → 乾淨 Markdown，支援方程式/表格/手寫/複雜版面，自動移除頁首頁尾，保留自然閱讀順序
- **olmOCR-Bench 分數對照**（v0.4.0，Overall 82.4±1.1）：優於 Mistral OCR API（72.0）、Marker（76.1）、MinerU（75.2）、DeepSeek-OCR（75.7）、Nanonets-OCR2-3B（69.5）；略低於 Chandra OCR（83.1）、Infinity-Parser（82.5），評測涵蓋 ArXiv/舊掃描數學/表格/多欄/長小字等 8 個子項
- **硬體需求**：本機 GPU 推論需近代 NVIDIA GPU（RTX 4090/L40S/A100/H100 等級）至少 12GB VRAM + 30GB 硬碟；若不想備 GPU，可用輕量安裝（`pip install olmocr`，不含 PyTorch）接遠端 vLLM 推論服務，官方驗證過 Cirrascale/DeepInfra/Parasail 三家（每百萬輸入 token 約 $0.07-0.10）
- **安裝與基本用法**：`olmocr ./localworkspace --markdown --pdfs file.pdf`，結果存在 `./localworkspace/markdown/`；也支援 Docker（含模型鏡像約 30GB）
- **大規模批次**：支援讀取 AWS S3 上的 PDF，用 S3 output bucket 協調多節點工作佇列；Allen Institute 內部用 Beaker 叢集執行百萬頁級任務
- **可重用元件**：專案內含可獨立取用的模組——ChatGPT-4o 高品質文字解析 prompting 策略、語言/SEO 垃圾內容過濾、Qwen2.5-VL 的 SFT 微調程式碼、GRPO RL 訓練器、合成資料生成腳本
- **版本演進**：v0.1.58（2025-02 首發）→ v0.2.1（olmOCR-Bench 分數 +3）→ v0.3.0（修自動旋轉偵測與空白文件幻覺）→ v0.4.0（2025-10，用合成資料+RL 訓練再 +4 分），顯示持續迭代而非一次性專案

## C（關鍵行動）

- [ ] 建置 RAG 知識庫時，PDF 前處理優先評估 OLMOCR 而非傳統 OCR，尤其含表格/公式/多欄的文件
- [ ] 無本機 GPU 時，用輕量安裝 + 遠端 vLLM 推論服務（Cirrascale/DeepInfra/Parasail），避免自建 GPU 環境的成本
- [ ] 百萬頁級批次任務可用 S3 佇列協調多節點，不需自行設計分散式排程
- [ ] 選型前參考 olmOCR-Bench 官方分數對照表，而非僅憑單一工具的行銷描述

## 補充資料：不裝工具的做法——直接貼給 Claude 的轉檔提示詞（2026-08-03 併入）

來源：數位時代《一天一AI》（韋惟珊，2026-07-28）〈PDF轉Markdown怎麼做？這段提示詞貼給Claude，就能成AI讀得懂的md檔〉（https://www.bnext.com.tw/article/91640/pdf-to-markdown-claude-prompt ）。

**與本條目互補**：本頁是**工具路線**（自架 VLM、批次、benchmark 可比較）；本節是**提示詞路線**（零安裝、上傳 PDF 給 Claude/ChatGPT 直接轉）。選型判斷：

| | OLMOCR（工具） | 提示詞轉檔 |
|---|---|---|
| 規模 | 百萬頁級批次、多節點 | 單份到數十份 |
| 前置成本 | GPU 或遠端 vLLM 服務 | 0 |
| 品質可比較性 | ✅ olmOCR-Bench 分數 | ❌ 無客觀基準，需人工抽驗 |
| 特別擅長 | 公式、多欄、掃描件、閱讀順序 | **把「隱含語意」逼成明確文字**（見下） |

### 🔑 核心洞察：轉檔的價值不在格式，在逼你檢查資訊完整性

> AI 通常讀得到 PDF 裡的資訊，有些模型也能看懂圖片、圖表與版面。**但看得到不代表每一層意思都能正確理解。**
> 例：公司習慣用**紅色代表「禁止事項」、綠色代表「同一層級」**——人看得懂，AI 不一定每次都正確理解這個脈絡。

所以真正的價值在轉換過程逼你回答：**這份文件要讓 AI 幫我做什麼？為了完成這個任務，到底有沒有寫清楚？**

目的不同，該寫清楚的資訊也不同——只是查電話、規格，找得到可能就夠；要 AI **判斷一筆申請能不能通過**，它還需要適用條件、例外情況與判斷標準。

### 可直接複製的提示詞

上傳 PDF 後貼給 Claude / ChatGPT：

> 把這份文件整理成適合 AI 使用的 Markdown：保留標題層級與重要資訊；**表格取消合併格，把隱藏條件寫成明確文字**；**顏色、符號、版面若有意義，也要轉成文字**；截圖與圖表中的重要內容不要略過；流程改成編號步驟，適用條件寫在對應步驟旁；**保留原始頁碼方便回查**；不確定的地方標 `[待確認]`，不要自行猜測；完成後，**列出可能遺失、矛盾或需要人工確認的地方**。

這段提示詞的三個設計要點值得單獨記住（可移植到任何文件轉換任務）：
1. **把視覺編碼轉成文字**（合併格、顏色、符號、版面）——這是純 OCR/VLM 工具最容易漏掉的一層
2. **保留原始頁碼**——建立可回查的錨點，避免轉換後無法追溯
3. **要求模型自報不確定處與矛盾**（`[待確認]` ＋ 收尾清單）——把幻覺轉成可審查的待辦

### 上百頁的做法：先分段、再批次

文件越大、表格與圖片越複雜，越不適合一次全部轉完。**先依「完整章節」或「完整 SOP」把 PDF 拆成幾個小檔**，一份份上傳轉換，每批都保留原始頁碼，最後合併成一份 Markdown。
（規模再往上就該切換到本頁的 OLMOCR 批次路線。）

### ⚠️ 最後檢查別只看文字——去測它能不能完成任務

轉完不要只校對文字，拿**一個真實任務**測：「請依這份文件判斷這筆申請該怎麼處理。」

> 你可能會發現文件整理好了，AI 還是做不準——因為它缺的是**隱性知識**：怎樣才算做對、做好？哪些情況是例外？**這些補上，才能真的完成任務。**

這一點對 RAG 建置尤其重要：**文件結構化（本頁 OLMOCR 解決的）只是必要條件，不是充分條件。**
