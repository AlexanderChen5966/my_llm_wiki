## T（核心論點）

**常駐代理的介面，主角要從「一段對話」換成「一個會長期負責的角色」。** 所以 Grok Bot 的側邊欄從對話紀錄改成 Bot 名單，長得像通訊軟體：通訊軟體的列表按「人」排，關係會延續；AI 聊天的列表按「問題」排，問完就沉到底。

接著每個設計決定都在回答同一題：**這樣做是在幫人委派，還是又多給他一件要管的事？** 頭像同時表示身分與狀態；電腦視窗分成狀態／預覽／接管三層，預設只給最淺的一層。

兩個可以帶走的論點：

1. **電腦放得越顯眼，產品就越在鼓勵使用者去監督它。** 顯眼度本身就是一種訊號，決定使用者會花多少注意力
2. **拿掉一個控制項，它原本替使用者處理的問題不會消失，只會換個地方出現。** 拿掉「開新對話」之後，脈絡管理從使用者手上移到 Bot 身上

官方設計文的結語：「代理扛的責任越多，介面該向人要的就越少。」

## B（適用場景）

**適用：**
- 設計任何「會自己動」的產品：AI 功能、自動化工具、有背景任務的 App
- 評估代理產品時，看它怎麼處理「人該看多少、什麼時候看、什麼時候放手」
- 設計多 agent 系統的使用者介面：哪些東西共用、哪些屬於個別 agent

**不適用 / 注意：**
- 🔴 **代價：拿掉「開新對話」之後的脈絡管理問題**。至九月初，官方人員回覆沒有開新對話的選項、不能手動壓縮上下文、也看不到上下文用了多少；官方文件建議做重要決定前，請 Bot 回頭查一次資料來源。這正是論點 2 的實例：一般 AI 聊天裡「開新對話」是對話太長時最簡單的逃生口，拿掉後問題轉給 Bot，而 Bot 目前還做得不夠好（原文作者判斷，不認為是設計失誤）
- 這是設計師對官方設計文的二手拆解，決策內容屬官方自述；「使用者研究發現」等說法未附研究方法
- 「能力放帳號層、脈絡放個別 Bot」與 [[grok-bot-cloud-agent-product-overview]] 的三層記憶架構部分重疊。本條目講的是**介面上東西歸在哪裡**，不重述記憶架構

## R（設計決策）

### 決定一：把主角從對話換成 Bot

- **14 個名詞收成 5 個物件**。原本的詞彙：Chats、Sessions、Models、Context windows、Memories、System prompts、Projects、Skills、Connectors、Agents、Tools、Sandboxes、Permissions、Automations。收成：

| 物件 | 定義 |
|---|---|
| Bots | 有身分、記憶、執行環境與工具的常駐代理 |
| Chats | 跟 Bot 一起工作的對話介面 |
| Prompts | 給 Bot 的脈絡或指令，可只用一次、存成技能，或設成自動觸發的 routine |
| Tools | 透過軟體、API、連接器、終端機或電腦操作取得資訊、採取行動 |
| Artifacts | Bot 產出或修改的文件、設計、程式碼與資料 |

- 其他概念收在介面底下，使用者有理由在意時才出現。**技能與 routine 變成 prompt 的兩種存法**，連接器歸到工具底下
- 側邊欄的觀察：對話是拋棄式的，很少有人回頭看最近五則以外的紀錄。互動單位是「一個問題」時合理；對面是「認得你、長期負責某件事」的東西時，一條往下沉的紀錄就不對了

### 決定二：讓人少看一點

- **頭像**：試過姓名縮寫、emoji、像素風、水彩、黏土風、線稿、剪影、identicon。有個性的縮到側邊欄細節太多，簡單的又讓 Bot 像可以互換；定案是固定基本結構（簡單形狀＋有表情的眼睛），靠受控的變化與配件區分
- **狀態放進身分**：六種狀態（待命／思考／工作／等待／卡住／完成）全用頭像的動態表現，**不另做指示燈**，因為指示燈是多一層要使用者解讀的 UI；想知道細節，游標移上去看目前的動作
- **工作細節要露多少**：三個跳動圓點資訊太少，分不出在做事還是卡住；顯示一行目前動作，使用者「看到一步就想看全部」。使用者研究發現，大家看細節主要是**為了安心**（確定它還在做、方向沒跑掉），所以第一層安心由頭像動態提供
- **電腦視窗**：試過浮動（好拿但蓋住對話）、並排（工作一直看得到）、彈出（把工作區當暫時的打擾）、全螢幕（把對話擠掉）四種。發現「越顯眼越鼓勵監督」後，定為三層：

| 層級 | 呈現 | 什麼時候 |
|---|---|---|
| 狀態 | 標題列圖示變紫色 | 電腦運作中，只需知道它在忙 |
| 預覽 | 旁邊釘一個側欄 | 想跟著看，但不離開對話 |
| 接管 | 全螢幕打開，人接手操作，做完交還 | Bot 需要幫忙時 |

- 小細節：Bot 電腦的桌布隨時間變化（早上偏亮、晚上偏暗），讓它有自己的時間感，跟使用者的桌面分開。官方比喻為與同事共事：看得出他在忙，需要時瞄一眼他的螢幕，出狀況才坐到他旁邊

### 決定三：讓每樣東西待在該待的地方

- **回應要有形狀**：早期幾乎全用文字回答（五天天氣寫成一段話），後來做了卡片與小工具，適合結構就給結構；Bot 建立 routine、改設定、傳訊息給其他 Bot，也以事件形式出現在對話裡
- **能力共用、脈絡分開**：工具與技能放帳號層（很多 Bot 都要上網、處理文件、寄信）；記憶與 routine 屬於個別 Bot（這個角色長期知道什麼、負責做什麼）。跨角色專案用群組聊天共享脈絡，每個 Bot 仍保有自己的專業記憶
- **考慮過但沒做**：儀表板、任務看板、明確的交接按鈕。理由是每一項都讓使用者多一份協調工作，日常分派改由負責協調的 Bot 處理
- 專案尾聲大部分工作是在刪東西：視窗與面板控制項、電腦檢視選項、各種代理細節都拿掉，並訂下每帳號約 50 個 Bot、每群組 6 個的上限

### 原文作者整理的四個可帶走原則

1. **把狀態放進身分**：不另加狀態燈，讓代表物件的頭像、圖示或卡片直接表現狀態
2. **監看分層**：狀態、預覽、接管三層，預設只給最淺的一層，越深越要使用者主動打開
3. **回應要有形狀**：能用卡片、表格或按鈕的，就別寫成一段話
4. **能力共用，脈絡分開**：每個角色都要的能力放最上層共用，只屬於某角色的記憶與排程留在角色身上

## C（關鍵行動）

- [ ] 設計代理介面時，先決定「使用者跟它的關係單位」是一次問題還是一個長期角色，再決定列表按什麼排
- [ ] 狀態盡量放進既有的身分元素（頭像、卡片），不要多一層指示燈
- [ ] 監看介面分層，預設最淺；把「顯眼度」當成你在鼓勵多少監督的設計參數
- [ ] 每拿掉一個控制項，寫下它原本替使用者處理什麼問題，以及現在由誰處理
- [ ] 能力與脈絡分開放：共用工具放帳號層，記憶與排程放個別 agent

## 原始摘要

設計師 Riven 整理 Grok Bot（SpaceXAI 2026-08-11 推出的常駐代理）的功能、方案與風險，並拆解官方設計文〈Designing Grok Bot for a world of persistent agents〉（2026-09-03）。作者把設計文整理成三個決定與一個代價：把主角從對話換成 Bot（14 個名詞收成 5 個物件、側邊欄改成 Bot 名單）；讓人少看一點（頭像兼狀態、電腦視窗三層）；讓每樣東西待在該待的地方（回應有形狀、能力共用脈絡分開、不做儀表板與任務看板）。代價是拿掉「開新對話」之後，脈絡管理移到 Bot 身上，而 Bot 還做得不夠好。作者從中整理出四個可以帶到任何「會自己動的產品」的設計原則。
