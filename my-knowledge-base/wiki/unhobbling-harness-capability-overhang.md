Anthropic Claude Code 團隊工程師 Thariq Shihipar 在 AI Engineer World's Fair 的演講精華：模型是「養成」（grown）而非「設計」（designed）出來的，能力像鋸齒一樣高低不平，真正卡住模型的常常是我們給的工具環境（harness）與系統提示——這叫「潛藏能力落差」（capability overhang），解開它的過程稱為 unhobbling。Claude Code 團隊近期把系統提示砍掉約八成，原則從「規定不能做什麼」改成「給足夠背景」。

## T（核心論點）

模型表現好不好，往往不只看模型本身。工程師給模型的工具環境、系統提示與規格，反映的其實是「我們對這個模型了解多少」——了解得越淺，就有越多能力被埋在檯面下（capability overhang）。**Unhobbling**（解開束縛）就是搞懂這些條件、把模型潛藏實力跑出來的做法。範例：一般聊天模型答不出「名字以 aw 結尾的寶可夢」，但同一問題交給能自己跑程式的 Claude Code，就能自己抓清單篩選出答案——差別不在模型聰不聰明，而在它能不能動手用工具。

## B（適用場景）

設計 Claude Code / Agent harness（系統提示、工具集、規格文件）；判斷提示詞該寫長還是寫短；理解為何同一模型換個環境表現差很多；找出專案裡「你不知道自己不知道」的問題。

## R（重點整理）

**系統提示長度的三階段擺盪**：新版 Claude 3.5 Sonnet 時代最佳做法是「提示寫短、工具給少、多塞範例」→ 模型變聰明後一度流行反過來「提示寫長、工具給多、範例塞滿」→ 最新一代又倒回短提示，**因為範例會綁住模型的想像力，它其實比你給的範例更有想法**。Claude Code 團隊近期把系統提示砍掉約八成，原則從「規定它不能做什麼」（禁令）改成「給它足夠的背景」（脈絡）。

**Harness 進化的關鍵轉捩點不是上下文視窗變大，而是給模型「一雙手」**：早期工程師以為把整個程式庫貼進大視窗就能讓模型寫程式，真正的突破是讓模型能自己下 bash 指令、自己搜尋、自己拼湊背景——這是 Claude Code 的起點。

**同一功能跨版本的能力釋放案例（反過來問問題）**：Opus 4 上這個功能只能勉強用；Opus 4.5 明確要求「針對這份規格問我 40 個問題」就能一口氣完成像樣訪談；Opus 4.8 和 Fable 5 甚至能直接生出把問題嵌在裡面的 HTML 報告——工具和模型是一起成長的。

**瓶頸移到人身上：地圖不等於實地**——你的計畫、提示、規格是地圖，真正的程式庫與現實限制是實地。強模型（如 Fable 5）會一口氣跑很大範圍，一路撞上地圖上沒畫的決策點，「對齊地圖和實地、把未知找出來」變成新瓶頸。四種「你知道什麼」的分類：①你知道的 ②你不知道的 ③你其實知道但沒特地寫下來（看到就認得）④你完全沒想到的——模型能幫你逼近後面較難纏的兩種。

**五個找出未知的具體做法**：
1. **盲點巡查（blind spot pass）**：「請幫這段 diff 做一次盲點巡查，把我可能沒注意到的風險和邊界情況，照嚴重程度列出來並說明理由」
2. **讓模型反過來訪談你**：「針對這份規格問我 40 個問題，優先問那些會改變整體架構的問題」，把心裡沒說出口的假設逼出來
3. **給它一份參考範例當地圖**：丟一份別套系統/別種語言的程式碼或 HTML 原型，請它對照出你這邊漏掉了什麼
4. **要它寫 implementation notes**：讓它把動工過程中遇到、但你沒交代清楚的決定即時記下來，事後回頭看問題出在哪一步
5. **請它反過來出題考你**：做完一段後讓模型出題考你，答不出來就表示你已經脫離狀況、沒跟上它在做什麼

「留在迴圈裡」、確定拿到的是你真正想要的東西，是跟這一代模型合作最重要的一環——否則只是按了個按鈕，對成果卻半句話都說不上來。

**最該記住的一句話**：「東西變好做了，但做出價值還是難（building is easier, but generating value is still hard）」——別太沉迷把流程和環境弄漂亮，那只是「變好做」的部分；真正難的是找到值得做的事，通常要試很多次才會浮現。

## C（關鍵行動）

- [ ] 系統提示過度膨脹時，優先評估「範例是否綁住模型想像力」，考慮改成給脈絡而非給禁令
- [ ] 讓強模型跑大範圍任務前，先用「盲點巡查」或「反過來訪談你」找出未交代的決策點
- [ ] 任務完成後可反過來讓模型出題考自己，驗證是否真的跟上了它做的事
- [ ] 不要把大部分心力花在把 harness 磨漂亮，記得「找到值得做的事」才是真正難的部分
