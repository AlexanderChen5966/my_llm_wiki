## T（核心論點）

AI 寫程式最常出事的環節是**在你還沒決定的事情上先動手**——等你發現方向不對，它已經照著錯的假設寫完三個檔案。Matt Pocock 的 `/wayfinder` 不切任務、不先動工，而是**把「現在還不能決定的事」全部攤成一張決策地圖**：命名終點、標出霧（已預感但講不清的決策）、只處理前緣（現在就能解的票）。核心紀律寫在規格檔裡——**Plan, don't do**。

> 本質是**由 AI 生成的決策系統**，不限軟體：Matt 用它在自家花園蓋辦公室（委託場勘、找廠商、把要決定的事排出來）。

## B（適用場景）

**適用：** 大範圍功能／專案，一次做不完又不知道該從哪切；模糊念頭需要收斂成規格書；跨領域的決策型專案（不限程式）

**不適用 / 注意：**
- 小型明確任務不需要——這套流程的成本在前期規劃
- 理想狀態需要支援「卡關關係」的 issue tracker，但**沒有也能跑**（退回本機 Markdown 地圖，`.scratch/` 底下），不必為了試它先辦一套 Jira
- 它**不會自己跳出來接手**，要你自己打 `/wayfinder`

## R（機制與動線）

### 三個核心概念

| 概念 | 定義 |
|---|---|
| **終點（destination）** | 🔑 **要最先命名**——因為終點決定了每張票長什麼樣 |
| **霧（fog of war）** | 你已經預感到、但還講不清楚的決策 |
| **前緣（frontier）** | 現在就能處理的票，定義很嚴格：**開著的、沒被其他票卡住的、還沒有人認領的** |

> 解掉一張票，前緣就往前推一格，霧也跟著散掉一塊。

### 地圖結構（貼 `wayfinder:map` 標籤的 issue，固定五塊）

1. **終點（Destination）**——一兩行寫清楚
2. **已決定的事（Decisions so far）**——只放一句摘要加連結
3. **還沒講清楚的事（Not yet specified）**——就是霧
4. **Notes**——領域背景與你的偏好
5. **Out of scope**——刻意排除的工作與理由

> **地圖只是索引，決策內容都留在各自的票裡。**

### 四種票型

| 票型 | 要真人參與 | 這張票在做什麼 |
|---|---|---|
| **研究**（research）| 不用 | 交給子 agent **平行**去查外部事實，查完回報 |
| **原型**（prototype）| **要** | 做出粗略的東西讓人有反應：大綱、粗稿、程式框架或介面 |
| **拷問**（grilling）| **要** | 用對話把某個實作細節或方向逼清楚 |
| **雜務**（task）| 兩者皆可 | 現實世界的前置作業（申請帳號、開通資源、搬資料）|

⚠️ 需要真人參與的兩種票，**規格明訂 agent 不得代替人回答**。

> **原型票是這套流程不會變成紙上作業的原因**——前期規劃再多，都要靠做出來的粗胚換真實回饋。
> `Plan, don't do` 的例外也寫明在規格：Notes 可納入執行工作、原型票會做出粗略成品、雜務票直接完成卡住決策的前置作業。

### 實際跑一輪

1. **先講終點**——叫出 `/wayfinder` 描述想要什麼，它先探一遍專案，接著用**拷問 skill 反問**「完成長什麼樣、要不要一份規格書」
2. **第一次只畫地圖**——範例開出 7 張票但當下只有 3 張能動。🔑 **官方流程寫明畫完地圖就停，不在同一輪繼續手動解票**（研究票例外，此時就派子 agent 平行查）
3. **一票一場對話**——開新對話、再叫一次 `/wayfinder` 並**帶上票的名稱**（規格要求用票名、不要用編號）。🔴 官方成功指標：**除研究票可平行，一場 session 最多解一張票**
4. **解完寫回地圖**——答案以留言留在票上、關票，主地圖只補一行摘要與連結；霧裡夠清楚的問題升級成新票
5. **最後收成**——`/to-spec` 把對話中的地圖合成規格書（Matt 說初稿長到超過 GitHub 字數上限），再用 `/to-tickets` 切成可實作的票。**規格書裡每個決策都連回原始的票**，AI 之後有疑問可回去看當時的討論

### 安裝：兩條路徑選一條

⚠️ 官方明講**兩種方式代表兩種哲學，選一條就好，兩個都裝會讓每個 skill 出現兩次**。

```bash
# Claude Code 使用者：官方 plugin（等於訂閱制，檔案唯讀、作者更新自動更新）
claude plugins install mattpocock-skills

# Codex／其他 agent，或想自己改內容：skills.sh 安裝器
npx skills@latest add mattpocock/skills   # 需 Node.js；不會自動更新，要跑 npx skills update
```

裝完每個專案跑一次 `/setup-matt-pocock-skills`，選 issue 放哪（GitHub 用 `gh`／GitLab 用 `glab`／本機 Markdown／第四選項用一段話描述你的流程如 Jira、Linear）。**官方特別提醒務必勾上 `setup-matt-pocock-skills`**。

## C（關鍵行動）

- [ ] 🔴 大專案開工前先問「有哪些事我還沒決定」，攤成地圖再動手——別在未決事項上先寫程式
- [ ] 終點最先命名，它決定所有票的形狀
- [ ] 嚴守「一場 session 最多解一張票」（研究票除外），別在畫完地圖那輪順手解票
- [ ] 保留原型票，讓規劃能換到真實回饋，避免整套變成紙上作業
- [ ] 收尾走 `/to-spec` → `/to-tickets`，讓規格書每個決策都連回原始討論
- [ ] 安裝只選一條路徑（plugin 或 skills.sh），別兩個都裝

## 補充資料：完整五站工作流與底層哲學（2026-08-07 併入）

來源：bnext〈AI Skills怎麼寫？grill-me工作流5步拆解〉。本頁原本只記 wayfinder（大到一次對話裝不下的計畫），此處補上**一次對話能處理完的五站主幹道**，以及 Matt Pocock 的設計哲學。

### 五站裝配線：想法 → 成品

| 站 | Skill | 做什麼 |
|---|---|---|
| **1. 拷問出共識** | `grill-with-docs`（grill-me 進化版）| 拷問同時順手寫下兩種文件（見下） |
| **2. 寫成規格** | `to-spec` | 共識一關掉對話就蒸發，立刻落成規格書 |
| **3. 拆成任務** | `to-tickets` | 用**垂直切片**拆，不按技術架構拆 |
| **4. 動工** | `implement` | TDD 防 AI 作弊 |
| **5. 審查** | `code-review` | 兩個平行子代理，各查一件事 |

### 第一站的兩種文件

1. **名詞表**——讓你、AI、程式碼三方說同一種語言。這在 DDD 中稱為**通用語言**（ubiquitous language，2003 年《領域驅動設計》）
2. **ADR 架構決策紀錄**——🔑 **只記那些難以回頭、沒有背景說明會讓後人意外的決定**

> 使用者回饋：用了四、五次之後，「**AI 神奇地跟我腦中還沒說出口的想法對齊了**」。

### 🔑 第二站的嚴格原則：規格書不放檔案路徑與程式碼片段

> **規格書原則上不放具體檔案路徑與程式碼片段**，因為它們很快就會過期；只有 prototype 產生的片段能比文字更精確保存決策時，才節錄必要部分。
> **過期的實作細節容易誤導 AI，讓規格與程式碼逐漸脫節。**

（這與 [[synthesis-spec-driven-workflow]] 的「規格漂移」是同一問題的預防面）

### 🔑 第三站：垂直切片（vertical slice）

**讓 AI 自己拆任務，它天生喜歡按技術架構分工**：先建完所有資料庫 → 再寫完所有邏輯 → 最後才做畫面。

> **最可怕的盲點是：在最後一步之前，你完全沒辦法測試任何東西。**

`to-tickets` 強制改用**使用者功能**拆：先做完整的「會員登入」（含資料庫＋邏輯＋畫面），再做完整的「加入購物車」。每做完一小塊就能立刻驗收，互不相依的任務還能同時發包給多個 AI 平行處理。

### 🔴 第四站：TDD 的理由是「防 AI 作弊」

這是本篇對 TDD 最有說服力的論證，與一般「TDD 是好習慣」的說法不同：

> **因為 AI 骨子裡是個作弊仔。** 如果讓它先寫功能再補測試，萬一功能寫錯，它為了交差**會直接生出一個「配合錯誤答案」的假測試**，讓一切看起來都過關。
> 先寫測試（此時必定亮紅燈），再寫程式讓紅燈變綠燈，才能鎖死 AI 亂寫交差的空間。

> 📌 對本知識庫的意義：TDD 目前**不在** [[decision-framework]] 的五情境流程中（品質關卡走 `/stack-review` 與 `/ai-pair dev`）。這個「防作弊」論證是重新評估 TDD 時值得納入的新理由——但也要注意 [[superpowers-framework]] 記錄的反證：完整跑完 TDD 流程，`isNumber` 對全形數字的漏抓**仍然沒抓到**（流程嚴格性 ≠ 正確性）。

### 第五站：兩個平行子代理，刻意分開

派出兩個平行子代理，分別檢查**程式是否符合專案規範**與**成果是否忠實實現原始規格**——🔑 **避免兩種判斷互相干擾**。

審查不是空泛的「幫我看看有沒有 bug」，而是把 Martin Fowler《重構》（1999）歸納的**約 12 種「爛 code 症狀」當成檢查基線**；⚠️ **專案自身規範優先，每種症狀都是需要判斷的警訊，不代表必然違規**。

兩個例子：
- **散彈槍手術（Shotgun Surgery）**：只想改一個按鈕的顏色，卻得動十幾個檔案
- **資料泥團（Data Clumps）**：姓名、電話、地址三個欄位永遠一起出現 → 該打包成一個「聯絡人」物件

### 🔑 底層哲學：越聰明的 AI，越需要老派基本功

**這套系統幾乎沒有任何新發明**——決策樹出自 Brooks 2010《The Design of Design》、通用語言出自 2003《領域驅動設計》、12 種爛 code 症狀出自 1999《重構》、TDD 更是老派日常。

Matt Pocock 在 AI Engineer 大會的核心主張：**「軟體基本功比以往任何時候都重要。」** 他親自試過「只改規格、不看程式碼」的 specs-to-code 流派，結果**每重跑一次產出的程式碼就爛一點**——「這只是換了個名字的 vibe coding」。

> 🔴 **一記警鐘：很多人說 AI 讓程式碼變便宜了，恰恰相反——爛程式碼從未像現在這麼昂貴。** 因為 codebase 一爛，AI 在裡面就只會繼續生產垃圾，你反而拿不到 AI 的紅利。

**什麼架構能讓 AI 發揮全力**：借用 John Ousterhout 的「**深模組**（deep module）」——把複雜細節藏在裡面，只留一個簡單好用的入口（像微波爐：按幾個按鈕，不必懂電路）。**入口越清楚，AI 需要同時理解的東西就越少**；反之一項功能散落在許多檔案、改一處牽動好幾處，AI 就更容易漏看或改錯。

### 🔑 writing-great-skills 的三條心法（為什麼他的 skill 這麼短）

| 心法 | 說明 |
|---|---|
| **修剪（pruning）** | 在 AI 面前每多一句廢話，它就多一分分心的可能——**連「不說它也知道」的指令都要刪** |
| **指引詞** | 大量使用深植在 AI 訓練資料裡的**經典術語**：對 AI 說一句「Data Clumps」，等於說了一百字的解釋 |
| **完成標準** | 給 AI 明確的終點，它才不會發散 |

> **與其寫一千字的完美 prompt，不如用對三個關鍵詞。**

→ 這三條與 [[claude-5-context-engineering-rules]] 的官方守則高度一致（減少過度約束、設計清楚介面而非堆範例），是社群側的獨立同結論。

### 不寫程式的人能帶走的三件事

1. **讓 AI 當拷問者，而不是代筆者**——重要企劃/提案/決定先被 AI 問過一輪再動工
2. **跟 AI 建立共同語言**——請它順手維護名詞表：「把我們對話中用到的專有名詞和定義整理成名詞表，之後的討論都用這些詞」
3. **把重複流程寫成自己的 skill**——任何做過三次以上的工作（寫週報、整理會議紀錄、審預算）都值得寫成一段短 SOP
