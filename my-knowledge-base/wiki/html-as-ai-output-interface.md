兩篇合併，剛好是同一問題的兩端：**為什麼要讓 AI 產 HTML**（讀者端價值）與**產出來之後放哪裡**（發佈基礎設施）。前者接續 [[claude-code-session-handoff]]（該系列 G5 的交接檔後來從 `.md` 換成 `.html`）。

## T（核心論點）

> **`.md` 只能「說」；`.html` 可以「指」。**

純文字要靠你自己讀完、自己判斷哪裡重要；HTML 可以直接把重要的東西指給你看。

🔴 **但作者第一件事就是排除誤解**：

> **這不是「調教技巧」。換成 HTML 不會讓 Claude 變聰明——對它來說 `.md` 和 `.html` 都只是文字，理解能力沒有差別。好處全部發生在「你」這一端。**

而第二篇補上被忽略的下半場：

> **「做」的速度已經超快了，但「展示」、「之後回頭看」、「在外面回覆」還停留在舊時代。**

## B（適用場景）

**適用：**
- 產出**資訊有結構、而且你會回頭看很多次**的東西：交接檔、調研／比較報告、資料分析、專案規劃與架構說明、wireframe
- agent 產物散落在案件資料夾、想在手機上查看與回覆
- 本知識庫的 outputs/ 報告（健檢、盤點）—— 目前全是 `.md`，正是本篇指出的痛點

**不適用 / 注意：**
- ⚠️ 一句話就能回答的東西不需要 HTML
- ⚠️ 第二篇的基礎設施綁 AWS（S3 + CloudFront + Cognito），是 OSS 需自架；作者也明說「內容不會飛到作者那邊」
- 🔴 **「知道 URL 的人都能看」不算存取控制**（見補充資料）

## R（為什麼 HTML 划算：三件 md 做不到的事）

markdown 的簡單是優點也是天花板——**字體大小沒辦法分層次、沒有顏色標重點、表格能力陽春**。HTML 多出三件事：

1. **層次** — 重點放大、次要縮小，**掃一眼就抓得到主線**，不用逐字讀
2. **標記** — 顏色、粗體、底色框讓「這是關鍵決定」「這裡有雷」「這件事還沒做」**一眼區分**
3. **結構** — 表格、卡片、分區塊；**比較三個方案時一張表格完勝三段文字**，差異攤在同一行上，不用在腦中對照

作者的實例對照很具體：同一份交接檔，`.md` 版是「七十幾行同樣顏色、同樣大小的字」（`##`、`-`、反引號全混在一起）；HTML 版最上面一排 **7 / 2 / 4** 讓你「連讀都不用讀就知道做完七項、卡住兩項、還有四項沒動」，橘色塊是「不要推翻的決定」、綠色塊是「接手先做這個」——**它們自己會跳出來找你**。

> 🔑 **差別不在資訊量，在你要花多少力氣才能把它讀出來。而且這份東西你不會只看一次——每次回來都省一遍，才是它划算的地方。**

### 🔑 最有感的一招：叫它先畫 wireframe

情境是你腦中有個版面（「左邊清單、右邊詳細、上面搜尋列」），打給 Claude 之後打開來**跟你想的不一樣**。

> **問題不在它做錯，而在「版面」這種東西用文字描述本來就很難對齊**——同一句「左邊放清單」，你腦中的寬度和它腦中的寬度可能差很多。你講一百字，也不保證兩邊想的是同一張圖。

所以先請它「畫一個 wireframe，讓我比較好理解」——**用一張圖對齊，比用一百字描述可靠**。

## R（產出之後：發佈與行動裝置這半場）

第二篇作者（把報帳、工時回報、review 回覆都交給 Claude Code）的痛點清單非常具體：

- `file://` 沒辦法在手機 Safari 開啟
- 貼到 Slack 每次更新都留下舊版
- 上傳 Drive 很難找，且每次都要設權限
- 聊天中的成果物分頁，**對話結束後就會迷路**
- 出門時想到的工作沒地方先放
- ⚠️ **Claude Code 的 remote control 以 Mac 持續開著為前提**，不適合搭車時的等待確認

五個設計原則：

1. **原始檔放案件資料夾，Git 是正本，發佈只是複製**
2. **人不用上傳**——用自然語言請 agent 幫忙，不用記命令
3. **依觀看對象分公開範圍**（自己 / 同事 / 任何人）
4. 🔑 **合格標準不是 PC，而是手機——能在電車上讀到才算完成**
5. **手機不只是拿來看**，也要能在外出時丟工作、回覆確認請求

架構刻意極簡：**S3 + CloudFront，LLM 在發佈過程中完全不參與**，快取從一開始就關掉（不必等 invalidation）。雙向流程是 `/inbox`（手機→Mac：把外面想到的工作先放進箱子）與 `/mobile`（Mac→手機：送出狀態頁與卡片，在電車上回覆核准）。

🔑 **與 remote control 的關鍵差異是「非同步」**：把工作丟出去之後可以直接關掉 Mac，外出時回覆的核准，下次打開 PC 會回到同一個 session。⚠️ 作者**刻意沒加通知機制**——「不想弄髒進行中的對話」。

## C（關鍵行動）

- [ ] 會回頭看很多次的產物（交接檔、比較報告）改請 AI 產 HTML
- [ ] 要對齊版面時**先要一張 wireframe**，不要用文字描述
- [ ] 驗收標準訂在手機實機，不是 PC 瀏覽器

## 補充資料

### 🔑 不要再判斷「這個值不值得發佈」

作者一開始每次都猶豫（怕 AWS 費用、覺得 token 可惜），實測後發現兩邊都只是誤差：發佈端沒有 LLM 運作（只有 S3 + CloudFront）、AWS 費用只是幾 MB 儲存與自用傳輸、**publish 一次的 token 不到「生成一頁 HTML」的十分之一**。

> **與其在聊天裡討論要不要發佈，成本反而更高。所以乾脆不再判斷——HTML 做好了就發佈，跟 git 的 commit → push 一樣是一組流程。**

結果：開始使用約 3 週累積 **273 頁**。🔑 **「我想大概就是因為不再猶豫要不要發佈吧。」**

### 🔴「知道 URL 的人都能看」不算存取控制

沒有 IP 限制的 URL 只要知道連結就能打開，**即使有 `noindex` 和期限也一樣**。所以包含客戶名稱或金額的 HTML 不能就這樣發出去——發佈前要先看內容，必要時改內部限定，或把專有名詞改成代稱後另出一版。

⚠️ **一個很實用的教訓**：作者曾相信文件裡寫的 CIDR 就直接拿去設允許清單，但**零信任產品的出口 IP 會依產品而不同，甚至同一產品因連線目標網域不同而改變**。所以他做了一個免認證的 `/whoami` 顯示目前來源 IP 與是否允許——**先用這裡實測再加，不要光從名稱猜**。

### 有期限的 URL 不要讓伺服器保存狀態

用 HMAC-SHA256 簽名（`payload = mode:expiresUnix:slug`），CloudFront Function 只檢查簽名與期限，**不把「這個 URL 有效」寫進 DynamoDB**。

🔑 **因為沒有保存狀態，在本機組出來的 URL 可以直接有效——也就是說 agent 不需要打開瀏覽器。** ⚠️ CloudFront Function 在快取查詢之前執行，這樣可避免未經認證的請求拿走已快取的正文（作者刻意不用 Lambda@Edge 就是想在這個時間點判斷且不要有狀態）。

### 🔑 畫面是給人手動操作的，agent 用 CLI

作者一開始想讓 agent 用瀏覽器點畫面上的按鈕，結果 renderer 卡住，被評為「慢吞吞地摸瀏覽器」。**分開比較好。**

⚠️ 另兩個踩坑：CloudFront 的 `defaultRootObject` 只對根路徑有效，所以 `/pages/foo/` 認證後會看到 S3 的 AccessDenied XML → **正式 URL 要讓命令輸出，不要手動組**；而 agent 幾次想「把外觀整理得更漂亮」竟**把 `index.html` 刪掉了**。

### ⚠️ 本機看得懂日文，不代表分享出去別人也看得懂

用沒有 charset 的 `text/html` 發佈時，**沒有 `meta charset` 的 HTML 會變成亂碼**——作者曾因此把要給編輯看的頁面全毀了。（對繁中內容同樣適用）

### 手機表格的實測數字很值得看

作者以為 `overflow-x: auto` 就處理好了，實際盤點發佈中的頁面：**202/237（85%）有表格、188（79%）已有內部橫向捲動、1198 個超過 40 字的儲存格（最長 545 字）**。

🔑 **問題根本不是欄數，而是日期的 `nowrap` 和儲存格裡的長文**——整頁不會動，但右邊欄位跑到畫面外。

解法不是手改 200 多頁，而是**在發佈端把溢出的表格轉成「標題＋數值」的卡片**（想看表格可切回表格檢視；合併儲存格與數值矩陣不折疊）。因為發佈用 `no-store`，**下次打開時連過去的頁面都會修正**。

### 把 HTML 外觀也做成 skill

🔑 **「光把容器整理好，如果裡面的 HTML 風格不一致，每次打開都像被丟到不同的 app。」** 所以不讓 agent 決定配色——可用漸層的地方只有四個：**Hero、區段分隔、編號、表格表頭**。

⚠️ 一個反直覺的發現：作者以為多用藍色就會像公司風格，但**被否決版本的問題不在「沒用藍色」，而在「藍色太分散」**——卡片、引用、編號徽章各放一點顏色，整體就會廉價又雜亂。

## 補充資料：Bento Slides —— 把「單一 HTML 檔」推到簡報領域（2026-08-18 併入）

來源：https://www.kocpc.com.tw/archives/665567

本條目的主張是「HTML 作為給人讀的輸出介面」；Bento Slides 是同一個主張在**簡報**上的實作，而且它多做了一步：
**讓 AI 能直接改那個檔案**。

### 它的核心設計

**整份簡報、編輯器、播放器、圖片、動畫與相關資源，全部封裝在單一 `.bento.html`**——
免安裝、免註冊、瀏覽器開啟即可查看／編輯／播放，**離線也能用**（Local-first，檔案存在自己裝置上）。免費開源。

🔑 **最關鍵的設計決定：簡報內容以「結構化資料」保存在 HTML 內，所以 Codex／Claude／Cursor／Gemini 可以直接讀取並修改。**

使用者只要用自然語言說「新增一頁產品比較」「把這些數據做成長條圖」「重新設計這張投影片」，AI 就能改原檔。

功能面不只文字與圖片排版：圖表（長條／折線／圓餅／散佈）、**Morph 轉場**、影片、音訊、Speaker Notes、互動效果；
素材可直接嵌入 HTML，**分享時只給一個檔案**。

### 為什麼這值得記在本條目底下

它同時滿足本條目的兩端：

| 本條目的主張 | Bento Slides 的對應 |
|---|---|
| HTML 讓人「掃一眼就懂」 | 圖表、動畫、Speaker Notes |
| 產出之後放哪（分享問題）| **單一檔案即可分享，不用打包資料夾、不用權限設定** |
| 🔑 agent 要能操作它 | **結構化資料存在 HTML 內，AI 直接改原檔** |

⚠️ 對照 [[claude-code-markdown-single-source-multi-format]] 的路線差異：那邊是 **md 當正本 → 轉出 PPTX**（正本與產物分離）；
Bento 是 **HTML 本身就是正本且可被 AI 編輯**（正本與產物合一）。

🔑 **後者少了一次轉換，但代價是失去 md 的 diff 可讀性**——選哪條路取決於「這份簡報會不會進版控、需不需要 review 差異」。
