## T（核心論點）

**個人用順了不代表團隊會順**——導入的難點不在工具，在**信任與共識**。個人使用只要對自己有用就算成功；團隊使用的標準更高：**一致性**（不同人叫 Claude 做同一件事，結果要夠接近）、**可信任**（成員能 review AI 產出並判斷好壞）、**可維護**（設定要有人維護，不能只有一個人懂）。

## B（適用場景）

**適用：** 個人已用順、要推廣到團隊；團隊有人不信任 AI 產出或擔心風格不一致

**不適用 / 注意：**
- 這是**落地工法**；若還在判斷「組織現在該推到什麼程度」，先看 [[ai-adoption-five-stages-boris-cherny]]（診斷地圖）
- 三階段需要時間，**不要一開始就全員推**

## R（三階段導入）

### 階段一：試用期——先讓 1–2 個人跑

讓對 AI 工具比較有興趣的人先試用 **1–2 週**，**刻意記錄三件事**（這些是後續 CLAUDE.md 的素材）：

1. 哪些任務 Claude **表現好**（寫測試、重構、解釋程式碼）
2. 哪些任務 Claude **容易出錯**（複雜業務邏輯、對外部系統高度依賴的程式碼）
3. **什麼樣的 prompt 效果最好**

### 階段二：共識期——把有效用法寫進團隊版 CLAUDE.md

整理成**三段結構**：

```markdown
## 適合讓 Claude 做的事
- 寫單元測試 / 重構現有程式碼 / 解釋不熟悉的程式碼 / 產生 commit message 與 PR description

## 需要人工確認的事
- 牽涉 API 合約的改動 / 資料庫 migration / 權限與安全相關邏輯

## Commit message 格式
Conventional Commits：feat / fix / refactor / test / docs
```

> 🔑 **把這份文件開一次短會**——**「不是宣布規定，是建立共識。」**

### 階段三：全員期——每兩週回顧三問

1. 有沒有**新的有效用法**值得加進去？
2. 有沒有**規則已經不適用**了？
3. 有沒有人**踩到新的坑**？

> **CLAUDE.md 不是一次寫完的規格書，是持續演進的團隊記憶。**

## Review AI 產出的四個關注點

| 關注點 | 為什麼 |
|---|---|
| **邏輯正確性** | Claude 理解你的描述，但**不一定理解你的業務背景**——確認符合實際需求，不只是「看起來對」|
| **邊界條件** | 主線流程通常沒問題，但**空值、超出範圍、並發容易被跳過** |
| **安全性** | 涉及使用者輸入、API token、資料庫操作的，要和審查一般程式碼一樣仔細 |
| **測試覆蓋** | Claude 寫的測試**有時只覆蓋 happy path**——確認有對應的 edge case 測試 |

### 🔑 反直覺原則：用同樣的標準

> **AI 生成的程式碼不需要比人寫的更嚴格地 review，也不需要更寬鬆。用同樣的標準即可。**

差別只在於：**不確定某段邏輯時，可以直接問 Claude**——它對自己生成的程式碼有完整上下文，解釋起來很清楚：
```
這段程式碼為什麼這樣寫？有沒有可能在 X 情況下出問題？
```

## 四個常見疑慮的答覆稿

| 疑慮 | 答覆 |
|---|---|
| **Claude 會取代我的工作嗎？** | 它擅長執行明確定義的任務，但「決定要做什麼」「判斷這樣做對不對」「理解業務背景」仍是人做的事。**比喻：Claude 像執行力很強的初級工程師，你是 lead**——你的工作從「把事情做完」變成「決定做什麼、確認做對了」|
| **每個人用法不同，風格會亂掉嗎？** | 這是 CLAUDE.md 要解決的問題。**重要的不是每個人用一樣的 prompt，而是 Claude 對每個人輸出一致的風格** |
| **AI 生成的程式碼安全嗎？** | 和人寫的一樣需要 review。Claude 不會故意寫出漏洞，但**可能沒考慮到你的系統的特定風險**——安全性 review 的責任還是在人身上 |
| **Claude 寫錯了怎麼辦？** | 找出來、修掉、弄清楚為什麼錯。**如果是 CLAUDE.md 沒說清楚導致的，把規則加進去**——每次修正都是讓 CLAUDE.md 更精準的機會 |

## C（關鍵行動）

- [ ] **不要一開始全員推**——先讓 1–2 個有興趣的人試用 1–2 週
- [ ] 試用期**刻意記錄三件事**（表現好／容易出錯／有效 prompt），當作 CLAUDE.md 素材
- [ ] 團隊版 CLAUDE.md 寫成三段：適合做 / 需人工確認 / commit 格式
- [ ] **開短會建立共識，不是宣布規定**
- [ ] 每兩週回顧三問，把 CLAUDE.md 當團隊記憶而非規格書
- [ ] Review AI 產出**用同樣的標準**，但特別留意邊界條件與測試是否只有 happy path
