整合 wiki/ 中 6 篇 CLAUDE.md 撰寫方法論條目（行為控制原則、設計範本集、撰寫技巧指南、精簡化技巧、Anthropic 官方 Claude 5 世代上下文工程守則，以及 Apple 官方檔案的量化拆解），解決「這些技巧彼此重複又偶有矛盾，究竟哪些是穩固共識、哪些數字不能盡信」的問題。

**2026-07 更新**：官方一手來源加入後，原本的兩大爭議（200 行門檻、NEVER vs 少禁令）已獲裁決。
🔴 **2026-09-03 重跑（E 層實質翻轉）**：新增 Apple 官方檔案拆解，並在上網查證後發現**本精粹前一版的核心前提有誤**——「精簡 ⇒ 更聽話」這個因果沒有實證支持。整套方法論的效益定位因此必須改寫。

## E（精粹論點）

CLAUDE.md 的本質是**行為控制而非能力追加**——它的工作是抑制 AI 的預設過度行為（擅自重構 / 過度抽象 / 改不相關檔案），所以「寫什麼」遠不如「不寫什麼」重要。

而「不寫什麼」有一個可操作的單一測試，六篇裡只有 Apple 拆解那篇講清楚：

> 🔑 **把每一條都翻譯成「如果沒寫，AI 會怎麼做錯」——翻得出來的才有資格留下。**
> 「請寫出乾淨的程式碼」翻出來是「不會怎樣」，所以沒有資格佔一行。

**但 2026-09 的查證推翻了這套方法論原本自我宣稱的效益。** 唯一的量化實測（1,650 sessions／16,050 個 function）顯示：**檔案長度、規則位置、檔案架構、內部矛盾，四項結構變數對遵守率全部沒有可測量差異**。真正的落差只有一個——**有沒有這個檔案（0% → 67.7%）**。

> 🔴 **所以精簡技巧的效益要改記為「省 context 成本與維護成本」，不是「提升遵守率」。67.7% 是結構優化拉不上去的天花板。**（官方措辭本來也只說 shorter files produce better adherence，從未給門檻；而「200 行」的硬截斷其實屬 `MEMORY.md`。）

三個真正有槓桿的地方，全部落在「怎麼寫這個檔案」之外：
1. **檔案存在與否**（0% → 67.7%，唯一的巨大躍升）
2. **編輯既有程式碼的情境**（71.3% vs **45.1%**，最弱環節）
3. **長 session 的衰減**（每多寫一個 function 遵守 odds 約 −5.6%）——要靠分段作業，不是改檔案

至於 Claude 5 世代的「刪」：官方刪掉 Claude Code 逾 8 成系統提示詞而評測零下滑，證明該刪的不只是冗詞，**更是那些為判斷力不足的舊模型寫的死規矩**。新判準是**規則要能通過「有沒有例外」這一問**——有例外就改成描述原則（「跟隨周圍程式碼風格」而非「絕不寫多段註解」）。

🔑 **而 Apple 那份 91 行給了「刪到什麼程度」的答案，也解釋了為什麼行數不能當目標**：它能只用 91 行，是因為 `Package.swift`／`Makefile`／`.swift-format`／CI／pre-commit hook **已經替它記了大半規則**——**規則只要工具能強制，就不必寫進 CLAUDE.md**。反過來，工具鏈薄的專案（例如沒有編譯器的寫作專案）行數自然會多，該做的是把可腳本化的檢查搬去讓機器擋，而不是硬壓行數。

## C（共識核心）
> 出現於 2 篇以上來源

- **NEVER / 負面清單優於正面清單**（4 篇）——AI 預設行為多半沒問題，需要約束的是它「過度做」的事
- **CLAUDE.md 是 advisory 非強制**（約 80% 遵守率）——要「一定擋得住」必須轉成 Hook（[[claude-md-behavioral-control-principles]]、[[claude-md-guide]]、[[claude-md-optimization-techniques]]、[[apple-claude-md-teardown]]）
  - 🔑 [[apple-claude-md-teardown]] 補上兩者**不是二選一**的理由：**工具是事後擋，CLAUDE.md 是讓它一開始就別走那條路**——一個省來回、一個保底
- **只保留「真正犯過的錯」、當活文件持續演進**（4 篇）——從空 NEVER 開始、犯錯就補、定期盤點刪膨脹
  - 官方判準：**同樣的錯犯第二次**才加一條；Apple 拆解的作者實證：那 47 行新增「**沒有一行是想出來的，全部是撞出來的**」
- **控制長度 < 200 行**，其餘靠路徑限定規則分層載入（Karpathy 原版 65 行為典範）
  - 🔴 **2026-09-03 修正定位**：這是**官方 target 而非 limit，理由是 context 成本**；「只讀前 200 行」的硬截斷屬 `MEMORY.md`（超出**靜默截斷**）。**不要說「超過就降低遵守率」**——實測無此效果（[[claude-md-guide]] 修正段）
- **漸進式揭露：資訊拆成檔案樹、需要時才載入**（3 篇）——多步驟流程拆成獨立 Skill，CLAUDE.md 只留一行指路
- **個人偏好放 `~/.claude/`、專案規則放專案根目錄**（3 篇）
- **抑制 AI 三大失敗模式**——擅自重構 / 過度抽象 / 改不相關檔案（Karpathy 四原則）
- **具體可驗證 > 抽象說教**（4 篇）——「願望清單型」是明確反模式
  - 官方對照組：寫「使用 2 個空格縮排」而非「把格式弄好」；寫「commit 前跑 `npm test`」而非「記得測試」
  - Apple 實測佐證：**230 個行內 code span 分布在 53 行**（每 4 個非空行有超過 3 行帶具體指令／檔名／設定值），空泛用語掃描**命中 0 筆**

## V（知識缺口）

- 🔴 **「結構優化能提升遵守率」已被實測否證，但本庫多數技巧仍以此為隱含前提（2026-09-03 新增，本精粹最重要的缺口）**：1,650-session 實驗顯示長度／位置／架構／內部矛盾**四項全部零可測量差異**（χ²(3)=5.16, p=0.16；BF₁₀=0.096）。**⚠️ 但此研究經二手轉述、本次未找到一手出處**，且與官方「shorter files produce better adherence」的措辭方向相左（官方未給數據）。**在找到一手研究之前，兩邊都不該當定論**——可確定的只有「官方從未主張超過 200 行會降低遵守率」
- 🔴 **45.1% 這個最弱環節完全沒有對策**：同一實驗顯示編輯既有程式碼的遵守率只有 71.3%（寫新程式）的六成多。**六篇來源沒有任何一篇針對「編輯既有程式」設計過規則寫法**——這是本主題目前最大的空白
- 🔴 **Session 衰減無人處理**：每多寫一個 function 遵守 odds 約 −5.6%（OR=0.944, p=1.08×10⁻⁴⁹）。這意味著**長 session 的遵守率下降與檔案怎麼寫無關**，但沒有任何來源討論該怎麼分段、何時重啟
- ⚠️ **判斷權該讓多少，仍無可操作判準**：「別立死規矩」與「仍需 NEVER 抑制過度行為」如何劃線，官方只說「哪些領域重要到不能交給判斷力仍需人決定」
- ⚠️ **「推導成本」判準缺量化門檻**：[[apple-claude-md-teardown]] 把判準從「能否推導」改成「推導成本 × 推導次數」，方向正確，但**多久算貴、幾次算多，沒有給線**。目前只能靠個案判斷
- ❓ **量化證據普遍薄弱（官方數據也不例外）**：78%→76%→52%、80% 遵守率、41%→3% 錯誤率全來自社群轉述；官方的「刪 8 成、零可測量下滑」雖是一手，但**未公開評測項目、樣本與方法**
- ❓ **自動記憶與 CLAUDE.md 的分工邊界未明**：官方說「互補而非取代」，但哪些該讓它自己學、哪些必須手寫，除了「需穩定約束的專案規則仍手寫」一句外沒有具體判準
- ✅ **階層合併機制已釐清（2026-07-30 更正）**：官方明訂 *concatenated into context **rather than overriding***，衝突時 `Claude may pick one arbitrarily`——**沒有 CSS 那種優先序覆蓋**，正確做法是**避免衝突而非依賴優先序**。唯一保證：同層內 `CLAUDE.local.md` append 在 `CLAUDE.md` 之後，跨層級無此保證
- ❓ **token 成本疊加仍無資料**：三層都會被串接進 context，各層疊加後的實際成本沒有量測——**而既然成本是 200 行建議的唯一正當理由，這個缺口現在比以前更關鍵**
- ❓ **Hook 轉換缺實作細節**：「屢次違反的規則轉 Hook」是官方修法，卻沒說哪類規則適合、怎麼寫、與 CLAUDE.md 如何分工

## 整合行動清單

- [ ] 🔑 **先確保檔案存在**——這是唯一有實測支撐的巨大躍升（0% → 67.7%）；還沒有 CLAUDE.md 的專案，寫一份粗糙的都遠勝於沒有
- [ ] 逐條做 **「不寫會怎樣」測試**：翻不出具體錯誤的一律刪（「請寫出乾淨的程式碼」翻出來是「不會怎樣」）
- [ ] 對每條再問 **「這條需要一定擋得住嗎」**：需要的話寫成 Hook／lint／CI；**規則只要工具能強制，就不必寫進 CLAUDE.md**
- [ ] **逐條做「有沒有例外」測試**：有例外的「絕不 / 一律禁止」改寫成描述原則，把判斷權還給模型；無例外的高風險項才保留為 NEVER
- [ ] **架構段落別無條件砍**——先算「推導一次要花多久 × 會推導幾次」，成本高就留著（`/doctor` 的建議要用這條過濾）
- [ ] 建新專案時用 [[claude-md-design-patterns]] 的「首日 15 分鐘檢查清單」**依規模選一個範本**，不要一律套多範本
- [ ] NEVER 區塊**從空白開始**，只補 AI 實際犯過的錯（官方判準：同樣的錯犯第二次）；**別坐下來想規則，等它撞出來**
- [ ] 定期刪（半年）並觀察活回來哪些：**活回來的是事實型規則、沒活回來的是能力型規則**；⚠️ 但**回饋慢的專案不適用刪除法**
- [ ] 用 Claude 5 世代鬆綁守則前先確認**模型版本**：舊模型拆護欄會出錯
- [ ] 🔴 **調整期待**：把精簡的效益講成**省 context 成本與維護成本**，不要講成「提升遵守率」；引用 200 行時說「官方目標值」
- [ ] 🔴 **遵守率真的不夠時，往檔案外找**——優先處理「編輯既有程式」情境（45.1%）與長 session 分段，而不是繼續改檔案
- [ ] 引用任何遵守率/行數數字前，記得它們**未經一手驗證**（包含本精粹引用的 1,650-session 研究），當方向參考而非硬指標
