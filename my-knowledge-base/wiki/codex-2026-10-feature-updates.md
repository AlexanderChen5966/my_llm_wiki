## T（核心論點）

Codex 2026 年 10 月的三項更新——**下一句建議（Composer Predictions）、快取帶來的有效用量提升、桌面版可編輯舊訊息**——共同點是**只降低操作成本**（少打字、少重算、少補一則更正），**沒有替使用者決定任務範圍，也沒有取代驗收**。三者各需一個判準：建議看「動詞／對象／完成條件」、快取看「通過驗收的完成數」、編輯看「修文字還是改方向」。任務定義與驗收仍要由人掌控。

## B（適用場景）

**適用：**
- 日常用 Codex 桌面版做中長任務、常需要接續下一步或修正提示詞的人
- 已有固定任務與驗收方式、想判斷更新是否真的讓工作變划算的人

**不適用 / 注意：**
- 🔴 **Codex 編輯舊訊息 ≠ Claude Code `/rewind`**：`/rewind` 會倒帶到 checkpoint、**可還原程式碼狀態**（見 [[claude-code-session-handoff]]、[[claude-code-commands-reference]]）；Codex 官方**只確認文字可改**，沒有承諾還原檔案或撤回外部動作——兩者不能混為一談
- 「預測不耗用量」只針對預測本身；接受建議後代理實際執行的工作**照常計量**
- API 提示詞快取折扣**不能換算**成訂閱方案的訊息數；Work 與 Codex **共用用量**（與 [[codex-advanced-tips-11]] 額度段一致）

## R（三項更新的判準與操作）

### 1. Composer Predictions：建議下一則訊息，不自動執行

- 依目前對話與使用者說話方式**建議下一則訊息**，只是輸入輔助，送出什麼仍由人決定
- **三項檢查**（幾秒內完成）：**動詞**（查詢、修改還是發布）→ **對象**（是否仍是原本頁面／檔案）→ **完成條件**（有沒有能核對的成果）
- 處理判準（作者自設練習表）：

| 建議 | 眼前狀態 | 較合理的處理 |
| --- | --- | --- |
| 請檢查修正 | 尚未驗證失敗情境 | 補上輸入條件後送出 |
| 全部重做 | 只有一處錯誤 | 縮回受影響範圍 |
| 直接部署 | 還沒有結果證據 | 先要變更摘要與檢查證據 |
| 再跑相同檢查 | 結果已清楚且無新改動 | 改要求整理結果 |

- 建議品質取決於原始任務：寫清「**誰在什麼情況得到什麼結果**」＋當次範圍＋完成條件
- 任務改向要**用明確文字宣告**，不能靠略過建議暗示
- 官方「內部測試很受歡迎」是產品團隊說法，不是效率證明；自己記錄「直接可用／需改寫／沒回答需求」的比例

### 2. 快取更新：提高有效用量，不保證訊息數

- 三個方向：**子代理之間重用上下文**、**延長快取保留**、**改善請求路由**（讓請求找到已有快取的節點）；無需手動開關
- 官方方案文件：模型、任務大小、上下文、工具使用、快取都影響消耗
- **衡量方式**：固定一個常做、有清楚答案的任務，記錄模型／資料版本／範圍／重試次數，看「**通過驗收的完成數**」，而非訊息數或速度感受；同時記錄帳戶內其他並行工作
- **快取 ≠ 長期記憶**：快取重用算過的前綴狀態；記憶是之後找回資訊。需求與決定仍放在可查閱的專案文件
- 實務：穩定需求（產品用途、不可改欄位、交付格式）與當次任務分開放；子代理給可獨立回答的問題並交回證據；需求變了就更新規則，**別為了重用快取保留過期背景**
- 撞上限時先看耗用集中在哪：**反覆探索** → 先交出已知結果與下一個最小問題（保存中間成果）；**持續修錯** → 收緊驗收條件
- 概念上與 Devin Fusion 的持久化 cached context＋快取路由呼應，見 [[fable-5-delegation-cost-benchmark]]

### 3. 編輯舊訊息：修文字用編輯，改方向補新訊息

| 情況 | 比較清楚的要求 | 需要再確認的事 |
| --- | --- | --- |
| 名稱打錯 | 修正原訊息 | 檔案裡是否已用舊名稱 |
| 漏掉條件 | 補齊尺寸或格式 | 已有成果是否需調整 |
| 看到成果後改方向 | 新訊息寫明「保留什麼＋新增什麼」 | 哪些工作仍有效 |
| 已做外部操作（CMS 草稿、寄信） | 先查實際狀態再改指令 | 是否需另行修正或撤回 |

- 對話文字改了，**現實結果另外核對**：程式檔用 Git 差異；但 Git 只管納入版控的檔案，資料庫、已寄出訊息、外部服務設定要各自確認
- 「系統接受任務」只代表請求進入流程，是否套用要看最終紀錄與實際頁面
- 官方專案文件建議「**每個可獨立驗收的成果一個聚焦對話**」；每輪結束留簡短決策紀錄（採用需求、保留成果、變更位置、完成證據）

## C（關鍵行動）

- [ ] 送出 Predictions 建議前，看動詞／對象／完成條件；從查詢變修改、小修變重構、檢查變部署時特別停一下
- [ ] 選一個固定任務當基準，記錄「通過驗收的完成數」與重試原因，再判斷快取更新的實際效益
- [ ] 改舊訊息前先問：我在修文字，還是改工作方向？後者改寫新訊息並註明保留範圍
- [ ] 改完提示詞後，用 Git diff＋外部系統實際狀態核對成果；**不要期待 Codex 編輯舊訊息像 `/rewind` 一樣還原檔案**
- [ ] 先用無外部變更的文字任務試編輯入口，再試有備份的本機文件
