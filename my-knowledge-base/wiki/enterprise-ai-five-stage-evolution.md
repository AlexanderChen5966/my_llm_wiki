## T（核心論點）

企業 AI 系統的演進**不是換一個更強的模型、或再加幾行 Prompt 就能完成**——每個階段的箭頭都代表一系列真實的工程與產品設計工作：

```
Chat
  ↓ 加入企業文件
RAG
  ↓ 接上資料庫與 API
Tool Use
  ↓ 讓 AI 自主選擇工具
Agent
  ↓ 加入流程控制與錯誤處理
Agentic Workflow
  ↓ 定義業務範圍、權限與可信度機制
Enterprise AI Product
```

而真正拉開「Demo 能跑」與「可實際使用」距離的，**不是那些精彩的成功畫面，而是那些看起來不特別精彩、卻每天都可能發生的例外情況**。

## B（適用場景）

**適用：** 規劃企業內部 AI 系統的導入階段；判斷目前卡在哪一段；向管理層說明「為什麼 Demo 到上線還要這麼久」

**不適用 / 注意：**
- 這是**單一產品（Data Machi）的演進實錄**，不是通用成熟度模型——階段劃分可借用，各階段耗時因組織而異
- 三個「不好讀」的文件處理細節見同系列 [[multimodal-document-processing-three-layers]]

## R（四個階段的實際門檻）

### 第一階段：從結構化資料查詢開始

先能回答「今年總共有幾張需求工單？」「各需求分類占比？」「哪個市場提出的需求最多？」

⚠️ **但連上資料來源後系統仍不知道**：哪一列是欄位名稱／哪個欄位代表市場／哪個欄位代表需求類型／日期欄位如何解析／**測試資料與正式資料如何區分**／空白值與異常值如何處理。

> 🔑 **連接資料來源，不代表系統已經理解資料。**

### 第二階段：加入文件檢索與業務定義

因為使用者的問題常混著**數據與定義**兩層：
- 「Priority 欄位中的高、中、低是**怎麼定義的**？」
- 「這一類需求工單的 SLA 是多少？」
- 「哪些情況**應該被歸類為** Data Request？」
- 🔑 混合型：「今年高優先級需求增加了多少？**高優先級又是怎麼定義的？**」——一句話同時要查數據與查文件

### 第三階段：讓 AI 自己判斷該用哪個工具

從「你指定工具」變成系統要自己：判斷問題屬於數據／文件／專案進度／決定呼叫一個或多個工具／**安排工具執行順序**／判斷第一輪結果是否足夠／決定是否補充查詢／整合不同來源。

⚠️ 但它可能**選錯工具、跳過必要查詢，或在工具沒有結果時自行補上一個答案**——所以必須進入第四階段。

### 第四階段：從能用走向可靠

> 這階段處理的**不再只是正常情境**，而是大量真實使用中可能發生的問題：第一次查詢沒找到資料怎麼辦？模型沒有真的呼叫工具怎麼辦？問題不明確時如何釐清？查詢多工具很久時如何回饋進度？工具返回錯誤該重試還是停止？**不同來源出現衝突時採用哪一個**？查不到資料時如何避免模型自行猜測？**系統如何知道任務已經完成**？

為此加入的機制（11 項）：
**上下文判斷／問題釐清／工具呼叫驗證／回答查核／Timeout／Retry／Fallback／執行狀態回饋／明確的結束條件／人工審核／會議前後的工作流**

> 這些功能單獨看都不算特別複雜，**但它們共同決定了一套 AI 系統能不能在真實環境中持續使用**。也正是在這個階段，Data Machi 才從技術 Demo 逐漸成為可實際使用的產品。

### 每個箭頭代表什麼工程工作

| 轉換 | 需要處理 |
|---|---|
| Chat → RAG | 文件解析、Chunk 切割、Embedding、檢索品質 |
| RAG → Tool Use | 工具介面、參數格式、權限、錯誤回傳 |
| Tool Use → Agent | 工具選擇、多步驟推理、上下文管理 |
| Agent → Agentic Workflow | 流程控制、狀態管理、錯誤重試、**可觀測性** |
| Agentic Workflow → 企業產品 | 權限、安全性、可信度、使用者體驗、部署、**長期維護** |

## 🔴 Demo 與可使用產品之間的四個真實落差

許多 AI 教學直接展示完成版架構（成功畫面最容易理解也最吸引人），但**展示時能成功回答問題，不代表在真實環境中可靠**。

### 問題一：第一次搜尋找不到資料（但資料明明存在）

常見原因：使用者輸入的名稱與欄位拼法不同／大小寫不一致／欄位含多餘空格／**使用者用簡稱而資料記正式名稱**／日期格式不同／查詢條件過度嚴格／同一概念在不同資料用不同名稱。

> 具體例子：使用者輸入 `Japan`，資料記的是 `JP`；使用者搜 `Data Request`，欄位寫成 `Data request` 或 `Data Analysis Request`。

**解法**：模糊查詢、名稱正規化、同義詞對照、多種查詢策略。🔑 **第一次查詢沒結果時系統不應立刻停止**，而應嘗試較寬鬆的條件，或**向使用者說明目前使用的查詢邏輯**。

### 🔴 問題二：模型說「正在查詢」，卻沒有真的查

模型回「好的，讓我查一下您的需求工單資料」，接著直接產生「根據目前資訊，Q3 大約有 200 張工單」——**整個過程沒有呼叫任何工具**。

> 原因：**語言模型的訓練目標傾向於產生連貫且有幫助的回答**。當它無法取得資料時，有時會用語言模式補足缺口，而不是停下來承認自己沒有查詢結果。

🔑 **解法不能只是再加一句「一定要呼叫工具」到 Prompt 中**，而必須在 Workflow 中**驗證是否真的存在工具呼叫**：若沒偵測到工具請求，就不能讓流程進入最終回答階段，而應要求模型重新選擇工具，或由程式直接切換到查詢節點。

→ 這正是 [[enterprise-ai-four-layers-prompt-policy-tool-workflow]] 的核心：**關鍵行為必須由 Workflow 保證，不能只依賴 Prompt。**

### 問題三：追問時該不該重新查詢——資料時效策略

先問「今年台灣市場有多少張工單？」再追問「那其中高優先級有多少？」——第二題要不要重查？

| 選擇 | 代價 |
|---|---|
| 完全不重查 | 速度快，但**可能用到過時或不完整的資料** |
| 每次追問都重讀所有來源 | 增加等待時間與工具成本 |

🔑 **本質是系統缺乏明確的資料時效策略**。做法：針對不同來源定義有效期限（例：同一對話中查詢結果五分鐘內可重用），但**使用者改變分析期間、加入新篩選條件，或來源本身更新頻繁時就該重查**。

> **這不是單純的技術選擇，而是速度、成本與資料新鮮度之間的產品設計取捨。**

### 問題四：等待太久，使用者不知道系統還在跑

複合問題可能要依序查 Google Sheets、Confluence、Trello，整體等待很容易超過十秒。畫面完全沒變化時，使用者分不清是正在處理還是已經出錯。

**加入中間狀態回饋**：正在確認問題需要的資料來源 → 正在查詢需求工單資料 → 正在查閱欄位定義 → 正在取得相關專案進度 → 正在整合查詢結果。

> 🔑 **這些狀態不只是視覺裝飾**——它降低等待焦慮，也**讓使用者知道系統實際執行了哪些步驟**（等於順手提供了可觀測性）。

## C（關鍵行動）

- [ ] 先定位自己卡在五段的哪一段，別把「換更強模型」當解法
- [ ] 🔴 **在 Workflow 層驗證「是否真的有工具呼叫」**——模型會說在查卻沒查，加 Prompt 沒用
- [ ] 查詢失敗時不要立刻回「找不到」，先試寬鬆條件（模糊查詢／名稱正規化／同義詞），並說明用了什麼查詢邏輯
- [ ] 為每個資料來源定義**有效期限**，明確處理追問要不要重查
- [ ] 加中間狀態回饋——超過十秒的複合查詢沒有進度顯示會讓使用者以為壞了
- [ ] 規劃時把第四階段（11 項可靠性機制）算進工期，那才是 Demo 到上線的真正距離
