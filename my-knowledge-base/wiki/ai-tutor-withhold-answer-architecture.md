## T（核心論點）

三個層層相扣的主張，每一個都可獨立帶走：

> **① 問題不是「年輕人依賴 AI」，而是 AI 讓開發變快、也讓實力變得看不見。** 作者看到後輩 3 秒內把錯誤丟給 AI 解決（一次都沒讀錯誤訊息），當天下午自己也想讀錯誤訊息——**讀不懂**。「在我開始讀之前，『丟給 AI 就好了』的念頭插進來了。」🔑 **「那根本就是我自己的樣子。」**

> **② 發想反轉：不是讓 AI 給答案，而是讓 AI 出問題。** 必須是 AI 的理由很精確——**「必須是知道答案、卻不說出口的對象」**，固定教材與 FAQ 做不到，而每次都要有看得懂原因的前輩全程陪著又本末倒置。

> **③ 🔑 LLM 再怎麼交代都不會老實保密，所以不再用機率去防，改用結構去防。**

## B（適用場景）

**適用：**
- 任何需要 LLM「知道但不能說」的場景（教學、評測、面試、漸進式揭露）
- LLM 應用的成本設計（本篇的實測與試算落差極有參考價值）
- 思考「AI 時代如何評估人的實力」

**不適用 / 注意：**
- ⚠️ 這是產品介紹文（v0.1，部分功能標明是 v0.2 構想），組織儀表板等尚未落地
- ⚠️ 成本數字為單一產品的 session 實測（日圓），不可直接外推

## R（① 結構防洩漏：讓出題者不知道答案）

如果叫 LLM 一次完成「找出原因、但不要直接說答案、只用提問引導」，**一定會漏**——它會先說出「看起來是某個變數變成 undefined 了，接著…」這種前言，等於先把答案說掉。**就算提示詞再怎麼調，總有一天還是會漏。**

解法是把 LLM 拆成兩段、分角色處理：

```
Diagnoser（第一段）→ 判定原因【知道答案】
      ↓ 只傳「應該讓使用者注意哪裡」這件事
Questioner（第二段）→ 生成問題【不知道答案 → 不可能洩漏】
      ↓
LeakGuard（洩漏檢查）→ 🔑 刻意不用 LLM，用決定性規則實作
```

🔑 **LeakGuard 不用 LLM 的理由值得抄下來：「如果再叫 LLM 來判斷有沒有洩漏，那檢查本身也會變成機率性的。」**

貫穿整個產品的一致方針是**在哪裡用 AI、在哪裡不用 AI**：

- 遮蔽敏感資訊 → 在送進 LLM **之前**處理，所以用**正規表示式**
- 分數計算 → 需要**可重現性**，所以用**純函式**
- 洩漏檢查 → 需要確定性，所以**不用 LLM**

（這與 [[enterprise-ai-four-layers-prompt-policy-tool-workflow]] 的「關鍵行為必須由 Workflow 保證，不能只加一句 Prompt」、以及 [[agent-tool-authorization-gatekeeper]] 的「引擎在模型外部而非藏在提示詞裡」是同一個工程直覺）

## R（② 三階段 Gate：不讓答案永遠藏起來）

「不教答案怎麼可能拿來工作？」——作者的回應是**設計成使用者嘗試到一定程度後才開放**的三階段（提示 Gate A → 題目 Gate B → 答案 Gate C）。

- **走到底一定能拿到答案，工作不會停**
- 🔑 **時間到就自動往前**——「為了救那些卡住卻不會自己往前推的人；越是不會自己說『我要往前』，就越容易把卡住的狀況吞下去」
- 會記錄在哪個 Gate 解決、用了多少提示。**開放答案不是失敗，而是「正確落點之一」**
- 只保留一個直觀激勵：**越不靠提示與引導解出來，評價越高**

⚠️ **Gate C 的開放扣分刻意設得很小**，因為「如果把開放當成懲罰，使用者卡住時就會直接去問 AI，學習和測量都無法成立」。

> 🔑 **整個產品的設計原則：會讓使用者吃虧的設計，最後一定會被繞過。**

## R（③ 除錯腦五軸：把「實力」變成可說明的東西）

把熟練者無意識在做的除錯流程拆成五個階段，從對話紀錄分別測量：

| 軸 | 測量什麼 | 問題例子 |
|---|---|---|
| **觀察** | 能否準確讀懂錯誤 | 「這個訊息是在說哪個東西是 undefined？」 |
| **切分** | 能否縮小問題範圍 | 「錯誤發生前，你改了哪個檔案？」 |
| **假設** | 能否推論原因 | 「那個變數，是從哪裡來的？」 |
| **驗證** | 能否驗證假設 | 「要確認的話，先印出什麼？」 |
| **修正** | 能否選擇不會再犯的修法 | 「為了避免再發生，你要在哪裡加什麼？」 |

🔑 **重點不是說「技術力高/低」，而是能進一步說成「觀察很強，但驗證較弱」**——這樣培育負責人知道該教誰什麼，當事人也知道往哪裡補強。

### ⚠️ 作者主動揭露的結構性限制（誠實度很高）

**最高層級的到達——只靠提示就自行解決——五個軸都會變成同一個值**，因為根本沒做題、沒有可供軸向差異判斷的資料。

> **這不是實作缺陷，而是「不讓他做題、直接靠自己解決」被設計成最佳結果之後，必然產生的結構性結果。如果為了測量而強迫他作答，就會失去自主解決的價值。**

所以 v0.1 選擇不隱藏：自力解決時的五軸**明確標示為參考值，且不納入成長率計算**。

### 對抗 Goodhart 定律的三個設計

「這不就是監控工具嗎？」——作者承認「工程師對測量工具抱有警戒心是合理的，而且**指標一旦拿來評估就會失真**」，所以：

- **任何計算依據使用者都能隨時查看**——不只給總分，**禁止出現無法說明的數值拿來評估人**
- **主要指標看成長率，不看絕對值**——「如果指標會讓經驗年數直接變成排名，那對年輕工程師就是『怎麼努力都翻不了盤』的指標，最後一定沒人用」
- **不預設做排名**，且**刻意不做會自動串接人事系統的功能**

## C（關鍵行動）

- [ ] 需要 LLM「知道但不說」時，**拆角色讓出題端拿不到答案**，別靠提示詞約束
- [ ] 檢查機制（洩漏／格式／安全）用決定性規則，不要再叫一個 LLM 來判斷
- [ ] 設計任何評量或閘門時先問：**這個設計會不會讓使用者吃虧到想繞過它？**

## 補充資料

### 🔑 成本實測：試算 74%，實際只有 45%（而且原因很有啟發性）

兩段式設計同時解決了洩漏防護與成本最佳化——困難的處理（Diagnoser 原因判定）**一個 session 只要 1 次**，簡單的處理（提示生成／出題／判定）要 **10–15 次**。所以把高品質模型留給那 1 次。

| 構成 | 1 個 session（實測）|
|---|---|
| 全部用高品質模型 | 約 12.5 日圓 |
| 角色分流後 | 約 6.8 日圓 |
| 削減率 | **45%**（試算原為 74%）|

🔴 **數字變小的原因**：原本以為要省的部分（出題生成）**比想像中便宜很多**——每題出題約 **0.043 日圓**，整個 session 只有 **3.4%** 的成本在這裡，**96% 的成本都花在高品質模型的三個角色**（診斷、說明、回顧）。

> **要省的地方本來就很小，節省額自然也不會大。這只是很普通的算術。**

⚠️ 且削減率取決於使用者解了幾題（使用者卡住多解題時可達 68%），**所以不能只用單一數字描述**。

### 🔑 最有趣的結構：成本由「啟動幾次」決定，不是「用了多少」

**開始一個 session 的當下約 4.2 日圓就已確定**（診斷與回顧一定會跑），就算解 100 題也只再增加 **+4.3 日圓**。只用提示立刻解決（約 4.9 日圓）與經過題目看完說明（約 6.8 日圓）之間只差約 2 日圓。

> 🔑 **使用者就算想很久，原價也幾乎不會變。** 對一個重視「讓人好好思考」的產品來說，**思考時間不會大幅拉高成本的結構雖然不是刻意設計出來的，卻意外地非常適合。**

### 🔑 什麼才配叫「實測」

作者把單價表 × token 數的預估值，與 **LLM Gateway 的實際帳單（credit 消耗）** 對照，確認誤差只有 **6%**（含顯示解析度最多 11%）。

> **不是相信單價表，而是拿帳單對答案——既然要把數字拿出來，就應該做到這一步。**

⚠️ 另一個品質設計：**診斷每個 session 只執行一次並保存，不重新診斷**——因為每次重跑，對原因的判斷就會飄移，題目的一致性也會壞掉。**成本與品質用同一個設計一起成立。**

### 一個容易忽略的資安細節：前後端共用同一個遮蔽純函式

敏感資訊遮蔽的結果會在送出前顯示給使用者預覽，而作者特別在意的是：**預覽時沒有把正規表示式再重寫到前端，而是讓瀏覽器與伺服器共用同一個遮蔽純函式**。

> 🔑 **只要兩邊實作有一點偏差，就會變成「畫面上看不到，但送到伺服器的是原文」——這種情況比不顯示還糟。**

為此他甚至改變了「不使用 bundler」的原本計畫。⚠️ 且誠實承認正規表示式仍可能漏掉專有名詞，**所以才需要送出前預覽讓使用者自行確認修改**。其餘：API 金鑰只放伺服器環境變數／組織專屬排除字典不發到 client（避免瀏覽器讀出正在處理哪家公司）／**Log 不留 PII**（只記 token 數與角色）。

### 「AI 時代還需要除錯能力嗎？」的三個理由

作者說「我同意一半」（未來大部分制式錯誤 AI 會處理得比人更準），但：

1. 🔑 **如果沒有人能驗證 AI 的修正建議，上線時就會卡死**——「看起來能動」和「真的正確」是兩回事，而**辨別這件事本身就是除錯能力**
2. **AI 解不出來的錯誤才會變成人類的工作**——AI 越擅長制式問題，人類接手的就越是非典型難題，要求反而更高
3. **觀察 → 切分 → 假設 → 驗證這個流程，同樣適用於指揮 AI**

用心算類比：**要鍛鍊的不是大位數乘法，而是「這個計算結果，位數看起來對嗎？」的敏感度。**

### 組織層面的三種反撲

**① 成員的實力看不見**（AI 讓成果物有加成，無法只靠產出衡量基本功）**② 培育高度依賴個人**（會教「怎麼看錯誤訊息」的往往只有少數資深工程師）**③ 評估依據變成主觀**（依賴印象與自我申報）。

🔑 作者的結論是「不要依賴 AI」講起來很簡單，但**既不能靠本人意志、也不能靠組織號令，那就只能用機制來解**——這與 [[harness-engineering]]「一條義務配一個 guide 加一個 sensor」是同一種思路。
