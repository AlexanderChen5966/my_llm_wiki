Cognitive Hub 是一個 AI 代理設計模式：把決策脈絡外部化為「活記憶」（人類可讀、AI 可讀、可協作編輯），解決 AI 每次新對話都從零開始的根本問題。記憶先於行動——AI 要能有意義地行動，必須先有持續、可控的脈絡。

## T（核心論點）
知識工作者的瓶頸不是某一天的工作量，而是決策脈絡隨時間不斷流失。Cognitive Hub 的核心主張：**外部化的活記憶比更強的 AI 模型更重要**——換模型不解決「腦不夠用」的問題。

## B（適用場景）
**適用：** 知識密集型專業工作（醫療、法律、研究）；需要跨時間/跨協作者維持決策脈絡的場景
**不適用：** 一次性任務；不需要累積知識的簡單自動化

## R（操作架構）

### 外部化活記憶的三個特質
- **外部化**：知識存在結構化系統，不在短暫對話或人的工作記憶裡
- **活的**：知識會成長、修正、被淘汰；AI 代理可跨領域交叉推理
- **多代理可存取**：人和 AI 代理可同時讀寫同一知識庫

### 分層架構（不綁定特定工具）
參考實作：Claude + Notion + MCP，但可用任何 LLM + 結構化知識平台實現。

## C（關鍵行動）
- [ ] 核心問題：「哪些決策脈絡是現在沒有被記錄下來、卻會反覆影響後續工作的？」
- [ ] 不綁定 LLM：設計讓換模型不會失去知識的外部化系統
- [ ] 用既有筆記平台（Obsidian / Notion）即可實作，不需要特殊工具

## 補充資料（來源：cognitive-hubREADME.zh-TW.md at main.md）

### 分層架構詳解

```
┌─────────────────────────────────────────────┐
│       運算層 Computation Layer (LLM)        │
│   可替換的運算引擎，不擁有知識               │
└──────────────────┬──────────────────────────┘
                   │ 雙向連接
┌──────────────────┴──────────────────────────┐
│       橋接層 Bridge Layer (例如 MCP)         │
│   知識平台與 AI 引擎之間的雙向通道           │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────┴──────────────────────────┐
│       知識層 Knowledge Layer (Hub)           │
│   ├── Rules & Protocols — 決策邏輯          │
│   ├── Projects — 進行中的工作脈絡            │
│   ├── References — 穩定的背景資訊           │
│   └── SOP — 重複性工作的標準流程            │
│   + Hub Index（路由表）                     │
│   + Governance Hierarchy（治理層級）         │
└─────────────────────────────────────────────┘
```

### Hub Index 路由機制

知識層維護頂層索引（路由表）：
- 列出各子區塊的一行摘要和觸發條件
- AI 在對話開始時**只讀這個索引**，按需載入相關子頁面
- 類比：Claude Code 的 Progressive Disclosure——只在需要時才載入詳細內容

### 治理層級（Governance Hierarchy）

- **頂層**：精簡、穩定、每次對話都載入——只放路由訊號
- **下層**：完整程序，按需載入
- 將規則提升到頂層的門檻：高頻率 + 跨對話 + 一行就能表達

### 核心工作模式

**異步接力工作流程**：主管在 Hub 列任務 → 團隊成員隔天用自己的 AI 接手（AI 讀共享專案頁面取得脈絡）→ 完成 → 更新頁面 → 主管審閱加入下一步。不需要同步開會。

**先定稿再產出（Settle-Then-Generate）**：先在 Hub 確定內容實質，再產出交付物。減少無效迭代，每個中間決策都被記錄可回溯。

### 五條設計原則

1. **同時服務人和 AI 讀者**：每條知識讓人類和 AI 都能理解
2. **知識與運算引擎分離**：LLM 是消耗品，知識庫是持久資產
3. **用成熟管理原則管理 AI**：SOP、授權、onboarding 文件
4. **資料層比工具層長壽**：用 Markdown 確保可攜帶性
5. **提升路由訊號，不提升完整程序**：頂層只放一行指標

### 維護成本

作者實測：每天約 15 分鐘維護 Hub。過時的 Hub 比沒有 Hub 更糟（錯誤路由比沒有路由危害更大）。

### 與 OpenClaw 的關係

- **OpenClaw**：擅長持續執行（排程、行動通訊、24/7 自主任務）
- **Cognitive Hub**：擅長深度脈絡（結構化決策記憶、跨角色知識）
- 兩者互補：Hub 作為思考層，代理平台作為執行層

### 快速開始（約一小時）

1. 建立 Hub 主頁，下設子區塊：Rules、Projects、References、SOP
2. 建立 Hub Index（路由表），列出每個區塊的一行摘要和觸發條件
3. 寫 5–10 條核心規則（溝通風格、決策原則、行為準則）
4. 加入基本 References（你是誰、你的角色、你的工具和偏好）
5. 設定 LLM 在對話開始時讀取 Hub Index
6. 測試：「你知道我目前有哪些專案嗎？」

## 補充資料：知識囤積 vs 知識內化的根本差距

來源：Kevin Shih（Vocus，2026-05-17）—《停止囤積知識！你根本就不需要 AI 當第二大腦》

### 第二大腦的核心誤區

作者建過兩次第二大腦系統後的核心發現：大多數第二大腦只是**更漂亮的囤積場所**，和電腦裡從來不打開的「重要資料」資料夾本質上差不多。原因在於它設計邏輯的核心是「收集」，但沒有處理「消化」這個環節。

> 收藏知識不等於擁有知識。知識必須經過思考、懷疑、連結、判斷，才會慢慢形成你的觀點。

**兩個完全不同的問題：**
- 收集導向：「這個東西要放哪個資料夾？」（系統問題）
- 內化導向：「這個東西和我的判斷有什麼關係？」（思考問題）

前者不會自動導向後者。

### 知識比例問題

> 你花在「整理知識」的時間，和花在「和這些知識對話」的時間，比例是多少？

大多數人大約 99:1。那個 1，才是真正讓知識有價值的部分。

### 改變輸入方式的操作原則

不要「先收集，之後要用再想」，而是**收集當下就要有一個初步判斷**：
- 「這個觀點跟我以為的不一樣」
- 「這個跟我現在正在思考的 X 問題有關係」
- 「我同意這裡，不同意那裡因為⋯⋯」

只要說得出來哪怕半句話，那半句才是你的——不是原作者的。

**實用測試**：「要存這個東西，我想說什麼？」如果說不出來，代表還沒準備好存，或者這個東西對你還不重要。

### 對 Cognitive Hub 設計的啟示

這個觀點與 Cognitive Hub 的「記憶先於行動」互補但方向相反：
- **Cognitive Hub**：解決「決策脈絡流失」的工具問題（設計更好的記憶系統）
- **Kevin Shih 的觀點**：提醒「工具解決不了思考不足」的根本問題（先思考再存）

結合兩者的最佳實踐：用 Cognitive Hub 管理「已消化過的知識」，而不是用來囤積未消化的內容。輸入門檻不是格式，而是「有沒有想過一次」。

> 📌 相關：[[ai-thinking-atrophy]]（2026-08-12 入庫）給出這條原則的機制解釋——**最危險的是 AI 給出「正確」的答案**，因為錯答會壞掉逼你學習，正確答案卻讓你信任它，在該理解的地方留下空洞。
