## T（核心論點）

當約 **90% 的程式碼由 Claude 撰寫**，人工逐行閱讀已追不上變更量，稀缺資源變成「能辨認風險的人類時間」。Claude Code 團隊的解法不是取消人工，而是**分層**：先讓代理用可執行的檢查（測試、建置）驗證自己，再由 AI 審查與安全審查、合併佇列把關，最後依**風險決定需要零／一／兩位人工核准**，並用撤回與事故檢查成效。**每項上線變更仍由人負責，AI 的核准不能頂替要求中的人工核准。**

內部結果：2026-06 到 09，合併的 PR 增加逾一倍，需撤回的比例下降逾四成。⚠️ 這是「需撤回的 PR 比例」，**不是事故數**，兩者不可互換。

## B（適用場景）

**適用：**
- 已有測試與版本管理、AI 產出開始超過人工逐行審查速度的團隊，借用「檢查順序」與「依風險分流」的思路
- 想設計「哪些變更可以少一點人、哪些一定要兩個人」的政策，或想為代理互改設停止條件

**不適用 / 注意：**
- 九成程式由 AI 撰寫描述的是**程式來源**，不是工時或人力替代比例
- 還沒有可靠撤回機制與問題追蹤的團隊，應先補基礎，再談減少人工
- 「零位人工」有前提（可信作者、自動檢查通過、屬低風險類別），**不能擷取成「文件一律可無人合併」**
- 內部流程是團隊自己的工程政策，與「商用 Code Review 產品會不會自動替客戶核准 PR」要分開（產品仍只提出發現，不替代必要人工核准）

## R（操作步驟）

### 1. 提出合併前：先拿出能執行的證據
- 讓 Claude 取得測試、建置或可對照設計的畫面，要求展示輸出（「我已完成」是敘述，執行結果才能被核對）
- 專案以短 `CLAUDE.md` 寫專案規則，`REVIEW.md` 寫負責人希望審查者特別留意的事；越具體越好（例如指出哪種變更會造成資料被錯誤存取，而不是只寫「檢查權限」）

### 2. 審程式與查安全各自保留阻擋能力
- 每份 PR 都有 AI 審查，另有獨立的安全審查；AI 看到的問題會再由其他代理確認，讓進入討論的內容盡量有實際證據
- 人要回應每項問題（修正或說明為何誤判），不留無人處理的討論
- 格式、型別、跨平台測試與建置維持自動阻擋
- **合併佇列**：把變更放進接近正式主線的狀態再檢查，降低「各自通過、合在一起失敗」；「代理已測過」不等於「正式系統已驗收」

### 3. 依風險決定人工核准人數

| 風險層級 | 官方舉例（依來源） | 人工核准 |
|---|---|---|
| 低 | 文件、文案、內部功能、功能開關後的新增內容 | 符合條件且檢查通過後，**零位** |
| 中 | 一般產品修改，快取、更新程式、系統提示等敏感區域 | **一位** |
| 高 | 最高風險程式與指定路徑 | **兩位** |

- 名單外作者額外需要人；某些敏感路徑固定需要人，不是代理自認熟悉就能跳過
- 差異來自「改動會造成什麼後果」，不看檔案大小（一行認證邏輯可能比大段文件更需要人）
- **核准綁在具體 commit**：之後加進系統無法確認的內容，需重新取得核准（代理收到留言後可能很快推多個版本，新修改不能沿用舊核准）

### 4. 反覆互改要設停止條件
- 案例：某 PR 夜間跑了 **50+ 輪**審查與修正，事後回看被持續指出的問題**約 59% 從第一輪就存在**，並非每輪新引入
- 因此「審到沒有新意見」不是有效的停止條件
- 做法：**三輪上限**，之後要求作者重新考慮做法；複查改以**新差異**為主（但原本的驗收要求與相關檢查仍要重跑，停止重複審查 ≠ 停止驗證）
- 作者建議（非官方）：把留言分成必須修正／需要人決定／不影響本次任務的建議；同類問題反覆出現時回頭改共同原因（例如把命名規則寫進專案文件）

### 5. 上線後：撤回、功能開關與事故回饋
- 功能開關可停用新行為；撤回提交可恢復較早版本，修改時就確認哪種適用
- 先內部使用、再逐步外放；上線後作者與輪值人員看撤回與事故紀錄，找出哪一層本應攔住
- **事故轉成審查者評估案例**：整理相關 PR、修復與撤回，讓熟悉程式的人確認問題，放進評估審查者的案例集；因為提示、模型、工具都會變，保留案例才能比較新版本是否又漏掉同類錯誤
- 噪音也要看：把正常行為判成錯誤，會讓代理作者白修一輪
- 追蹤指標：每份提案的人類核准數、中位數與較慢尾端、人類留言與等待時間；要與撤回、事故**一起看**，否則只是把審查工作搬到後面

## C（關鍵行動）

- [ ] 挑**一個**程式庫試行：要求每份提案附測試與撤回證據（作者建議）
- [ ] 先用原有流程留下基準（人工等待、核准次數、來回輪數、上線後問題），再逐項調整門檻；不要一次同時換模型、規則、風險門檻與發布方式
- [ ] 為代理互改設輪數上限與「只審新差異」規則，保留原驗收檢查
- [ ] 若合併較快但需要更多人善後，收回較寬鬆的路徑
- [ ] 讓負責人能說出「這次檢查證明了什麼、沒證明什麼」（例如測試涵蓋指定輸入，未必涵蓋正式資料與所有權限情況）
