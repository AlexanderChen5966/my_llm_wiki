## T（核心論點）

多數人以為 Knowledge Map 是一張「資料在哪裡」的清單。實際上該記的是四件事：

> 🔑 **什麼資料在哪裡、由誰負責、多久更新，以及發生衝突時應該相信誰。**

核心提問從「資料在哪裡？」升級為：

> **哪一種問題，應該去哪一個 Source of Truth 找答案？**

## B（適用場景）

**適用：** 決定要不要接某個外部系統（Confluence／Trello／Jira）；設計多來源 Agent 的資料來源優先序；處理兩個系統答案不一致；規劃固定憑證 vs 個別授權。

**不適用 / 注意：**
- ⚠️ 這是**盤點方法**而非工具。畫完地圖才決定自動化範圍，順序反了會接一堆用不到的系統。
- 🔴 「PDF 的 Source of Truth」欄位原文標的是**「視文件而定」**——不要一律把 PDF 當權威來源。

## R（操作步驟）

### 一、Knowledge Map 的欄位長什麼樣

| 資料來源 | 保存內容 | 更新頻率 | 主要用途 | Source of Truth |
|---|---|---|---|---|
| Google Sheets | 工單、銷售、營運數字 | 每日 | 精確查詢與計算 | 是 |
| Confluence | SOP、名詞定義、流程文件 | 不定期 | 正式知識與規範 | 是 |
| Trello / Jira | 任務、Owner、Deadline | 即時 | 專案狀態 | 是 |
| PDF | 政策、歷史報告、簡報 | 低 | 歷史文件與參考資料 | **視文件而定** |

### 二、🔑 衝突裁決表：兩個來源答案不一樣時

這是本篇最值得抄的一張表——多數知識庫盤點只做到「列出來源」，沒有裁決規則：

| 衝突情境 | 建議判斷方式 |
|---|---|
| PDF 與 Confluence 的政策定義不同 | 比較**文件狀態、生效日期與內容負責人**，以指定的正式版本為準 |
| Google Sheets 數字與簡報報告不同 | **優先保留原始結構化資料、查詢條件與查詢時間**，簡報作為解讀 |
| Trello / Jira 狀態與會議紀錄不同 | 以團隊指定的專案系統與**最後更新時間**為主要依據 |
| 無法判斷哪個來源較權威 | **並列差異、來源與更新時間，交由內容負責人確認**（不自行裁決） |

> 🔑 最後一列是關鍵：**設計上要保留「不裁決」這個選項**。強迫系統每次都給單一答案，等於逼它在資訊不足時猜。

### 三、要不要接這個系統？判準是工作流程

> 🔑 **這個資料來源是否真的回答了工作流程中不可缺少的一個問題？**

| 工作問題 | 需要的資料 | 來源 | 是否需要 Tool |
|---|---|---|---|
| KPI 怎麼定義？ | KPI 定義文件 | Confluence | 是 |
| 本月 KPI 是多少？ | 最新數據 | Google Sheets | 是 |
| 改善任務進度？ | Project Status | Trello | 是 |
| 去年分析結論？ | 歷史報告 | PDF | 已有 RAG |
| 員工電話是多少？ | **與工作流程無關** | HR System | **暫時不要接** |

最後一列示範了這個判準怎麼擋掉「反正接了也不吃虧」的擴張衝動。

### 四、憑證模式：固定 vs 個別授權

⚠️ **後端用誰的 Token，就繼承誰的權限**——這是接外部系統時最容易忽略的一句。

| 模式 | 說明 | 適合情境 |
|---|---|---|
| **固定憑證** | Backend 使用同一組低權限整合帳號，所有使用者共用相同資料範圍 | 個人專案、內部測試、固定 Board 或 Space |
| **個別授權** | 每位使用者用自己的帳號授權，依原本個人權限取得資料 | **不同使用者應看到不同內容**、多組織或 SaaS 產品 |

一律從**最小權限**開始。

### 五、Tool Layer 的價值：把系統差異包起來

> **讓資料留在最適合自己的系統，再透過 Tool Layer 提供一致的存取方式。**

| Tool | 負責的能力 |
|---|---|
| `query_google_sheets` | 查詢與計算結構化數據 |
| `search_documents` | 搜尋 PDF 與文件知識 |
| `search_confluence` | 搜尋正式定義、SOP 與知識頁面 |
| `get_project_status` | 查詢專案狀態、Owner 與 Deadline |

### 六、先畫地圖，再決定自動化範圍

實際盤點表只要四欄就夠開始：

| 工作資訊 | 現在去哪裡找 | Source of Truth | 是否需要即時 |
|---|---|---|---|
| KPI 定義 | Confluence | Confluence | 否 |
| KPI 數值 | Google Sheets | Google Sheets | **是** |
| 改善計畫 | Trello | Trello | **是** |
| 過去分析 | PDF 報告 | 報告 Archive | 否 |

## C（關鍵行動）

- [ ] 盤點表一定要有 **Source of Truth** 與 **更新頻率** 兩欄，缺了就只是資料清單不是知識地圖
- [ ] 每一組可能衝突的來源都先寫好裁決規則，並**保留「並列差異交負責人確認」這個出口**
- [ ] 決定接不接一個系統，只問「它是否回答了工作流程中不可缺少的問題」
- [ ] 選憑證模式前先確認「不同使用者是否應該看到不同內容」——答是就不能用固定憑證
- [ ] 接系統前先確認後端 Token 繼承了誰的權限

## 補充資料：企業 AI 知識庫的入庫與維護——給人看≠給 AI 看、入庫一律人審（2026-09-29 併入）

來源：韋惟珊〈把文件全丟給AI就好？企業建立知識庫前，先想清楚這6件事〉，數位時代〈一天一AI〉，2026-09-29，<https://www.bnext.com.tw/article/92404/enterprise-ai-knowledge-base-guide>。受訪者為叡揚資訊處長王瑞斌。🔴 **廠商觀點（叡揚資訊，知識管理廠商）**，文中未見產品推銷，偏觀念分享；以下只收與本條 T（誰負責、多久更新、衝突信誰）相關的增量。

1. **給人看的資料≠給 AI 看的資料**：合併儲存格、多維度交叉表、用顏色代表狀態的報表、流程圖色塊，人一眼看懂，AI 不一定能穩定判斷 → 為重要的分析維度、欄位定義、圖表關係與結論**補文字說明**，必要時轉成結構化資料；另建**部門術語／縮寫對照表**。作者實例：把財務部報帳規則放進 Gemini Notebook（原 NotebookLM）仍答錯，原因是標色邏輯只有財務部看得懂
2. **先鎖定單一任務建小知識庫**：不要一開始整理全公司數萬份資料；例如行銷只收產品說明、新聞稿、過往素材與主要客戶類型
3. **去識別化要「同一人全文同一代號」**：代碼化不一致會切斷前後文關係（隱私面見 [[chatgpt-claude-privacy-protection-9-checkpoints]]）；權限面的「人機身分對齊」見 [[enterprise-ai-permission-three-layers-governance]]
4. **過期偵測＋人審**（直接對應本條的「由誰負責、多久更新」）：AI 可從日常工作內容辨識尚未收錄的新知識、找出可能過期的資訊 → **通知權責單位** → 人工確認後才入庫或更新。所有準備入庫的內容都要經人審；AI 幻覺一旦混入知識庫又被拿來生成新內容，錯誤會自我累積——「不出半年」可能失去使用價值（**廠商經驗說法，無數據**）
5. **收斂三問**：AI 要執行什麼任務？現有文件格式 AI 讀得懂嗎？**誰負責審查與維護知識？**

（另一點「SOP 拆成步驟式學習地圖＋AI 出測驗留稽核紀錄」與本條 T 關聯較弱，僅記一句。）
