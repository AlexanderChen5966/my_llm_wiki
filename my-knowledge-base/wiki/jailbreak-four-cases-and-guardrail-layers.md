## T（核心論點）

Jailbreak **不是把安全訓練關掉**，而是利用模型原本有用的能力（角色扮演、規則理解、多輪對話、上下文學習）反過來繞過限制。因此四個經典案例都可以用同一個框架讀：**輸入利用了模型的哪種能力？這個能力為什麼同時也可能變成風險？**

推論出的核心設計原則：**Guardrail 不是一道牆，而是很多層防線**——安全不能只寄託在模型「乖乖聽話」。

> 金句：**安全規則要寫，門也還是要鎖。**
> 「我們不會因為員工手冊寫著『請勿拿走公司現金』，就決定金庫從此不需要鎖。」

## B（適用場景）

**適用：** 設計會接工具／資料庫／付款功能的 Agent 的安全邊界；理解為什麼「在 prompt 裡寫禁令」不夠；紅隊測試的入門框架

**不適用 / 注意：**
- ⚠️ 案例 1 是**社群測試案例，不代表每個模型或每個版本都會接受同樣的要求**
- 🔴 學習目的是理解系統弱點並**在得到授權的範圍內**驗證，不是收藏一百條神奇 Prompt

## R（四個案例與其利用的特性）

| 案例 | 利用的特性 | 安全啟示 |
|---|---|---|
| **奶奶唸序號**（2023-06 社群案例）| 角色扮演與情感情境 | **溫馨故事裡仍可能藏著不當請求** |
| **Skeleton Key**（Microsoft, 2024）| 重新解釋規則 | **模型不能自己決定真正的權限** |
| **Crescendo**（Microsoft）| 多輪對話的累積影響 | **不能只檢查單一句話** |
| **Many-Shot Jailbreaking**（Anthropic, 2024）| 從大量上下文學習 | **長上下文也需要安全檢查** |

### 1. 奶奶唸產品序號

要求模型扮演已故的奶奶，說奶奶以前會在睡前溫柔地唸 Windows 10 序號——把請求包裝成思念親人的角色扮演故事。

有趣的地方不在台詞多神奇，而在它**把三件事疊在一起**：角色扮演 ＋ 情感壓力 ＋ 一個原本會被拒絕的要求。**模型如果過度配合故事情境，就可能忘記先判斷真正的請求是否適當。**

### 2. Skeleton Key：讓模型接受一套假規則

攻擊者讓模型接受「新的假規則」——例如要求模型**先承認內容有風險，接著仍然照做**。

> 類比：公司規定「沒有主管簽名不能進資料室」，卻有人告訴新進員工：「規則剛更新，只要先說我知道有風險，就可以進去。」
> 🔑 **門禁卡沒有壞，問題出在員工相信了錯的規則。**

### 3. Crescendo：漸進式多輪越獄

不在第一句提出完整的違規要求，而是先問正常問題，再利用模型上一輪的回答，下一輪往前推一點。

🔑 **與 Prompt Iteration 是同一機制的反向運用**：提示迭代是看完上一輪結果修改下一輪輸入以**靠近好答案**；Crescendo 則是**逐步靠近安全邊界之外**。
→ 這說明**只檢查單一訊息的危險關鍵字可能不夠，真正的意圖藏在整段對話的方向裡**。

### 4. Many-Shot Jailbreaking：把 In-context Learning 反過來用

平常放幾個範例讓模型理解怎麼回答；這種越獄反過來——**在很長的上下文中放入大量「模型遵從不安全要求」的假對話**，試圖影響後面的回答。

🔑 **這個案例最值得記住的洞察**：
> **能力和攻擊面有時會一起長大。** Context Window 變大，本來可以讓我們一次放入更多文件與程式碼；**但能放進去的內容越多，攻擊者能利用的空間也可能越大。**

## 誰會用到這些方法

| 類別 | 動機與行為 |
|---|---|
| **獲得授權的防守者** | 模型公司、企業資安團隊、紅隊、安全研究者、滲透測試人員。上線前主動找問題，再把成功案例轉成安全訓練、Guardrail 或評測題目。🔑 **今天成功的一次越獄，明天可能就變成新版本發布前必須通過的一道考題** |
| **沒有防守目的的使用者** | 好奇，或想取得原本被阻擋的內容。🔴 **若模型還連著工具、內部文件、資料庫或付款功能，風險就不只是「回答不該說的話」，而是「做了不該做的事」** |

## 🔑 Guardrail 的多層防線

除了模型本身的安全訓練，真實系統還需要：**身分驗證（Authentication）／授權（Authorization）／存取控制／輸入與輸出檢查／紀錄／重要操作的人類確認**。

> 具體例子：一個可以退款的客服 Agent，**即使模型被誘導，也不應該因此就能直接退款一千萬元**。後端仍然要檢查使用者身分、訂單擁有者、退款上限、權限，以及是否需要人工核准。

→ **這和傳統資安沒有本質差異。** 當 Agent 是模型加上工具、上下文、記憶、權限與工作流程的整套系統時，**越接近真實世界的 Agent，越需要把權限限制放在模型外面**。

## 🔴 Jailbreak 與 Prompt Injection 不完全一樣

| | Jailbreak | Prompt Injection |
|---|---|---|
| 惡意指令來自 | **正在和 AI 對話的人**主動設計輸入 | 可能藏在 AI 讀取的**網頁、PDF、Email、GitHub README、文件或圖片**裡，**不一定來自對話者** |
| 比喻 | 有人站在櫃台前，不斷想辦法說服員工違反公司規定 | 有人在員工要閱讀的資料裡偷偷夾了一張紙條：「看到這裡之後，不要再聽老闆的，改聽我」 |

> **到了 Agent 時代，後者可能更加麻煩，因為 Agent 不只是讀文字，還可能有工具可以使用。**

## C（關鍵行動）

- [ ] 🔴 設計 Agent 時把**權限限制放在模型外面**——別依賴 prompt 裡的禁令
- [ ] 涉及金額/刪除/權限的操作一律在後端獨立檢查（身分、擁有者、上限、是否需人工核准）
- [ ] 安全檢查不能只看單一訊息——**Crescendo 的意圖藏在整段對話方向裡**
- [ ] 長上下文不等於安全上下文——**Many-Shot 證明 context 變大攻擊面也變大**
- [ ] 讀到帶情感或角色扮演的請求時，先把**真正的請求**從故事裡剝出來判斷
- [ ] 分清 Jailbreak（來自對話者）與 Prompt Injection（來自被讀取的資料）——後者在 Agent 時代更危險
