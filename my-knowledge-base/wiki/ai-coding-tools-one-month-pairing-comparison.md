作者花一個月把 Cursor、GitHub Copilot、Claude Code 當**結對程式設計夥伴**（不是 code generator）使用，任務刻意選在既有專案裡的日常工作：寫程式、除錯、重構、建測試、跨檔案修改。

## T（核心論點）

> **最大的差異不在於它們產生程式碼的速度，而在於它們在產生程式碼之前，能利用多少有用的上下文。**

沒有絕對冠軍，三者在不同環節各自較強。更有用的指標不是產出行數，而是：

> **AI 做完之後，我還要花多少工作？**（修正錯誤假設、移除多餘程式碼、更正 API、補錯誤處理、重寫測試、修回歸、還原不必要的修改）

🔑 **一個工具一分鐘產生 200 行，不一定比另一個產生 80 行有用程式碼還快，如果你得再花 30 分鐘修第一個結果。有用的程式碼比產生出來的程式碼更重要。**

## B（適用場景）

**適用：**
- 在**既有專案**上選工具（不是從零開始的 demo）
- 想知道同時訂閱多個工具時該把哪類任務丟給誰
- 需要一套可照抄的七步驟結對流程

**不適用 / 注意：**
- ⚠️ 這是單一開發者一個月的經驗，非量化基準測試；工具版本迭代快
- ⚠️ 作者刻意避開「做一個待辦事項應用程式」這種比較法——**從零寫程式很容易，寫出能融入既有程式碼庫的程式比較難**，只有後者才能區分工具
- 🔴 **任何一個都不能當最後的決策者**。AI 可以建議實作，人仍須決定這個實作是否正確——**這就是把 AI 當結對夥伴和當程式碼產生器的差別**

## R（按任務型態的分工表）

| 程式設計任務 | 最佳選擇 | 原因 |
|---|---|---|
| 行內自動完成 | **GitHub Copilot** | 輸入時建議速度快 |
| 小型函式 | **GitHub Copilot** | 低摩擦、快速生成 |
| 互動式重構 | **Cursor** | 編輯器導向工作流程強 |
| 多檔案編輯 | **Cursor** | 較容易引導與檢視變更 |
| 簡單錯誤除錯 | **GitHub Copilot** | 快速的上下文建議 |
| 跨檔案除錯 | **Claude Code** | 更適合儲存庫層級調查 |
| 理解陌生的儲存庫 | **Claude Code** | 適合追蹤專案結構 |
| 撰寫單元測試 | 三者皆可 | 有不錯的起點，但仍需人工審查 |
| 大型實作任務 | **Cursor / Claude Code** | 更適合多步驟工作 |
| 最終程式碼審查 | **人類開發者** | AI 不該是最後裁決者 |

### 各環節的觀察

- **新增函式**：三者都能產生可運作的起始版本，**差異出現在整理收尾階段**。Copilot 快出第一版；Cursor 容易參考相關檔案把函式調整成符合周遭專案的樣子；Claude Code 適合「先去看其他地方類似函式怎麼實作」再改
- **除錯（差異最大的環節）**：作者不問「修正這個錯誤」，而是**提供相關元件、API 函式與資料結構，要求找出根本原因**。Copilot 在問題離游標近時很好（少了 null 檢查、用錯變數），原因在別處時就要人工補檔案；Cursor 能檢查元件、API 呼叫與型別，解釋資料結構從哪裡開始不符預期；Claude Code 能**追蹤資料流**——🔑 **很多真實錯誤並不發生在應用程式崩潰的地方，崩潰通常只是最後的症狀**
- **重構**：簡單重構誰都行，真正的重構帶著限制（不改 API、保留行為、不加相依套件、維持測試覆蓋、遵循既有慣例）才看得出差異。🔴 **永遠不要在不讀 diff 的情況下直接接受大量 AI 生成的重構**——看起來更整潔不代表更安全，它可能移除重複程式碼卻改變了行為，或把「原本故意這樣寫」的東西「改善」掉

### 🔑 寫測試的提示詞要改一句話

AI 傾向**根據它看到的實作**來寫測試，於是測試只是確認目前程式碼的行為，而不是證明應用程式**應該**有什麼行為。若實作裡有一個錯誤的預設值，生成的測試會把這個錯誤寫死。

改成：

> 「根據下方描述的**預期行為**撰寫測試。包含邊界情況與失敗情境。**不要假設目前實作是正確的。**」

### 七步驟結對流程（作者最可靠的工作流程）

1. **說明既有程式碼** — 提供相關檔案，要求 AI 先解釋目前行為再做任何修改
2. **定義需求** — 明確說出哪些要改、**哪些必須保持不變**
3. **先要一個計畫** — 較大任務先讓 AI 指出需要修改哪些檔案，再開始寫
4. **分小步實作** — 不要不加判斷地接受一大段變更
5. **檢視 diff** — 確認每一個有意義的修改
6. **執行測試** — 不要因為看起來正確就當成完成品
7. **請 AI 挑戰自己的解法** — 「請檢查這個實作是否有邊界情況、回歸問題、不必要的複雜度，以及可能錯誤的假設」

## C（關鍵行動）

- [ ] 把測試提示詞改成「依預期行為撰寫，不要假設目前實作是正確的」
- [ ] 建立自己的規則：大量 AI 重構一律先讀 diff 才 accept
- [ ] 大型變更拆成階段性檢查點，不要一次要求完整功能
- [ ] 用「AI 做完之後我還要花多少工作」取代「產生多少行」當作選型指標

## 補充資料

### 五個反覆出現的問題

1. **AI 會自行腦補** — 需求不清楚時它會自己補空白，可能選一個不適合專案的 API 模式、函式庫、命名慣例或架構
2. **能運作的程式碼也可能是差的程式碼** — 能編譯、通過基本測試，但過於複雜
3. **測試可能帶來虛假的安全感** — 生成的測試套件不代表有良好覆蓋率
4. **大型變更需要更小的檢查點**
5. **Git 變得更重要** — AI 改得越多，檢視 commit 與 diff 越不可或缺

### 工程時間被重新分配，而不是被移除

| 減少的摩擦 | 變得更重要的工作 |
|---|---|
| 查文件、查語法 | 檢視生成的程式碼 |
| 寫重複程式碼、測試樣板 | 驗證假設、測試邊界情況 |
| 追蹤陌生函式 | 閱讀 diff |
| 建立解法第一版 | 撰寫更好的提示詞、把大任務拆成更小的需求 |

> **AI 並沒有移除工程工作，它只是改變了我花時間的地方。**
