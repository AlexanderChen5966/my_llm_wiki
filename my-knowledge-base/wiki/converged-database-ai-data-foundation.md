## T（核心論點）

> **融合式資料庫（converged database）不是指「能儲存多種資料模型」，而是指交易、最佳化器、一致性、治理、存取介面這五種保證能跨模型維持為一體。**

而它之所以突然和 RAG、AI Agent 一起被提起，是因為原文那句話：

> **AI did not create the multi-store consistency problem. It removed the tolerance for it.**
> （AI 並沒有創造多儲存系統的一致性問題，而是讓我們不再能容忍它）

## B（適用場景）

**適用：**
- 判斷「向量資料庫 / 圖資料庫要不要獨立拆出去」時的架構決策依據
- RAG 系統回答用到過時資料時的根因分析（不是模型問題，是同步管線問題）
- 理解 SQL:2016／SQL:2023 之後「為特定模型拆資料庫」的技術理由為何變弱

**不適用 / 注意：**
- 🔴 **立場必須先標清楚**：converged database 一詞由 Oracle 於 2020 年前後提出，原文作者 Rick Houlihan 是 Oracle Developers Blog 作者（且曾在 AWS 建立與教授 DynamoDB 單表設計）；中譯者也自行聲明「並非 Oracle 官方立場」。**JSON Relational Duality View 是 Oracle 專有功能，不是 SQL 標準**
- 🔴 **原文討論的是結構與保證，不是效能比較**——「融合式是否比較快」不是它要回答的問題，作者特別要求讀者把兩者分開
- ⚠️ 5 個測試是判定標準而非中立第三方基準；驗證腳本由原作者提供（5 份腳本、20 個斷言，公開執行）

## R（判定是否為「融合式」的 5 個測試）

「可以儲存多種模型」是儲存層的屬性；融合式指的是**其上層提供的保證**。這 5 個測試就是用來區分兩者的：

| 測試 | 通過時 | 不通過時 |
|---|---|---|
| **1. 單一交易邊界** | 關聯式插入、文件寫入、向量更新可放在同一個 ACID 交易，回滾整體一起復原 | 中途失敗留下「只更新一部分」的半完成狀態 |
| **2. 單一最佳化器** | 含圖／JSON／向量／關聯式的查詢只產生一個做過成本評估的執行計畫 | 應用程式得自己硬寫「先查圖庫再逐筆查向量庫」，沒有統一的查詢執行腦 |
| **3. 單一一致性模型** | 不論透過哪個 API，都成立「寫完立刻可讀」 | 模型間有同步管線，資料可見性會延遲 |
| **4. 單一治理領域** | 同一套權限、列級政策、稽核記錄套用到所有存取路徑 | SQL／文件 API／向量搜尋／圖各自在應用層重做權限，稽核分散 |
| **5. 存取介面共享** | SQL、MongoDB 相容 API、REST 只是同一引擎的不同投影，操作同一份資料 | 即使入口只有一個，後面串多個引擎時保證仍各自分離 |

🔑 **第 5 個測試最實用**——它專門擋掉「把多個引擎包在同一個 gateway 後面」這種偽融合：入口看似統一，內部的交易、一致性、權限保證仍然各自為政。

## C（關鍵行動）

- [ ] 手上的 RAG 若答錯，先確認**索引與實際資料是否同步**，再懷疑模型或 prompt
- [ ] 檢查權限是否在多條存取路徑上各自重做——這是最容易形成資料外洩缺口的地方
- [ ] 引用任何「融合式」宣稱時標明它是廠商用詞與其立場（本條目 B 段的三點）

## 補充資料

### 為什麼 AI 讓落差變得不可容忍

RAG 與 Agent 的搜尋**同時需要三種特性**，這組三件事是本篇最可複用的檢查表：

- **新鮮度** — 剛更新的內容要立刻反映在搜尋結果中。獨立向量資料庫在同步延遲期間，AI 看到的仍是舊資料
- **權限** — 「這個使用者能不能看這筆」要在搜尋過程中就生效。資料庫只有一個時定義一次就好
- **篩選條件** — 「這個客戶的、尚未解決的工單裡，與這問題相似的案件」這類查詢，需要向量相似搜尋與關聯式條件篩選結合

多個專用資料庫加同步管線（CDC 或批次）時，同一份資料在多處有副本，**副本未同步完成前搜尋端看到的仍是舊資料**。這不是設計瑕疵，而是複製式架構的固有特性，AI 出現之前就被指出過。

差別在於：使用者是人時，新品晚幾分鐘出現通常可容忍，而且**畫面前還有人的判斷可以介入**。但 RAG 與 Agent 每次回答都先取資料再交給 LLM——

🔴 **當索引與實際資料不同步時，LLM 不會因此「比較沒把握」。它會在依據舊事實的情況下，非常自信地答錯。** 原文把這狀態命名為 **State Vector Dissonance**（⚠️ 作者自創詞，非既有學術術語、無固定中文譯名）。

聊天機器人的使用者還可能發現它講錯；**會自動執行下單或退款的 Agent，這種延遲會直接變成商業風險**。

融合式的答案不是「更快的同步」而是**沒有同步管線**——只要是複製傳遞機制，再快都有時間差，不可能為零。

### 詞義從 consolidation 變成結構性特質的三個變化

1. **SQL 標準演進** — SQL:2016 加入 JSON 運算子；SQL:2023 新增原生 JSON 型別，並以 ISO/IEC 9075-16（**SQL/PGQ**, Property Graph Queries）把圖的模式比對納入標準 SQL。圖探索變成可以寫在 `FROM` 子句的語法，**為這些功能拆資料庫的技術理由就變弱了**
2. **AI 工作負載出現** — 同步延遲與資料落差不再能被接受（見上節）
3. **獨立學術支撐出現** — Stonebraker（Postgres 研究者）與 Pavlo（CMU）2024 SIGMOD Record《What Goes Around Comes Around… And Around…》檢視 20 年資料模型演變，結論包括：文件資料庫與 RDBMS 正朝「相互碰撞的軌道」前進、**向量資料庫本質上可視為「加上 ANN 特殊索引的文件導向 DBMS」，索引只是一項功能而非新架構的根基，不足以作為新產品類別的立論依據**

### 分化的另一半：文件 DB 為何從關聯式分出去

原文作者是「分出去那一方」的親身參與者，所以這節的論證特別完整：

- Stonebraker/Pavlo 的解釋是對**阻抗不匹配**的不滿——程式裡資料常是「客戶→訂單→明細」的巢狀形式，到關聯式 DB 得拆成多表、讀取時再 JOIN 組回來
- 作者自己的解釋是**工作負載實測後的設計判斷**，引 Amazon CTO Werner Vogels 公開的分析：約 **70%** 的關聯式操作只是依 key 取單筆、另約 **20%** 只是從單一表回傳多筆——**約九成操作不需要 JOIN**。存取模式如此明確時，不如預先把資料整理成最終要讀取的樣子（非正規化）

但非正規化帶來的「保留副本、同一筆資料重複存在」，正是正規化想移除的**冗餘性**。原文回溯 E. F. Codd 本人：

- **1969 研究報告** — 只有在查詢負載比其他操作重得多的環境下，強烈冗餘才合理
- **1970 論文** — 冗餘是一種交易：用「更多儲存空間與更新時間」換「查詢時間改善」

🔑 **冗餘從一開始就是理論中的一個調整旋鈕，會隨讀寫比例而改變**——文件資料庫的設計者調的其實是同一個旋鈕。

### JSON Relational Duality View（Oracle 專有）

Codd 同一份 1969 報告還提出**資料的「邏輯形態」與「物理儲存方式」分離**：邏輯模型應保持正規化，儲存表示可依工作負載選擇。但文件資料庫把兩者綁在一起——**保存的文件長相本身就等於你想讀取的答案長相**，所以存取模式改變時得連資料形狀一起重做。

Duality View（Oracle Database 23c 登場，延續到 2026-08 的 Oracle AI Database 26ai）把這個分離重做回來：用 `CREATE JSON RELATIONAL DUALITY VIEW` 把多張表宣告成一份巢狀 JSON，透過 MongoDB 相容文件 API 直接讀寫，**底層實體仍是正規化的表格列**——不是另存一份 JSON 副本，而是同一份資料同時是「文件」也是那些表列。更新衝突用文件上的 `etag` 偵測。

原文把這節總結為 **「建模領域，投影存取」（Model the domain. Project the access.）**：資料本體以正規化表設計，應用看到的樣子以檢視表投影宣告。🔑 **融合式不改變「文件該不該嵌入關聯資料沒有通用答案」這件事，它改變的是重新調整的成本**——如果文件只是正規化列的投影，存取模式改變時往往只需改「投影定義」，不必遷移整份資料。

### 五種模型的實作型態

不是替 5 種資料形態各建一個資料庫，而是**只儲存正規化的表**：

| 模型 | 實作方式 |
|---|---|
| 表（關聯式） | 直接使用正規化表，這就是儲存實體 |
| JSON（文件） | 表之上定義巢狀 JSON 檢視表（Duality View） |
| 圖 | 表之上增加節點與邊定義（`CREATE PROPERTY GRAPH`）|
| 向量 | 表中加入 `VECTOR` 型別欄位 |
| 空間 | 表中加入空間型別欄位 |

跨模型查詢因此能收斂成單一語句（例：沿推薦圖走 1–4 跳找相關客戶 → 未解決工單依向量距離排序 → 關聯式 JOIN，用 `GRAPH_TABLE` + `VECTOR_DISTANCE` 寫在同一個 `WITH` 查詢裡）。⚠️ 原文附註：能儲存多種模型的資料庫通常稱**多模型資料庫（multi-model）**，與融合式的比較原文有討論但未展開。
