三天合併：**Day 5（文件清理）＋ Day 6（Chunk 切分策略比較）＋ Day 7（中文斷詞與搜尋基準）**。與 [[rag-retrieval-augmented-generation]] 是同一條線的不同段落——那邊是四步 pipeline 的全景與企業落地，這邊是**繁體中文語料在 Parse → Chunk → 檢索三步各自會壞在哪裡**，而且每個結論都附實測輸出。

## T（核心論點）

> **繁體中文的 RAG 品質在餵給模型之前就已經決定了大半——而三個前處理步驟各有一個「看起來乾淨、其實把線索弄壞了」的陷阱。**

貫穿三天的方法論同樣值得單獨記下：**每個技術選擇都要能被實驗結果驗證，所以先把最笨的做法做出來當地板。** 之後的 TF-IDF、BM25、向量搜尋、Hybrid Search 都要回答同一個問題——**你比最簡單的做法好多少？**

## B（適用場景）

**適用：**
- 自建繁中知識庫檢索（本知識庫本身即為此類：Markdown + YAML frontmatter + 技術識別字混排）
- 判斷「清理／切分／斷詞」三個步驟各自該做多少、不該做什麼
- 建立可比較的檢索基準，而不是靠感覺說「向量搜尋比較好」

**不適用 / 注意：**
- 實作為 Python 3.11 + `python-frontmatter` + jieba 0.42.1；語料僅九份文件、17 個 Chunk（作者刻意選小規模：**先求可核對，再求規模**）
- ⚠️ Day 6 的大小單位是**字元數不是 Token**，作者明說這是簡化，等接上 Embedding 再換算
- ⚠️ 手工維護詞典**不是可以無限擴張的做法**，只是為了先把基準建起來

## R（三步各自的原則與實測）

### Day 5：清理不是把文章改得漂亮

原則：**移除不影響語意的雜訊，同時保留未來搜尋與引用需要的資訊。** 若為了「乾淨」直接刪掉所有標點、英文、數字或程式碼，會失去技術文件最重要的線索——`SecurityFilterChain`、`spring.security.user.name`、`HTTP 401`、版本號往往正是使用者查詢時最關鍵的內容。

**做**（不改變原始語意的格式問題）：統一換行符號、移除 BOM、刪段落結尾多餘空白、壓縮過多空白行，以及兩個繁中特有雜訊：

- **全形空白 U+3000** — 常混在行尾，只針對半形空白的規則抓不到
- **全形英數字** — 從 PDF 或舊網頁複製常出現「ＨＴＴＰ　４０１」，不轉成「HTTP 401」則關鍵字搜尋永遠比對不到

**不做**（三條界線，本篇最值得記的部分）：

1. 🔴 **全形標點不轉換**——「，」「。」「？」是繁體中文的正規標點，不是雜訊；換成半形等於改寫作者的文字
2. 🔴 **不用 NFKC 正規化**——它能一次轉換所有全形字元，但影響範圍過大（連上標、分數都會被改寫），**套用在程式碼上更可能直接改壞範例**。只轉「全形英數字＋全形空白」這個明確安全的子集
3. 🔴 **程式碼區塊完整保留**——不只空白與縮排維持原樣，**全形轉換也不進入程式碼區塊**：字串裡的全形字元究竟是不是雜訊，不是清理程式可以代替作者判斷的

重複文件、過期版本、HTML 標籤、內容錯誤一律**今天不處理**：重複與版本要靠 Metadata 判斷、HTML 要看資料來源、正確性需人工或另建驗證流程。策略是「先做安全的格式整理，保留原始檔案」。

⚠️ **一個具體的坑**：檔案開頭帶 BOM 而 `frontmatter.load()` 用預設 UTF-8 讀取時，**整份 Front Matter 會無法被辨識**——Metadata 變空、`---` 區塊整段留在正文裡，而且**過程中不會出現任何錯誤訊息**。解法是讀檔指定 `encoding="utf-8-sig"`（讀沒有 BOM 的檔案也完全正常），另在清理函式內用 `lstrip("﻿")` 做第二層防禦。

`Document` 同時保存 Metadata、清理後正文與**原始檔案路徑**——後面 Chunk 要能一路連回原始文件產生引用連結，若最初只留清理後的文字，之後才發現需要顯示來源就得重新設計資料流。

### Day 6：四種切分策略的實測性格

為什麼不能把整份文件當搜尋單位：① Context 有容量與品質限制 ② **搜尋粒度影響排序品質**（長文件只有一段相關，以整份計分時訊號被稀釋）③ **引用也需要粒度**——「答案在這份文件裡」和「答案在這一段」是完全不同的體驗。

反過來切得越碎越難被獨立理解（「它會影響搜尋結果」單獨成 Chunk 時，沒人知道「它」是什麼）。

九份文件的實測：

```
fixed(300)               chunks= 15  avg= 245  min=  1  max= 300
fixed(300, overlap=50)   chunks= 20  avg= 207  min= 10  max= 300
paragraph                chunks= 38  avg=  95  min= 11  max= 461
structured(400)          chunks= 17  avg= 217  min= 13  max= 461
```

🔑 **統計數字只是性格，真正的問題要看切分邊界**：

- **固定長度**把「登入」切成兩半（前段收尾「以帳號密碼登」、後段開頭「入為例」）——**之後無論關鍵字搜尋還是斷詞，都無法在任何一個片段找到完整的「登入」**；Java 程式碼區塊也被切成兩段，各自帶著未閉合的圍欄；`min=1` 是某份文件剛好比 300 的倍數多一個字，最後一個 Chunk 只剩一個句號。🔴 **它的問題不是「偶爾切壞」，而是對內容結構完全沒有概念**
- **重疊切分**讓邊界句子有機會在下一片段完整出現，代價是片段變多、內容重複，且**仍然會切壞程式碼區塊，只是壞的位置不同**
- **段落切分**完整性最好但長度失控：平均只有 95 字，`min=11` 那個 Chunk 是「# Token 是什麼」——一行單獨成塊的標題，對搜尋幾乎沒價值
- **structured(400)**（段落優先合併、超過上限的長段落再按句子打包）平均回到 217；`max=461` 是那個 Java 程式碼區塊，超過上限但完整保留——**這是設計上的取捨而不是缺陷**

繁中的句子邊界由全形「。！？；」決定（`(?<=[。！？；])`），與英文半形句點加空白不同。

⚠️ structured 也不完美：長段落觸發句子打包時，**前面的標題被單獨排擠成一個只有 17 字的 Chunk**。「標題該和內文黏在一起／Chunk 該不該記住自己的標題路徑」留到 Day 21 設計引用機制時處理。

🔑 本篇最誠實的一句：今天的比較**只涵蓋「結構完整性」**——還沒有任何證據說 structured(400) 的搜尋品質比較好，400 也只是合理起點而非結論。固定長度與重疊並沒有被淘汰（實作簡單、行為可預期），等有評測集之後所有策略要用同一組問題重新受檢。**到時候比的不是誰切得漂亮，而是誰讓正確的內容更容易被找到。**

### Day 7：jieba 預設詞典切繁中的災難

子字串比對對精確識別字很有效（查 `SecurityFilterChain` 直接命中 3 個 Chunk），但使用者會問問題——「如何設定密碼雜湊」這個完整字串不會一字不差出現在任何文件裡，命中數是 **0**。

jieba **預設詞典**（以簡體與通用語料為主）的實際輸出：

```
向量資料庫入門        → 向量 / 資料 / 庫入門
關鍵字搜尋和語意搜尋…  → 關鍵 / 字 / 搜 / 尋和語 / 意 / 搜尋有 / 什麼 / 差別
中文斷詞會影響搜尋品質 → 中文 / 斷 / 詞會 / 影響 / 搜尋品 / 質
```

🔴 **「搜尋」被攔腰切開，組出「尋和語」「搜尋有」這種不存在的詞**——因為「搜尋」「品質」這些繁體用語根本不在預設詞典裡，只能靠統計硬猜。載入 20 個詞的專案詞典（`jieba.load_userdict()`）後才正常：「向量資料庫 / 入門」「中文 / 斷詞 / 會 / 影響 / 搜尋 / 品質」。

✅ **值得慶幸**：英文識別字毫髮無傷——`SecurityFilterChain`、`CSRF`、`HTTP`、`401` 都保持完整，因為 jieba 對連續英數字元不做切分。對技術文件來說這保住了最重要的一類查詢線索。

更完整的選項是 jieba 繁體詞典 `dict.txt.big` 與中研院 CKIP 系列模型，但「哪個斷詞方案讓搜尋品質更好」是**應該用數據回答的問題**，留給評測集。

三個實作決定：① `tokenize()` **同時用於索引與查詢**——文件與查詢必須用同一套切法，否則同一個詞在兩邊被切成不同樣子，永遠比對不上 ② 索引沿用 Chunk 識別碼，結果天生可追溯 ③ **計分刻意不加任何權重**（分數＝查詢詞中有幾個出現在這個 Chunk），因為基準的意義就在誠實記錄「什麼都不做會怎樣」。

## C（關鍵行動）

- [ ] 清理規則逐條回答兩個問題：**它要解決什麼問題？它會不會改變原始語意？**（NFKC 與全形標點會，所以不用）
- [ ] 讀 Markdown 一律 `encoding="utf-8-sig"`——BOM 讓 frontmatter 靜默失效，**不會有錯誤訊息**
- [ ] 索引與查詢必須用同一個 tokenize 函式；繁中一定要先確認預設詞典有沒有把常用詞切壞

## 補充資料

### 四種問題類型的基準實測：一好三壞

用四種使用者問題各出一題（Top-3）：

- ✅ **概念理解**「什麼是 CSRF 攻擊？」答對——CSRF 是整個語料庫的罕見詞，一命中就把正解推上第一
- 🟡 **技術比較**「關鍵字搜尋和語意搜尋有什麼差別？」勉強及格——第一名確實是 Embedding 文件，但**連「和」都貢獻了一分**
- 🔴 **操作查詢**「如何設定密碼雜湊？」露餡——真正的答案（PasswordEncoder 段落）只排第三，且與第一二名**同分**：命中「密碼雜湊」得一分，命中「設定」或「如何」也得一分，同分後按識別碼字母序排，正解被排到最後
- 🔴 **問題排查**「HTTP 401 是什麼意思」全面潰敗——真正含 HTTP 401 的兩個 Chunk 排第四與第六，Top-3 一個都沒有。第一名是文字清理文件，靠「什麼」「意思」「是」三個到處都有的詞拿下最高分

⚠️ **一個意想不到的細節**：正解 Chunk 原文是「權限不足則是 HTTP 403」，**「則是」被斷成一個詞，所以它連「是」這一分都沒拿到**——斷詞的細節會從意想不到的方向影響結果。

### 失敗模式收斂成一句話

🔑 **所有詞都值一分。** 「是」出現在 17 個 Chunk 的絕大多數，「401」只出現在兩個，但計分完全等值。這立刻指向兩個直覺：

- 一個詞出現在越少文件裡，辨識力應該越高 → **文件頻率（Document Frequency）**
- 一個詞在某 Chunk 出現越頻繁，關係應該越深 → **詞頻（Term Frequency）**

把兩個直覺變成公式就是 TF-IDF（Day 8）。**地板鋪好了，接下來才輪得到樓層。**

### 對本知識庫的直接對照

本庫的 raw/ 素材正是「繁中正文 + 大量英文技術識別字 + 程式碼區塊」的混合型，且已用 YAML frontmatter 保存 metadata——與本系列的資料契約幾乎一致。三個可直接套用的判準：全形標點不動、程式碼區塊視為原子單位、繁中檢索前先確認斷詞。（本庫目前採 LLM Wiki 路線而非 RAG，理由見 [[llm-wiki-over-rag-claude-code]] 與 [[hand-coding-agent-file-tools]] 收錄的「刻意不做 RAG」論證）
