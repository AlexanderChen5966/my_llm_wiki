## T（核心論點）

Anthropic 官方開發者文件《Prompting Claude Opus 5》的調校建議。核心轉變：**Opus 5 已會主動驗證與修正產出**，所以「完成後再檢查一次」「交給子代理複查」這類舊習慣不一定有幫助，反而增加工具呼叫與 token。提示詞該用在**具體規則**上——回覆多長、何時更新進度、任務範圍到哪、哪些工作才需要子代理。**最關鍵的技術提醒：不要為了省 token 關閉 thinking，改用較低 effort。**

## B（適用場景）

**適用：** 透過 API 或系統提示整合 Opus 5 的開發者；從 Opus 4.8 升級要調整既有提示詞的團隊

**不適用 / 注意：**
- 官方明說**不代表每個產品都該原封不動套用**——回覆長度、子代理數量、驗證流程仍要看任務類型與產品介面，**應用實際任務重新測試**
- 主要寫給 API/系統提示整合者，一般 Claude Code 使用者部分適用

## R（8 個重點）

### 🔴 8. 不要隨便關閉 thinking（最重要的技術警告）

Opus 5 **預設開啟 thinking**，且只有在 `high` 或更低 effort 下才能關閉。關閉後模型偶爾會出現兩種異常輸出：

| 異常 | 後果 |
|---|---|
| **工具呼叫被寫成一般文字** | 原本該以結構化格式送出的工具呼叫，被直接寫進回覆文字裡——**代表工具其實沒有被執行**；多輪代理工作中這段文字還留在對話紀錄，影響後續回合。需頻繁使用搜尋等工具的任務較易發生 |
| **回覆出現內部 XML 標籤** | 可見回覆中輸出 `<thinking>` 等內部標籤。⚠️ **若系統提示裡有「不要思考」「不要推理」等規則，建議移除**——這類指令反而增加標籤外洩機率 |

> **官方建議：不要為了省 token 直接關閉 thinking，而是保留 thinking、改用較低的 effort 控制成本。多數任務下，開啟 thinking 的 `low` effort 在相近成本下通常比關閉 thinking 更穩定。**

若整合環境仍必須關閉：
```
使用工具前，你可以先說一句簡短說明。若沒有工具能完成使用者的要求，請直接說明，不要猜測。回覆中不得包含內部或系統 XML 標籤。
```

### 1. 別直接沿用 Opus 4.8 的設定

Opus 5 更擅長跨多檔案開發、重構、找 bug，**在較低 effort 下也能維持不錯表現**。

- 沿用前代 `effort` 預設值的團隊，**應重新比較不同設定的品質／成本／回應時間**
- 過去習慣固定用高 effort 的，該重測 `low`／`medium` 是否已足夠；只有特別複雜的程式任務才提到 `xhigh`
- ⚠️ 舉例：code review 要求「只報高嚴重度問題」，Opus 5 **可能真的只列出少數問題**——官方建議先讓它列出所有發現，再由後續流程決定要處理哪些
- 過去為視覺任務加的提示補強，可重新確認是否仍必要

### 2. 設定回覆篇幅

> ⚠️ **關鍵澄清：`effort` 控制的是模型的思考量，不是畫面上顯示的回答長度。**
> 把 effort 從 high 調到 medium/low 會減少思考 token 與回應時間，但**不保證回覆變短**。

Opus 5 預設給使用者看的回覆通常比先前 Opus 更長。要它少寫，得**直接在提示詞說明篇幅**：
```
回覆請保持聚焦、簡短、精煉。免責說明與注意事項請簡要帶過，主要篇幅用來回答核心問題。
若使用者要求解釋，除非明確要求深入說明，否則先提供高層次摘要。
```
系統提示很長時，可在**接近結尾處**再加一句短提醒，避免篇幅要求被前面規則淹沒：`請讓輸出適度維持精簡。`

### 3. 設定任務進行中的回報規則

Opus 5 用工具時傾向主動說明接下來要做什麼——沒規範的話，使用者會先看到一串過程說明才看到結果。

```
第一次使用工具前，用一句話說明接下來要做什麼。工作期間，只有在發現重要資訊或改變方向時才提供簡短更新。
完成時，第一句先說明結果，再補充需要的細節。
```
> 重點不是禁止回報，是**定義回報的時機與篇幅**。官方也提醒：**提供你希望看到的正面範例，通常比列出一長串禁止事項更有效。**

### 4. 報告和文件要「另外」控制篇幅

寫入檔案的報告、Markdown 文件與摘要，篇幅也可能更長。**這要另外加規則，不是只在對話提示詞要求「簡短」**：
```
書面文件的長度應符合任務需要：完整涵蓋必要內容，但不要用填充段落、重複摘要或制式內容湊篇幅。
```

### 5. 移除重複驗證，限制任務範圍

Opus 5 會自行驗證產出。仍要求「每個非簡單任務都要最後驗證」或「另派子代理複查」→ 增加不必要的工具呼叫與 token，**卻不一定改善結果**。

另一個問題是**任務範圍擴大**（模型加入沒被要求的步驟、自行改寫目標）：
```
請依使用者要求，在原定範圍內交付成果。一般的例行判斷請自行處理；只有對需求的不同理解會導致實質不同的工作時，才向使用者確認。
若你認為需求有誤，或有更好的做法，請用一句話說明，但仍依原要求繼續執行；不要自行縮小、擴大或改變任務。
請完整完成任務，但不要進行明顯超出要求範圍的動作。
```

### 6. 設定子代理的啟動條件

```
只有大型、可獨立且可平行處理的工作才委派子代理。不要將可在少量工具呼叫內完成的工作外包，
也不要用子代理複查自己的結果。若一個子代理能完成任務，就不要建立多個。
```
> 除了提示詞，**對成本敏感的系統也應在工具層設定子代理數量上限**。

### 7. 少加「再檢查」指令，只在必要時說明更正

Opus 5 本身就會發現並修正錯誤，反覆要求「再三確認」與模型原有檢查行為重疊。
另一差異：Opus 5 **更常主動說明自己修正了前面的說法**——面向一般使用者的產品裡，每個小修正都解釋會讓對話冗長。

```
只有當先前的錯誤會影響使用者的程式碼、結論或決策時，才更正先前的說法。更正時，請直接且簡短地說明，然後繼續完成任務。
若錯誤不影響使用者，直接修正即可，不需要另外提起。
```

## C（關鍵行動）

- [ ] **檢查有沒有為了省 token 關掉 thinking**——改成保留 thinking + 降 effort
- [ ] 移除系統提示裡的「不要思考」「不要推理」規則（會增加 XML 標籤外洩）
- [ ] 從 Opus 4.8 升級時**重測 effort 預設值**，別直接沿用
- [ ] 刪掉「最後驗證」「子代理複查」這類重複驗證指令
- [ ] 分開設定三種篇幅：對話回覆／進度回報／**寫入檔案的文件**
- [ ] 子代理除了提示詞規範，**在工具層設數量上限**
- [ ] 調整說明風格時**給正面範例**，別列一長串禁止事項

## 補充資料：effort 階梯與成本定位（2026-08-03 併入）

來源：TechNews（徐知誼，2026-07-29）〈我們知道 Claude Opus 5 很厲害了，怎麼用才划算？〉（https://technews.tw/2026/07/29/claude-opus-5/ ）。
⚠️ **該篇提示詞部分與本條目同源（皆出自官方《Prompting Claude Opus 5》），已飽和不重複**。以下只收本條目原本沒有的三項。

### ① effort 的完整五階與起步建議

本條目原文只提到 `low`／`medium`／`high`／`xhigh` 的相對關係，補上完整階梯與操作細節：

| 項目 | 內容 |
|---|---|
| 完整階層（低→高） | `low` → `medium` → `high` → `xhigh` → `max` |
| **建議起點** | **預設 `high`**，再依自己的評測往兩邊調 |
| 往下調的時機 | 品質不變時多用 `low`／`medium` 省成本 |
| 往上調的時機 | 吃重的程式與代理工作才升到 `xhigh` |
| 🔴 **跑 `xhigh` / `max` 時必做** | **把 `max_tokens` 設大**——否則沒留足夠空間給思考與工具呼叫 |

### ② 停用 thinking 在 `xhigh` / `max` 會直接回 400

本條目已記載「只有在 `high` 或更低 effort 下才能關閉 thinking」，補上失敗行為與版本落差：

- 在 `xhigh` 或 `max` 時設定停用思考 → **直接回傳 400 錯誤**（不是靜默忽略）
- 這是**相較於 Opus 4.8 的一項重大變更**——4.8 時代的整合程式若硬寫「停用 thinking」，升級後會在高 effort 路徑上直接壞掉

📌 Opus 5.5（2026-09-23）起 thinking 完全不能設為關閉，tool_choice any 或指定工具也會回錯誤，詳見 [[claude-opus-5-5-release-notes]]。

### ③ 成本定位與 Thariq 的一句話原則

- **成本定位**：Anthropic 宣稱 Opus 5 逼近旗艦 Fable 5 的智慧水準，但**只需一半成本**（⚠️ 官方宣稱，未見第三方複現）
- **官方工程師 Thariq 的原則**：過去用逐步腳本的方式是「**過度約束**」Claude，如今應「**給判斷力、別給規則**」，並**刪掉互相矛盾的舊指示**（例：同時要求「詳盡」又「簡短」）
  → 這句是本條目 8 個重點背後的共同心法，也與 [[claude-md-optimization-techniques]] 的「過度約束（overconstraining）是病因」完全對得上
- **心態轉換**：把 Opus 5 當「**勤奮的代理人**」而非聊天機器人——給明確目標，它會自我檢查、反覆更新；但**長時間自動執行時仍要有人在旁把關**

## 🔴 調和：Fable 5 說「派 verifier 子代理更好」、Opus 5 說「不要用子代理複查」（2026-09-03）

兩份都是 2026 當代官方一手文件，先前零交叉連結，是本庫唯一「還沒有答案」的真矛盾。拆開兩邊的原文後，**衝突其實不在模型家族，而在「驗證的對象不同」**：

| | Opus 5 反對的 | Fable 5 建議的 |
|---|---|---|
| 原文 | 「**也不要用子代理複查自己的結果**」；Opus 5 不提醒也會自己檢查 → 重複驗證浪費時間與 token | 「長流程中**每隔一段間隔**，派一個 **context 全新**的子代理**對照原始規格**驗證，比主模型自我批評效果更好」 |
| 驗證對象 | **剛剛那一次的產出**（redundant self-check）| **整段長流程有沒有偏離原始規格**（drift detection）|
| 用什麼當基準 | 無外部基準，等於再問一次同一個腦袋 | 🔑 **原始規格**——而且刻意用**全新 context**，避免繼承已經跑偏的脈絡 |
| 解決什麼問題 | （解決不了什麼，所以官方要求刪掉）| 長時序任務的**漸進漂移**——單步都合理、累積起來離題 |

> 🔑 **調和後的判準：看你要驗的是「這一步對不對」還是「整段有沒有走偏」。**
> - 「這一步對不對」→ **不要派子代理**。Opus 5 自己會檢查，多一層只是重複；官方遷移指南要求「**刪除，而不是改寫**」這類指令。
> - 「整段有沒有偏離原始規格」→ **值得派 fresh-context verifier**，但它的基準必須是**原始規格文件**，不是前一個子代理的輸出摘要。

**次要的模型家族差異**（成立但不是主因）：Opus 5 放著不管也會主動委派，所以提示詞該給的是**反方向的上限**（`子代理的啟動最多以 3 個為限`）；Fable 5 的使用指南則把子代理與記憶並列為要主動搭建的東西。

⚠️ **兩邊都同意的一件事**：對成本敏感的系統應在**工具層**設子代理數量上限，而不是只靠提示詞約束。
