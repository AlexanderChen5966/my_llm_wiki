## T（核心論點）

RAG 答錯時最直覺的三個動作（換更大模型、調高 Top-K、補幾句 Prompt）往往修錯層：同一句「回答錯了」背後可能是完全不同的故障——正解沒進候選池、證據閘門錯殺、模型拿到正解卻拒答、引用格式不合法，或答案只漏了一個關鍵條件。**修錯層不只沒用，還會製造新的變因**。`FailureDiagnosis` 依資料流順序判定（retrieval → evidence_gate → output_validation → generation → refusal → answer_content → success），順序很重要：候選池沒有相關文件時，後面模型再強也沒有證據可用。修復順序應**由上游到下游**：先保證資料與 Chunk 正確，再看候選召回與排序，之後校準 Evidence Gate，最後才調生成與輸出；且要用**控制變因的單變量實驗**定位真正原因，同時檢查交互作用（Chunk 變大會消耗更多 Context、Top-K 增加可能讓原本有效的 Prompt 漏列引用）。

## B（適用場景）

**適用：** 建立失敗追蹤（Failure Trace）機制定位 RAG 錯誤發生的層級；設計單變量實驗矩陣（固定資料/模型/評測，只改一個因素）；判斷 Chunk、Top-K、Prompt、拒答門檻、標註各自該負的責任；決定何時該停止調參（標籤爭議、資料缺漏、樣本太少時）。

**不適用 / 注意：** 自動診斷只能指出「結果和標籤不一致」，不能自動判定標籤真偽——最後仍需第二位標註者仲裁；控制變因只能先定位主效果，RAG 各層並非完全獨立，確認單項影響後仍需少量組合實驗檢查交互作用。

## R（操作步驟）

1. **先定位失敗層**：`diagnose` 依序檢查候選池是否命中標籤 → 證據閘門是否錯殺 → 輸出驗證是否有誤 → 模型是否誤判 insufficient → 拒答是否放過無答案題 → reference_coverage 是否達標，回傳最早出現問題的層級。
2. **Chunk 失敗兩極**：過碎（孤兒標題被 BM25 長度正規化放大成假命中，修法是讓標題與正文一起切分或設最小內容長度）；過大（同時談多主題，檢索容易命中但模型拿到大量不相關內容）——須透過檢索與回答評測共同驗證，不能只看平均字數。
3. **Top-K 失敗兩極**：太小（正確證據被截掉，回答不完整或拒答）；太大（干擾來源增加、Token 成本增加、模型可能過度引用）。`context_ablation.py` 固定同一問題，分別以 1/3/5 個來源執行比較，比一次改多個變因更有資訊量。
4. **Prompt/輸出驗證失敗**：如 Day 26 的 a01 案例，正解在候選池第一名、證據閘門通過、事實合理，但引用欄位不一致被 Fail Closed——調 Chunk 或 Top-K 對此完全無用，正確修法是加強格式示例、服務端結構化輸出、有上限的驗證後修復，或換更能遵守 Schema 的模型。
5. **拒答失敗（Evidence Gate False Positive）**：如 Day 22 的 FastAPI 問題以 0.144 分穿過 0.10 門檻——不代表最後一定幻覺（模型仍可能自行判斷 insufficient），修法應是擴充近域無答案題與評估第二層模型判斷，而非追著一題調常數。
6. **標註失敗**：多個獨立方法（BM25/E5/Cross-encoder）一致選到與標籤不同的文件時，可能是標籤本身有爭議，需第二位標註者仲裁，評測程式本身不能決定標籤真偽。
7. **建立修復對照表**：五種症狀（正解不在候選池／正解在池中但被拒答／回答引用不存在來源／引用正確但漏要點／所有方法都偏離標籤）各自對應優先證據、應先檢查項目與不該先做的事。
8. **失敗追蹤要保存完整上下文**：原問題與改寫查詢、資料與索引版本、候選 Chunk 與各階段分數、去重後文件排名、證據閘門理由、Context 實際內容、Prompt 版本、模型原始輸出、解析錯誤與最終狀態，以 Trace ID 串起 API/Retrieval/LLM 呼叫。
9. **單變量實驗矩陣**：固定資料、模型與評測，每次只改一個因素（Baseline/C1 改 Chunk/K1 K2 改 Top-K/P1 改 Prompt），每個版本同時看檢索、回答、引用、拒答與延遲，保存逐題差異避免總平均掩蓋退步。
10. **修復順序由上游到下游**：先保證資料與 Chunk 正確，再看候選召回與排序，之後校準 Evidence Gate，最後才調生成與輸出；若標籤爭議、資料缺漏或樣本太少導致的失敗，繼續調參只會對評測集過度擬合，應新增或仲裁資料。

## C（關鍵行動）

- [ ] 建立 FailureDiagnosis 依資料流順序判定失敗層級，不要看到「答錯」就直接調 Prompt 或 Top-K
- [ ] 保存完整 Trace（候選分數、證據閘門理由、Prompt 版本、驗證錯誤等），讓每次執行可重播
- [ ] 用單變量實驗矩陣（固定資料/模型/評測，每次只改一個因素）定位真正原因，再檢查交互作用
- [ ] 修復順序由上游到下游：資料/Chunk → 候選召回排序 → Evidence Gate → 生成/輸出
- [ ] 遇到標籤爭議或樣本過少導致的失敗時停止調參，改為新增或仲裁資料，避免對評測集過度擬合
