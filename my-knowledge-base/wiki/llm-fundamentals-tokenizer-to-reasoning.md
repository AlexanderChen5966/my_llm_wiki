整合 iThome 系列 Day 01–04（Day 01 為引言，貢獻有限，併入背景一句話；Day 02–04 是連續論證：**Transformer 怎麼猜下一個字 → GPT 三代怎麼把任務搬進 Context → CoT 怎麼給模型草稿紙**）。

## T（核心論點）

三篇構成一條連貫的原理鏈：**Transformer 每次只是在猜下一個 Token 的機率分布**（Day 02）；**GPT 三代真正改變的不是規模，而是「任務放在哪裡」**——從模型外部的微調流程，逐漸搬進使用者提供的 Context（Day 03）；**Chain-of-Thought 不是新架構，只是讓模型在給答案前多生成一些「計算草稿紙」Token**（Day 04）。三者疊起來的結論：**LLM 的每一層進化，都是把「怎麼做」的決定權從訓練階段移向推論階段**。

## B（適用場景）

**適用：** 想建立 LLM 運作的正確心智模型（不是玄學也不是純數學）；判斷「這個提示技巧為什麼有效」時需要底層原理支撐

**不適用 / 注意：**
- 這是**原理教育**角度，與知識庫既有 [[chain-of-thought-reasoning]]（提示技巧角度）互補而非重疊
- Day 04 明確提醒：**可見的推理軌跡不等於真正透明**——CoT 本身也是模型生成的文字，可能不完全反映真實計算過程

## R（三層論證）

### 一、Transformer：文字如何變成「猜下一個字」（Day 02）

**輸入流程**：`文字 → Token → Token ID → Embedding`

- **Tokenizer** 把文字切成 Token，不一定等於完整單字（`transformer` 可能拆成 `transform` + `er`）——這是為了在「詞彙表膨脹」與「句子太長」之間取平衡，**像樂高積木：準備可反覆組合的零件，不替每種情況做專用模具**
- **Token ID 只是置物櫃號碼**，本身沒有語意——編號 8000 不比 2000 聰明
- **Attention 用 Query/Key/Value 類比搜尋引擎**：Query（我想找什麼）、Key（哪些可能相關）、Value（真正要取回的內容）
- 🔑 **模型不是一次寫完整句話**：每次替整個詞彙表的所有 Token 計算 **Logits**（分數），再經 Temperature/Top-k/Softmax 轉成機率分布，抽出一個接回前文，**重複「選 Token → 接回前文 → 再預測」**——你看到的一整段回答，是這個步驟快速重複的結果

**Top-k 與 Temperature 的常見誤解澄清**：
- **Top-k** 不是叫模型「只認識 k 個字」——模型仍先給整個詞彙表打分數，只是取樣前縮短候選名單
- **Temperature 不是模型心情**——只改變取樣時的機率分布形狀，**不會替模型增加知識，也不是關掉幻覺的旋鈕**

### 二、GPT 三代：任務逐漸從訓練搬進 Context（Day 03）

| 模型 | 規模 | 資料 | 任務適應方式 | 記憶口訣 |
|---|---|---|---|---|
| **GPT-1**（2018）| 1.17 億參數 | BooksCorpus | 預訓練 + **微調**（更新參數）| 先讀書，再準備特定考試 |
| **GPT-2**（2019）| 15 億參數 | WebText（Reddit 篩選連結）| **Zero-shot**（不微調，靠提示喚起訓練中學過的條件結構）| 從大量文字認出任務形式 |
| **GPT-3**（2020）| 1,750 億參數 | 更大更多元語料 | **Zero/One/Few-shot**（In-context Learning，參數不變）| 指令與範例直接放進 Context |

🔑 **In-context Learning vs Fine-tuning 的本質差異**：
> **Fine-tuning**：真的去上課，模型內部參數被修改
> **In-context Learning**：考試前拿到幾題範例，暫時照著規則作答——**對話結束、Context 消失，那張便利貼也跟著消失**

**Zero-shot 不是無中生有**：「提示喚起了模型在訓練資料中曾經學過的條件結構」——若某種輸入輸出關係在訓練資料裡很少出現，表現自然受限。**模型吃什麼長大，多少會反映在它後來會做什麼**（這也解釋了「模型公司大量買書掃描」這類新聞的動機）。

⚠️ **Scaling Law 是過度簡化的答案**——能力同時受模型大小、資料量、資料的語言與任務結構、Context 怎麼描述任務、評估方式是否測到真正在意的能力**五件事**共同影響。

### 三、Chain-of-Thought：給模型一張計算草稿紙（Day 04）

**不是新架構**：模型仍是 Transformer、仍在預測下一個 Token，差別只是**先生成中間 Token 再給答案**：
```
原本：問題 → 答案
CoT： 問題 → 中間步驟 → 中間步驟 → 答案
```
> 模型並非突然獲得更多知識，而是**多取得一些可以用來計算、檢查與延續模式的 Token**——原本要心算，現在至少發了一張草稿紙，**至於會不會算錯，仍是另一回事**。

**Zero-shot CoT**：不給示範，只加一句「Let's think step by step」也能提升部分任務表現（2022 年論文）——但**不是萬用咒語**，簡單查詢/翻譯/格式轉換硬要求長篇推理只會更慢更長。⚠️ **現在的模型基本上已不需要這句咒語**。

### 🔑 CoT Prompting ≠ Reasoning Model（本篇最重要的釐清）

| 面向 | Chain-of-Thought Prompting | Reasoning Model |
|---|---|---|
| 核心概念 | 用 Prompt 引導模型展開步驟 | 特別後訓練 + 更多推論計算 |
| 需要特定模型？ | 不一定，一般 LLM 也可 | 通常需要相應訓練機制 |
| 是否更新參數 | 使用時不更新 | **訓練時會更新**；使用時通常不更新 |

以 OpenAI o1、DeepSeek-R1 為例：透過大規模強化學習學會**拆解問題、辨認錯誤、改用其他策略**——**依然是逐步生成 Token**，只是訓練後更能在回答前利用更長推理軌跡。

### ⚠️ 推理越長不代表越正確

增加推理步驟可能：一開始假設錯誤導致後面全走偏、在簡單問題上過度思考、產生看似合理實則無關的步驟、**為錯誤答案補上一段非常有說服力的說明**。

> **這有點像考試寫滿整張計算紙——寫得多只能證明筆很努力，不一定代表答案正確。**

對需要外部資料的問題仍要查核來源；對數學或程式問題，用計算器/Python/測試工具等**可驗證的方法**，而非只信任推理軌跡本身。

### 🔴 可見的推理，不等於真正透明（Day 04 最關鍵警示）

> **這裡所說的「內心戲」是一種方便理解的比喻**——畫面上看到的是模型生成的**推理軌跡（Reasoning Trace）**，不等於直接讀取神經網路裡全部、真實且完整的內部計算。研究已發現，模型寫出的 CoT **有時能反映解題過程，有時可能不完整，甚至與真正影響答案的因素不完全一致**。

檢查推理軌跡時該問的問題：每個步驟是否符合已知事實？前後有無矛盾？計算能否重新驗證？引用的資料是否真的存在？修改其中一個條件，後續推論是否合理改變？

> **CoT 讓我們多了一個可觀察的對象，但沒有讓查核責任消失。它讓 AI 從「只交答案的學生」變成「連計算紙一起交上來的學生」——老師確實比較好檢查，但計算紙寫得密密麻麻，仍可能從第二行就算錯。**

## C（關鍵行動）

- [ ] 理解 Top-k/Temperature 只改變取樣分布，不是知識開關或幻覺旋鈕
- [ ] 判斷任務該用 Zero-shot／Few-shot／Fine-tuning：只是暫時性上下文示範還是要真正改變模型行為
- [ ] 別再無腦加「請一步一步思考」——先判斷任務是否真需要多步驟推理
- [ ] 看到 CoT／Reasoning 軌跡時，**主動查核**每一步是否符合事實、能否重新驗證，不要因為步驟完整就當成已驗證
- [ ] 對需要精確計算或外部事實的任務，交給可驗證工具（計算器/程式碼/測試），不要只信任模型的推理描述
