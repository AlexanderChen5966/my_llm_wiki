作者把 Xcode 26.3、26.6、27(beta) 內建 MCP 丟進一個有十年包袱的商業 iOS 專案實測，發現**工具層／基礎設施層**本身會製造假訊號——這與「agent 自己沒驗證卻自信宣稱成功」的**模型層造假**是不同的問題來源，但結論同構：不能只信結構化回傳。

## T（核心論點）

> **不是「照單全收」的假訊息生成，是工具在建置失敗時刻意拿舊結果充數；而換一種失效方式（選錯模擬器），同樣的「一切正常」假象會再發生一次。**

Xcode 26.3 在建置失敗時，會把上一輪真實跑過的測試結果原樣（含重新生成、時間戳更新的假 log 檔）回傳給 agent，163 個測試全過的假訊息一次只花 1.2 秒。26.6 已修正此快取 bug，但 27 headless 模式又因自動選錯模擬器導致 app 啟動即崩潰，MCP 仍回報 `failed:0`——與快取 bug 情境下的 JSON 一模一樣。

## B（適用場景）

**適用：**
- 設計任何會呼叫 MCP／CI 工具讀取測試結果的 agent 驗收邏輯
- 理解「工具回報造假」與「模型自己造假」是兩種不同成因，需要分別設防
- 評估要不要把 `failed == 0` 當作唯一通過判準（答案：不要）

**不適用 / 注意：**
- 快取回報舊結果的 bug 僅存在於 Xcode 26.3，26.6 已修正（且是正式版，可直接升級解決）
- 27 headless 選錯模擬器的問題屬 beta 階段快照，正式版前仍可能變動

## R（三個實測發現）

1. **證明「什麼都沒發生」需要外部證據**：光看回傳值無法證偽（長得跟真的一樣）。作者用兩個外部證據反駁——同一件事真的做要多久（1.0 秒連模擬器都來不及啟動）、CPU 有沒有在動（十六秒內完全沒有編譯或執行活動的行程紀錄）
2. **不是照單全收**：丟一個不存在的測試 ID，工具會在 0.0 秒正確回報「not found」，證明它確實讀參數，只是建置失敗時刻意拿舊結果充數；空 session（從未跑過測試）時建置失敗會誠實回報全部 notRun，證明是「複製上一次結果」而非隨機造假
3. **連完整報表都是重寫的複製品**：回傳裡的 `fullSummaryPath` 指向一份 78,689 bytes 的全文報表，三次不同時間戳的檔案內容逐字元相同——「去讀完整 log」這條退路也是死的

27 headless 模式的新陷阱：headless 自動選了 app 跑不起來的模擬器（iOS 27.0），導致 189 個測試全部 `notRun`、app 崩潰，但回傳 JSON 仍是 `failed:0`，且沒有錯誤欄位；換一台模擬器（iPhone 16 Pro 18.6）同一份產物就變成 163 passed。

**唯一沒有失真過的訊號**：Xcode「測試成功/失敗播放音效」這個給人聽的功能，即使 headless 沒開 GUI 也會響，12 次測試中音效與事實從未不符——同一次執行，agent 讀到的 JSON 說「163 passed, 0 failed」，Xcode 播給人聽的卻是安靜（什麼都沒發生）。**同一個程式，對人說了實話，對 agent 漏了這句。**

## C（關鍵行動）

- [ ] 檢查邏輯不要用 `failed == 0`，改用 `passed == total - disabled`——這個欄位在快取 bug 與選錯模擬器兩種完全不同的失效情境下都會回傳同樣的假象
- [ ] 讓 agent 驗收流程留一個「不經過工具本身」的外部驗證管道（真實耗時、資源使用量、甚至給人聽的提示音）
- [ ] 若使用 Xcode 26.3，直接升級到 26.6（已修正快取 bug，且是正式版）；headless 環境跑出全 notRun 時，先確認自動選中的模擬器/系統版本

## 原始摘要

作者對比 Xcode 26.3/26.6/27(beta) 內建 MCP 的建置測試工具在一個真實商業專案上的行為，發現 26.3 版建置失敗時會回傳快取的舊測試結果（163 passed, 0 failed），連完整報表檔案都是重新生成的複製品；26.6 已修正此 bug；27 headless 模式則因自動選錯模擬器讓 app 崩潰，卻仍回報 `failed:0`。唯一沒有失真的訊號是 Xcode 內建的測試成功/失敗提示音，即使在 headless 環境也會照實播放。結論：機器開始回報自己的工作成果時，需要一個不經過它的管道去驗證。
