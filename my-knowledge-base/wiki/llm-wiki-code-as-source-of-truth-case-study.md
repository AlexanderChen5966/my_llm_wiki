iknow.dev 開發者親自 dogfooding 的實戰紀錄：用 Cursor 讀取自家未公開產品的原始碼，2 小時生成 83 筆 LLM Wiki 知識（Karpathy 概念的實作），但 4 天後新增一個小功能，剛寫好的知識就開始過時（docs drift）。核心洞察：**Lint 有兩層，一層可自動化，另一層永遠需要人工**——① 內部矛盾可由 LLM 大量清除 ② 與實際程式碼/行為的落差，只能由知道「正解」的人拿程式碼核對，光靠內部一致性檢查抓不到。

## T（核心論點）

未公開產品是 LLM「事前不知道」的典型案例，若讓它憑空想像會產生幻覺——「大致對但細節亂講」的文件。解法是把**原始碼當作 Single Source of Truth**，強制知識撰寫「不要憑空想，要根據實際程式碼來寫」，之後才能把知識與程式碼對照驗證。但這篇文章最重要的發現是：**做出知識只是 Ingest（匯入）一次性工作，真正的挑戰是 Lint（同步）——這是只要產品還活著就要持續做下去的營運流程，不是一次性專案**。

## B（適用場景）

自家產品的 onboarding/導覽 AI 建置；內部 Wiki 長期追不上產品變化的團隊；任何要用 LLM Wiki（Karpathy 概念）維護「活的知識庫」而非靜態文件的場景。

## R（實戰流程與關鍵發現）

**架構對應 LLM Wiki 三層**：Raw sources（Git repository 實際程式碼與畫面行為）→ The Wiki（知識庫平台上的知識群）→ The Schema（給 LLM 的培養指示 prompt）。運作流程套用 Ingest（匯入）→ Query（提問）→ Lint（同步）三階段。

**三步實作**：
1. **先做目錄**：讓 LLM 讀 repository，根據實際存在的畫面/路由/功能反推設計目錄骨架，人工修正後定為 No.0（index.md）——目錄先行，後續撰寫與 Lint 才能對應到明確頁面，不會混亂
2. **生成知識**：依目錄整理原始碼建知識，明確指示「相關知識不要寫在本文中，而是指定相關知識」；先產出 66 筆基於程式碼的知識，再請 AI 主動提案補「第一次使用者容易卡住的地方」，又新增 17 筆，總計 83 筆。**所有變更紀錄保留、可回復**，這是敢讓 AI 大膽寫的前提
3. **對話驗證（教育知識）**：把「第一次接觸者可能問的問題」整理成 15 題逐一測試，13 題完全沒問題，2 題「事實正確但不是想表達的導覽感」——這種情況比明顯錯誤更麻煩，需要人工判斷「精確但不理想」

**docs drift 真實案例（4 天後）**：知識庫完成 4 天後新增「★重要標記」小功能，導致舊的列表操作知識立刻過時，且容易與既有的「唯讀鎖定」概念混淆（★只是標記不限制編輯，但 Navigator 可能誤導成「加標記會受保護」）——**一個小 UI 新增就足以造成語意誤解**，這正是 docs drift 的可怕之處。作者甚至自曝：這篇談「腐化」的文章草稿 6/26 寫完，公開前已經先腐化一次。

**兩層 Lint 的關鍵區分**（本文最有價值的洞察）：
- **① 內部矛盾**（頁面互相打架、舊說法殘留）→ LLM 幾乎可以大量自動清除
- **② 與實際程式碼/行為不一致** → 只能由知道正解的人拿程式碼核對，內部一致性檢查完全抓不到這類落差

案例佐證：「知識超過 80,000 token 會怎樣？」Navigator 回答「會被拆分」，看似合理，但實際核對程式碼後發現**依路徑不同而有不同行為**（匯入時自動拆分，但從編輯器/MCP 儲存時超過會直接報錯無法存）。「會拆分」和「會報錯」都像合理答案，但**真正答案只存在程式碼裡，不打開程式碼連對錯都判斷不了**——這正是無法自動化、必須人工核對的第二層。

**組織性啟示**：本次是開發者本人新增功能所以當場發現落差，但一般團隊裡「新增功能的人」和「寫文件的人」通常不是同一人，這種落差沒人通報就會被默默放著。**對策不是靠某人「剛好想到」，而是建立以程式碼差異為起點、同步更新知識的流程制度**。

## C（關鍵行動）

- [ ] 建置產品 LLM Wiki 時，第一手資料優先用原始碼而非人工複述，讓 AI 能「有根據地寫」而非憑空生成
- [ ] 設計知識驗證環節時，除了對錯判斷，也要留意「事實正確但導覽感不理想」這類更隱蔽的品質問題
- [ ] 把 Lint 拆成「LLM 可自動清內部矛盾」與「人工核對程式碼落差」兩層，不要誤以為跑完自動化 Lint 就等於同步完成
- [ ] 建立「程式碼變更→受影響知識重新核對」的制度化流程，而非依賴個人記得去同步文件
- [ ] 新功能上線前，主動盤點是否會與既有知識產生語意混淆（如本案例的「★標記」vs「唯讀鎖定」）
