兩篇都在談「AI 改**既有**程式碼」：一篇是 OpenAI 的低資源程式語言研究（COBOL、Fortran、Visual Basic，含 COBOL 搬遷評估），一篇是 OpenAI 工程師用 Codex（GPT-6 家族）主動找技術債並提清理 PR。兩篇皆為 aiposthub 二手整理；**文中所有百分比都是 OpenAI 自家評測或個案，本庫未核對原文**。訂閱導流段落已忽略。

## T（核心論點）

> **改舊程式碼的難處不在「能不能寫出來」，而在「證明沒改掉不該改的」。** 搬遷的驗收標準是**相同輸入、相同輸出**；刪除的驗收標準是**正式環境的執行證據**，而不是「最近沒人用」或「有人在 Slack 說可以刪」。

三個支撐點：

1. **能執行≠結果相同**：COBOL 固定小數某些情況是捨去、明確要求才四捨五入；翻成新語言自動四捨五入，程式照跑、金額已不同
2. **沒有呼叫紀錄≠可刪**：低頻的保護開關、降級路徑只在事故時啟用，平常就是零流量
3. **行為搬遷與缺陷修正要分開**：新舊結果不同時，先判斷是「要保留的行為」還是「本次另外授權修正的缺陷」；混在同一次變更，事後分不出是刻意改進還是無意改掉

## B（適用場景）

**適用：**
- 用 AI 協助舊系統搬遷、換語言、換框架
- 讓代理找死碼、過期實驗開關、不穩定測試並提清理 PR
- 判讀「模型在某評測進步 X%」對自己專案的意義

**不適用 / 注意：**
- 評測分數不是專案成功率：資料庫測試、搬遷題目都不含部署、資料轉換、與其他系統串接
- 清理流程前提是**已有測試、流量紀錄與審查流程**；只有原始碼、缺執行證據時，結論只能停在「候選」
- 讓代理讀 Slack／內部資料要先限定範圍（特定專案與相關紀錄），不是為了找更多線索就全開

## R（操作步驟）

### 一、搬遷：先證明行為沒變

1. **選一段範圍清楚的功能**：輸入輸出明確、可在隔離環境執行（例如一個格式轉換步驟，而不是整個帳務流程）；先畫出它讀哪些資料、改哪些資料、呼叫哪些外部服務
2. **先保存原系統在關鍵輸入下的實際輸出**——文件寫的預期行為可能和長期實際行為不同
3. **建立含邊界與例外的驗證案例**：空值 vs 零值、合法的負數更正紀錄、缺漏資料該跳過還是中止整批；測試資料保留特徵與關係、去掉不必要的個資
4. **用相同條件逐項比較**：OpenAI 的 COBOL 搬遷評估要求可觀察輸出**逐位元組一致**、以**隱藏測試**全過為成功（避免只對已知例子修）；自家專案還要補欄位順序與格式（下游系統要吃的）、以及「讀了哪些檔、更新了哪些資料」，抓出「輸出相同但多改了別的」
5. **差異先查規則再改**：要保留的行為 vs 授權修正的缺陷，分成不同變更
6. **第一份報告寫清楚**：選了哪段、涵蓋哪些輸入、通過哪些條件、剩下哪類差異——要能讓別人重跑與追查

即使最後不搬遷，留下可核對的規則也改善後續維護（降低知識只在少數人腦中）。

### 二、清理技術債：先找證據再刪

OpenAI 的做法（官方個案）：Astra 讀過去 PR、Slack 討論與內部專案資訊找候選 → 對照**正式環境效能資料**確認是否真的沒執行 → 拆成小型清理 PR → 工程師審核。

**判斷順序**：先找成本與用途 → 詢問保留理由 → 最後才修改。只依「近期沒用過」排序最容易漏掉低頻但重要的功能。

官方案例：模型發現一個**標為永久保留**的功能開關可能帶來額外運算，因仍可能有操作用途先交人工審查，確認後才移除，估計該服務省 **0.42% CPU**（單一服務個案，不能外推）。

每份候選提案至少要附：

| 提案內容 | 審查用途 |
|---|---|
| 程式位置與使用者 | 確認誰可能受影響 |
| 即時設定與執行證據 | 支持「已無用途」 |
| 保留例外與風險 | 找出低頻保護功能 |
| 小型差異與測試 | 驗證修改符合原意 |
| 回復方式 | 出問題時能退 |

- 聊天線索只是方向，要再接到呼叫位置、即時設定、歷史變更與正式行為；**資料不一致時代理要列出差異交人判斷**，不能挑最容易刪的說法
- 清理本身增加的複雜度高於節省時，可以不採用
- 配置取捨：官方比較 GPT-6 Astra 與 GPT-6.1 Sol 不同配置，成本與發現數量有取捨 → 用同一小任務先試便宜配置，夠用再擴大

### 三、怎麼讀評測數字（OpenAI 自家公布，未核對）

| 評測 | 數字 | 正確讀法 |
|---|---|---|
| MultiLangBench（從頭實作 SQLite 相容引擎，20 種語言） | 最高推理設定 GPT-6 Astra 平均 **87.4%** vs GPT-5.6 Sol **26.8%**；COBOL **10.9%→72.1%** | 新建能力的跨語言比較，不是所有程式任務成功率；COBOL 仍低於平均 |
| COBOL 搬遷（→C++／Java／Kotlin／Python／Rust，隱藏測試） | 較低推理設定 GPT-6.1 Sol **86.6%** vs GPT-5.6 Sol **5.4%** | 研究題目通過比例，不是整套系統直接上線的成功機率 |

- 新建（MultiLangBench）與搬遷要分開衡量：新建考組織功能與狀態管理，搬遷額外要求理解既有規則
- 成本比的是「完成一段合格搬遷的總投入」：模型帳單之外還有建測試、查差異、維持環境的人力

## C（關鍵行動）

- [ ] 下次讓 AI 重構或搬遷既有程式前，先固定一組原系統輸出當基準（characterization），再開始改
- [ ] 讓代理提「可刪」候選時，要求附執行證據與保留例外，沒有證據的只列為候選
- [ ] 行為保留與缺陷修正分成不同 PR

## 原始摘要

**低資源程式語言研究**（OpenAI，2026-10-19）：針對公開訓練材料少的 COBOL、Fortran、Visual Basic，分兩類評估——MultiLangBench 讓模型從頭寫 SQLite 相容引擎、COBOL 搬遷評估用隱藏測試要求輸出逐位元組一致。作者建議企業先保存原系統輸出、建立含邊界與例外的案例、行為搬遷與缺陷修正分開，模型高分不能直接換成上線決定。

**Codex 清理技術債**（OpenAI 開發者部落格）：GPT-6 家族從 Slack、歷史 PR 與專案線索找維護候選，再對照正式流量證據提出小型清理 PR，由工程師審核；沒有呼叫紀錄不等於可刪，每份候選要附位置、執行證據、保留例外與回復方式。

**合併判斷（2026-11-19）**：[[refactor-with-claude-code-measured-by-graph]] 是單一重構實作（以圖結構衡量、characterization test），[[ai-code-review-safeguards]] 是 AI 生成新程式碼的審查防護，都不涵蓋「搬遷看結果相同、刪除看正式流量證據」這條既有程式碼的驗證論點，故合併兩篇新建。[[gpt-6-astra-prompting-guide]] 是提示詞校正、[[codex-2026-10-feature-updates]] 是產品功能更新，主題不同只連結。
