## T（核心論點）

多個程式代理同時工作時，最大的難題不是「開得出來」，而是**掌握狀態**：「代理還在工作」與「修改已經完成」是兩個不同的資訊。

🔑 **會話、分支、工作目錄是三個不同的東西，不能互相代替**：會話存「工作脈絡」、分支存「程式版本的發展方向」、工作目錄是「實際檔案所在」。恢復會話不代表檔案還是當時的版本，**恢復後先讀目前狀態再繼續**。

🔑 **「完成」只留給「成品已儲存且驗收通過」的工作**；只是產生程式或跑完指令，標「已修改」或「已檢查」。並行的成本通常出現在**整合**，不在執行。

## B（適用場景）

**適用：** 已在用終端機程式代理（Grok Build、Claude Code、Codex 等）、開始同時跑多段任務、需要人能接手與驗收的工作流

**不適用 / 注意：**
- 任務共用檔案多、需頻繁合併時，並行未必比較快，管理與驗收時間反而增加——先排成前後順序，獨立部分才並行
- 本文的狀態表欄位是**工作管理建議，不是工具內建功能**
- 社群轉貼的版本號只當查詢線索，功能以官方 changelog（x.ai/changelog/build）核對為準
- 本文操作案例是練習流程，作者未宣稱實測

## R（操作步驟）

1. **先確認版本與安裝方式**：`grok --version` 並寫進工作紀錄；套件管理器安裝的版本有自己的更新流程。互動介面適合需求仍在變動時，非互動適合輸入與完成標準已寫清楚的任務
2. **第一次只做一項小修改**（例：修錯誤日期格式），走完「讀檔 → 修改 → 檢查 → 儲存」。工作說明要含：觸發問題、預期結果、不得改動的內容，再給一正一反範例；用 `@` 明確指定檔案
3. **逐步增加授權**：對外上線、不可恢復操作的完成點與本機修改分開
4. **多段並行用一張狀態表**（工作／目錄與版本／目前狀態／下一步），並**記錄依賴**——兩段工作可能改不同檔案卻依賴同一功能，合併後才爆
5. **驗收先看 diff**：是否在授權範圍、再跑最相關檢查，並重現使用者實際操作；**測試後又改檔就要重驗**，不能沿用上一版成功紀錄
6. **失敗恢復**：先存狀態（版本、目錄、最後可確認操作），別急著清目錄；讀 diff 與未儲存變更分辨「真的存在」與「代理曾提出的計畫」；認證、網路、測試失敗、程式錯誤分類處理；分享紀錄前移除憑證
7. **合併**：先合併提供基礎功能的改動，再查使用它的工作，**合併後要有自己的驗收紀錄**；無法解決時退回已確認可用版本，保留失敗分支與原因
8. **最小交接紀錄四項**：一句問題描述、一個工作位置、一份改動差異、一組檢查結果；決定過的範圍附原因

## 原始摘要

Grok Build 是 xAI 官方在終端機中的程式代理（互動、非互動、編輯器整合）。文章把重點放在工作管理：確認版本、寫可驗收的完成標準、區分會話／分支／worktree、用狀態表追蹤多段工作、以 diff＋實際操作驗收、失敗時保留現場再恢復、合併前處理依賴，並以「兩段工作各自通過、合併後按鈕沒反應」說明整合成本。
