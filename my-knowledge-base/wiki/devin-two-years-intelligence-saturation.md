## T（核心論點）

Cognition（Devin 開發商）兩年半的產品演進指向三個判斷：

1. **智慧飽和（intelligence saturation）**——模型能力跨過可用門檻後，**再多一點智慧未必顯著改善結果**，開發者反而更在意延遲與費用
2. **既有評測抓不到「可合併性」**——程式碼通過測試 ≠ 你願意合併它，所以自建 Frontier Code 評測
3. 🔴 **許多 AI 廠商有強烈誘因鼓勵客戶不斷增加 token 用量**，把使用量排行當成功指標；Cognition 反向操作，提出**最高 1,000 萬美元生產力保證**

## B（適用場景）

**適用：** 評估「該不該升級到更強模型」；設計 AI 工具的成效量測；理解廠商激勵與你的利益何時分歧；規劃 AI coding agent 的組織導入

**不適用 / 注意：** 廠商自述，數據與評測皆為自建（Frontier Code 為 Cognition 自有）；「智慧飽和」有明確範圍限定（見下）

## R（關鍵論點）

### 一、智慧飽和及其邊界

> 「大家想要快速而正確的答案，不想有任何多餘浪費，也不想每次使用編碼代理時，**還得先煩惱該選哪個模型**。」

⚠️ **Kaplan 自己限定了範圍**：金融交易等**對抗性任務**仍需最前沿能力（因為對手也會持續變強）；但許多日常軟體需求有明確門檻（如替行銷網站做註冊頁）——**當多款模型都能完成，選對模型與控制浪費的價值便迅速上升**。

**瓶頸會移動**：他 2017 年在 Tesla Autopilot 團隊時最缺 GPU 算力，現在自駕研發的瓶頸已變成**評測**（人工介入事件太少，必須累積龐大行駛量才找得到問題）。軟體工程尚未走到那一步，但可能比預期更早遇上。

### 二、🔑「讓使用者選模型是雲端代理的 UX 缺陷」

這是本篇對模型選擇最有價值的一段：

| 產品 | 是否讓使用者選模型 | 理由 |
|---|---|---|
| **Devin Desktop**（原 Windsurf 改名）與 CLI | ✅ 允許 | **本地代理的使用者有偏好控制權** |
| **雲端 Devin** | ❌ 只提供價格與能力**層級**，底層模型由 Cognition 決定 | 見下 |

早期測試讓雲端使用者直接選模型，常出現兩種抱怨：**選了便宜模型後覺得 Devin 變笨，選了昂貴模型後認為費用太高**。

> 「人們要的是最好的效能與價格，而且不能犧牲正確性。**代理廠商有責任把這些最佳化處理好，不該讓使用者為此操心。**」

→ 這正好對照 Claude Code 的設計選擇：它是本地 CLI，因此**讓你選**，且沒有自動路由。兩家在這件事上的產品判斷是**分歧的**——不是誰錯，是本地 vs 雲端的定位差異。（模型解析機制見 [[fable-5-delegation-cost-benchmark]]）

### 三、Frontier Code：把「可合併性」變成可執行測試

SWE-bench 已趨近飽和——團隊常覺得新模型明顯更好，卻找不到既有測試支持這個直覺。缺的指標是**可合併性**（程式碼風格、後續可修改性、其他模組演進時是否容易出錯）。

> 「問題不只在於程式碼有沒有通過測試，還在於**你是否真的願意合併它**。它會改善程式碼庫的品質嗎？」

**建構方法**：與高標準開源維護者合作——**維護者先提出自己接受一筆變更所需的條件，研究團隊再把這些判斷轉為測試**。部分條件可直接寫成程式斷言（例：某改動用 A 或 B 模組都能運作，但維護者知道只有 A 能承受未來演進，測試就要求必須用 A）。**判斷仍由人提出，再轉成可重複執行的規則。**

⚠️ **每位研究員都親自貢獻、審閱與評估題目，沒有把資料品質工作交給另一批人或模型**；每道題像一個完整工程專案，可能投入數百小時。

**雙層評分**：
| 層 | 機制 |
|---|---|
| **Blocking** | 測試是否通過、維護者指定的硬性條件是否滿足，皆**二元判斷**；任一沒過即不可合併 |
| **Non-blocking** | 通過硬門檻後以**線性加權**計分。模型可能改對目標程式碼卻順手碰了不相關檔案——不影響功能但拉低品質分 |

🔑 **反向驗證**：套用正確 patch 後測試必須通過；**不套用 patch 或換成其他 patch 時測試則應失敗**——避免測試本來就會通過卻被誤認為模型解題成功。

**數據**：Frontier Code 的 Diamond 子集在 Fable 5 推出前只有十幾個百分點，之後提高到三十多個百分點。

### 四、Devin Fusion 為什麼要「並行」而非按需切換

> 「前沿模型會判斷，這個任務交給能力較弱的模型也沒問題。這和人的職涯發展很像：往上走時要學會委派，把自己留在槓桿最高的工作上。」

🔑 **並行的真正理由**：**讓雙方都保有任務脈絡**——若只在需要時才切換，接手者很難立即取得同等理解。兩者共享大量脈絡，也頻繁把資訊寫回檔案系統避免超出脈絡視窗。配合**注意快取的路由決策**，價格效能改善約 **35%**。

（此段補強 [[fable-5-delegation-cost-benchmark]]：Sidekick 是常駐並行而非按需生成，正是為了維持脈絡對等）

### 五、🔴 追高 token 用量的激勵錯位

> 許多 AI 廠商有強烈誘因鼓勵客戶不斷增加 token 用量，把**使用量排行當作成功指標**。企業帳單升到每年數千萬、數億美元後，管理層終究會問這些支出換到了什麼。

**獨立代理公司的結構性優勢**：不必只替特定模型拉高用量，理論上更容易站在客戶一邊、**拒絕低價值工作**。

**如何量測「有效工程產出」**（人工估算 ROI 無法規模化，改測較容易自動判斷的指標）：
1. **判斷 session 是否產生有效產出**：建立了 PR 卻**從未合併** → 保守歸為無生產力；**合併進正式環境** → 有生產力；沒有 PR 的資料分析類任務 → 由**客戶共同標註資料訓練的分類器**判斷
2. **估計有效 session 節省多少工程時數**：人工訪談＋資料蒐集估計使用 AI 前後差異，再與第 1 步結合，為個人／團隊／公司提供可比較分數

### 六、1,000 萬美元生產力保證

> 「如果客戶只是空燒用量、沒有得到相應價值，而支付金額又超過省下的工程時數價值，**我們就退還差額**。這迫使我們和客戶站在同一邊。」

內部曾擔心有人用迴圈不斷呼叫 API 燒掉幾百萬美元。**結論是：既然公司承諾補差額，就應在產品裡加入預算上限與算力分配工具**，讓管理員決定總預算，也協助判斷誰可使用更多算力、誰還需較嚴格限制。

### 七、儀表板是教練，不是監控器

生產力資料**最常用於團隊學習**。成本偏高通常**不是惡意浪費，而是使用方式不同**，使用者也未必知道哪個步驟效率差。

Cognition 把教練功能放進產品：Devin 可以**指出提示寫得太簡略並提出具體改善方式**。理由是技術變化太快，幾個月前的能力限制可能已消失，**依賴人工訓練很難跟上**。

## 其他值得記的點

- **資安任務需精確率／召回率分工**：Fable 類精確率較強、GPT-5.5 與 5.5 Cyber 召回率較高 → 做法是**先用 GPT 系列找出較多候選，再用 Fable 系列過濾**
- **自訓模型的半衰期只有幾個月**：AI 新創必須以**三到六個月**為單位思考——用當下模型能力做出有差異的產品，優勢消失後再訓下一個。SWE 1.6 品質約 Opus 4.6 水準，依 token 用量計是 Devin Desktop 最受歡迎的模型；同時維持的專用模型只有**個位數**（避免管理五十上百個過度細分的模型）
- **Cerebras 每秒約 950 token**，比同等規模模型用 GPU 快數倍，服務成本略高——「價格與吞吐量帕累托曲線上的獨特位置」
- **Devin Security Swarm**：每個 session 在獨立 **microVM** 執行，可重現漏洞再驗證修補；大型 codebase 先切片→找脆弱部分→分派修補→合併結果並驗證 = **「資安工作的代理式 MapReduce」**。一名工程師能啟動相當於大量工程人力的全公司修補
- **主動式代理**：Devin 接入多個 Slack 頻道自行分類訊息、判斷是否加入討論；知道程式碼庫各部分由誰負責。「穩定運作後，公司多數工程工作應**預設由代理主動完成**」
- ⚠️ **Kaplan 不喜歡「software factory」這個詞**：工廠讓人想到重複生產相同物品，而編碼代理的價值在於**依公司脈絡完成高度客製的工作**
- **新進工程師未必劣勢**：「大家使用代理的經驗都沒幾年，某種意義上我們站在同一起跑點」；且代理不會嫌問題愚蠢，可反覆解釋程式碼庫讓新人更快熟悉
- **FDE 人數已超過其他工程師**；具創業經歷者較適合——習慣在模糊問題中工作、能兼顧技術與客戶痛點。「當編碼代理幾乎什麼都能嘗試時，**選對問題本身就成了重要能力**」

## C（關鍵行動）

- [ ] 判斷任務屬「有明確門檻」還是「對抗性」——前者別再追最強模型，後者不能省
- [ ] 量測 AI 成效時，用「**PR 有沒有被合併**」當第一道自動化訊號，別只看使用量
- [ ] 🔴 評估任何 AI 工具時問一句：**廠商的激勵是讓我多用，還是讓我用得有效？**
- [ ] 設計自家評測時加入**反向驗證**（不套 patch 應失敗），避免測試本來就會過
- [ ] 團隊成本偏高時先假設「使用方式不同」而非浪費，把儀表板當教練而非監控
- [ ] 自訓／專用模型的規劃以 3–6 個月為週期，別假設能長期領先
