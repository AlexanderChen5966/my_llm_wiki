BrainPad 工程師依田分析「讀 AI 寫的 Design doc/PR 為何疲憊」，歸納四個成因並用同一需求（EC 購物車優惠券邏輯）實測對照：加入寫法指南的 Skill 產出的文件量從 284 行/8521 字/32 標題縮到 41 行/1239 字/6 標題，約縮減 7 倍，**實作內容完全相同**（皆通過 pytest 24 項測試）。

## T（核心論點）

> **讀 AI 文件會累，原因不是內容錯誤，是它有四個習慣：不篩選重要度、結論放最後、老實填滿模板、對顯而易見的方案也正反並列。這些習慣不明確寫進 Skill，AI 就會傾向「盡量完整」。**

疲憊問題出在文件表達，不是內容正確性——兩版本用同一個 Issue、同一份程式碼，皆通過 pytest 24 項測試全過，差異純粹來自 Skill 中對文件寫法的指示。

## B（適用場景）

**適用：**
- 讓 Claude Code 等 AI agent 撰寫 Design doc、PR 說明的場景
- 想重新檢視自己 Skill 或 prompt 設計，抑制「AI 傾向寫到看起來很完整」的傾向
- 需要一套可直接寫進 Skill 的判斷準則，而非靠事後人工砍字數

**不適用 / 注意：**
- 本篇為單一案例（一個 Issue、兩次實作）的對照實驗，非大規模統計驗證，但差距達 7 倍具參考價值
- 判準本身需要「讀者已具備基本技術背景」的前提（例如省略用語定義的條件是「讀者應該看得懂」）

## R（四個疲憊成因與對應解方）

| 疲憊成因 | 對應解方（寫進 Skill 的具體指令） |
|---|---|
| 不分重要度全部同等篇幅 | 明確寫出 Non-goals（不做什麼），不要羅列範圍外的一般論 |
| 結論放在文件最後 | 開頭 3 行內先寫結論（採用的設計與理由），細節之後再補 |
| 老實填滿模板標題即使內容很薄 | 只有讀者可能不懂時才寫用語定義、背景等固定章節；若屬理所當然則省略 |
| 對顯而易見/未採用方案也正反並列優缺點 | 替代方案改用表格（只列「方案」「淘汰理由」兩欄，不逐一寫優缺點文章） |

**判斷準則（可直接寫入 Skill）**：「即使沒有這個段落，審查者是否仍能理解決策？」若可以就刪除，不確定時傾向刪減。

定量對照：Design doc 由 284 行/8521 字/32 個標題（Before）減至 41 行/1239 字/6 個標題（After），約 7 倍差距；PR description 由 1232 字減至 396 字，約 3 倍差距。兩版本實作內容完全相同（同一 Issue、同一程式碼、皆通過 pytest 24 項測試全過），證明差異純粹來自「文件寫法」而非內容正確性。

作者保留可公開驗證的實例：Before PR 與 After PR 皆在 GitHub 原始倉庫供對照（github.com/Taketo-Yoda/Qiita issues/4, pull/5, pull/6）。

## C（關鍵行動）

- [ ] 把「開頭 3 行先寫結論」寫進文件撰寫類 Skill 的固定指令
- [ ] 替代方案比較一律改用表格（方案/淘汰理由兩欄），停止逐條優缺點文章
- [ ] 加入判斷準則句：「拿掉這段審查者還能理解決策嗎？」不確定時傾向刪減
- [ ] 明確寫出 Non-goals，避免 AI 把「完整性」誤當成「重要度」

## 原始摘要

BrainPad 工程師依田以 EC 網站購物車折扣優惠券套用邏輯為題材，比較「沒有特別優化的 Skill」與「加入 Design doc 寫法指南的 Skill」產出的文件差異。實作內容一致（皆通過 pytest 24 項測試），但加入四項具體指令（結論先行、替代方案表格化、非必要不寫固定章節、明確 Non-goals）後，文件量縮減約 7 倍。作者主張：發現自己不想讀 AI 輸出時，該先檢視 Skill/prompt 是否有指定「不要寫什麼」，而非先懷疑內容本身。
