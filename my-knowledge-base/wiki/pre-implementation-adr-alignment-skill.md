## T（核心論點）

> **目標不是「讓輸出的程式碼更容易讀」，而是「讓自己能事先預想輸出會長什麼樣子」。**

作者是入職滿一年的工程師，發現用 AI 實作雖然縮短寫程式時間，但因為要花時間理解生成碼，
**整體開發並沒有變快**。他先做了「閱讀生成程式碼的審查指南」——結果失敗（作者自己標記為**一敗**）：
照指南能懂每段處理在做什麼，但仍搞不懂彼此如何串接、為何是這種架構。

於是把問題重新定義為 **「請 AI 實作之前的準備不足」**：
🔑 **沒有事先畫出完成樣貌，即使生成碼偏離預期也察覺不到那個「落差」**，只能一直問 AI
「這段在幹嘛」——省下的實作時間又還回去，還推高 API 成本。

Before/After 的差別不在「有沒有用 AI 生成」，而在 **實作前有沒有判斷基準**。

## B（適用場景）

**適用：**
- 覺得「AI 寫得很快但我 review 得很慢」、每次都得請前輩幫看的情境
- AI 老是把單點改動做成跨多類別的架構（Overengineering）
- 需要向他人說明「為什麼這次要這樣實作」而不只是「這段程式在做什麼」

**不適用 / 注意：**
- ⚠️ 作者誠實記載副作用：**dig 問得很細會有點累**
- ⚠️ 這不是完整 spec-driven 流程；最小準備只要三句話，不需把實作細節全決定好
- 範例情境為 `spring-petclinic`（該 codebase 沒有 User entity，只有 Owner / Vet，AI 第一問就先釐清「使用者列表」指誰）

## R（操作步驟）

### 1. 先能用自己的話說明三件事（最小準備）

- **要解決什麼問題**
- **要實現什麼**
- **這次不處理什麼**

有了這三句就能判斷哪些範圍可交給 AI，也能請 AI 刪掉不必要的實作。

### 2. 認識 Overengineering 的具體病例

一句「讓使用者列表可以下載成 CSV」，AI 可能自行補出：
格式切換介面 → 依輸出格式產生類別的 Factory → 檔案 storage → 背景 queue → 失敗重試機制。
原本一個處理就能完成的改動，膨脹成跨越多個類別與設定檔的實作。

🔑 若沒先決定實作範圍，**即使逐一問 AI 每個類別的用途，也無法判斷它是不是這次真的需要**。

### 3. 用 `dig-and-write-adr` Skill 把準備流程固定下來

```yaml
---
name: dig-and-write-adr
description: 透過徹底提問來精煉計畫與設計，同時也建立 ADR 與術語表。
disable-model-invocation: true
---

執行 Skill 工具的「dig」，在結束並輸出整理格式後，將對話內容以 ADR 的形式記錄成 md。
```

- 呼叫方式：`/dig-and-write-adr <question>`
- 設 `disable-model-invocation: true`（只由人明確觸發，不讓模型自行呼叫）
- 參考自 `grill-with-docs` Skill

### 4. dig 階段：AI 反覆提問 + 每題四個選項 + 建議選項與理由

範例（`/dig-and-write-adr 想讓使用者列表可以下載成 CSV`）：

> **Q1：「使用者列表」是指既有領域中的哪個列表？**
> A 飼主列表（`/owners`）／B 獸醫師列表／C 兩者／D 新增認證使用者管理
> **建議 A** — 目前 UI 有可搜尋的人物列表，且姓名、地址、城市、電話這些 CSV 需要的欄位都齊備

🔑 價值在於 **初階工程師不必自己從零想出所有檢討項目**——從選項中挑方針就能發現漏掉的考量
（例外情況行為、對既有功能的影響）。看不懂的詞可隨時追問，AI 會補充說明後再重問一次。

### 5. 把決定寫成 ADR，當作判斷基準

ADR 記錄格式（例 `adr/user-list-csv-export.md`）：

| 段落 | 內容（CSV 例） |
| --- | --- |
| **Context** | codebase 沒有 User 模型，「使用者列表」確定指 `Owner` |
| **決策** | 對象是 Owner、沿用既有列表取得流程、輸出格式僅限 CSV |
| **非目標** | 檔案儲存、非同步處理、JSON 等非 CSV 格式 |
| **理由 / 決定因素** | 資料量不大、暫無其他格式需求；要能取得整份而非只有目前顯示那頁；不能把數萬筆全留在記憶體 |

### 6. 實作時把 ADR 當前提交給 AI

- 實作中迷路時回頭讀 ADR，確認生成碼是否符合當初方針
- 🔑 **AI 遺失前文脈絡時，重讀 ADR 即可再次共享實作範圍與方針**
- review 時把程式碼與 ADR 一起交給前輩，讓對方先理解意圖與判斷理由再看程式碼

### 7. 實踐後的實際變化（作者自陳）

Code Review 次數明顯減少／對前輩的指正比較能說明自己的意圖／對 AI 產碼更有「我看得懂」的感覺／
和 AI 的來回對話變少／比較容易回想「當初為什麼這樣做」。

## C（關鍵行動）

- [ ] 下次請 AI 實作前，先寫下那三句話（解決什麼問題／實現什麼／這次不處理什麼）
- [ ] 檢視自己的 Skill 清單，把「反覆提問對齊 + 產出決策紀錄」這一步補上（可比對 `grill-with-docs` / `dig`）
- [ ] 為近期一次 AI 實作補寫 ADR，特別是「非目標」段落——這是判斷 Overengineering 的依據
- [ ] 對不該讓模型自行觸發的 Skill 補 `disable-model-invocation: true`

## 原始摘要

入職滿一年的工程師發現用 AI 實作沒讓整體開發變快，因為理解生成碼要花時間。他先做「閱讀生成程式碼的
審查指南」但失敗（能懂每段處理卻不懂串接與架構理由），於是把問題重新定義為「請 AI 實作之前的準備
不足」：目標不是讓輸出更好讀，而是讓自己能事先預想輸出長什麼樣，才有落差可比對。做法是實作前只需能
說明三點（要解決什麼問題／要實現什麼／這次不處理什麼），並用自製 `dig-and-write-adr` Skill 由 AI
反覆提問四選項來對齊，最後把決策寫成 ADR 當判斷基準。實踐後 code review 次數明顯減少、能向前輩說明
意圖、與 AI 來回對話變少。
