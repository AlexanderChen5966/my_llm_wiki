用生成式 AI 推進 Push 通知功能設計時，作者在**設計階段**（不是正式環境事故）發現：處理 1 位通知對象最多要對 DB 查詢約 11 次。

| 通知對象 | DB 查詢 |
|---|---|
| 1 人 | 約 11 次 |
| 100 人 | 約 1,100 次 |
| 1,000 人 | 約 11,000 次 |

## T（核心論點）

> **「能正確運作」和「使用者增加後仍能承受」是兩回事。**

這不是「因為 AI 所以出錯」的故事——人類自己設計也一樣會這樣寫。差別在於**使用生成式 AI 時，從設計到實作的速度非常快**，所以「能不能動」這個檢查點通過得太早、太順，設計就直接往下走了。

判準本身很單純：**避免出現「對象人數增加 10 倍，DB 查詢次數也跟著增加 10 倍」的架構**——重點不在 SQL 一定要寫幾條。

## B（適用場景）

**適用：**
- 任何交給 AI 產出的**設計稿**進入實作前的審查（尤其批次寄送、通知、報表、匯出這類「對每個對象重複一組處理」的功能）
- 🔑 **直接適用於 Spring Boot 工作**：「有沒有在迴圈內存取 DB」就是 N+1 查詢的白話版
- 想把「效能面審查」制度化成一個獨立的 AI review 回合

**不適用 / 注意：**
- ⚠️ 本篇是**設計階段**的檢查清單，不是效能調校方法論；實作層的效能問題見 [[rust-hot-path-optimization-ai-review]]
- 每一個處理單獨看**都很自然**——問題只在「乘上對象人數」之後才浮現，所以審查時必須主動把數字乘上去

## R（操作步驟）

### 1. 看送來的設計裡，針對每位對象的處理中 DB 存取重複了幾次

被審出問題的設計長這樣（每一步單獨看都合理）：

```
確認通知對象
確認通知條件
取得裝置資訊
確認是否已通知
保存結果
```

→ `每人約 11 次 × 對象人數`

### 2. 把人數乘上去，算出 100 人 / 1,000 人時的絕對次數

DB 查詢不是單純計算一次而已，會發生「應用程式發出查詢 → DB 搜尋 → 回傳結果」的往返。1,000 人就是 11,000 次往返。伺服器不會立刻壞掉，但 **DB 的通訊、查詢、連線等待會增加，甚至讓其他 API 的處理也變慢**。

> 原本「請幫我一次整理這 1,000 人的資料」就能完成，卻變成每 1 個人都要跑 11 次櫃檯確認。

### 3. 改成「批次取、逐一送、彙總寫回」

Push 通知本身確實需要對每位對象分別發送，**但通知所需的資訊不需要每次都去 DB 重新取得**：

```
先從 DB 一次取得所需資訊
↓
再針對對象逐一發送 Push 通知
↓
最後將結果彙總寫回 DB
```

### 4. 四個審查問題（可直接當提問清單）

- **如果是 100 人呢？**
- **如果是 1,000 人呢？**
- **SQL 會發出幾次？**
- **有沒有在迴圈內存取 DB？**

### 5. 讓 AI 做一個「只看效能」的 review 回合

> 「請**只針對效能面**進行審核」

🔑 把審查維度單獨切開，比在一次通用 review 裡順帶問更有效。

## C（關鍵行動）

- [ ] 把「如果規模變成 100 倍會怎樣？」加進自己的設計 DoD，AI 產出的設計一律過這一關
- [ ] 審查 Spring Boot 設計稿時，逐段標出「迴圈內的 DB 存取」——那就是 N+1
- [ ] 對批次類功能，預設架構寫成「批次取 → 逐一處理 → 彙總寫回」，而不是逐筆來回
- [ ] 在 AI review 流程中加一個只跑效能面的獨立回合
