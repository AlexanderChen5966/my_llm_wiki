## T（核心論點）

Graph Engineering 是把模型、工具、程式、人工審核與驗證器拆成**不同節點**，再用明確路徑、共享狀態與停止條件控制協作的方法。它**沒有宣告 Loop 失效**——Loop 是 Graph 中的循環路徑；真正擴大的是工程師從「管理單一 Agent 的反覆執行」進到「處理多個工作單元之間的分工、交接、並行與恢復」。**關鍵不是 Agent 數量，而是責任是否清楚。**

## B（適用場景）

**什麼時候只需要一個 Loop（不要上 Graph）：**
翻譯一段文字／產生十個標題／修改單一函式／摘要短文件／只有一種工具與一種輸出／人類可立即判斷結果對錯

**哪些訊號代表真的需要 Graph：**
1. **需要不同權限或工具**——研究 Agent 只能讀網頁、寫作只能建草稿、發布必須人工核准
2. **存在清楚的條件分支**——編譯成功／失敗走不同路徑；客服依帳務／技術／安全轉不同流程
3. **任務可自然並行**——市場規模、競品、法規可分頭搜尋再匯總
4. **需要保存 Checkpoint**——長任務可能因網路、額度或人工核准暫停，需知道從哪個節點恢復
5. **單一 Agent 的角色開始互相衝突**——同一套提示詞要求模型研究＋寫作＋審查＋批准，標準會混在一起

> ⚠️ Anthropic 與 OpenAI 都建議**先用能完成任務的最簡單架構**。多 Agent 會增加延遲、Token、除錯與整合成本。

## R（核心結構與五個模組）

### 三元素

| 元素 | 定義 | 要點 |
|---|---|---|
| **Node** | 工作單元 | 可以是 LLM 呼叫、Python 程式、DB 查詢、API、測試套件、**人工確認**——**不一定是 AI**。判斷是否值得獨立：是否有不同的責任／工具／權限／上下文／驗收方式 |
| **Edge** | 完成後往哪走 | 固定順序／條件分支／並行執行／循環路徑／**人工閘門**（發布、付款、部署前）|
| **State** | 節點間傳遞什麼 | **不應只是越來越長的聊天紀錄**，而是有結構的任務資料；每個節點只讀必要欄位、只改自己負責的欄位 |

### 🔴 Graph ≠ Multi-agent（最常見誤解）

```
讀取表單 → 程式檢查欄位 → LLM 判斷問題類型 → 查詢資料庫 → 人工核准 → 寄出回覆
```
整個流程**只有一個 LLM 節點**，其餘都是確定性程式、工具與人工。Google ADK 2.0 強調圖式工作流可混合確定性程式與 AI 推理——固定商業規則由 Graph 控制，只在需要解讀自然語言時才交給模型。

### 五個核心模組

1. **Node Contract**——每個節點明訂：任務目標／可讀狀態／可改欄位／可用工具／輸出格式／驗收標準／時間與 Token 上限／失敗處理。**兩節點若能合併且不失去權限隔離、專業能力或獨立驗收，就不該拆**
2. **Deterministic Routing**——能用程式判斷的條件優先用程式；模型路由只留給語意分類、風險判斷、資料不足這類難以列舉的情況，且應**限制可選路徑並保存判斷依據**
3. **Structured State**——需要 Schema、版本與**欄位 Owner**。錯誤資料一旦寫入共享狀態，後續節點會當成事實繼續處理；重要主張要保留**來源、查核狀態、有效時間**
4. **Independent Verification**——審閱節點應取得**乾淨上下文**與可驗證證據，而非繼承執行 Agent 的全部推理歷史。程式碼由實際 Build/Test 驗證、資料由 Schema 與來源驗證、發布由回讀結果與人工核准驗證。多 Agent 可提供唯讀意見，但**最終寫入維持單一路徑**
5. **Budget 與停止條件**——最大執行次數／修正輪數／Token 與費用／執行時間／平行數／人工接手條件／不可逆操作前的核准節點
   > **沒有預算與停止條件的 Graph，只是規模更大的失控 Loop。**

### 確定性控制 vs 概率性控制（知乎「居丽叶」補充）

一張 Agent Graph 通常同時包含兩類控制，Graph Engineering 的工作就是決定這兩類控制怎樣組合：

| 控制類型 | 範例 |
|---|---|
| **確定性控制** | 權限、預算、依賴關係、Schema、停止條件、人工審批 |
| **概率性控制** | 任務拆解、語意路由、研究策略、衝突解釋 |

傳統工作流節點（SQL、HTTP、確定性腳本）成功與失敗容易判斷；Agent 節點可能正常返回語言流暢的報告，卻混入錯誤數字、遺漏條件或無來源的推斷——**進程成功只能說明模型給出了輸出，任務是否合格還需要規則、測試、證據或獨立 Reviewer**。判斷一套系統是否真做了 Graph Engineering，要看「圖有沒有承擔系統可靠性的責任」：任務會不會依輸入改變？並行結果怎麼合併？結論有沒有證據？部分節點失敗後重跑哪裡？程序中斷能否恢復？哪些決定留給模型、哪些必須由規則或人工？調用了 `StateGraph`、畫出了圖，不代表自動做到了這些——很可能只是換了外觀的固定流水線。

### 三路線實測對照表（同一股票研究 Agent 案例）

知乎「居丽叶」用同一個「請研究貴州茅台基本面、估值、技術走勢與新聞風險」案例，實測比較三條實現路線：

| 維度 | 路線一：固定拓撲 Graph-shaped Workflow | 路線二：單 Agent Loop | 路線三：Graph Engineering（穩定控制圖＋運行時任務 DAG） |
|---|---|---|---|
| 路徑 | 人提前寫好順序流程（LangGraph 四 Agent 固定 fan-out/fan-in） | Agent 根據觀察持續決定下一步 | 穩定控制圖 + 運行時任務 DAG |
| 自主性 | 低 | 高 | 分層控制 |
| 並行與依賴 | 依靠手寫並發和條件 | 單循環裡較難表達 | 圖中顯式表達（Planner 生成 DAG → Policy 校驗 → Scheduler 動態調度） |
| 狀態 | 局部變數或自由文本 | 對話歷史與外部 Memory | 結構化 State + Checkpoint |
| 驗證 | 流程末尾集中檢查 | 每輪可加入 Verifier | 獨立 Evidence Verifier 節點與控制分支 |
| 局部恢復 | 較弱（某分支失敗常需整條重跑） | 依賴 Loop 自己記住進度 | Checkpoint 與任務狀態支持中斷恢復 |
| 開發成本 | 低 | 中 | 高 |
| 適合場景 | 短任務、固定流程、快速 Demo | 開放探索、單 Agent 長任務 | 多角色、並行依賴、需審批與恢復 |

**路線一的代價**：使用者只問技術走勢，系統仍會把四類分析全部跑一遍；某分支失敗要嘛整條重跑、要嘛靠額外異常代碼拼報告；一旦需要人工確認或中斷恢復，固定流程會逐漸堆出大量 `if/else`、狀態欄位與補償邏輯——這時系統其實已經出現了圖，只是**圖藏在調用棧和條件語句裡**。

**路線三的具體結構**：`請求解析 → 混合 Planner 生成任務 DAG → Plan Policy 校驗 → Scheduler 找出依賴已滿足的任務 → 動態並行 Worker → Evidence Verifier → Controller（繼續分發/重新規劃/等待人工/生成報告/安全終止）`。外層控制圖保持穩定，每次運行的研究任務圖可依問題變化（只問技術走勢時 Planner 只生成一個 `technical` 任務）；Scheduler 不需提前知道會產生多少任務，只讀取當前計劃動態分發已滿足依賴的節點；每個 Worker 內部仍可運行自己的 Agent Loop——**Graph 負責 Worker 之間的依賴、並行與恢復，Loop 負責單個 Worker 如何用工具完成任務**。

路線三的收益集中在複雜任務（顯式依賴/並行/局部失敗恢復/驗證與審批有清楚位置/執行軌跡易於評測審計），代價則是需要設計狀態 Schema 與 reducer、動態任務與重試恢復增加測試組合、節點過細會讓系統難讀、簡短任務用這套架構投入可能超過收益。**這裡沒有絕對正確的路線，工程判斷在於能否用最低的結構成本換到當前任務真正需要的可靠性。**

### FSM 視角與框架對照（老周聊架构補充，2026-07-24）

Graph Engineering 更精確的類比不是普通有向圖，而是 **FSM（有限狀態機）**：Node＝狀態、Edge＝轉移條件，系統在有限狀態間切換直到終態——這比單純「資料流向圖」更貼近 Graph Engineering 實際在描述的東西：**系統處於什麼狀態、在什麼條件下切換到下一個狀態**。FSM 用在 UI 狀態管理（XState）、遊戲 AI（行為樹）、網路協議（TCP 狀態機）已有數十年歷史，概念不新，只是換了應用場景。

三個常混用概念的邊界：**DAG**（有向無環，適合編譯依賴／批次管線，可拓撲排序但無法表達重試回環）vs **有向圖**（允許環，是 DAG 的超集，Agent 編排用的正是這個）vs **FSM**（有向圖的特化形式，強調狀態與轉移條件）。

主流框架的實作路線並不相同：**LangGraph**（Node/Edge/State 三元素，顯式圖）、**LlamaIndex Workflows**（事件驅動，節點間用 Event 通信而非直接邊，更鬆耦合但適合非同步）、**AutoGen**（不顯式建圖，Agent 直接對話，拓撲隱式存在於對話流程，靈活但可讀性與可除錯性較弱）、**CrewAI**（Crew+Task 抽象，背後仍是流程圖，對不懂圖論的人更友好、適合快速搭原型）。

### 🔴 觀察性不是可選項，是多 Agent 圖的必要條件

單一 Agent 的執行路徑通常固定；圖的執行路徑**不確定**（同一次呼叫可能走 `A→B→C→D→END`，也可能走 `A→B→C→D→B→C→D→END`）。沒有追蹤（Trace），你不知道這次走了哪條路、哪個節點花多少時間、哪個節點輸出品質有問題——**這件事在單 Agent 場景是「重要」，在多 Agent 圖裡是「不可妥協」**。

### 具體：三重退出條件組合 + Reducer 範例

退出條件建議三種組合使用，不要只用一種：**品質門檻**（如 `quality_score >= 0.85`）＋**最大迭代次數**（`retry_count >= 3`，防止只看品質陷入死循環）＋**逾時**（整條鏈超過 X 秒強制終止）。只設品質門檻沒有次數上限，容易死循環；只設次數上限沒有品質判斷，可能過早截斷。

並行節點寫入同一個 State 欄位時的衝突，LangGraph 用 **Reducer** 解——例如 `context` 欄位指定 `operator.add` 作 Reducer，兩個節點的並行寫入結果會被**合併**而非互相覆蓋。這是「Structured State 需要 Schema 與版本」這條原則具體到程式碼層的樣子。

節點粒度的一句話判準：**節點的輸入輸出契約要能用一句話說清楚**——如果描述一個節點需要說「它做 A，然後做 B，還會做 C」，就該拆成三個節點；反之，若拆到每個小操作都是一個節點，圖會變成有幾十個節點的意大利麵，維護噩夢，圖結構反而比程式碼更難讀。

① 先找「真的邊」：沒有資料流就別讓它空等　② 把 Node 寫成「有合約的工作包」
③ 在獨立處 Fan-out，在相依處 Fan-in　④ 把 Verifier 放在 Edge 上，但要看證據

### 三個可直接套用的模板

| 模板 | 結構重點 |
|---|---|
| **深度文章** | 站內查重 → 研究與來源查核 → 大綱 → 初稿 → 獨立審閱（通過→人工確認→建草稿／不通過→修改最多 2 次）。**研究負責事實、寫作負責表達、審閱只輸出問題清單，寫入必須在人工確認之後** |
| **程式開發** | 讀需求 → 修改方案 → **隔離工作區** → 改碼 → Lint/Type/Test（通過→產 Diff 與測試報告→人工 Review／失敗→分析→修復最多 3 次）。**測試節點不應只接受模型宣稱「已完成」**，要保存實際命令、退出碼、失敗案例 |
| **並行調研** | 定義問題 → 五路並行（市場／競品／痛點／技術／法規）→ 等全部完成 → 去重整合 → 事實查核。匯總節點仍要處理重複、矛盾、時間差與來源品質 |

## C（關鍵行動）

- [ ] 上 Graph 前先確認訊號成立（權限分離／條件分支／可並行／需 Checkpoint／角色衝突），否則維持單一 Loop
- [ ] 為每個節點寫 Node Contract——尤其是**驗收標準**與**最大重試次數**
- [ ] 確定性條件一律用程式路由，模型只做語意判斷
- [ ] State 設計成結構化欄位（含來源與查核狀態），**不要把整段對話當 State**
- [ ] 一定要設 Budget 與停止條件，並在**不可逆操作前放人工核准節點**
- [ ] 檢查是否過度設計：**移除一個節點後，若權限、品質、恢復能力、驗收都沒損失，該節點就沒有存在必要**

## 新手常見五個錯誤

1. **為了看起來複雜而增加節點**——節點數量不是成熟度
2. **把所有對話當成 State**——缺乏欄位責任、版本與來源
3. **所有路由都交給模型**——確定性條件交給模型只增加成本與不穩定
4. **讓所有 Agent 都能修改共同產物**——沒有 Branch/Lock/Merge/Owner 機制就該維持單一寫入者
5. **只有重試，沒有失敗狀態**——達上限後應保存最後可靠狀態、錯誤證據與未完成項目再交人工
