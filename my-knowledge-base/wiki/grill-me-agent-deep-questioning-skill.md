## T（核心論點）

`grill-me`（Matt Pocock）核心理念：在正式寫任何一行程式碼或 PRD 之前，讓 AI 轉型為極具批判性思考的系統架構師——**不盲目奉承或直接輸出程式碼，而是展開高強度的深度訪談**，每次只拋一個關鍵問題（附建議解答），等使用者明確反饋後才推進下一關。與 Superpowers 這類「全自動強制約束」的重量級框架相反，`grill-me` 是**極簡可自由組合的「手術刀」策略**——CyberQ 認為這更適合新一代高推理模型（Sol 5.6、Fable 5），因為過度嚴苛的引導框架反而造成昂貴 token 消耗與無謂對話迴圈。

## B（適用場景）

**適用：** 規劃新功能、設計 API 介面、撰寫規格書前的決策收斂；搭配高推理模型（Sol 5.6/Fable 5）時想保留人機協同的決策節奏

**不適用 / 注意：** 與 Superpowers 比較是 CyberQ 的觀點性主張，非中立評測；未附原文出處，部分細節（如具體安裝指令）建議自行核實

## R（三個核心機制）

### 一、拒絕無效廢問——強制自主調查

若某個事實可透過檢視現有檔案、讀取配置檔或搜尋程式碼庫取得，**AI 代理必須自主完成調查，嚴禁向使用者提問已知資訊**。AI 只針對**需要商業邏輯選擇、架構權衡、技術選型**的「決策點」提問——這是 `grill-me` 與許多流於形式的提示詞技巧的關鍵差異。

### 二、單點聚焦的追問節奏

實戰範例：
```
/grill-me 我打算新增一個支援多租戶的 RBAC 權限管理系統，請開始追問我。

AI：檢查 schema.prisma 與認證機制後，注意到採用 JWT。
   第一個問題：租戶之間的資料隔離層級為何？
   建議選項：採用 Row-Level Security 結合 tenant_id 欄位，
             對現有資料庫結構變更最小。
   請確認是否採用，或給予其他指導？
```

> **AI 在收到確認前，絕對不會一口氣丟出多個問題，也不會冒然建立檔案。**

安裝：`npx skills add https://github.com/mattpocock/skills --skill grill-me`

### 三、下游閉環：`grill-me` → `to-prd` → `to-issues` → TDD

Matt Pocock 推薦的完整流程：**`grill-me`/`domain-model` 概念壓力測試 → `to-prd` 轉標準 PRD → `to-issues` 拆解任務清單 → TDD 撰寫程式碼**。

另有 **`grill-me-doc`**：針對已寫好的 PRD/架構草案，AI 化身嚴苛審查委員，掃描文字裡的**模糊條款、未定義邊界條件、潛在邏輯矛盾**，在交付開發前完成壓力測試。

## 🔑 CyberQ 觀點：為何組合拳優於 Superpowers（世代適配論）

> 由於 Sol 5.6/Fable 5 本身就有強大自主探索與推理底子，**過度嚴苛與重型的引導框架反而造成昂貴 token 消耗、拉長回應延遲，甚至衍生無謂對話迴圈**。

`grill-me` 一次僅拋一個關鍵決策 + 自動給建議選項，**恰到好處引導高智慧模型聚焦架構權衡**——這與知識庫既有 `superpowers-skill-bloat-risk-tiering`（強模型時代該把硬門檻改風險分級）是**同一世代適配命題的另一個案例**。

## C（關鍵行動）

- [ ] 規劃新功能前先跑 `grill-me`，讓 AI 自己查程式碼庫再問，別讓它問已知資訊
- [ ] 確認 AI 每次只問一個決策點、附建議選項——若它一次丟多問題，代表沒配置對
- [ ] 用完整閉環：`grill-me` → `to-prd` → `to-issues` → TDD，別只做概念訪談就跳去寫碼
- [ ] 已有初稿 PRD 時用 `grill-me-doc` 抓模糊條款與邏輯矛盾
- [ ] 用高推理模型時，優先考慮這類輕量可組合技能而非全自動強制框架

## 補充資料：五條規則完整中文版、理論來源與可複製 prompt（2026-08-07 併入）

來源：bnext〈AI Skills怎麼寫？grill-me工作流5步拆解，附中文提示詞可複製〉。本頁原本只記了三條規則，此處補齊五條與其理論出處。

### 五條規則（完整）

```
1. 決策樹建模
   把使用者的計畫或設計視為一棵決策樹，系統性地走訪每一個分支與邊界情況（Edge Cases），
   確保沒有任何被隱含假設的死角。
2. 一次只問一個問題
   嚴禁一次拋出大量問題清單。每次提問後必須暫停並等待使用者回應，避免造成認知負荷。
3. 事實靠查閱，決策才發問
   嚴格區分「事實」與「決策」。只要是能透過閱讀程式碼庫或環境檔案找到答案的事實，
   AI 必須先自行讀取，絕不向使用者提問。
4. 提供建議解答
   拋出問題時必須同時附上 AI 自身的建議答案與理由，
   讓使用者以「審查提案」的方式做決策，而不是面對空白提示詞。
5. 確認後才動工
   在所有決策樹分支尚未確認並達成共識之前，絕不提前撰寫程式碼或執行修改。
```

### 🔑 「決策樹」的理論來源

靈感來自《人月神話》作者 **Frederick P. Brooks 的《The Design of Design》**（2010）：

> **所謂設計，就是走完一棵樹的每個分枝，把選擇一個個定下來。**

而為什麼非做不可——**寫程式其實是連續做出幾百個微觀決定**（防呆怎麼做？斷線怎麼辦？極端資料怎麼處理？）。把模糊想法直接交給 AI，等於把這幾百個決定一併外包。**grill-me 讓 AI 沿著決策樹挖出盲點，但拍板定案仍由人負責。**

### 可直接複製的中文 prompt（非工程場景通用）

```
針對我接下來提出的計畫，毫不留情地訪問我，直到我們達成共識為止。
沿著決策樹一層一層往下走，把每個決定之間的依賴關係逐一解開。
每個問題都要附上你建議的答案。
一次只問一題，等我回答後再問下一題；一次丟出多個問題只會讓人混亂。
如果某件「事實」你自己查得到（搜尋、讀檔案），就自己查，不要問我；但所有「決策」都必須由我拍板。
在我確認我們達成共識之前，不准動手執行任何東西。
```

可用在企劃、報告、簡報、季報、換工作——任何需要先想清楚的決定。

## 補充資料：同名不同目的——Grill Me 的「入職訓練版」（2026-09-10 併入）

來源：〈ChatGPT「Grill Me」提示詞教學！每天簡單答 3 題，1 個月養出最懂你的 AI〉，韋惟珊，數位時代，
2026-09-07，<https://www.bnext.com.tw/article/92143/ai-employee-onboarding>
（整理自 Podcast《數位關鍵字》雲發互動科技創辦人陳子龍的做法）

⚠️ **這一節收的是一個同名但機制完全不同的做法，放在本條目是為了避免日後檢索時混淆。**

| | 本條目（Matt Pocock 版） | 入職訓練版（陳子龍） |
|---|---|---|
| 對齊的對象 | **一次任務**——開工前把模糊需求問清楚 | **一個人**——讓 AI 認識你這個人與公司脈絡 |
| 時間尺度 | 單場對話，達成共識即結束 | **約一個月**，每天幾分鐘的長期養成 |
| 提問節奏 | 一次一題，附建議解答，確認後才動工 | 每天 2–3 題，回答後複述理解，**每天最多追問一次更深的問題** |
| 產出 | 決策樹被走完，可接 `to-prd` → `to-issues` | 累積在 Memory／Project 裡的個人與組織脈絡 |

🔑 **兩者不衝突，可並存**：一個對齊任務，一個對齊人。本條目 T 層的「深度追問取代盲目奉承」在兩版都成立，
差別在**追問的標的是決策樹的分支，還是使用者本人的偏好與脈絡**。

### 做法（四步）

1. **開一個 ChatGPT Project**，在專案指令寫：每天問我 2–3 個問題，了解我的工作角色、管理風格、決策偏好、
   溝通習慣與生活中在意的事；我回答後**先複述你的理解**；每天最多追問一次更深的問題，追問後結束今天的提問；
   每次對話結束前整理這次學到的重點；記憶功能可用時，**把適合長期使用的資訊存進記憶**。
2. **建每日排程**：在該專案底下開新對話，請 AI 建立每天固定時間（例如 09:30）的排程，
   依專案指令自動啟動當天的第一輪提問。
3. 🔑 **光問答不夠——把真實產出丟進同一個專案**：週報、常用信件、簡報、工作文件。
   問答讓 AI 知道你**怎麼想**，文件讓它看到你實際**怎麼做**（表達方式、判斷標準、在意的細節）。
   這是這個做法最容易被略過、也最關鍵的一步。
4. **定期驗收並當場糾正**：隔一段時間問「根據目前對我的了解，你覺得我的工作風格是什麼？」
   答不準就直接糾正——把糾正也當成訓練資料。
