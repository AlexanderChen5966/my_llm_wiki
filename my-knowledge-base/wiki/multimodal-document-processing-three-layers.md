## T（核心論點）

處理企業 PDF 時該問的不是「**怎麼把 PDF 文字抓出來**」，而是「**怎麼讓系統保留文件中的視覺結構與語意關係**」。

因為 🔑 **OCR 抽取的是文字，不是語意關係**——一張流程圖 OCR 完之後，「誰先誰後、箭頭方向、哪個條件造成分支」全部消失。

> **OCR 能讓 AI 看到文字，但多模態理解才有機會讓 AI 看懂文件中的結構。**
> **RAG 的目標不是單純讓所有文件都「變成文字」，而是盡可能保留原本文件中的真正知識。**

## B（適用場景）

**適用：** 企業文件庫含掃描合約／舊版規章／紙本表單／流程圖／系統操作手冊截圖；RAG 建好了但問到流程類問題就答不準

**不適用 / 注意：**
- 🔴 **多模態理解成本高**，不能無差別套用——必須配合 Lazy OCR 與按需使用（見下）
- 純文字型文件（政策文件、文字報告、會議紀錄、條款）走第一層就好，別過度工程

## R（三層內容處理思路）

### 第一層：原生文字直接解析

**適用**：一般政策文件、文字型報告、會議紀錄、條款文件。**處理速度快、成本低，文字最接近原始內容。**

```
PDF → Text Parser → Chunk → Embedding → Index
```

### 第二層：掃描頁使用 OCR

**適用**：沒有文字層但主要內容仍是文字——掃描合約、舊版規章、紙本表單。

```
Scanned Page → OCR → Extracted Text → Chunk → Embedding
```

**這一層的目標**：把原本**完全不可搜尋**的圖片文字轉成可搜尋內容。

### 第三層：視覺結構交給多模態模型理解

**適用**：頁面中真正重要的是**流程圖、表格、截圖、圖表或視覺位置關係**時——單純 OCR 不足夠。

🔑 **該要求多模態模型回答的八件事**：
1. 這張圖的**主要目的**
2. 有哪些可見文字
3. **哪些元素彼此連接**
4. **流程的先後順序**
5. **哪些條件造成分支**
6. 表格中的欄列關係
7. 有哪些**重要警告或例外**
8. 🔑 **哪些關係只是推論，不能視為確定事實**

> 第 8 項最容易被忽略——**它是把不確定性一起結構化，而不是讓模型的推論偽裝成事實。**

## 🔑 視覺摘要的結構化格式（可直接借用）

一頁費用申請流程圖，視覺理解結果整理成 Metadata：

```json
{
  "page": 12,
  "content_type": "flowchart",
  "visual_summary": {
    "page_purpose": "說明費用申請的審核流程與分支條件",
    "visible_text": ["申請送出", "主管審核", "通過", "拒絕", "財務核銷", "退回申請人"],
    "relationships": [
      "申請送出 → 主管審核（固定步驟）",
      "主管審核 → 通過 → 財務核銷（審核通過路徑）",
      "主管審核 → 拒絕 → 退回申請人（審核拒絕路徑）"
    ],
    "do_not_confuse": "此流程為一般費用申請，不適用於超過 10 萬元的專案採購"
  }
}
```

**同一頁的純 OCR 產出**：
```
申請送出 主管審核 通過 拒絕 財務核銷 退回申請人
```

> 🔴 **兩者包含的文字差不多，但後者幾乎保留不了流程邏輯。** 視覺摘要的價值不只是把圖片「翻譯成文字」，而是**把原本只有人看得懂的空間與流程關係，轉換成模型可以理解的結構化語意**。

⚠️ 特別注意 `do_not_confuse` 欄位——**它把「這份知識的適用邊界」也一起存進索引**，避免檢索命中後被套用到錯誤情境。

## 系統截圖也需要理解「畫面正在做什麼」

企業操作手冊常見大量截圖。文件可能只寫：
> 「進入 Settings 後，點擊右上角的 Add User。」

**真正的資訊全部存在截圖裡**：Settings 在哪裡／Add User 按鈕的位置／**哪個頁籤需要先被選中**／**按鈕是否可能是灰色狀態**／畫面中有哪些必要欄位。

→ 只抽取圖片上的文字（`Settings`、`Add User`⋯）等於把操作步驟的**空間與狀態資訊全部丟掉**。

## 完整處理流程七步（含成本控制）

1. **優先解析原生文字**
2. 對掃描文字執行 **OCR**
3. 對流程圖、表格與截圖進行**視覺理解**
4. 將**視覺關係轉換成結構化摘要**
5. **保留來源、頁碼與不確定性資訊**
6. 🔑 透過 **Lazy OCR 控制處理成本**
7. 🔑 對昂貴的**多模態能力採取按需使用**

> 第 6、7 兩步是這篇最實用的部分——**三層策略不是「全部都跑」，而是依頁面類型分流**，否則成本會失控。

## C（關鍵行動）

- [ ] 先分類頁面類型（原生文字／掃描文字／視覺結構），**別對所有頁面套同一條 pipeline**
- [ ] 🔴 流程圖／表格／截圖**不要只跑 OCR**——OCR 保留文字但丟掉關係
- [ ] 視覺摘要一律含 `relationships` 與 **`do_not_confuse`**（適用邊界）兩個欄位
- [ ] 要求多模態模型明確標出**「哪些關係只是推論」**，別讓推論偽裝成事實
- [ ] 用 **Lazy OCR ＋ 多模態按需呼叫**控制成本，這是三層策略能否落地的關鍵
- [ ] 索引一律保留來源、頁碼與不確定性資訊（可追溯性）
