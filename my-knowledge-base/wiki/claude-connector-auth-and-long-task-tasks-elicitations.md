> 合併理由：兩者共同回答「**連接器要使用者或組織出面授權／補問時，路徑怎麼走**」，互為對照。受眾不同（外掛開發者 vs Team／Enterprise 管理員），條目分區閱讀即可。

## T（核心論點）

**連接器的兩個「回來問你」時刻——長任務中途缺條件、以及第一次存取第三方服務——官方都在把「人要介入的地方」從聊天視窗搬到明確的通道：補問走 Elicitations（表單或外部網址）、授權走外部流程或組織層級的集中授權。** 規範的底線一致：**密碼、API 金鑰、存取權杖、付款憑證不該經過聊天或表單**。

兩件事的使用者感受都是「流程變順」，但各自留下一條容易讀漏的邊界：Tasks 的「完成」不等於內容正確、「取消」不等於復原；企業自動登入省掉逐人登入，卻**不是**身分驗證的替代品。

## B（怎麼選、注意什麼）

**適用：**
- 外掛開發者：要做深度研究、文件整理這類**耗時、會中途缺條件**的工具 → 看 Tasks＋Elicitations
- Team／Enterprise 管理員：員工要連多個工作工具、不想每人逐一登入同意 → 看 Claude-issued auth

**不適用 / 注意：**
- ⚠️ **Tasks 在 MCP 2025-11-25 規範版仍標「實驗性」**；協定存在不等於所有客戶端／外掛都能用，需**客戶端與服務端都實作**。Claude Code 的文件不能直接推定 Claude 網頁版畫面相同
- ⚠️ **企業自動登入為測試版（beta，2026-11-03）**；身分提供者（IdP）管理方式則是正式開放。連接器也必須支援 Claude 作為簽發者
- 🔴 **安全類事實（下方〈不驗 MFA〉〈撤權行為〉〈簽發者唯一〉）均引自二手整理，引用或據以設計離職流程前，回官方文件（Anthropic 支援文件 15537633、Supabase 部落格）核對**
- 官方展示影片（Tasks 示範）是官方製作，非作者實測

## R（內容）

### 一、MCP Tasks：長工作的「寄件單號」（2026-10-24 快照）

- **Tasks 給耗時工具工作一個可查詢的身分**，呼叫端不必把整段等待塞在同一次回覆；結果可用後再取回。
- **五種狀態**：工作中／需要輸入／完成／失敗／取消。價值是把「安靜」拆開——在跑、在等你補資料、還是已停止。
- 三個容易誤讀：
  - **完成≠內容正確**：只表示協定要求的工作產生了結果；缺漏的報告也可能「完成」，來源與範圍仍要自己查。
  - **取消不復原已發生的動作**：取消只是「請求停止」；已讀取的資料、已產生的費用／暫存／外部變更不會自動倒轉。需要寫入其他服務的外掛，應讓工具回報目前產物，使用者才不會把取消誤解為「從未發生」。
  - **狀態細節取決於工具實作**：看到「工作中」只能期待可追蹤的狀態，不能推定會有完整的內部過程紀錄。
- **重試判斷**：先讀任務身分與狀態再決定接續取回或重跑，連續重送同一要求可能讓多份工作一起跑。
- **開發者提醒**：任務存取要綁授權背景（能查任務身分的人不應讀到別人的結果）；要說清楚任務**保留期限**，過期時別報成「從未開始」；補問的答案要對得上哪個人、哪個任務。測試別只走正常路徑——試拒絕補問、失敗、任務到期、取回時斷線。

### 二、Elicitations：工具透過客戶端向你補問（2026-10-24 快照）

- **兩種模式**：**表單**（可整理的條件：期間、語言、數量）與**外部網址**（適合在網站完成的步驟，如第三方授權）。
- 🔴 **規範禁止用表單索取密碼、API 金鑰、存取權杖與付款憑證**；第三方服務授權應走外部流程，讓使用者在可信任的目的地完成，不要把憑證貼進聊天。
- 網址模式也要小心：不應在連結夾帶個資或憑證（網址可能被瀏覽器紀錄、日誌或轉貼保存）。
- 補問應提供**拒絕／取消**；「客戶端連上 MCP 服務」與「服務連上第三方平台」是兩層關係，後者的授權不能寫成前者已取得全部權限。
- 值不值得補問的判準（作者舉例）：答案會改變內容的才問（讀者是工程師還是主管），不影響內容的細節（字體大小）用合理預設。

### 三、企業連接器自動登入：Claude-issued auth（測試版，2026-11-05 快照）

**運作**：管理員核准後，由 Claude 為仍在組織內的成員簽發身分聲明（文中稱 ID-JAG）；連接服務先信任**組織專屬的簽發者網址**，再依**電子郵件**對應到自己的帳號並發**短期存取權杖**，沿用該成員既有角色。省掉的是「每人逐一登入與同意」，成員仍需在服務端有符合條件的帳號，能讀什麼仍由服務權限決定。

**適用方案與名單**：Claude Team／Enterprise（採 Claude 簽發時不需另設 IdP／SSO，但第三方服務可有自己要求）。**2026-11-05 查詢，官方測試名單 14 個**：Amplitude、Apollo.io、Atlassian、Datadog、Dropbox、Figma、Granola、HubSpot、Linear、Mixpanel、Notion、PagerDuty、Semrush、Supabase（完整企業管理授權的連接器另有更多項目；名單屬快照，可能變動）。

**Supabase 設定流程（廠商自述視角）**：組織已設 SSO → 成員先以**與 Claude 相同的 email** 登入一次 → 擁有者／管理員核准 → Claude 組織設定選 Supabase、身分來源選「由 Claude 簽發」取得簽發者網址 → 貼到 Supabase SSO 進階設定 → 連線測試 → 選角色與範圍。小範圍試用時，確認**未一併勾選內建角色群組**（否則一般使用者、管理員、擁有者可能全被納入）。建議先找兩三位成員跑真實請求，並**走一次撤銷流程**。

🔴 **三項安全邊界（二手整理；引用前回官方核對）**

1. **不驗 MFA**：Claude 檢查的是**組織成員資格**，不替企業驗證使用者在 IdP 的登入、多因素驗證或連接服務自己的登入規則。原本靠這些條件控制存取的企業，要確認改用 Claude 簽發後由哪一層落實。
2. **撤權行為**：移除 Claude 成員只**停止新的身分聲明**，既有服務權杖仍依服務端到期與撤銷規則生效；在 IdP 停用帳號**不會自動阻斷**這條授權路徑（Claude 與 Supabase 不再詢問 IdP 該成員是否有效）；目錄同步須**實際刪除**成員（暫停／標不活躍效果不同）；email 重新分配前，先把舊帳號從連接服務移除。離職作業要把 Claude 與連接服務兩邊一併處理。
3. **簽發者唯一（Supabase）**：每個 SSO 提供者只信**一個**簽發者，填 Claude 的網址會**取代**原 IdP 網址、Supabase 會拒絕原提供者的聲明直到恢復，其他依賴同一提供者的 AI 工具可能受影響；同一個 Claude 簽發者網址只能供一個 Supabase 組織使用。

**其他**：管理授權與瀏覽器登入同時開啟時，Claude 先試管理授權、失敗再提示個別登入；成員仍可加個人連接器，管理員要辨認哪些來自集中設定；官方另有「要求連接器僅走管理授權」的控制；關閉 Claude 簽發後，服務端已發出的權杖如何失效依該服務而定。

### 四、兩者並讀的對照

| 面向 | Elicitations（補問） | Claude-issued auth（組織授權） |
|---|---|---|
| 誰決定 | 使用者當下答覆或拒絕 | 管理員事前核准＋角色範圍 |
| 憑證怎麼走 | 禁止進表單；第三方授權走外部網址 | 簽發身分聲明，服務發短期權杖 |
| 最容易漏看 | 補問答案綁錯任務／人 | 不驗 MFA、撤權不即時 |
| 成熟度（本庫快照） | 規範中 Tasks 屬實驗性 | Claude 簽發為 beta |

## C（關鍵行動）

- [ ] 做長任務外掛：先確認客戶端與服務端都支援 Tasks，再選「固定來源、結果易驗證」的任務試跑；完成後仍抽查一兩條核心事實
- [ ] 補問設計：任何需要密碼／金鑰／權杖的情境一律改走外部網址流程，不放進表單
- [ ] 管理員試行：只選一個團隊的自訂角色，確認內建角色群組沒被勾；通知全組織前走完「連線→真實請求→移除成員」
- [ ] 離職流程：Claude 成員、連接服務帳號、IdP 三處都列入；不要只停用 IdP 帳號
- [ ] 以上安全邊界落實到制度前，先回官方文件核對（本條目為二手整理）
