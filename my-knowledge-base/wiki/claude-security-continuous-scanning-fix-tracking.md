## T（核心論點）

Claude Security 在 4 月公開測試後，於 2026-10-21 新增**持續掃描**：先做一次深度基準掃描，之後追蹤新提交、判斷既有發現是否已被修掉（可標已修、再現時重開），並支援多程式庫專案、可編輯威脅模型與 API／MCP。**重點是把「一次性報告」變成持續維護的清單；但「持續」不等於即時**——後續掃描依風險與複雜度排程，沒有固定時間表。

## B（適用場景）

**適用：**
- 已有 Claude Enterprise、跨服務資安待辦很多、想把掃描發現接進現有修補流程的團隊，從**一個專案**試起

**不適用 / 注意：**
- Pro／Max 使用者；需要服務完全不保留資料（不支援 ZDR）的團隊——先核對資格與條件
- 不能用「剛提交、畫面沒新發現」推論變更已通過檢查；要看發現附的**分支與提交**判斷覆蓋到哪個版本
- 同一份程式碼不同次掃描結果可能不同（代理依情境調整，非固定規則）
- Claude Code 的資安外掛（見 [[claude-code-security-guidance-plugin]]）是另一條部署路徑，**條件不能互相套用**

## R（功能與操作要點，依來源轉述）

### 持續掃描
- 建立專案、連接程式庫、選分支與範圍 → 深度基準掃描（幾分鐘到幾小時，視規模）→ 之後定期檢查變更
- 每項發現列出檔案位置、受掃描的分支與提交

### 修補追蹤與重新開啟
- 系統比對變動程式碼判斷發現是否已修正（即使在別的工具修）；問題再出現時重開
- 結案理由：已修正／由合併請求修正／誤報／接受風險／重複——**報表加總時應分開**（把「接受風險」算成修正會讓數字好看卻無法回答是否更安全）
- ⚠️ **fixed ≠ 正式環境已部署**：程式碼修好與服務更新是兩段，建議把發現狀態與部署紀錄連起來
- 修補仍需人工審查；官方定位是產生有針對性的修正建議，不宣稱可略過回歸驗證

### 多程式庫與威脅模型
- 每專案最多 **8 個**程式庫，含「正式掃描範圍」與「僅供背景脈絡」兩種，兩者都算上限；背景庫會被讀取但不在其中提出發現
- 適合放同一服務的前端、後端、共用元件；互不相關的庫放一起仍需說明關係
- 威脅模型由 Claude 先依程式碼產生，團隊可編輯、可加入架構文件；後續掃描用它決定哪些問題值得提出與嚴重度評分——**環境說明錯誤（例如服務已改公開但仍寫僅內部）會低估影響**

### API、MCP、Webhook 與角色
- API 可列出／管理專案、程式庫與發現；MCP 讓 Claude／Claude Code 接同一套資料；Webhook 在新發現時通知現有系統（需保留發現識別，避免同一問題被當成兩個新漏洞）
- 專案角色 Full／Triage／View；個人存取權杖只能看與改該使用者有權限的內容
- GitHub.com 與 GitHub Enterprise Server 經 Claude GitHub App 連接；其他 Git 服務用位址與授權權杖；內部自架環境還要符合官方網路連線要求

### 方案與額度
- 需 Claude Enterprise 的 premium seat，組織開啟按用量計費的 credits，由擁有者啟用；不要求另有 Cyber Verification Program 存取權（但這不代表 Pro／Max 可用）
- 促銷額度的「期」是從組織開始日算到下一個月同日，不是每月月初重置；額度先於原有承諾支出或 credits 扣除
- 組織可另設專屬支出限制，並在專案設定看當月與每日用量

### 舊專案遷移限制
- 舊版專案不自動享有新優惠，需遷移到新版體驗
- 遷移會建立新專案、複製發現並封存舊專案；**成員、Webhook、排除資料夾、掃描歷史與原排程不會帶過去**，遷移後要重新核對連接與範圍
- **GitHub Enterprise 專案不能使用此遷移方式**

## C（關鍵行動）

- [ ] 先確認是否為 Enterprise、資料政策是否允許（不支援 ZDR）
- [ ] 選一個已有測試、部署範圍清楚的服務試點：確認首次掃描引用的提交 → 追一項人工確認的發現，到修改、合併、重新掃描後的紀錄
- [ ] 誤報要把具體條件寫進威脅模型，而不是只按忽略
- [ ] 評估時看有用發現比例、修補品質與待辦結清速度，不看發現總數
- [ ] 若要用促銷額度，先查自己組織的起算日與到期日（2026-12-31 UTC 為整體截止）
