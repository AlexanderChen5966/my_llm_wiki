## T（核心論點）

多輪任務中途改需求時，常見兩種失敗：**舊要求回流**（已撤回的條件被寫回來），或**整份重做**（浪費仍有效的成果）。GitHarness 的主張是：問題不只在記憶容量，而在**缺少明確的版本關係**——把每一版需求和當時對應的工作狀態一起存成版本（借用 Git 的 commit／branch），新需求來時，選一個**語意上仍相容**的版本接著做，而不是一律從最後狀態延續。

🔑 判斷「更合適」的版本 ≠ 挑最早的、≠ 挑文字最相似的，而是檢查舊成果是否仍符合目前條件。

## B（背景）

**適用：** 長時間、多次改規格、涉及大量檔案或工具操作的 agent 任務。

**不適用 / 注意：**
- 短任務：清楚說明最新要求與撤回條件，通常比導入版本系統更划算（作者觀點）
- 照抄研究名稱或在 prompt 加一句「請忽略舊要求」，不會讓聊天工具自動具備分支記憶（作者觀點）
- 為何不補進 [[agent-memory-lifecycle]]：該條的 T 是**跨 session 記什麼、淘汰什麼**；GitHarness 處理的是**同一任務內需求變更時，回到哪個版本**，軸線不同，所以獨立成 ideas

## R（關鍵細節）

**研究設計（論文，媒體轉述）**
- 保存「任務要求＋對應工作狀態」，更新要求時選擇可延續的版本
- **GitAgent** 負責版本選擇，以強化學習訓練——🔴 被訓練的是**版本選擇器**，不是底層解題模型；不能說成每個接入的模型都被重新訓練
- 新評測集 **MTAgentBench**：數學、資料查詢、搜尋、程式、研究五類多輪任務（中途會收到需求更新）
- 比較設定：工作流程 TCRAG／StackPlanner／OpenHands × 模型 Qwen3-32B／DeepSeek V4 Flash × 五類任務 ＝ **30 個測試設定**
- 原文只說「版本化記憶有助於處理中途修改」，🔴 **沒有給品質或 token 改善的具體數字**
- 「某設定大幅降低程式任務 token 用量」——🔴 **社群（X）摘要轉述，文中無數字**，不可寫成量化結論；原文也提醒 token 減少 ≠ 所有成本等比下降

**方法比較（作者整理）**

| 方法 | 主要能力 | 可能的盲點 |
|---|---|---|
| 長上下文 | 讀入更多原始歷史 | 有容量，不等於理解版本優先順序 |
| 摘要記憶 | 壓縮對話與工作重點 | 摘要可能漏掉撤回或例外條件 |
| 一路延續最新狀態 | 實作直接 | 可能帶著失效工作繼續 |
| GitHarness 版本方式 | 連結需求與工作狀態，選相容起點 | 需要可靠的版本選擇與保存機制 |

**落地限制（作者觀點）**
- 🔴 **外部操作不能隨版本倒帶**：寄出的信、付過的款、改過的客戶資料不會因回到舊版本而撤回；需要另做**操作日誌與重複執行保護**，並把內部思考、檔案成果、對外操作分開記錄
- 程式碼版本正確 ≠ 代理理解的需求版本正確；現有 Git 只管檔案差異，不管「這段改動是為哪一版需求做的」
- 重啟某個舊版本前，要確認輸入仍可讀、工具版本與權限仍適用
- 使用者端最容易立即採用的習慣：改需求時講清楚「**撤回什麼、保留什麼、新增什麼**」
- 文中的市場報告（台日→只剩台灣）、登入頁（撤回設計只留錯誤修正）都是**作者示意情境**

## C（連結與應用）

- [ ] 在本庫的長任務 handoff 文件裡，改需求時固定用「撤回／保留／新增」三欄記錄，而不是只寫新方向
- [ ] 涉及寫入外部系統的 skill，把「已執行的對外操作」另列一份紀錄，避免重跑時重複執行
- [ ] 若日後取得論文原文，補上 MTAgentBench 的實際品質與 token 數字
