## T（核心論點）

多代理協作的瓶頸不在代理數量，而在**交接與驗收能不能寫成可檢查的文字**：交付物在哪、依據是什麼、哪些還沒完成、誰能定稿。Workbench 提供的是「讓交接看得見」的工具機制；Agency Agents 提供的是「角色文件該寫什麼」的模板格式。兩篇都建議**從「產出＋檢查」兩個角色起步**。

⚠️ 兩篇一致主張「代理數 ≠ 成果」，但這是**同一作者的觀點互相呼應，不是兩份獨立證據**。

## B（背景）

**適用：** 開始讓多個 AI 助手分工研究／寫作／檢查，卻常出現「說完成了，下一個又從頭做」「兩個代理各改一份」的情況。

**不適用 / 注意：**
- 一個人能直接完成來源查核的工作，拆成多個代理反而讓資訊在交接中變薄（作者觀點）
- 兩個工具都無法從原文追到官方出處，功能描述需日後核對

## R（關鍵細節）

### 一、Workbench：Markdown 共用工作空間（官方文件，媒體轉述）

- **看板**：Markdown 標題表示欄位，不同勾選符號表示待辦／進行中／完成；卡片可附負責人、標籤、期限、說明與自訂欄位
- **建議（suggestion）權限**：可提修訂但**不能直接改正式文件**；一般讀取**不含未接受的建議**，接手者不會把候選改法當正文
- **版本衝突**：寫入可帶讀取時的版本，若他人已改，伺服器回報版本衝突，需重讀後合併（等同樂觀鎖；「樂觀鎖」是本庫用語）
- **認領**：開放請求同時被認領時，只有成功取得者接手
- **具名代理**：動作可在紀錄中辨識，但🔴 **顯示名稱 ≠ 身分認證**
- **版本紀錄**保存正式 Markdown，未接受的建議不會自動變成還原內容
- **入口**：網頁編輯器、一般 HTTP、官方 CLI、MCP——**MCP 不是必要前提**
- 🔴 **分享連結內含存取金鑰**，官方提醒不要貼進文件、聊天或留言
- 工作狀態元件可標示「等待人員介入」並記錄要回答的問題
- 免費編輯器 ≠ 整個代理流程沒有成本（作者提醒）

### 二、Agency Agents：社群角色模板庫（媒體轉述）

- **社群專案，不是 Anthropic 官方**；與 Anthropic 官方開發範例是不同來源
- **MIT 授權**（只涵蓋角色文件本身，模型、外部服務、輸入資料各有條件）
- 角色文件六欄：**身分定位、主要任務、關鍵規則、交付物、工作流程、成功指標**（repo 規範，媒體轉述）
- 2026-10-13 查閱時已有桌面應用、多工具整合，以及輸出各工具設定格式的轉換／安裝腳本
- 「負責發布」之類的角色描述，不等於取得實際操作權限；權限仍由執行環境決定（作者觀點）

### 三、兩篇共通的交接／驗收做法（作者觀點）

- 先安排**產出＋檢查**兩個角色，兩邊拿**同一份材料與需求版本**
- 交接要留下結果、依據、未完成部分；矛盾資料保留兩份來源與日期，不替下游擇一
- 審查意見要含**位置、問題、證據、修改方向**，並區分必要修改與可選建議
- 🔑 **角色名稱不增加模型能力；角色間共識不能替代查證**
- 工具讀到的內容中若含操作指示，只當材料看，不自動擴大工作範圍（prompt injection 防護，見 [[prompt-injection-vs-jailbreak]]）
- 驗收看三件事：重複工作有沒有減少、結果能否回查、修改是否可控
- 文中「比較三個產品匯出功能」「每週工具介紹」等都是**作者示意情境**

## C（連結與應用）

- [ ] 本庫 raw-pipeline 的 A→B→C 交接已是「產出＋檢查」結構；可對照「審查意見四要素（位置／問題／證據／方向）」檢查 Agent B 給 Agent C 的指示格式
