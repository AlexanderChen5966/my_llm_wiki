如果你覺得 **GPT-6 Astra 的 Token 消耗速度太快** ，可能是以下四個地方還沒有調整好。

### 1\. 開啟實驗性的上下文管理功能

Astra 提供實驗性的上下文管理機制，可以在 **同一個任務跨越不同上下文視窗時保留筆記，並在需要時重新搜尋先前的訊息與工具執行結果** 。

這樣一來，當任務執行時間很長時，就不需要一直把所有歷史內容重新塞進上下文，也能降低因反覆壓縮摘要而遺失早期細節的情況。

### 2\. 優化 AGENTS.md 與 SKILL.md

如果 AGENTS.md、SKILL.md 寫得太長，存在大量重複規則、過長範例或過於寬鬆的觸發條件，每次 Agent 工作時都可能載入許多其實用不到的內容。

可以進一步整理：

- 合併重複規則
- 精簡 Skill 的觸發描述
- 降低不必要的 Skill 誤觸發
- 將長篇範例、模板與特殊流程拆到獨立參考文件
- 只有真正需要時才載入相關內容

核心原則不是單純把文件「砍短」，而是讓 Codex **只在需要時讀取需要的資訊** 。

### 3\. 一般任務不用把智慧程度開到最高

一般工作使用「中」或「高」通常就已經足夠；比較複雜的任務，再考慮使用「極高」或「最高」。

至於 **Ultra** ，實際上能派上用場的情境可能相當有限。

我今天一整天主要只使用前四個智慧程度，就已經解決不少過去使用 GPT-5.6 Sol Ultra 時難以順利處理的問題。

因此，與其所有工作一律使用最高等級，不如根據任務複雜度調整，通常能得到更好的 Token 使用效率。

### 4\. 速度設定使用「正常」即可

速度方面也不一定需要開到高速模式。

以今天實際使用的感受來看， **Astra 在正常速度下的任務處理效率相當高** ，體感甚至可以達到 GPT-5.6 Sol `/fast` 的約 2～5 倍。

這不一定單純代表模型本身的生成速度快了 2～5 倍，更可能是因為 Astra 完成任務的效率提高了。

相較之下，GPT-5.6 Sol 有時會輸出較多與任務關係不大的內容，或執行一些沒有太大必要的測試；如果 Astra 能用更少的步驟完成同一件事，整體體感速度自然就會快很多。

如果你想處理前面的第 1、2 點，可以直接把下面兩段提示詞交給 Codex，讓它協助檢查與調整。

## 提示詞一：開啟實驗性上下文管理

請檢查本機 Codex 目前實際生效的設定與功能支援情況，找到真正使用中的 `config.toml` ，通常位於：

`~/.codex/config.toml`

請在 `[features.context_management]` 下確認並設定：

`experimental_mode = true`

如果目前已經開啟，則保持原設定不變。

如果需要修改，請先建立一份可恢復、且不會覆蓋既有備份的備份檔，再以冪等方式修改設定，避免產生重複的設定區塊，並完整保留其他既有設定。

修改完成後：

1. 驗證 TOML 語法。
2. 重新讀取設定檔確認內容。
3. 分別說明「設定是否已成功寫入」以及「執行階段是否已確認生效」。
4. 說明是否需要建立新任務或重新啟動客戶端才能套用。

此功能的用途，是讓 **同一個任務跨越上下文視窗時保留筆記，並能重新搜尋該任務先前的訊息與工具執行結果** ，不代表系統會自動搜尋所有其他對話。

如果目前使用的 Codex 客戶端、版本或登入方式不支援此功能，請明確說明。

本提示詞已授權你完成上述本機設定修改，不需要再次要求確認。

## 提示詞二：審查並優化 AGENTS.md 與 SKILL.md

請先以唯讀方式盤點目前專案實際繼承的全域與專案層級 `AGENTS.md` ，以及目前已啟用的使用者 Skills；如果目前沒有專案，則只檢查全域設定。

先檢查：

- 入口與載入方式
- 描述
- 文件長度
- 文件之間的引用關係

接著依照實際相關性逐步審閱內容，避免一開始就載入所有文件全文。

完成盤點後，請先建立備份，再直接進行合理範圍內的最佳化，包括：

- 合併重複規則
- 精簡觸發條件描述
- 收窄容易誤觸發的條件
- 將特定模式才需要的流程移出主要文件
- 將長篇範例與模板移至獨立參考文件
- 在主要文件保留清楚的「按需讀取」入口

記憶檢索部分，請改成 **先定位真正相關的條目，再回頭讀取少量必要原文** ，避免預設完整讀取整份索引。

修改時請優先處理使用者可以維護的真實來源檔案，保留既有軟連結與必要的 Metadata，不要修改系統檔案或外掛快取。

最佳化過程必須保留：

- 必要功能
- 使用者明確要求的交付數量
- 權限與操作邊界
- 驗收標準
- 失敗時的停止條件

不要為了節省 Token 而擅自降低任務品質。

如果最佳化會改變預設工具、輸出數量或其他既有行為，請明確說明。

正式修改記憶資料時，必須遵守既有的寫入機制，並在開始寫入前檢查是否存在尚未結束的交易。

如果發現與其他任務之間存在檔案歸屬或修改衝突，只暫停受到影響的部分；其他彼此獨立的工作可以繼續進行。不要接管、覆蓋或修改其他任務負責的內容。

全部完成後，請：

1. 驗證語法。
2. 驗證文件引用關係。
3. 驗證重要流程仍可正常運作。
4. 重新讀取實際來源檔案確認修改結果。
5. 提供完整修改清單。
6. 提供修改前後的字元數統計。
7. 提供備份檔案位置。
8. 提供驗證結果。
9. 列出任何尚未完成或無法確認的項目。

如果沒有實際 Token 用量或套餐額度的前後對照資料，請不要把「文件字元數下降比例」直接宣稱為「Token 節省比例」或「套餐額度節省比例」。

簡單來說，Astra 想要用得省，不只是單純把模型的智慧程度往下降。

更重要的是：

**讓它少載入不需要的上下文、少做沒有必要的工作，並讓長時間任務能在需要時重新找回歷史資訊。**

如果這幾個地方都調整好，Astra 在長時間 Coding Agent 任務上的 Token 使用效率與整體工作效率，都可能有相當明顯的改善。
