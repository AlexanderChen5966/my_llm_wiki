已經付費訂閱 Claude，換到另一個協作工具時，最直接的疑問是：同一份模型能力，是否又要多付一張帳單。

Capy 0.5 更新讓 Pro 與 Max 使用者連接既有訂閱，透過 Claude Code 模式執行工作。這把原本分散的訂閱與工作介面接了起來。

但選模型時要選對入口，因為這個模式使用的執行框架，和 Capy 自己的代理不同。

Capy 同一次更新也加入 OIDC 雲端身份，讓機器交換有期限的憑證。前者關係模型額度，後者關係機器可以存取什麼資源，兩者需要分開理解。

我認為已經使用 Claude、也需要雲端與個人裝置協作的開發者，可以先拿一個小任務試用。比較時應一起看完成結果、額度與機器成本。

先釐清訂閱如何被使用，才能知道這次更新究竟省下哪一段重複設定。

## Capy 0.5 如何使用 Claude 訂閱，模型要從哪裡選？

要使用原本的 Claude Pro 或 Max 訂閱，應在模型選單中選擇 Claude Code 分類下的模型。

依十月二十二日的 [官方更新說明](https://capy.ai/changelog/0.5.0?ref=aiposthub.com) ，Capy 會透過 Claude Agent SDK 執行這個模式。SDK 是供開發者整合功能的套件，這裡負責提供 Claude 的代理執行能力。

因此，畫面上出現同一個模型名稱，不代表所有入口都使用相同額度來源。選對分類，才能讓工作走到已連接的訂閱，避免把一般模型連接和訂閱模式混在一起。

官方也特別區分，Claude Code 模式與 Capy 原生代理是不同的執行框架。框架可以理解為圍繞模型安排工具、對話和工作步驟的那層程式。

這個差別會影響評估方式。同一個模型在不同框架裡，取得的工具和工作安排可能不同，所以不能只看模型名字，就預設每項任務的行為完全一致。

更新說明指出，Capy 的工具、機器、子代理與 Pull Request 在這個模式裡仍可使用。Pull Request 是提交程式修改、讓團隊審查合併的入口，因此原本的協作結果仍可接回開發流程。

使用者也能連接多個個人 Claude 訂閱，並在模型頁面調整順序。官方說明，某個訂閱用完後，會按排列順序改用下一個。

這讓額度來源更有彈性，但團隊應知道這段工作由哪個帳號執行。若幾個訂閱有不同用途或管理者，事先分配比等到用量出現差異再追查容易。

第一次驗證時，可以先建立一段新工作，確認所選分類與連接帳號，再執行小型修改。保存工作結果與額度變化，能幫助團隊知道實際路徑是否符合預期。

### 連接檢查通過後，為什麼仍要跑一次實際任務？

Capy 保存雲端連接前會檢查設定，這能確認一段身份交換是否接通。但某個服務能認得機器，不等於代理已經能讀取任務需要的每份資料。

例如，角色可能允許列出儲存空間，卻不允許讀某個資料夾。連接成功後的實際查詢，能把這類差別變得可見，讓維運者按具體資源調整。

因此，測試任務應明確寫出目標與預期結果。如果只要求「確認雲端可用」，代理可能停在列清單成功，團隊卻以為整條工作已經驗證。

同樣的做法也適用模型訂閱。先確認連接，再做一項有輸出的工作，最後查看額度來源，能分清登入、可呼叫和實際完成是不同階段。

若工作需要在不同帳號之間接續，團隊還要確認結果保存在哪裡。某個人的私人連接可以完成查詢，不代表其他成員也能讀取輸出，交接權限應一起測。

Capy 這次把多種入口集中到同一個工作區，便利也來自這種連續性。把每段責任看清楚，才能讓同一個介面裡的模型、機器與服務，各自使用正確身份。

這類試點不用追求大規模。能清楚解釋一次工作如何完成，通常比同時啟動多個難以追查的任務，更適合建立團隊的日常使用方式。

訂閱帶得進來，只回答了模型額度從哪裡來。這還不能直接回答整項工作是否完全免費。

## 免費連接 Claude 訂閱，哪些費用仍要分開看？

原訂閱仍受它的額度與使用條件限制，雲端機器和平台方案也需要按各自規則計算。

Capy 0.5 的分享貼文以免費連接作為重點，官方更新頁則描述如何使用既有 Pro 或 Max。這表示可以沿用已付費的模型方案，不能推成所有運算資源都沒有費用。

對開發者而言，一項代理工作可能同時使用模型、工作機器與外部工具。把模型額度移到原訂閱後，其他資源仍可能照原本方式使用，應分項確認。

例如，代理在雲端跑測試，消耗的是工作機器的資源。如果又透過外部服務產生圖片或讀取付費資料，那些服務也有自己的計費條件。

因此，比較成本時，適合記錄同一個任務的總投入。只看到模型帳單少了一筆，卻沒有看機器執行時間，可能低估整段流程需要的資源。

訂閱額度也不等於固定可完成多少任務。不同工作需要的上下文、重試與工具步驟不同，簡單修改和大型搬遷不能用同一個任務數直接比較。

官方這次也把雲端 iOS、Android 手機與行動建置，列入 Pro 以上方案，不再需要另外申請存取。這是方案可用性，和每項資源是否有額度限制仍是不同問題。

準備測試行動應用的團隊，應先查看帳號的方案與實際可用資源，再安排建置與操作。若只根據公告標題就派長時間工作，較難預估最後成本。

合理的試點是挑一項過去已完成的工作，用新模式重做相近範圍，觀察人需要介入多少次。因為目標是完成同樣品質，便宜卻需要大量重工也未必划算。

把模型與機器分開計算後，團隊還要處理另一件事：機器要如何證明自己，才能碰到公司的雲端資源。

## OIDC 短期憑證怎麼運作，和貼一把服務金鑰差在哪？

Capy 會簽發機器身份，再讓機器向雲端交換有期限的權限，減少長期保存固定密鑰的需要。

OIDC 是一套讓服務證明身份的共同規格。在這次更新裡，可以把它理解為機器拿著可驗證的身份證明，向雲端申請這次工作需要的臨時通行證。

官方列出 Google Cloud、AWS、Azure 與 Vault，也提供可讓其他相容服務信任的通用入口。不同服務的設定方式不同，但核心都是先確認身份，再交換短期憑證。

這和把一把長期金鑰放進每台機器不同。API 金鑰是程式呼叫服務、取得權限的機密資料。固定金鑰一旦散落到多個地方，日後撤換就需要找出所有副本，臨時憑證則有自己的有效期限。

但憑證有期限，只處理「能用多久」。能看哪些資料、可以修改什麼，仍由雲端角色與信任條件決定，不能把短期直接等同於最小權限。

例如，某個專案只需要讀測試資料，角色就應以這段需求設定。若給的是整個帳號的廣泛管理權，憑證即使會到期，在有效期間仍可能碰到過多資源。

Capy 的新設定頁讓使用者選擇專案，以及機器要使用的帳號或角色，並在保存前檢查連接。這能幫助發現設定是否接通，但接通仍不等於授權範圍正好合適。

對團隊而言，可以先用只讀角色驗證一項明確查詢，再按任務需要加入有限寫入。這樣每次擴權都有具體用途，也較容易知道失敗是身份還是資源權限造成。

如果原本已經把長期金鑰放進其他部署，加入 OIDC 也不會自動刪除舊副本。轉換流程需要列出哪些工作已改走新身份，哪些仍依賴舊設定。

身份管理因此是一項持續整理工作。這次更新降低了接短期憑證的門檻，接著還要看多人共用工具時，代理究竟使用誰的帳號。

## 個人 MCP 帳號與配對裝置，如何影響團隊工作？

同一台團隊工具可以按成員使用個人帳號，雲端工作也能把子任務送到指定的配對裝置。

MCP 是讓 AI 取得外部工具的共同介面。Capy 0.5 針對以 OAuth 登入的組織工具，加入每位成員各自連接的模式，讓工作使用建立該段對話者的帳號。

OAuth 可以理解為在服務的登入流程中批准外部工具存取，而不必把密碼直接交給它。不同帳號能看到的資料不同，所以使用誰的連接會影響工作範圍。

官方也讓個人新增的工具連接限制在自己的私人對話。這對多人共享工作區很實際，因為別人能傳訊息到某段共用對話，不應直接被當成可以使用你的私人帳號。

私人對話也加入自動化工作。官方說明，只有能看見該對話的人能看見其中的自動化與執行紀錄，因此設定工作時要一起確認誰會接收結果與處理失敗。

裝置協作則處理另一種限制。某些工作需要本機檔案、軟體或特定環境，雲端代理無法只靠同一台遠端機器完成。

Capy 讓雲端對話按裝置名稱啟動子代理，讓必須在你的電腦執行的那一段工作留在對應裝置，主對話仍留在雲端。

這不表示所有資料都自動留在本機。哪些內容會回到主對話、工具會讀哪些檔案，仍應按具體任務與連接方式確認，不能只因子任務在本機就下整體結論。

若團隊想處理一份本機測試檔，可以先指定資料夾與輸出內容，確認雲端收到的是預期結果。這樣較容易看出跨機器協作是否真的減少人工搬運。

更新頁也說，裝置斷線時工作會等待重新連接。對需要長時間執行的任務，團隊應知道哪一台裝置必須保持在線，才能避免把等待誤當成模型卡住。

當帳號與機器的分工都清楚，升級測試才有具體的觀察重點。

## 哪些團隊值得升級，第一次該怎麼測？

已經付費使用 Claude，又需要跨雲端與本機協作的團隊，可以先測一條模型路徑和一個最小雲端角色。

這樣的範圍足夠小，若工作失敗，能分清問題來自訂閱連接、模型選擇還是雲端權限。一次把所有工具和自動化都接上，反而較難知道哪個改動帶來影響。

第一個任務可選簡單的程式修改，要求代理提交可審查差異與測試結果。因為工作有明確終點，團隊能比較新模式是否保留原本需要的協作內容。

第二個任務再加入雲端只讀查詢，核對機器使用哪個身份、可達哪些資源。這能讓開發與維運一起檢查設定，而非只由代理回報「已連接」。

若要使用配對裝置，則選一項只有本機具備的工作，觀察任務送到哪裡、裝置離線時如何顯示，以及完成後主對話收到什麼。

Capy 0.5 還允許把工作移到較大的新機器，並保留相同程式庫。這對資源不足的任務有用，但需要留意，移動機器與擴大任務內容是兩回事，仍應保留原本驗收範圍。

團隊也應檢查更新提到的記憶體不足處理。官方說明會停止最大的程序以避免整台凍結，這可能讓工作中某個測試或建置中斷，結果仍需查看實際執行狀態。

因此，試點紀錄除了成功與否，也要記錄重試、人工介入與等待裝置的時間。這些情況會影響實際工作成本，單看模型回覆速度不容易反映。

若一條流程能穩定完成、帳號可追查、成本也清楚，再把相同方式擴到團隊其他任務。這比把功能清單全部啟用，更容易看見新版本帶來的改變。

Capy 的這次更新把訂閱、機器身份與裝置協作拉近。它的價值會出現在具體工作能否少一次搬資料、少一份長期金鑰，以及少一段重複設定。

## Capy 0.5 常見問題 FAQ

### Capy 0.5 能用 Claude Pro 和 Max 嗎？

官方已宣布支援，需連接訂閱並在模型選單選 Claude Code 分類。原訂閱額度和條件仍適用。

### 連接免費，代表雲端機器也免費嗎？

不能這樣推論。模型訂閱、平台方案、雲端機器與外部服務應分開核對，依實際任務計算。

### OIDC 會讓機器自動取得所有雲端權限嗎？

權限由設定的帳號、角色與信任條件決定。短期憑證減少長期密鑰保存，但不會替你選好適當範圍。

## 結語：沿用訂閱之後，把整段工作的成本和身份一起看

Capy 0.5 適合已有 Claude 訂閱，又希望把雲端和本機工作接起來的開發者。若目前只需要單機短任務，可以先確認協作需求再加入更多連接。

建議先用一個程式修改與一項只讀雲端查詢驗證新流程，保存額度、權限與結果。想持續掌握 AI 開發工具更新，歡迎免費訂閱 AI 郵報。
