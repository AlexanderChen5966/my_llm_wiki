替每一位聊天使用者啟動一個容器，能隔開工作環境，卻也讓簡單問題背上啟動時間與維運成本。Microsoft Copilot SDK 2.0 要解決的，就是每段對話都得綁住一套基礎設施的限制。

開發者容易把「代理隔離」理解成「每個工作階段都必須有容器」。但只查詢訂單的助理與需要執行未知程式碼的開發代理，實際需要的隔離方式並不相同。

微軟在 2026 年 11 月 17 日宣布的新版本，允許同一個執行環境承載多個工作階段，並把身分、工具、檔案和紀錄分開管理。核心改寫為 Rust，讓代理運作位置也能與程式執行位置分開。

官方以已暖機的指定負載比較，建立客戶端、工作階段並完成一輪的時間，從 5.25 秒降至 55.3 毫秒。這是特定架構的測試，對團隊的意義是減少基礎設施等待，不能當作所有模型回答都快了同樣倍數。

已有多使用者助理、而多數任務只呼叫受控工具的團隊，可以評估共用執行環境。若代理需要編譯程式或執行不可信腳本，仍應保留硬體或容器的隔離邊界，不能只靠工作階段分隔。

選擇架構前，得先把「代理在哪裡思考」和「工具在哪裡動手」拆成兩個問題。

## Microsoft Copilot SDK 2.0 為何拆開執行環境與工作階段？

共用執行環境的用途，是讓不需要完整機器的對話不必承擔容器啟動成本。SDK 是讓開發者把既有能力接進程式的工具組，這次更新的是代理如何運作，並非單純推出另一個聊天模型。

依 [微軟官方技術文章](https://commandline.microsoft.com/microsoft-copilot-sdk-2-0-github/?ref=aiposthub.com) ，舊架構把工作階段和容器綁在一起。容器可以理解成有明確邊界的程式執行環境，但每段對話都啟動一個，會增加等待與資源成本。

如果助理只需要查詢使用者的訂單，完整命令列與檔案系統未必派得上用場。讓這種對話也配一套容器，相當於為了查一筆資料而先準備整個工作間，服務規模越大，閒置成本越明顯。

新版把工作階段變成較輕的單位，同一個程序能同時承載多段對話。每段對話仍有自己的狀態、憑證、工具、檔案與歷史，因此共用的是執行核心，而不是把所有人的對話合成一份。

微軟也把核心改寫為 Rust，這是一種重視效能和記憶體安全的程式語言。它提供較輕的執行基礎，但應用程式仍要決定資料放在哪裡、工具能讀什麼，以及使用者如何驗證身分。

### 官方加速數字應該怎麼看？

官方用相同已暖機負載比較，建立客戶端、工作階段並完成一輪，從舊版的 5.25 秒降到 55.3 毫秒。暖機表示必要資源已經準備好，這個條件不能省略，否則讀者容易把它當成首次啟動的等待時間。

同一份文章列出，十個客戶端的記憶體從 1,383MB 降到 126MB，吞吐量則從每秒 7.55 個工作階段提高到 120 個。這些都是官方指定測試的結果，沒有證明任何模型推理都會加速到相同比例。

對團隊而言，更值得量的是自家服務在「真正開始回答之前」花了多少時間。如果主要等待來自資料庫、外部工具或模型本身，換核心後能節省的比例就可能不同。

工作階段既然共用程序，權限就必須從啟動程序的人移回提出請求的使用者。

## 每個工作階段的身分與工具怎麼隔開？

新架構把每次對話可用的身分和工具交由應用程式明確提供。多租戶代表同一套服務處理不同客戶，而客戶之間不應因共用程序，就能讀到彼此的訂單、檔案或憑證。

官方示例在建立工作階段時帶入該使用者的憑證，讓模型與工具呼叫歸屬到提出請求的人。這和整台伺服器一律使用服務管理員身分不同，也更容易把責任對回實際操作的人。

但傳入憑證不等於應用程式已完成所有驗證。伺服器仍要確認呼叫者有權建立或接回該工作階段，不能只因對方知道一個對話識別碼，就把原本的歷史與工具交出去。

### Empty 模式為何值得注意？

新版提供 empty 模式，讓工作階段從沒有主機命令列、檔案系統與預設工具的狀態開始。開發者再逐項加入需要的工具，因此能力範圍能從產品需求出發，而非沿用命令列工具的全部預設權限。

例如查詢訂單的助理，只需要一個受控的訂單查詢工具。工具應依登入者身分查詢可見訂單，不能讓模型自己填一個客戶編號，就任意切換到別人的資料，因為授權應由程式執行。

官方範例也使用明確的工具清單，限定工作階段能呼叫哪些操作。這讓同一個執行環境可以服務不同用途，但每項工具的實作仍是安全邊界，不能把工具說明文字當成存取控制。

對短期或輪替憑證，新版提供按工作階段取得新憑證的方式。團隊因此可以減少長期金鑰的保存，但仍要安排到期、撤銷與失敗處理，避免登入失效後持續重試造成混亂。

這種隔離主要由應用程式控制工具與身分，並不等同把未知程式碼放進獨立容器。若允許代理任意執行腳本，就應重新評估硬隔離，而不能只依賴對話彼此看不見的設計。

權限最小化處理的是代理可以做什麼，會不會因服務重啟而失去進度，則是另一個設計問題。

## 服務重啟後怎麼接回對話？

工作階段紀錄能放到程序之外，因此服務重啟不必等於對話消失。新版會把訊息、工具呼叫、結果、計畫與檢查點寫進工作階段日誌，讓能存取這份日誌的執行環境繼續工作。

日誌可以想成持續追加的工作紀錄，而不是只存在畫面上的聊天泡泡。另一個服務實例讀到相同紀錄後，才有機會知道先前做了什麼、拿到哪些結果，以及下一步應從哪裡接續。

官方提供 sessionFs 介面，讓應用程式決定工作階段檔案和狀態的儲存方式。它們可以放在受控的物件儲存、資料庫或依客戶分隔的路徑，程序所在的本機磁碟便不必永久綁住對話。

### 對話延續和工作不重複，是同一件事嗎？

能接回歷史不表示所有外部動作都能保證只執行一次。例如服務在建立訂單後、回寫完成紀錄前中斷，重新執行工具就可能產生重複訂單，因此工具本身仍需要防重與狀態查詢。

這是部署時要驗收的情境，而不是本次官方效能測試已回答的結果。團隊應挑可回復的範例，模擬連線斷開、服務重啟與憑證過期，檢查結果能否接續且不超出原本授權。

官方也提到，同一段對話可以由不同介面接手。這有助於讓網頁、命令列或其他客戶端查看進度，但若同時有多個人連上同一工作階段，還需要共同狀態與操作協調。

Agent Host Protocol 是官方另列的開放協定，用來把代理工作階段變成可供多個客戶端同步連接的資源。它不是單純把日誌放到遠端儲存，也不能與資料保存功能混成同一項能力。

儲存位置一旦從本機移到共用服務，資料保留與刪除責任也會跟著改變。團隊應確認誰能讀取日誌、保留多久、使用者刪除對話後如何處理，而不只是測試服務能否重新啟動。

有了可接回的紀錄，才適合進一步比較共用、沙箱與多代理的部署方式。

## 共用、沙箱與多代理架構應該怎麼選？

是否從第一輪就需要命令列與檔案，決定了隔離環境該多早啟動。對只呼叫應用程式受控工具的客服助理，共用執行環境可能已足夠；對需要編譯和測試的代理，容器仍有明確用途。

官方也提出先共用、需要時再移進沙箱的方式。沙箱是限制程式影響範圍的環境，這種安排讓簡單對話不先支付啟動成本，但轉入沙箱仍有等待，而且官方描述的移轉是單向的。

另一種方式是把模型工作循環留在共用環境，只有命令與檔案操作放進沙箱。這樣不用每個沙箱都跑完整代理，但主機必須負責把工具操作送到正確環境，並把結果帶回對話。

若任務真的能拆成獨立工作，也可以讓協調者派給各自有沙箱的代理。這有助於平行處理，代價則是每個工作者都有模型與環境成本，不能把多開代理直接等同更省錢。

### 遷移前要比較哪些數字？

同一批任務應保留相同模型、工具資料與完成條件，再比較啟動等待、記憶體、處理量與錯誤率。如果新架構同時換了模型與任務，很難知道改善究竟來自哪裡。

隔離測試也應使用至少兩種測試身分，確認不能讀取彼此的工作階段與資料。這比只檢查正常登入更重要，因為多租戶服務的核心要求，就是一位使用者的請求不會越過自己的範圍。

費用要一起看模型、基礎設施與工具服務。這次公告沒有給出所有架構通用的省費比例，所以即使記憶體下降，也不能直接把整份月帳單按相同比例縮小。

[官方 SDK 專案](https://github.com/microsoft/copilot-sdk?ref=aiposthub.com) 提供後續文件與入門方式。截至 2026 年 11 月 18 日公告查核，支援語言包括 TypeScript、Python、Go、.NET、Java 與 Rust，實際接入仍需依版本文件核對。

架構選定後，官方速度數字才有對照意義，因為不同工作負載省下的是不同成本。

## Microsoft Copilot SDK 2.0 常見問題

### Rust 核心代表所有 AI 回答都快近百倍嗎？

沒有。官方比較的是相同已暖機負載中，客戶端與工作階段建立加上一輪工作的時間。模型、網路和外部工具仍可能主導自家服務的等待，必須用自己的任務重新量測。

### 共用程序還需要容器嗎？

需要視任務決定。只呼叫受控工具可以評估共用環境，但執行不可信腳本、編譯程式或需要客製映像時，官方仍把硬容器邊界視為重要設計。

### SDK 會替我代管所有代理服務嗎？

這次技術文章說明的是可以在自有基礎設施建立的架構。GitHub 和 Microsoft 另有代管環境，但不能把 SDK 的可部署性理解成不需自行安排執行、儲存、權限與費用。

## 先量出等待與隔離成本，再決定是否遷移

值得優先試行的是大量輕型工作階段，而不是一開始就移除所有沙箱。對話主要依賴受控查詢時，新版能提供更細的部署選項；需要執行未知程式時，隔離仍應放在架構核心。

開始前先畫出模型、工具、身分與紀錄各自的位置，再選一種架構做小規模比較。這會讓團隊知道自己省下的是啟動等待、閒置容器，還是跨介面交接，而非只追逐一個效能倍數。

用同一批任務比較啟動、記憶體、工具越權與重啟恢復結果，再決定遷移範圍。當正常路徑和中斷情境都能交代清楚，新的執行核心才會成為可維運的產品能力。
