當你把單純的聊天機器人升級成多步驟 AI 代理後，系統就變成了一個難以除錯的黑盒子。

使用者抱怨回應慢了八秒，或是某個回答突然出現幻覺，但你打開傳統的應用程式日誌，卻只能看到最後噴出的錯誤訊息，完全不知道究竟是檢索漏抓、工具呼叫卡住，還是哪一段提示詞被改壞。

`langfuse/langfuse` 是目前開源界最完整、且經過大規模生產環境驗證的 LLM 工程與可觀測性平台。它能幫你把每一次模型呼叫、檢索步驟、代理決策與花費的 Token 成本，全部串成一條清晰的時間軸。

更關鍵的是，這套平台以 OpenTelemetry 為底層標準，不僅支援一分鐘內用 Docker Compose 自架於企業內網，還整合了提示詞版本控制、實驗資料集與線上評估機制。

這篇 `Langfuse 教學` 將帶你拆解它的核心架構、完成 Docker 自架與 Python SDK 實戰串接，並整理主流框架整合方式與資料隱私邊界。

## 為什麼多代理應用不能只靠傳統日誌除錯？

傳統軟體架構的錯誤大多是確定性的，只要看堆疊追蹤與狀態碼就能定位問題。

但 AI 代理的執行路徑是動態生成的，一個使用者提問可能在背後觸發了意圖判斷、三次資料庫檢索、兩次外部工具呼叫，以及最後的摘要生成。

如果沒有專為語言模型設計的追蹤工具，工程師每次排查問題都得手動把好幾層函式印出來的 JSON 拼湊在一起，既無法一眼看出哪個節點拖慢了整體延遲，也算不出單一功能到底燒掉了多少美金。

因此，一套合格的 LLM 可觀測性平台必須做到三件事：自動記錄巢狀呼叫鏈、即時統計成本與延遲，並且能把線上的失敗案例直接拉進測試場重新驗證。這正是這套開源平台能成為超過十萬顆星級專案首選工具的核心原因。

## Langfuse 教學核心：六大模組打造完整 AI 工程閉環

這套平台並不是單純的日誌檢視器，而是圍繞著語言模型應用生命週期設計的六大核心模組。

第一是基於 OpenTelemetry 建構的 **AI 可觀測性追蹤** 。每一次請求都會產生一筆 Trace，裡面記錄著底層所有的檢索、向量化、工具執行與模型生成步驟，讓你能清楚看見代理每一步的輸入輸出與時間分佈。

第二是 **提示詞管理與 Playground 實驗場** 。團隊可以把散落在程式碼裡的提示詞抽離出來集中版控，透過伺服器與用戶端快取做到不增加額外延遲。當你在追蹤紀錄裡發現某次回答表現不佳，只要點一下就能直接跳進 Playground 調整提示詞並重跑測試。

第三是 **技能管理系統** 。針對越來越多團隊採用的 `SKILL.md` 代理技能規範，平台支援將任務指令與輔助檔案進行版本控管與標籤切換，不需修改主程式就能升級或回滾代理技能，並將技能版本直接關聯到對應的追蹤紀錄。

第四是 **自動化評估與資料集實驗** 。平台內建模型裁判評估、程式碼規則檢查、人工標註與使用者回饋收集，讓你能在正式發布新模型或新提示詞之前，先用歷史資料集跑過一輪基準測試，避免線上品質回歸。

第五是 **AI Gateway 統一閘道** 。開發者可以把所有供應商的金鑰集中在閘道層管理，對內核發個人或服務帳號的專有金鑰，不須改動現有程式碼就能集中控管可用模型、追蹤各部門花費並自動寫入追蹤紀錄。

第六是 **指標儀表板與完整 API** 。從首字延遲、Token 吞吐量到單日成本預算，都能自訂儀表板與告警規則，同時提供完整的 Python、JavaScript/TypeScript SDK、CLI 工具與代理專屬的技能套件。

## 五分鐘自架指南：Docker Compose 與雲端部署選擇

在部署方式上，這套專案提供了極大的彈性。如果你正在做個人原型驗證或資料不涉及機密規範，可以直接註冊官方託管的雲端服務，免綁信用卡即可使用免費額度，並支援歐洲、美國、日本與合規專區等不同資料落地節點。

但對於重視程式碼與對話紀錄隱私的企業團隊來說，自架才是最吸引人的選項。只要本機或測試主機安裝好 Docker，執行以下三行指令就能在五分鐘內把整套平台跑起來：

```bash
# 1. 淺層複製官方儲存庫
git clone --depth=1 https://github.com/langfuse/langfuse.git
cd langfuse

# 2. 使用 Docker Compose 啟動所有相依容器
docker compose up
```

啟動之後，建議順手按照官方文件設定容器日誌輪替機制，避免長期跑大量追蹤紀錄時把主機磁碟塞爆。

若要將平台推進正式的企業生產環境，單機容器通常不夠用。這時可以改用官方維護的 Kubernetes Helm Chart 進行高可用部署，或是直接套用官方提供的 AWS、Azure 與 GCP Terraform 範本快速拉起基礎設施。

值得一提的是，這個專案於 2026 年初加入 ClickHouse 體系，底層分析與大量追蹤資料寫入效能非常強悍，能輕鬆應付高併發的生產環境流量。

## Python SDK 快速上手：用裝飾器完成第一筆追蹤

平台架設完成並進入專案設定取得 `LANGFUSE_PUBLIC_KEY` 與 `LANGFUSE_SECRET_KEY` 後，接著就能在應用程式裡埋入追蹤點。

如果你平常使用 Python 開發，最快的方式是安裝官方套件並利用 `@observe()` 裝飾器，同時搭配官方提供的 OpenAI 替換模組，系統就會自動攔截並記錄所有模型參數、回應內容與 Token 消耗。

```bash
pip install langfuse openai
```

接著在專案根目錄建立 `.env` 環境變數檔。如果是使用雲端服務，請依區域填入對應網址；如果是自架主機，則將網址指向你的內部伺服器位址。

```bash
LANGFUSE_SECRET_KEY="sk-lf-..."
LANGFUSE_PUBLIC_KEY="pk-lf-..."
LANGFUSE_BASE_URL="https://cloud.langfuse.com"
```

寫好程式後，只要在關鍵函式加上 `@observe()`，巢狀的函式呼叫就會自動被組織成父子階層的追蹤樹：

```python
from langfuse import observe
from langfuse.openai import openai

@observe()
def story():
    return openai.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": "What is Langfuse?"}],
    ).choices[0].message.content

@observe()
def main():
    return story()

main()
```

執行這支腳本後，打開後台介面就能看見 `main` 與底下包著的 `story` 呼叫鏈，包含耗時、輸入提示詞與輸出字數全都一清二楚。

如果你已經在專案中使用 Claude Code、Cursor 或其他具備代理能力的編輯器，官方還提供了更懶人的整合方式。只要安裝官方 Agent Skill，就能請程式代理幫你自動盤點專案並埋入符合最佳實踐的追蹤程式碼。

```bash
npx skills add langfuse/skills --skill "langfuse"
```

此外，官方也開放了免驗證的說明文件 MCP 伺服器端點，讓你的開發代理在改寫程式碼時能隨時查詢最新的 SDK 規格，大幅減少寫出過時語法的機率。

## Prompt 版控、資料集實驗與 AI Gateway 實戰工作流

除了事後查看追蹤時間軸之外，這套平台在團隊日常開發中還有三個非常實用的工程工作流，能直接把追蹤紀錄轉化成產品品質的改善動力。

第一個工作流是「追蹤到 Playground 的無縫除錯」。當團隊在線上日誌裡抓到某一次工具呼叫失準或回答偏題時，不需要回到本機翻找程式碼重組上下文。只要直接在該筆追蹤紀錄點擊進入 Playground，系統就會自動帶入當時的完整訊息、模型參數與系統提示詞，讓你立刻微調並驗證修正結果。

第二個工作流是「基於資料集的發版前回歸實驗」。你可以把線上收集到的高難度提問、使用者給予負評的對話，全部一鍵收錄進專屬的測試資料集。每當團隊準備升級底層模型或改寫提示詞版本時，就能先對這份資料集跑過一輪模型裁判與規則評分，確認關鍵指標沒有退化才正式發布。

第三個工作流是「AI Gateway 集中金鑰與預算控管」。當公司內部有多個專案團隊都在呼叫外部模型時，把商業 API 金鑰分散在各個服務裡既危險又難以對帳。透過閘道層統一管理供應商憑證，並為不同服務帳號核發獨立的閘道金鑰，不僅能精準統計每個部門與每位使用者的花費，還能把所有呼叫自動寫入追蹤紀錄，不需改動任何應用程式碼。

這套平台的另一大優勢，是幾乎不用擔心與現有技術棧相衝突。因為底層全面採用 OpenTelemetry 協議，任何支援 OTLP 標準的語言與收集器都能直接把追蹤資料送進來。

| 模型供應商與本地推論 | OpenAI、Amazon Bedrock、Ollama | 原生 SDK 替換模組或 OTLP 協定 |

## 開源授權、資安邊界與自架注意事項

在決定全面採用之前，有三個工程實務與授權邊界必須先確認清楚。

首先是 **開源授權範圍的區分** 。雖然主體程式碼採用寬鬆的 MIT 授權條款，可以免費自架與商用，但儲存庫中標記為 `ee` 目錄下的企業進階功能屬於商業授權範圍。

對於多數開發團隊而言，MIT 核心版已經涵蓋完整的追蹤、提示詞版控、資料集評測與 AI Gateway 功能。但如果你需要特定的企業級單一登入或細粒度合規稽核功能，導入前務必先核對官方授權說明。

其次是 **敏感資料遮罩與隱私邊界** 。可觀測性系統的本質，就是把使用者的真實提問與模型的完整回覆記錄下來，這代表個人身分資訊或商業機密極可能進入追蹤資料庫。

如果使用的是自架版，資料雖然留在自己的機房，仍應在 SDK 送出追蹤前或代理閘道層實作欄位遮罩邏輯，並嚴格控管後台登入權限。

最後是 **高流量環境的日誌與儲存維運** 。當線上代理進入大量併發運作時，每次對話可能產生十幾層巢狀紀錄。單純用測試用的單機 Docker Compose 很容易面臨磁碟空間或查詢延遲瓶頸，正式上線前務必規劃好資料保留期限與容器日誌輪替。

## 常見問題

### 1\. Langfuse 跟直接印出 Console Log 或用傳統 APM 工具有什麼不同？

傳統 APM 工具專注於 HTTP 請求延遲、CPU 使用率與資料庫查詢，看不懂多輪對話的上下文結構，也無法自動計算不同模型的 Token 單價。這套平台專為 AI 打造，能把提示詞版本、檢索結果、模型參數與評估分數綁定在同一個時間軸上分析。

### 2\. 如果我已經用了 LangChain 或 Dify，還需要手動寫 @observe() 嗎？

不一定需要。針對 LangChain、LangGraph、LlamaIndex 等框架，只要在設定檔掛載官方提供的 Callback Handler 就能自動記錄所有步驟。若是使用 Dify 或 OpenWebUI 這類視覺化平台，甚至只要在介面裡填入專案金鑰就能立刻啟用追蹤。

### 3\. 在這份 Langfuse 教學中，自架版和官方雲端版功能有落差嗎？

核心的可觀測性追蹤、提示詞管理、Playground、資料集評測與基本儀表板在開源自架版中都能免費使用。兩者主要的差異在於雲端版幫你省去了維運資料庫與擴展叢集的功夫，而自架版中的部分大型企業級權限管理與合規稽核模組則包含在商業授權目錄內。

### 4\. 串接追蹤 SDK 會不會拖慢原本 AI 代理的回應速度？

正常情況下影響微乎其微。因為官方 SDK 採用非同步批次在背景上傳追蹤資料，不會卡住主要請求的執行緒。而在讀取提示詞版本時，系統也同時在伺服器與用戶端設計了強效快取機制，確保應用程式維持低延遲回應。

沒有可觀測性的 AI 代理，上線後就像在濃霧中盲目飛行。把追蹤鏈、提示詞版控與自動化評測整合在單一開放平台上，是 `Langfuse` 能在競爭激烈的 AI 工具生態中站穩腳步的核心理由。

- **適合誰** ：正在將多步驟 AI 代理推進生產環境的開發團隊、需要精準統計各部門模型費用與延遲瓶頸的技術主管，以及對資料落地有嚴格要求、希望在內網自架追蹤平台的企業。

- **為什麼** ：因為它用標準化的 OpenTelemetry 架構打通了幾乎所有主流開發框架，讓你不必被單一模型商綁死，就能擁有一套可觀察、可版控且可量化的工程級基礎設施。
