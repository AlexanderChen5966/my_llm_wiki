Rive CLI 讓設計動畫的工作多了一條入口：你可以用文字描述與可編輯檔案，把 AI 接進互動動畫的製作流程。

Rive 創辦人分享的城市示範在 X 被轉貼，街景裡的看板能回應互動，也讓更多人注意到動畫不必只有固定播放的影片。

但漂亮示範與可交付網站之間，還隔著載入速度、狀態切換與手機操作。這些問題要在真實頁面裡檢查。

CLI 是從終端機輸入指令來操作工具的方式，適合讓代理接續建立、預覽與修改檔案。它並不會替你決定動畫是否有必要。

我建議第一次練習只做一張可以切換狀態的資訊卡，讓畫面回答一個明確問題，例如課程已開始報名，或報名已截止。

要讓第一張資訊卡有幫助，先決定使用者做了什麼，畫面應如何回應。

## Rive CLI 能做什麼？先選一個需要互動的場景

互動動畫會依照使用者操作或程式傳入的資料改變。固定影片則依時間播放，同一段影片通常不會因為按鈕被點選就切到另一種邏輯。

例如報名卡片可以在滑鼠經過時顯示細節，在截止後改成灰色，成功送出時顯示完成。這些狀態比單純播放一段亮眼動畫更貼近工作需求。

先把每個狀態寫成文字，再考慮視覺效果。若你還不知道使用者按了什麼、畫面該回應什麼，直接讓工具做動畫很容易只得到裝飾。

狀態之間的切換也要寫清楚。表單尚未通過檢查時，不能因為點到按鈕就顯示成功。錯誤訊息則應停留到使用者知道如何修正。

把效果限定在這些情境，能縮小第一個專案。等到資訊與操作都成立，再逐步增加光影、場景或角色。

## 建立專案，分清來源檔與播放檔

[Rive 官方 CLI 概覽](https://rive.app/docs/cli/overview?ref=aiposthub.com) 提供建立與預覽專案的流程。安裝與平臺條件請依官方文件當下版本執行，避免混用舊教學的指令。

文件中的基本建立方式如下。這裡的專案名稱是練習範例，執行前先確認目前所在資料夾沒有同名的重要內容。

```sh
rive create myproject
rive myproject
```

第二個指令會進入專案預覽流程，編輯來源後可重新建置。第一次先確認官方範例能預覽，再請代理改畫面，比同時追查安裝與設計問題容易。

RML 是這套流程使用的可編輯文字來源。你可以把它理解成描述場景的檔案，代理修改的是這些描述，工具再把它們編成可用的動畫資產。

`.riv` 是給執行環境使用的動畫檔，`.rev` 則是編輯器相關檔案。交付時應保留來源與製作檔案，讓接手的人能修改。

只留下播放檔，未來即使能顯示，也未必能順利調整內容。這就像只有一張成品圖片，卻沒有保留文字與圖層的設計專案。

建立後先做一份原始副本，寫下檔案用途與啟動方式。代理開始修改前，應能說明它打算改哪個來源檔，以及如何看見結果。

## 給 AI 的指令要包含狀態與固定條件

你可以從這段工作說明開始：「請製作一張課程資訊卡，包含開放報名、額滿、已截止三種狀態，文字要保持可讀。」

接著補上固定條件：「維持相同卡片尺寸，按鈕位置不要移動。狀態切換時只改顏色、提示文字與小幅動作。」

再交代驗收方式：「每一種狀態都要能在預覽裡重現，提供操作方式，保留原始來源，最後列出修改過的檔案。」

這些說明把創作自由放在適合的位置。背景與動作可以有變化，資訊順序和按鈕作用則要穩定，讓使用者不用重新理解介面。

若要沿用品牌色，直接提供色碼與字型規則。不要只寫「看起來專業」，因為這句話無法幫你判定深色背景上的小字是否看得清楚。

一次只改一類問題。先把三種狀態接好，再改視覺，再調速度，能保留清楚的比較基準，也比較容易找到哪次修改造成問題。

## 用預覽確認狀態，再把檔案交給網站

預覽成功表示動畫來源能被工具處理，但網站還需要執行環境。執行環境就是讀取動畫檔，並把它呈現在頁面上的程式。

[Rive runtime 程式庫](https://github.com/rive-app/rive-runtime?ref=aiposthub.com) 是官方提供的參考入口。網站端選哪個整合方式，應由實際使用的技術與部署環境決定。

不要讓代理同時更換網站架構，只為了放進一張動畫卡。先要求它說明既有頁面怎麼載入資產，再在一個測試頁完成整合。

如果狀態由後端資料決定，網站就要把資料轉成動畫輸入。此時應把缺少資料的情況也列出來，避免畫面預設顯示「可以報名」。

例如名額欄位尚未載入時，顯示中性等待文字，等確認後才呈現可報名。使用者看到的動畫應反映真實資料，而不是最樂觀的猜測。

完成整合後，重新開一個分頁檢查。不要只看代理正在修改的預覽，因為快取或舊檔案可能讓你看到上一版結果。

## 桌機與手機驗收，分成四個可觀察結果

動畫驗收可以整理成一張表。每一列都應有具體操作，讓另一位同事照著做，也能看到同樣的結果。

| 檢查項目 | 操作方式 | 應看到的結果 |
| --- | --- | --- |
| 狀態 | 依序切換三種報名狀態 | 文字、按鈕作用與視覺一致 |
| 尺寸 | 在桌機與窄螢幕開啟 | 文字不被裁切，頁面不橫向溢位 |
| 操作 | 用滑鼠、觸控與鍵盤測試 | 每種可用操作都有清楚回應 |
| 載入 | 重新載入頁面並觀察 | 資產未就緒時仍能讀取重要資訊 |

窄螢幕上最容易出問題的是字太小、按鈕被裁切與觸控範圍不足。先把資訊放大到能讀，再減少不必要的裝飾。

滑鼠經過才出現的內容，在手機上可能沒有對應動作。重要資訊應能直接看見，或透過明確可點的控制取得。

鍵盤操作則需要確認焦點與按鈕作用。互動卡片如果只在滑鼠下成立，就會讓其他操作方式的人卡住。

也要測試減少動態效果的需求。可採用較短或較平穩的切換，保留提示文字，讓動畫速度不會成為理解資訊的前提。

這些是網站驗收建議，並非官方城市示範已完成的測試結果。示範可以提供創作方向，自己的頁面仍需要逐項檢查。

## 效能與版本管理，避免動畫愈改愈難交接

複雜場景會增加載入、運算與維護成本，但不能只依畫面元素數量猜測速度。應在實際裝置與頁面裡測試，再找出明顯負擔。

先記錄資產大小、首次顯示時間，以及操作是否卡頓。第一次練習可以採用簡單記錄表，不必為一張卡片建立龐大的分析系統。

若畫面載入太慢，先確認是不是其他網站資源拖慢整頁。把動畫獨立放在測試頁，可以幫你縮小問題，但不能代替正式頁面的複查。

修改時保留上一版可用檔案。每次提交版本都寫明改了哪個狀態，避免把「調得更好看」當成唯一說明。

當網站出現異常，你就能判斷應先回復動畫檔，還是網站輸入邏輯。這比重新要求代理把整個專案做一遍更容易控制。

若來源來自遠端檔案，官方文件也介紹了建立與同步的能力。實際團隊使用前，先確定誰能修改、誰負責合併，以及同步後哪份檔案算最新版。

多人直接覆蓋同一個檔案，可能讓已完成的修改消失。先建立一個簡單交接規則，比追求更多同時工作的代理更有價值。

### 怎麼把一次示範變成能重複使用的範本？

先保留最小可用版本，包含卡片尺寸、三種狀態與固定文字區。之後換課程時，只改內容與顏色，避免每次重做狀態連線。

範本說明應有啟動方式、輸入名稱與驗收步驟。接手者看到「額滿」的輸入，就應知道畫面會怎麼變，無須靠猜測找控制項。

另外儲存一張每種狀態的參考畫面。這些畫面不是完整測試，卻能讓設計修改時更容易發現文字被遮住或按鈕位置偏移。

最後把素材授權與執行環境條款分開記錄。程式庫的授權不能直接代表編輯器方案、字型、角色或外部素材都能同樣使用。

## 範例：報名狀態與畫面不同步，怎麼找原因？

假設網站顯示還能報名，動畫卻已切到額滿。先保留當下資料與畫面，檢查網站傳入的值，而不是立即重做動畫。

如果輸入本身是額滿，問題可能發生在資料取得或轉換。應先確認哪個來源代表目前名額，再檢查網站如何把它轉成狀態。

如果輸入是開放，動畫卻顯示額滿，就回到狀態連線檢查。這時才需要看動畫輸入名稱、預設值與切換條件。

若兩個地方都正確，還要檢查是否載入舊檔案。可以依資產版本與重新載入結果比對，避免把快取問題誤判成狀態設計錯誤。

每次修正只改一個相關位置，再重現相同操作。這樣你能知道哪個改動有效，也能保留沒有造成問題的部分。

這個案例是工作排查示例，沒有宣稱已替某個網站修好。它示範的是如何沿著資料、輸入與畫面，逐段縮小問題。

修好之後，把這個情境加入驗收表。下次換文案或更新檔案時，再走一次相同路徑，才能避免同樣的落差回來。

### 如何決定互動動畫是否值得保留？

先問動畫有沒有幫助使用者辨識狀態。若大家仍需要讀一大段文字才知道能不能報名，動作本身可能沒有提供資訊價值。

再看維護成本。每次更改課程都需要重新調整場景，可能不如一張清楚的靜態卡片。可重用範本則能降低這個負擔。

最後讓第一次看到頁面的人操作一次，請他說出目前狀態與下一步。看得懂、按得到且資料一致，才有理由繼續增加效果。

如果使用者只記得動畫漂亮，卻不知道按鈕作用，就先改善文字與資訊順序。實際操作結果，比創作者自己的印象更能支援決定。

## Rive CLI 常見問題

### 使用 CLI 就不需要設計判斷嗎？

仍需要。工具可以加快建立與修改，但資訊順序、動作是否幹擾閱讀，以及狀態是否對應真實業務，都要由你決定。

### X 上的城市示範代表手機也能同樣流暢嗎？

不能直接推論。示範的裝置、場景與測試條件可能不同，應用自己的頁面與目標裝置檢查載入及操作，再決定效果的複雜程度。

### 可以直接把影片當成互動動畫使用嗎？

影片能播放示範，互動則需要動畫資產與網站邏輯配合。若需求只是展示成果，影片就可能足夠。若要回應按鈕與資料，才需要互動整合。

## 從一張能驗收的資訊卡開始

Rive CLI 的實用價值，是把可編輯來源接進代理工作流程，讓動畫能隨版本修改。成品是否好用，最後仍取決於使用者能不能讀懂並完成操作。

先建立三種狀態的資訊卡，在桌機與手機各走一次操作流程。保留來源、版本與驗收表，確認這張卡有幫助後，再擴展到更大的場景。
