本機 AI 專案的更新速度，往往也受測試能不能跑完影響。llama.cpp CI 的改造經驗，說明開源團隊如何處理程式碼變多、硬體測試排隊與快取空間不足的問題。

CI 是持續整合，也就是程式碼修改後自動編譯與執行測試。這些檢查若一直排隊，開發者就得等更久才知道修改是否破壞其他平台。

團隊在 2026 年 11 月 16 日的原文指出，八月至十月收到 3,181 個修改提案，合併其中 1,802 個。完整檢查包含一百多項工作，因此單靠原先的快取與執行名額逐漸不敷使用。

他們保留 GitHub Actions 負責工作調度，同時把部分編譯快取移到 Hugging Face Buckets，並用 Hugging Face Jobs 啟動臨時執行機器。這項調整針對開發流程，不代表本機模型推論直接變快。

這個案例適合跨多種硬體測試的專案維護者參考。小型專案則可以先減少重複工作，因為外接儲存與雲端執行資源也會增加費用和權限管理負擔。

要看懂這次改造，得先分清楚快取不足和執行名額不足，因為多租機器並不會自動解決每台都重新編譯的問題。

## llama.cpp CI 為什麼開始塞車？

同一個修改需要跨多種平台檢查，讓編譯工作量和等待名額同時增加。

[原作者的改造文章](https://huggingface.co/blog/ggml-org/llama-cpp-ci-buckets?ref=aiposthub.com) 描述，完整檢查會涵蓋多種硬體後端。有些工作需要約三十分鐘，而合併到主要分支後的預先發布建置，部分又可能跑上數小時，因此工作量會隨更新持續累積。

編譯是把原始程式轉成機器可執行的內容。團隊使用 ccache 保存編譯產物，只要原始檔和建置條件沒有改變，下次就能沿用，減少重複計算，尤其對大量使用 C++ 範本的 GPU 後端很有幫助。

但快取需要空間，等待工作需要執行機器。文章列出當時公開免費儲存庫的 GitHub Actions 快取額度為 10GB，而 ggml-org 使用的免費方案同時執行工作上限為二十個，其中最多五個是 macOS。

這些數字是該組織與當時方案的條件，不能推成所有企業方案都一樣。它們的意義在於說明兩個瓶頸如何疊加：快取被淘汰會增加重編譯，而重編譯又會占住有限的執行名額。

團隊先把修改提案與主要分支的流程分開。修改提案依程式差異挑需要的工作，推送到主要分支才跑完整檢查，因而不必讓每一次小改動都承擔相同的工作量。

這項安排仍需要維護測試選擇規則，因為少跑並不等於安全。若某個共用檔案可能影響多種後端，規則就應涵蓋那些測試，否則縮短等待時間可能只是把錯誤延到合併後才發現。

因此團隊先改變每次修改要跑哪些工作，再處理剩下的資源問題。

## Hugging Face Buckets 如何保留編譯成果？

Buckets 提供跨機器共用的儲存空間，讓新的執行機器可以沿用符合條件的編譯快取。

改造保留原有的 ccache，用 [Hugging Face Buckets](https://huggingface.co/docs/huggingface_hub/en/guides/buckets?ref=aiposthub.com) 儲存非發布建置的快取。它的角色是共享儲存，讓不同機器可以取得相應建置條件下的產物，不必依賴上一台機器的磁碟仍存在。

官方流程是由符合條件的主要分支建置上傳快照，修改提案建置先下載這份基準，再讓編譯工具決定哪些檔案能重用。若提案與主要分支差距很大，仍可能需要重新編譯很多內容。

因此，快取命中不是保證。編譯器版本、目標硬體和建置選項不同，都可能讓舊產物不適用，團隊需要把這些差異反映在快取分類，而非把所有檔案放進同一個名稱就當成通用。

文章指出，儲存採用 Xet 技術處理重複內容，目的是減少上傳下載的重複資料。但這是儲存設計特性，實際傳輸時間仍受網路、快取大小與工作流程影響，沒有一個可套到所有專案的固定加速倍數。

非發布快取移出後，原有 GitHub 快取能留更多空間給發布建置。這說明改造是分工，而非把所有快取清空或全面換掉原先系統，團隊也保留了既有編譯工具的使用方式。

若要借鏡這個設計，可以先檢查儲存的是否真是可重建的編譯產物。正式套件、憑證與其他重要資料有不同管理需求，不能因為它們也能放進儲存桶，就沿用相同的清理規則。

快取的生命週期也影響費用。若每種建置都永久保留所有版本，儲存需求仍會持續增加。官方案例會為建置鍵保留近期快取並清理較舊封存，因此採用者需要把清理策略一併規劃。

建置鍵可以理解成辨認一組編譯條件的名稱。它需要足以區分不同平台，又不能細到每次小修改都完全無法重用，否則即使儲存很多檔案，實際節省的編譯仍可能有限。

驗收快取時，可以在同一提交上分別觀察有無快取的結果。除了比較時間，也應確認測試與產物一致，讓加速仍維持原本應完成的檢查，而不是跳過必要步驟。

快取能帶著走之後，臨時執行機器才不必每次從零開始。

## Hugging Face Jobs 如何接回 GitHub？

Jobs 供應臨時運算資源，GitHub 仍負責安排工作與呈現測試結果。

Hugging Face Jobs 提供執行腳本的雲端 CPU 或 GPU 環境。llama.cpp 的案例把部分自管機器與許多 GitHub 託管的 Linux x64 工作移到這裡，但工作仍從 GitHub Actions 進入，結果也回到原介面。

中間由 [jobs-actions 專案](https://github.com/huggingface/jobs-actions?ref=aiposthub.com) 銜接。當 GitHub 工作指定相應的執行標籤，調度服務收到事件後，會依標籤對應所需資源，啟動一個臨時容器作為執行者。

臨時執行者會向 GitHub 登記，領取等待中的工作，照原本步驟執行，再把紀錄與結果傳回。這讓開發者仍可在修改提案附近閱讀狀態，減少跨兩套管理畫面追蹤的負擔。

共用快取在這裡有先後關係。臨時機器每次重新建立，若無法取得前次編譯成果，就可能把增加的運算資源花在重做相同工作，因此團隊先安排可攜的快取，再擴充執行資源。

這也不代表 GitHub 的所有限制都消失。不同作業系統與硬體仍有各自的設定，連線、資源額度、容器啟動及快取下載也會花時間，因此必須把整條工作流程一起量測。

對使用者而言，能看見原處的測試紀錄很重要。如果外部資源執行失敗卻沒有把結果傳回，開發者可能只看到長期等待，因而調度橋接的錯誤回報也是維護工作的一部分。

但讓外部機器加入測試流程，也必須把權限限制說清楚。

## 快取與執行權限怎麼分？

誰能讀取既有快取、誰能寫回新的快取，會影響測試是否可信。

官方說明調度服務會驗證簽署的事件、檢查儲存庫權限，並向 GitHub 取得短效的執行者登記權杖。這些檢查讓外部運算資源知道自己應該為哪個專案工作，避免只靠可被偽造的文字標籤。

這裡的權杖是讓臨時機器登記用的憑證，和公開分享程式碼的權利不同。團隊不應把它寫進公開紀錄，也不需要為了啟動工作，就讓容器取得與任務無關的組織管理能力。

快取寫入也應有清楚邊界。案例讓主要分支的合格建置更新共享基準，修改提案以讀取為主，能降低尚未通過審查的變更污染後續建置的機會，但仍需要檢查實際儲存權限是否吻合。

若讓來自外部貢獻者的程式在具有機密的環境執行，風險會變大。因此沿用此架構時，要先分開不受信任的提案測試與需要秘密資料的發布工作，不能把方便調度當成可以共用一切權限。

快取失敗也要能回到正常編譯。因為快取的用途是節省時間，若缺檔或內容不符就讓測試跳過，反而會破壞品質檢查。維護者需要保留可觀察的失敗狀態與重新建置方式。

這些安排會增加維護內容，但和跨平台大型專案的需求有關。對規模較小的儲存庫而言，可以先把目前的秘密、快取和觸發條件整理清楚，再決定是否需要引進外部調度服務。

權限邊界確定後，才適合評估增加雲端資源是否划算。

## 其他開源專案要照搬嗎？

先量出等待和編譯各花多少時間，才能知道應該減少工作還是增加資源。

首先可記錄工作從排隊到開始、從開始到完成各花多久，再看編譯中有多少成果可重用。如果大多時間在等機器，增加執行資源可能有幫助。若大多在下載巨大快取，擴機反而可能增加傳輸成本。

費用也要分成儲存與運算。原文連到各自的價格頁，Jobs 按機器運行時間計費，因此測試腳本結束後是否真的退出，會影響帳單，不能把閒置的臨時環境當成沒有成本。

評估時可以先移一類容易觀察的 Linux 工作，保留原有流程作比較。把快取命中、下載時間、總完成時間與實際用量放在同一份紀錄，較能確認是改善瓶頸，還是把成本轉移到別處。

也要記錄維護者花在處理失敗上的時間。若測試本身快了，卻經常因調度錯誤需要手動重啟，團隊實際省下的等待未必多，因此穩定性與可理解的紀錄不能只當成附帶功能。

對沒有大量跨硬體需求的專案，先挑選必要測試、清理無效快取與避免重複觸發，可能已足夠。這些改善能沿用既有環境，不必為了追隨大型專案的架構就增加管理層。

llama.cpp 的案例則展示了另一個規模階段：當完整測試真的超出原來的容量，可以保留大家熟悉的工作入口，把共享儲存與臨時運算拆開調整。這樣每一項新增資源都有對應的瓶頸。

用可比較的實際數據決定規模，才能避免把免費額度問題換成雲端帳單問題。

## llama.cpp CI 常見問題

### llama.cpp CI 改造會讓本機推論更快嗎？

這次公告針對開發與測試流程。模型在使用者電腦上的速度，仍由模型、硬體與推論實作決定。

### GitHub Actions 被 Hugging Face 取代了嗎？

沒有。案例仍用 GitHub 調度與顯示結果，Hugging Face 提供部分共享快取與臨時運算資源。

### Buckets 和 Jobs 都免費嗎？

不能這樣推論。儲存與機器運行各有費用條件，應依當日方案估算，並追蹤工作是否如期退出。

## 先量出等待原因，再決定增加哪一種資源

若維護中的專案正面臨測試排隊，可以先挑一週紀錄，分開看等待、下載與編譯時間。這些資料會比單看總工作數更直接指出改善方向。

需要擴充時，再選一小類工作接上共享快取和臨時機器，確認權限、結果回報與費用都可追蹤。這樣才能把大型開源專案的經驗，改成適合自己規模的維護流程。
