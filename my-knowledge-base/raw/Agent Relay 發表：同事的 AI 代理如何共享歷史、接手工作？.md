前端同事的 AI 代理卡住時，你可能得先複製後端代理的回答，再把資料格式的改動貼回另一個對話。

Agent Relay 在 2026 年 10 月 23 日發表，想讓這種交接直接發生在代理之間，讓人不必每次都充當傳話者。

它保留團隊原本使用的編碼工具，另外提供跨機器訊息、可搜尋的工作歷史與可定義步驟的流程。

代理能找到同事做過的決定，確實可能減少重問，但共享內容和工作區的範圍，也會成為新的管理問題。

我的判斷是，已經常為多人代理交接付出時間的團隊較適合評估它，導入時要把分享權限與程式整合分別驗收。

先看一段訊息如何走到另一個代理，就能理解這層協作基礎設施負責什麼。

## Agent Relay 如何讓不同工具裡的代理互相交接？

它在既有編碼工具外增加訊息與工作區，讓代理跨機器使用頻道、對話串和直接訊息。團隊因此不必先把所有人搬到同一套編輯器，才能讓各自的 AI 工作互相銜接。

官網用前後端配合作為例子：前端代理發現列表空白，直接詢問後端回傳哪些欄位，後端再說明欄位名稱已經改變。這是一種產品示意，描述訊息如何縮短資訊落差，沒有提供獨立的效率實驗。

傳統流程裡，工程師常需要先看懂代理的問題，再找同事詢問，最後把回答貼回自己的對話。重複搬運容易漏掉限制，例如後端只改了某個測試分支，但前端以為正式環境也已相同。

訊息系統能減少搬運，但要讓答案有用，仍需要對方知道正在談哪個專案、分支和任務。這些脈絡越明確，代理越容易回到正確檔案，而不是拿另一個專案裡相似的介面來回答。

Agent Relay 的專案文件列出頻道、對話串、檔案、搜尋與即時事件，讓工作可以按議題分開。跨機器連線則讓筆電、本機代理與遠端節點加入同一個協作範圍，機器位置不再等於對話邊界。

這一層主要負責連接與傳遞，不會因為兩個代理開始對話，就自動取得對方程式庫的全部寫入權。原本工具的權限、分支和專案設定，仍是執行變更時的條件。

訊息能到達對方以後，接手者還需要知道回答來自哪次工作，而不只是收到一段結論。

## 共享會話搜尋，能補上哪些程式碼以外的背景？

Shared Sessions 讓團隊搜尋先前的修復、決定與任務脈絡，找到後再讀取會話內容。程式碼能告訴代理目前怎麼運作，對話歷史則可能解釋當初為什麼選擇這個做法。

例如某段重試邏輯看似多餘，實際上可能是為了處理第三方服務的一種失敗模式。若代理只看到現有程式，容易建議簡化。如果能找到先前的討論，就有機會理解那個保留條件。

共享會話工具分成搜尋、取得會話資訊與讀取相關脈絡，讓代理先找可能相關的紀錄，再展開內容。這個順序能避免把大量不相干歷史一次塞進對話，但找到的結果仍應留下來源。

官方文件說，Cloud 依登入工作區的 History 存取權處理搜尋。因此，能搜尋哪些內容取決於工作區與分享設定，而不是所有安裝相同外掛的人都能讀到整家公司的代理對話。

對團隊而言，這也改變工作紀錄的角色。一段原本只給自己看的測試對話，可能成為日後同事代理查詢的材料，所以哪些任務可以共享、哪些要保留在個人範圍，需要在使用前說清楚。

搜尋結果最好能讓人回到原會話，而不是只留下代理整理後的一句結論。原始脈絡可以顯示當時的假設、尚未解決的問題和後續修正，避免摘要把不確定的討論變成既定決策。

歷史提供的是當時的證據，因此它如何被讀取、是否對應現有程式，會影響下一步判斷。

## 搜尋到舊修復後，為什麼還要核對目前程式？

會話記錄能解釋決策，但程式庫可能已經改版，舊結論未必仍然成立。官方共享會話說明也提醒，歷史不會證明程式庫現在還有相同行為，代理需要再查目前實作。

假設一週前的對話提到資料欄位叫作 user，今天的分支已改成 owner，舊會話就只能解釋變更前的狀態。如果代理直接照舊回答，訊息雖然傳得更快，錯誤也可能更快擴散。

比較可靠的交接應把歷史與現況連起來：先找到改名原因，再確認目前檔案與測試使用哪個欄位。這樣對方收到的不是一段沒有時間位置的建議，而是一個能回查的變更背景。

同樣地，之前通過的測試也有版本條件。代理可以引用當時成功處理的方法，但仍要在目前分支執行相關檢查，才能知道新依賴或後續修改是否改變結果。

共享歷史也不等於獲准繼續操作。文件明列，這個套件讀取工作區歷史，不會因此取得恢復會話、改變分享或向其他代理傳訊的權限。查閱背景與執行新工作，仍是不同能力。

這些限制使共享搜尋比較像工程證據的入口。它能省下找人的時間，卻不該取代程式版本、資料來源與實際測試，否則團隊只是把口耳相傳換成代理彼此引用。

背景與現況核對完，如果想讓重要步驟每次都執行，就需要超出一般聊天的安排。

## Flows 和一般技能說明有什麼差別？

Flows 把多步工作、必要檢查和人工關卡寫進程式，目標是讓關鍵規則由流程執行。這與在技能說明裡請代理記得做某件事不同，因為流程可以具體安排下一步何時發生。

例如團隊規定程式修改後必須先跑某組測試，才提供合併的選項。自然語言說明能告訴代理規則，程式流程則可以在沒有測試結果時停止前進，讓要求成為執行順序的一部分。

Agent Relay 的文件以 TypeScript 定義這些多步流程，包含固定檢查與人工關卡。這有助於把反覆使用的作業方式交給其他代理，但規則仍需要作者正確設定，並不是自動理解所有公司政策。

流程也應處理部分失敗。例如資料取得成功、建立分支成功，最後測試失敗，接手者需要知道哪些動作已做過，才能決定修正或停止，而不是重新執行全部步驟。

這裡的改善來自把必要條件寫得可判斷。若條件只是「品質很好」，程式仍難以自動確認。若改成指定檢查結果與可供審閱的修改，流程就有比較明確的前進依據。

因此，適合寫進流程的是團隊反覆要求、又能觀察結果的步驟。需要產品取捨或例外決定的部分，則可以保留人工關卡，不必為了自動化把重要判斷藏進一段提示詞。

流程中的人工關卡也應交給有權決定的人。例如測試通過後，工程審閱者確認修改範圍，產品負責人確認行為是否符合需求。這是可依團隊安排的流程設計，不是宣稱平台已替所有團隊預設相同角色。

流程能規定先後，卻不會替團隊選擇資料要放在哪裡，雲端與自架仍需分開比較。

## Agent Relay 自架能涵蓋什麼，哪些功能仍需雲端？

自架 Relaycast 主要替換訊息引擎，本機節點能向自家服務傳訊，但共享會話和雲端沙箱仍依賴 Cloud 帳號。這項邊界在官方自架文件有明列，不能把開源理解成全部雲端功能都可直接搬回來。

Relaycast 處理工作區、代理、頻道與即時訊息。各機器上的節點再把代理連到這個引擎。對只想連接幾臺可控制機器的團隊而言，這提供了不經代管訊息服務的選項。

官方自架引擎採單一程序與 SQLite，屬單租戶安排。單租戶是由同一部署服務一個租戶範圍，這讓初始架構較直接，但也表示需要先讀取擴充限制，不能自行假設能承受任意規模。

自架後，團隊會接手服務可用性、升級與備份，也要讓即時連線能穿過自己的網路設定。省掉的是部分代管依賴，增加的是維運責任，兩者應依實際需要比較。

另有 Relayfile 把外部服務資料呈現成檔案介面，讓代理用熟悉的讀取和搜尋方式處理。它可以涉及寫回服務，因此是否啟用這個元件，以及外部帳號允許哪些動作，需要另行安排。

核心專案採 Apache 2.0 授權，雲端則提供免費開始的入口。原始碼授權與雲端資源費用分開，免費試用不等於所有算力、儲存與團隊功能都永久無限制。

自架還要讓各機器上的節點指向正確服務位置。官方文件說，沒有設定時會使用代管訊息服務，所以只啟動自家引擎並不足夠；團隊需要確認節點與代理實際連到同一個自家端點，才能知道訊息真的走預期路徑。

因此，選擇自架之前，先確認需求是訊息協作還是完整的雲端工作歷史，才能估計維運範圍。

## 共享歷史與套件版本，導入前要確認什麼？

團隊要先確認工作區的 History 存取，以及已安裝 CLI 和 Cloud 部署是否支援想使用的共享會話功能。CLI 是在終端機執行的命令列工具，程式庫裡有功能說明，不代表已安裝版本一定能執行。

這一點在 Shared Sessions 的安裝文件尤其明確：它要求包含相應命令的 CLI 與雲端端點，並警告當時已發布的 CLI 可能尚未支援該參數。因此讀者應依相容版本操作，不能照新文件就宣稱全面穩定上線。

桌面工具還可能使用不同的執行環境。若終端機找得到命令，代理應用程式卻找不到，就要確認它實際使用的工具路徑。這是連接設定問題，和工作區是否存在是不同原因。

登入與憑證也應由既有連接流程處理。官方預設透過命令列橋接管理登入與更新，不需要把存取憑證貼進代理對話或公開設定檔，避免為了讓工具連上而擴大分享範圍。

當搜尋不到資料時，應分辨是沒有相關會話、權限不包含該歷史，或目前功能版本不相容。三者需要不同處理，直接改用更大的資料分享範圍未必能解決問題。

確定資料範圍和相容版本後，就可以把驗收放回一次真實的跨代理交接。

## 怎麼判斷代理交接真的讓工程工作變快？

我會選一個需要前後端配合的變更，觀察雙方能否引用歷史、同步資料格式，最後交付同一份可測試修改。它應包含原本需要人類搬運的資訊，才能看出新連接層減少了哪一段工作。

過程裡要保留代理問了什麼、回答引用哪次決策，以及修改最後落在哪個分支。這些紀錄能區分真正的接手，和兩個代理各自做完一份互不相容的變更。

若兩邊改到同一個檔案，最後仍要看整合後的程式與測試。代理彼此同意解法，只代表達成一個提案，沒有替產品負責人或工程審閱者完成最後確認。

能減少人類搬運背景，又保留可檢查的變更和人工關卡，才是這次協作工具值得留下的成果。

## 常見問題 FAQ

### Agent Relay 一定要所有人用同一套編碼工具嗎？

官方設計是保留既有工具，再增加訊息和協作層。實際可用範圍仍要依工具整合、版本與權限確認。

### 自架後可以完全不使用 Agent Relay Cloud 嗎？

本機節點與訊息可對接自架引擎，但官方文件說明共享會話、雲端沙箱和代管儀表板仍需Cloud帳號。要先區分自己需要的元件。

### 搜尋到舊對話就能直接照做嗎？

舊對話提供歷史背景，仍應核對目前分支、檔案與測試。歷史讀取本身也不會取得恢復會話或改變分享的權限。
