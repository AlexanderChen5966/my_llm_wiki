企業把 Claude 接上多個工作工具後，員工往往還要逐一登入並同意連線。

Claude 企業連接器新增的自動授權方式，讓管理員先核准，再由 Claude 替現有成員簽發身分聲明。

這項 Claude-issued auth 在十一月三日以測試版公開，適用 Claude Team 與 Enterprise。

連接器提供者也必須支援這種方式，服務端再依使用者帳號與既有權限決定可存取內容。

登入步驟因此縮短，但企業必須先決定由誰驗證身分，以及員工離職後由誰收回權限。

先把管理員、Claude 和連接服務的分工對上，才適合擴大到整個團隊。

## Claude 企業連接器為何能省去逐人登入？

管理員為支援的連接器完成一次設定後，符合角色條件的成員就能自動取得連線。

連接器負責把 Claude 和工作服務接起來。例如，員工需要從專案工具查任務，或讀取組織資料，通常要先以自己的服務帳號登入，再同意 Claude 存取。

當使用人數和工具一起增加，每位成員重複連線就成了導入流程的一部分。企業集中授權把這件事往管理員端移動，讓組織先決定哪些連接器可以使用。

原有的身分提供者管理方式，會沿用公司的單一登入系統。這種系統讓員工以既有企業身分進入多個服務，再由身分提供者簽發所需的授權資訊。

新的 Claude-issued 方式則讓 Claude 成為簽發者，替仍在組織裡的使用者提供身分聲明。服務端信任這個簽發者後，才能進一步把使用者對應到自己的帳號。

因此，省去的是每個人重複登入和同意的步驟。成員仍需要在連接服務中有符合條件的帳號，能讀哪些資料也由設定與服務權限決定。

Anthropic 將由身分提供者管理的方式列為正式開放，Claude 簽發的方式則仍在測試。兩種方式同屬企業集中管理授權，企業可以依自己的身分架構選擇。

對原本身分系統尚未支援相關授權擴充的組織，這提供另一個接入選項。選擇之前，還需要理解 Claude 簽發的聲明究竟保證了哪些資訊。 [Anthropic 官方管理文件](https://support.claude.com/en/articles/15537633-auto-connect-your-organization-s-apps-to-claude?ref=aiposthub.com)

## Claude 簽發身分後，服務如何決定存取範圍？

Claude 會確認使用者仍是組織成員，再簽發供連接器使用的身分聲明。

這份聲明包含可對應使用者的資訊，由組織專屬的簽發者網址識別來源。連接服務先把這個網址加入受信任的簽發者，之後才能確認資訊確實來自該 Claude 組織。

在使用者指示下，Anthropic 會把成員電子郵件地址與唯一識別資訊送給連接器。服務利用這些內容確認帳號，所以兩邊的電子郵件是否一致，會直接影響自動連線能否成立。

官方文件說明，Claude 檢查的是組織成員資格。這個步驟不會替企業驗證使用者在身分提供者端的登入、多因素驗證，或連接服務自己的登入規則。

多因素驗證是登入時除密碼外，再要求另一種證明的機制。因此，企業若原本依靠這類條件控制存取，就需要確認改用 Claude 簽發後，實際由哪一層繼續落實要求。

服務端接著依自己的帳號和權限發出存取權杖。權杖可以理解為限時使用服務的憑證，連接器拿到之後，才能在授權範圍內代表該成員工作。

Supabase 的官方例子更清楚地展示了這段分工。它會確認簽章符合已登錄的簽發者、使用者有匹配的組織身分，而且擁有者或管理員已核准 Claude。

這些檢查通過後，Supabase 發出綁定該成員的短期權杖，沿用成員既有角色。權杖到期時，Claude 再提供新的身分聲明，讓成員持續連線。

這讓使用者感受到的流程較簡單，背後卻仍有明確的帳號對應和服務授權。確認完這個分工，才有辦法判斷自己的方案與工具是否符合條件。

## 哪些方案與連接器能用自動授權？

Claude 簽發的測試版涵蓋十四個連接器，各服務的方案和身分條件仍分別適用。

截至二〇二六年十一月五日查詢，官方列出的測試名單包括 Amplitude、Apollo.io、Atlassian、Datadog、Dropbox、Figma 與 Granola。

另外還有 HubSpot、Linear、Mixpanel、Notion、PagerDuty、Semrush 和 Supabase。這份清單對應支援 Claude 簽發的測試範圍，完整企業管理授權的連接器名單另有更多項目。

因此，看到某個服務支援企業集中授權，還要再看它是否接受 Claude 作為簽發者。服務提供者需要完成對應支援，自建或其他 MCP 服務也要先加入這項能力。

MCP 是讓 AI 工具與外部服務交換能力的通訊協定。連上 MCP 服務本身，只是建立工具入口，企業管理授權則進一步處理使用者如何取得該入口的存取資格。

在 Claude 端，Team 與 Enterprise 組織可以啟用這項測試。採用 Claude 簽發時不需要另外設定身分提供者或單一登入，但第三方服務可以有自己的要求。

例如，Supabase 對外提供的這項整合已正式開放給設有單一登入的 Team 和 Enterprise 組織。這是 Supabase 端條件，和 Claude 端的測試資格需要一起確認。

若企業本來就有可運作的身分提供者簽發方式，也可以繼續使用原本流程。管理員要比較的是現有身分控制、工具支援和維護方式，選出符合組織需求的來源。

同一個連接器一次使用一種身分來源，之後可以切換。因此，實際設定前先把兩端需求列清楚，較容易知道測試失敗是帳號、方案，還是來源尚未受信任。

## 以 Supabase 為例，管理員如何完成設定？

Supabase 組織需要已設定單一登入，成員也須先具備可對應的單一登入身分。

官方要求每位成員至少先透過單一登入進入 Supabase 一次，使用的電子郵件要和 Claude 相同。這能讓後續聲明找到既有帳號，而服務權限沿用該帳號角色。

設定需要兩邊的管理能力，包含 Supabase 組織的擁有者或管理員，以及 Claude 組織管理員。不同人負責時，就要協調簽發者網址登錄與連線測試。

首先，擁有者或管理員連接 Claude 與 Supabase，替組織核准應用程式。官方指出，這項核准可在 Supabase 組織設定的已授權應用程式中查看或撤銷。

接著到 Claude 組織設定，開啟連接器，選擇 Supabase。在設定頁的管理授權項目中開始設定，於身分來源選擇由 Claude 簽發，取得組織專屬網址。

管理員把網址登錄到 Supabase 的單一登入進階設定，作為受信任的身分聲明簽發者。這個步驟決定服務會接受誰簽出的聲明，因此要確認貼入的是正確組織來源。

回到 Claude 執行連線測試，檢查通過後再啟用，接著選擇適用角色和授權範圍。如果測試失敗，官方建議核對網址、工作區或租戶資訊，以及目前帳號能否對應。

角色設定決定哪些人自動取得連接器，授權範圍則決定 Claude 可要求哪些權限。先讓一個團隊試用時，可以只選該團隊的自訂角色。

官方文件也提醒，若要維持小組測試，應確認內建角色群組沒有一起選上。否則一般使用者、管理員與擁有者可能同時被納入自動連線範圍。

個別角色還能縮小某個連接器的權限，因此「哪些人能連」與「連上後能做什麼」要分別核對。成員實際看到的資料，最後仍須符合 Supabase 既有角色。

設定完成後，符合條件的成員第一次使用就會看到已連接。若電子郵件對不上服務帳號，則仍會看到一般的連線提示，管理員可用這個差異追查身分匹配問題。

官方建議在通知全組織之前，先找兩三位成員確認連線並執行真實請求。測試成功後，也應走一次撤銷流程，才能理解權限何時停止生效。 [Supabase 官方設定說明](https://supabase.com/blog/claude-issued-enterprise-managed-auth-for-mcp?ref=aiposthub.com)

### 從角色端管理，如何檢查整組工具？

管理員也能從組織角色設定進入連接器頁籤，查看某個角色的成員要如何連線。官方提供個別登入、管理授權，以及按連接器分別設定的選擇。

這對同時使用多個服務的團隊有實際用途。管理員可以先確認一個角色的整體連線方式，再對特定服務安排不同設定，避免只逐項啟用而漏掉角色之間的差異。

企業集中授權以外，成員仍可加上個人連接器，依自己的帳號完成連線。因此，管理員檢查組織工具時，需要辨認哪些來自集中設定，哪些是成員另外加入。

若希望工作工具只走管理授權，官方也提供要求連接器僅透過此方式連線的控制。是否採用這項設定，可以配合企業對個人帳號和工作帳號的管理需求決定。

把實際角色、身分來源與服務權限一起記錄下來，後續擴大或撤銷時就有可核對的起點。這也讓成員遇到連線差異時，管理員能沿同一套設定追查。

## 成員離職與切換簽發者時，權限如何收回？

移除 Claude 成員會停止新的身分聲明，既有服務權杖仍依服務端的到期與撤銷規則生效。

因此，企業應把 Claude 和連接服務的成員移除放在同一項離職作業。只在其中一處關閉帳號，可能無法涵蓋已發出的憑證或另一處仍保留的組織資格。

Supabase 特別指出，在由 Claude 簽發的情況下，停用身分提供者中的帳號不會自動阻止這條授權路徑。因為 Claude 與 Supabase 不會再向該提供者詢問成員是否仍有效。

若組織使用目錄同步，也要確認實際刪除了 Claude 成員。官方說明，目錄刪除會觸發移除，單純暫停或標成不活躍則有不同效果，需查看成員清單的最後狀態。

電子郵件重新分配也要納入帳號處理。由於服務透過電子郵件匹配使用者，舊帳號應先從連接服務移除，再把同一個地址交給新成員，避免對應到前一個人的帳號。

切換簽發者則有另一種影響。Supabase 每個單一登入提供者信任一個簽發者，填入 Claude 的網址會取代原本的提供者網址。

替換後，Supabase 會拒絕原提供者簽發的聲明，直到管理員恢復原網址。因此，其他依賴同一個提供者進行管理授權的 AI 工具，也可能受到這次變更影響。

同一個 Claude 簽發者網址也只能供一個 Supabase 組織使用。若企業有多個組織，設定計畫就需要配合這項限制，逐一確認信任來源與目標。

這些條件會影響組織選擇哪種身分來源。先測試一位成員從連線到移除，再核對其他既有工具是否仍能使用，較能看清切換後的管理負擔。

## 常見問題

### Claude 企業連接器可以在原有連線失敗後改成個別登入嗎？

如果管理授權與瀏覽器登入同時開啟，Claude 會先嘗試管理授權，失敗時再提示個別登入。管理員可依組織設定決定提供哪些方式。

### 管理員可以之後再擴大自動連線對象嗎？

可以。設定頁會顯示已套用角色與授權範圍，管理員可編輯角色，將小組試行擴大到其他團隊或內建角色群組。

### 關掉 Claude 簽發後，使用者怎麼繼續？

管理員可以在管理授權設定中停用這種方式，成員之後自行連接服務。服務端已發出的存取權杖如何失效，仍需依該服務的生命週期與撤銷功能處理。

## 先讓一個團隊走完登入與離職流程

需要集中管理連接器的企業，可以先選支援的服務與小組角色試行。確認兩端帳號、原有權限和撤銷結果都能對上，再擴大自動連線範圍，才容易把登入便利和日常管理接在一起。
