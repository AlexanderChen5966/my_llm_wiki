Cursor Grok Bot 的代理通訊文件，讓本機助手可以請另一個 Bot 提供資訊或協助。近期 X 使用者分享 Codex、Claude Code 與 Grok Bot 交接的體驗，引起討論。

本機代理擅長接近專案檔案，遠端助手可能保留長期工作脈絡與已連接的工具。兩邊能合作，使用者便不必手動搬每段資訊。

但另一個 Bot 不會自動看到目前對話，傳過去的訊息仍要自成一個完整任務。不同呼叫者也不一定擁有獨立的遠端記憶。

這個更新適合用來減少交接步驟，前提是接收對象、資料範圍與結果狀態清楚。

## Cursor Grok Bot 文件說明了哪種連接？

[官方 BDK 指南](https://cursor.com/docs/bdk/guides/grokbot-agents?ref=aiposthub.com) 描述 cursor-grokbot-agents 擴充，讓 BDK 代理諮詢其執行主機帳號中的 Grok Bot。

BDK 是建立與執行 Bot 的開發工具組。這項擴充屬於本機執行環境的連接，並非把本機助手搬到另一個 Bot 的執行場所。

因此，讀者不能把使用者的便利體驗理解成所有程式助手已預設開通。實際接法仍要符合官方文件與自己的工具環境。

### 傳送訊息前，要把背景補足

官方說明接收的 Bot 看不到目前 BDK 對話。訊息應交代誰在詢問、重要事實與需要的回答形式。

假設本機代理想查會議安排，就應提供日期、參與者與需要比較的選項，而不是只傳「依上面說的處理」。

這是交接原則的應用例子，並非示範會自動讀取所有行事曆。必要資料越清楚，接收方越不容易再猜一次。

### 讓接收方只看一則訊息，也知道要做什麼

假設本機助手正在整理專案進度，想向遠端 Bot 確認交件日期。訊息應帶上專案名稱、文件版本與要確認的事件，讓對方知道這次詢問的範圍。

若只寫「確認那件事」，遠端可能從既有記憶找出別的事件。回答看似合理，卻沒有處理眼前問題，這種錯誤比明確失敗更難發現。

完整訊息還要說明結果形式。例如要求回覆日期、原始來源與仍有疑問的地方，本機助手才知道哪些內容能接回自己的工作。

這是訊息設計建議，不代表擴充會自動建立工作單。官方提供通訊工具，任務背景仍需要由呼叫的一方整理，再傳給指定的 Bot。

兩邊角色也可以寫清楚。假設本機負責修改文件，遠端只負責查公開資料，詢問就不應加上「查到後順便處理」這種模糊範圍。

有了明確分工，遠端回覆能被當成參考結果，而不會直接變成執行命令。本機仍應對照來源，判斷回答是否適用目前版本。

傳送摘錄時，可以保留足以辨識事件的上下文。只截一個數字，接收方很難知道單位與時間區間，容易從記憶補出錯誤背景。

整份全文都傳過去，也未必比較有效。與問題無關的內容會分散注意，真正需要的是一段足以讓對方回答的明確材料。

這種交接尤其適合資訊分散的情況。例如本機知道專案檔案，遠端知道之前的討論，但雙方都必須說清楚哪些條件是這次新補上的。

若接收方完全沒看過本機對話，只讀訊息也能知道要回答什麼，以及什麼狀態才算完成，這次交接就有了可檢查的起點。

## 工具回報仍在工作，不能當成已完成

擴充提供 ask、check、interrupt 與 list。ask 用來詢問，check 用來接回結果，interrupt 則能停止目前的工作。

如果等待時間到了，工具可能回傳 running，也就是尚在執行。此時應繼續等待所需結果，而不以已經送出訊息當成任務完成。

### 檢查結果需要保留順序

check 會推進呼叫者的讀取位置，接回尚未消費的回覆。之前未讀的訊息也可能一起出現，因此要分清各回覆屬於哪次工作。

當多項任務交錯進行，明確的任務名稱與交付要求能降低混淆。若只是反覆查詢同樣狀態，也會增加不必要請求。

### 延後到達的答案，要接回正確的任務

假設本機助手送出規格比較後，繼續整理自己的表格。遠端答案回來前，表格應保留空位，不能把發送成功當成比較完成。

可以在訊息中放簡短的任務名稱，回覆也沿用它。例如「六月規格比較」更容易與之前的工作區分，也能避免兩份答案混在一起。

這個名稱是使用上的安排，並非官方保證自動產生的識別碼。目的在於讓兩方認出同一次諮詢，減少後續追問與誤用。

官方說，較早的未讀回覆也可能跟目前結果一起送回。因此，收到多段內容時，要先分清各段對應的問題，再決定哪些仍適用。

若 Bot 正在處理先前的訊息，ask 不會送出新工作。把這種狀態當成排隊成功，後面就可能一直等待不存在的答案。

已聯絡過的 Bot 可以接回原工作結果，或停止錯誤方向。首次聯絡遇到忙碌，則需等既有工作結束，再重新提出詢問。

停止不會把 Bot 的對話與記憶清空。新的詢問仍要交代哪些舊條件不再適用，才不會繼續沿用被取消的目標。

例如原先詢問戶外活動，後來只想比較室內場地，新的訊息應寫出這個變更。只說「重做」，對方仍可能照原方向處理。

答案回來後，本機先核對來源，再把結論接回檔案。若只有部分問題得到回答，就補問缺的部分，避免整項工作不斷重送。

知道工作卡在哪裡，比增加等待次數更有用。訊息沒送出、仍在執行與答案不符需求，三種情況需要的下一步完全不同。

## 名稱清單與帳號隔離，是兩個不同設定

官方指出代理清單是名稱允許範圍，沒有填清單時可接觸任意名稱。名稱拼錯，也可能在首次使用時建立新的空 Bot。

因此，設定共享工具時，應用清楚的名稱與用途。若結果顯示剛建立新的Bot，先確認是否找對對象，再繼續交付。

### 呼叫者分開，不等於遠端記憶分開

官方文件說，不同認證的 BDK 呼叫者可有自己的聯絡清單與讀取位置，但操作的仍是主機帳號現有的 Bot 對話。

這代表共享主機的團隊不能只憑各自登入，就認為不同客戶的資料與記憶完全隔離。工作範圍應與帳號使用方式一起設計。

### 團隊共用主機時，要看實際資料走向

假設兩位同事共用一部主機，一位處理公開課程，另一位處理客戶專案。即使各自登入，遠端仍可能接觸同一個主機帳號的 Bot 對話。

官方分開聯絡清單與讀取位置，讓呼叫者各自追蹤接收的內容。這種分開不會自動建立新的遠端帳號，也不代表記憶完全隔離。

因此，不能只憑兩個登入畫面判定客戶脈絡已分開。應先確認主機使用哪個帳號、會聯絡哪些 Bot，以及那些 Bot 原本保存什麼內容。

名稱允許清單限制可以聯絡的名稱，卻不檢查名稱背後是否有既存 Bot。它也不能取代帳號安排，兩種設定處理不同問題。

假設要找「課程助手」，設定時卻多打一個字，首次呼叫可能建立空 Bot。使用者於是以為原有助手忘記內容，其實是找錯對象。

遇到新建提示時，先核對名稱比繼續補送資料更有效。若只是拼錯，傳更多客戶內容只會增加一份不需要的副本。

團隊可以先用公開問題確認接收方名稱與用途。這樣能排除基本設定問題，也能看清楚回答是否真的沿用預期的工作脈絡。

若所有人共用相同認證，呼叫者的追蹤也可能合併。需要分開聯絡歷史時，要依文件採用個別認證，不能只在訊息裡標上姓名。

個別認證仍只是其中一層。對需要分開的工作，還應評估遠端帳號與 Bot 的安排，讓資料邊界符合實際分工。

## 什麼任務適合先測？

可以先做公開資料的諮詢。例如本機助手把一份公開規格摘要交給另一個 Bot，要求回答指定問題，再由本機對回原文件。

這是低風險測試建議。它能檢查訊息、等待與結果交接，而不必先開放寄信、改資料或付款。

測試成功後，才依工作需要逐步增加工具。每一步都應能說清楚哪個助手對結果負責。

### 用一份公開規格，驗收完整交接

假設手上有兩版公開規格，可以要求遠端找出指定欄位的差異。先限定欄位與版本，避免第一輪同時加入修改、通知與其他目的。

本機負責保存來源，遠端負責提出差異與引用位置。答案回來後，再對照原文件，檢查每個變更是否確實存在。

若有漏掉內容，先看訊息是否提供足夠背景。背景完整卻仍對錯版本，就需要調整接收方的查詢方式，而非擴大任務範圍。

也可以安排一次取消情境，讓遠端查詢途中停止。測試重點是新的詢問能否接上更正條件，以及舊答案是否被誤當成最新結果。

這些情境不用讓助手真的寄信或改資料，就能檢查通訊流程。成功標準是來源與答案可核對，而且每種工作狀態都能說清楚。

一輪結束後，再看節省了哪種時間。若仍需手動重述背景、追問進度與整理回覆，通訊已建立，工作流程卻可能還沒有縮短。

如果遠端能利用既有脈絡補足本機缺的資訊，本機也能接回結果完成文件，這種分工才有價值，不只是多一個對話視窗。

擴大連接工具後，也應沿用相同驗收方式。每項結果都要能指出資料來自哪裡、哪些動作已發生，以及下一步由誰決定。

代理確認需求，不等於程式變更已通過測試。若交接接到程式專案，還要檢查版本與實際執行結果，避免把兩種完成混為一談。

測試時也可以刻意省略一個必要條件，觀察接收方是否要求補充。例如沒有提供規格日期，合理的回覆應先釐清版本，避免直接選出某一份資料。

這個情境能看出助手是否知道答案依賴什麼前提。若它總是給出肯定結論，則要改善交接要求，把無法確認時應回報的內容寫清楚。

最後讓同事只看傳送訊息與回覆，說出這次工作完成了什麼。若他還需要翻本機聊天，代表交接材料仍少了一步，應先補足再擴大用途。

比較規格時，也可以要求回覆逐欄對照，而不是只給整體結論。若助手說兩版相同，卻沒有列出指定欄位，仍要回原文件檢查，不能省略核對。

這種格式會讓缺資料的位置浮出來。某欄在舊版沒有出現，就應說明缺少內容，不能把新版數值填回舊版，製造看似完整卻不忠實的比較。

## Cursor Grok Bot 的背景與記憶邊界

### 傳送訊息仍需完整背景

官方說接收的 Bot 不會看到目前對話，傳送訊息仍需完整背景。資料範圍應由交接內容控制。

### 呼叫者紀錄與遠端記憶分開理解

不同本機使用者不會因此取得獨立的 Bot 記憶。官方區分呼叫者紀錄與主機帳號的 Bot 對話，兩者是不同的資料邊界。

## 先讓一次諮詢的來源與結果可追查

代理通訊能減少手動搬資訊。先用公開資料完成一次詢問、等待與回覆核對，確認沒有找錯Bot或接錯結果，再增加實際工作範圍。
