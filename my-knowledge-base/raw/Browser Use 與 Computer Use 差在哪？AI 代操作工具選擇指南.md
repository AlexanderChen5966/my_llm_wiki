Browser Use 與 Computer Use 都能讓 AI 幫忙操作介面，但適合的工作範圍不同。只是讀一篇公告、需要填寫網頁表單，以及要把資料搬進桌面軟體，會用到不同的入口。

因為任務會碰到的資料與操作範圍不同，選工具前先把工作拆清楚，比直接開放整台電腦，更容易判斷它是否做對。

繁中學習地圖 awesome-agentic-ai-zh 的 Stage 8，正是從這個問題安排教學。本文再對照 2026 年 11 月 5 日查詢的供應商文件，整理選型時需要理解的差異。 [Stage 8 原始章節](https://github.com/WenyuChiou/awesome-agentic-ai-zh/blob/main/stages/08-agent-interfaces.md?ref=aiposthub.com)

對想委派查資料、整理檔案或操作網站的人，先選能完成任務的操作範圍，再要求留下可核對的成果，就比較容易知道何時需要換工具。

判斷可以先從一個問題開始，這件工作是否全都發生在網頁裡？

## Browser Use 與 Computer Use 差在哪裡？

Browser Use 指讓代理在瀏覽器裡讀取與操作網頁。Computer Use 的操作範圍則可以涵蓋桌面環境，讓代理透過畫面、滑鼠與鍵盤，在不同應用程式之間工作。

例如，在網站上找日期、切換分頁與填入欄位，可以先評估網頁操作工具。若要把網頁資料放進桌面程式，再調整原生視窗與選單，就需要檢查桌面控制能力。

以下先依工作範圍比較，方便對照自己的任務。

| 比較項目 | Browser Use | Computer Use |
| --- | --- | --- |
| 主要操作範圍 | 網頁、分頁、表單與網頁元件 | 桌面畫面與應用程式 |
| 常見觀察方式 | 網頁結構、元素狀態與截圖 | 截圖及工具提供的桌面資訊 |
| 適合先評估的工作 | 網站查詢、網頁資料整理、填表 | 跨桌面軟體的操作與交接 |
| 需要提供的環境 | 可受控的瀏覽器 | 可受控的桌面環境 |

網頁工具也可能使用截圖與座標，桌面工具也能操作瀏覽器，因此兩者在畫面處理上會重疊。評估時，先看工具能進入的環境，以及它能回傳哪些結果。 [Anthropic 瀏覽器工具說明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool?ref=aiposthub.com)

確定操作範圍後，還要挑取得資料最直接的入口。有些工作只需要拿到資料，就可以先從搜尋與服務介面評估。

## 為什麼先確認 API、搜尋與資料擷取？

API 是讓程式與服務串接的介面。如果任務需要的資料與操作已由正式 API 提供，應先確認它能否交出需要的欄位與結果。

例如，要取得一組公開資料，服務若提供包含日期、標題與識別編號的回應，就能直接依欄位核對。這是本文的選型示範，重點在輸出是否符合交付需求。

若只是找公開文章與讀內容，搜尋與網頁擷取也可能已經足夠。擷取是把頁面內容取回，適合資料閱讀，後續再整理成摘要或表格。

當內容需要互動才會出現，例如先選日期、切換頁籤或展開清單，網頁操作工具就有更明確的用途。選型時可以先畫出資料藏在哪一步，再決定需要哪些能力。

這樣做也方便比較成本。若整個工作只缺一個欄位，先改善資料取得方式，通常比重新安排全部滑鼠操作，更容易查出問題。

## 網頁元素、無障礙樹與截圖怎麼合作？

代理需要知道哪個地方可以操作，以及操作後發生了什麼。網頁結構與畫面各自提供不同線索，所以工具常會把它們搭配使用。

DOM 是瀏覽器整理網頁程式節點的結構，可以包含元素與屬性。無障礙樹則把內容整理成角色、名稱與狀態，例如「搜尋按鈕」或「已勾選的選項」，方便輔助工具理解。

因此，按鈕有清楚名稱時，代理可以依元素資訊尋找目標。如果介面是一張互動圖片或繪圖區，截圖就能補上結構資訊沒有呈現的外觀。

Microsoft 的 Playwright MCP 提供結構化無障礙資訊來操作瀏覽器。MCP 是讓 AI 應用程式連接外部工具的協定，實際可用能力仍取決於接入的工具與設定。 [Microsoft 專案說明](https://github.com/microsoft/playwright-mcp?ref=aiposthub.com)

### 模型提出動作後，誰負責真的按下去？

以 Anthropic 的瀏覽器工具為例，模型會提出導覽、讀頁面或點擊等呼叫，應用程式負責在自己的瀏覽器環境裡執行，再把結果交回模型。 [Anthropic 工具執行流程](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool?ref=aiposthub.com)

電腦操作也有相同的分工。模型可以提出滑鼠或鍵盤動作，但整合程式仍要處理執行環境與結果回傳，因此導入工具時，也要確認這一段由誰提供。 [Anthropic 電腦工具文件](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool?ref=aiposthub.com)

對現成產品的使用者，這些工作可能已經包在產品裡。對自己串接的開發者，則需要把動作執行、狀態回傳與完成判定接起來，才能形成連續流程。

## 什麼情況需要跨 App 與沙箱？

當任務需要原生桌面軟體，或資料必須在多個應用程式之間移動，就應評估桌面環境與電腦操作工具能否支援完整流程。

以下是原創情境示範。一份資料先在網站上下載，再交給桌面排版軟體製作報表，過程可能需要切換視窗、操作選單與儲存檔案。

評估時，先確認每個環節的輸入與輸出。資料是否下載完成、桌面軟體是否讀到正確版本，以及報表能否重新開啟，都會影響最終交付。

OpenAI 的電腦操作指南也把應用程式執行動作、回傳觀察結果與持續執行放在同一流程中。實作時可依自己的瀏覽器或桌面環境，選擇相應的整合方式。 [OpenAI 電腦操作指南](https://developers.openai.com/api/docs/guides/tools-computer-use?ref=aiposthub.com)

沙箱則是提供受限制的程式執行空間，用來安排代理可以接觸的檔案、網路與工具。若工作是執行整理資料的程式，就可以另外評估這種環境。

因此，一個完整任務可能同時需要幾種入口。例如網頁工具取回檔案，程式在沙箱整理，最後再回到網頁檢查輸出。每一段都應有自己的結果，才能找到失敗發生的位置。

## 第一次委派，怎麼判斷工具有沒有做對？

第一次可以選擇範圍小、結果容易核對的任務，先觀察工具如何讀取環境、執行動作與回報成果，再增加更多步驟。

以下是本文的教學示範。請工具只開啟 example.com，讀取頁面標題與主要文字，附上網址與一張畫面，完成後停止。完成範圍寫得小，才容易逐項核對輸出。

驗收時，自己打開網址，確認標題與文字確實對得上。截圖能幫助了解它看到了什麼，實際內容與來源則能補上結果是否正確的證據。

接著可以一次增加一種互動，例如在自己的測試網站裡展開一個選單。先約定操作後應出現哪個項目，工具回報完成時，就有明確狀態可比較。

如果頁面結果與預期不同，先保留網址、畫面與操作紀錄，再查是哪個步驟出了問題。直接反覆點擊，可能會讓後續狀態更難理解。

### 網頁內容如何影響代理的下一步？

提示注入是把新的指令藏在代理讀到的內容裡，試圖改變它原本的工作。因為網頁文字可能來自其他人，所以操作範圍應以使用者的交辦與工具規則為準。 [Anthropic 電腦操作考量](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool?ref=aiposthub.com#security-considerations)

交辦時可以把可用網站、修改範圍與停止條件寫清楚，讓工具知道何時該回報。涉及送出資料或其他狀態變更時，也要依已授權的任務範圍執行。

這些規則會隨任務變動，因此值得和專案資料一起保存。下次交辦相同工作，就能沿用已確認的邊界與交付格式。

## Browser Use 常見問題

### 使用 Browser Use，一定要安裝同名開源專案嗎？

Browser Use 也用來描述瀏覽器操作能力。browser-use/browser-use 則是具體的開源專案，有自己的函式庫與雲端產品，可依實際整合需求選用。 [browser-use 專案](https://github.com/browser-use/browser-use?ref=aiposthub.com)

### 能不能讓代理自動登入網站？

需要先確認所用產品的登入流程、網站要求與使用者授權。登入後能接觸的資料與動作也要符合任務範圍，因此應和執行環境一起評估。

### 有截圖，就代表任務完成了嗎？

截圖能呈現一個時間點的畫面。若任務包含儲存或產生檔案，還應重新開啟結果，確認內容與狀態符合要求。

### 怎麼比較不同工具的效果？

可以用相同任務、資料與完成條件，比較交付是否正確、耗時多少，以及需要多少人工修正。不同環境與步數設定的展示，適合作為進一步試用的線索。

## 先完成一個可核對的任務，再擴大操作範圍

只需要網頁工作的使用者，可以先評估瀏覽器工具。需要跨桌面軟體時，再確認電腦操作與執行環境，讓選擇跟著工作需求前進。

下一次委派前，先寫下來源、輸出與完成條件。工具交回結果後，沿著同一條路核對，才能知道該改善資料取得、操作步驟，還是最後的交付方式。
