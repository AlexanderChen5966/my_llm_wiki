《Clean Code》作者 Uncle Bob 不再閱讀 AI 程式碼，但他開源了 swarm-forge，一個以 tmux 為底層、讓多個 AI 代理並行協作的平台，並將 Clean Code 原則直接寫入代理的行為規範。

《Clean Code》作者 Robert C. Martin（暱稱 [Uncle Bob](https://www.inside.com.tw/tag/Uncle+Bob) ）在今年 7 月公開表示，他已不再閱讀 AI 產生的程式碼。這不是放棄，而是一個工作方式的根本轉變：與其審查每一行輸出，不如把精力放在設計能約束 AI 行為的系統架構。

他把這個想法落地成一個工具，在 GitHub 開源了 swarm-forge，這是一個以 tmux 為底層、專為多個 [AI 代理](https://www.inside.com.tw/tag/%E4%BA%BA%E5%B7%A5%E6%99%BA%E6%85%A7) 並行協作設計的平台。

### 三種規模對應不同任務量

swarm-forge 提供 3 種預設編組：two-pack（2 個代理）、four-pack（4 個代理）、six-pack（6 個代理），開發者依任務規模選擇適合的組合。小型原型驗證用 two-pack 即可快速跑完，中型功能開發或並行測試情境，four-pack 或 six-pack 則更有效率。

tmux 作為底層並非隨意選擇，tmux 是資深開發者熟悉的終端機多視窗工具，swarm-forge 利用它的 session 隔離特性，讓每個 AI 代理在獨立的 pane 中執行，彼此不共享環境狀態，降低代理間互相干擾的風險。

各代理之間透過握手協定（handshake protocol）傳遞任務與回傳結果，確保非同步溝通時不會互相覆蓋工作進度。平台附有 web 儀表板，讓開發者一眼掌握各代理的執行狀態，不需要一一切換終端機視窗人工確認。

### 把 Clean Code 原則寫進代理的行為規範

swarm-forge 最核心的設計，是把 [Clean Code](https://www.inside.com.tw/tag/Clean+Code) 原則直接寫入每個代理的行為規範（constitution）。

意思是 AI 代理在產出程式碼時，必須符合可讀性要求、命名規範、函式長度限制等原則，而非純粹追求功能達成或通過測試。Uncle Bob 相信，把品質約束前移到生成端，才能在不逐行審查的前提下維持輸出品質。

這和目前多數 AI 程式碼工具的設計邏輯截然不同。主流做法是讓 AI 快速產出可運行的程式碼，人工事後補充審查。Uncle Bob 的路線是在生成端就施加結構性約束，把審查成本從後端移到前端，用工具設計取代人工閱讀。

### 開發者的角色從審閱者轉向系統設計者

Uncle Bob 在 7 月的文章裡說，他之所以不再閱讀 AI 程式碼，是因為他信任在正確引導下 AI 能產出可靠結果，逐行閱讀只是重複驗證一件他已經決定信任的事。

swarm-forge 可以看作這個哲學的實作版本：不靠人工逐行審查，而是靠 tmux 隔離、handshake 協定、Clean Code constitution 共同構成品質保障架構。在這套框架下，開發者的工作從「確認每行程式碼是否正確」，轉向「設計一個能產出正確程式碼的系統」。

swarm-forge 目前已在 GitHub 公開，採開源授權，開發者可直接取用，也可依需求修改編組設定或調整 constitution 規範。

## 【專訪】從漏洞揭露到實戰利用只剩幾小時！AWS 安全與基礎設施副總裁 Hart Rossman：駭客攻擊自動化，企業如何重構安全防線？

面對AI時代加速演進的漏洞威脅，企業該如何以快制快？AWS安全與基礎設施副總裁Hart Rossman解析防禦關鍵，包括利用AI加速修復、自動化推理驗證，以及獨立AI代理身分，協助企業重構多層次資安防線。

從漏洞公開揭露到首次遭實戰利用的時間窗口大幅縮短，傳統仰賴人力的資安防線面臨轉型。隨著Amazon Web Services（AWS）亞太（台北）區域啟用滿一週年，亞馬遜宣布對台投資逾50億美元的長期計畫持續推進，於AWS服務超過14年的安全與基礎設施副總裁哈特・羅斯曼（Hart Rossman）接受專訪，剖析AI時代如何加速漏洞修復，並透過自動化推理與外部控制，為AI Agent建立安全防護機制。

2026 年，生成式 AI 與自主 AI 代理（AI Agent）技術持續演進，正改變全球企業的營運模式。然而，當企業加速導入 AI 提升效率的同時，資安攻防型態也隨之轉變。

過去，發現漏洞與發動攻擊往往需要高技術人員耗費數週至數月進行偵察，並花費數月開發概念驗證漏洞利用程式。然而，隨著具備自動化能力的大型語言模型普及，攻擊門檻與漏洞利用開發的時間正被大幅壓縮。

### 軟體安全經濟學轉變，漏洞利用窗口縮短至數小時

AWS安全與基礎設施副總裁羅斯曼指出，隨著自動化技術演進，軟體安全的經濟學已出現根本轉變。

![](https://bucket-image.inkmaginecms.com/version/mobile/9dde7c0f-a597-445c-80dd-9a93db8a4006/image/2026/09/1b98040e-a27f-48c8-b759-c1f7b56cc7af.webp)

AWS安全與基礎設施副總裁哈特・羅斯曼（Hart Rossman） Photo Credit: AWS

他引用「零日漏洞時鐘」（Zero Day Clock）的數據指出，2025年從CVE（Common Vulnerabilities and Exposures）公開揭露到首次確認遭到利用，時間仍以週計算；到了2026年，間隔期已縮短至個位數小時。

羅斯曼分析，Mythos等前瞻模型正降低漏洞利用工具的開發門檻。過去資安工具所依據的「漏洞利用稀缺且難以開發」假設已不再成立，這項永久性的營運轉變，也讓資安防禦的重心轉向縮短修復時間。

他認為，隨著前瞻模型能力持續提升，攻防時間差還將進一步縮短。因此，企業必須為不斷加速的威脅做好準備，建立相應的防護系統。

當攻擊方透過自動化工具加快行動，企業若仍仰賴人力分類與人工介入的傳統修復流程，修復速度將難以跟上AI發現漏洞的速度。

### 防禦焦點轉向修復速度，AI 日誌分析提升 50 倍效率

因應攻擊自動化，資安防禦的核心也必須從「發現更多問題」轉向「判斷優先順序並加速修復」。

羅斯曼指出，單純找出漏洞並不會讓組織更安全。若缺乏部署環境與資安脈絡，所有警報看起來都同樣緊急。若企業仍仰賴人力分類及人工介入，不僅難以迅速辨別真正高風險的漏洞，修復成本與時間也將難以跟上AI發現漏洞的速度。

舉例而言，位於 Web 應用程式防火牆後方、處於無外部路由且具嚴格身分驗證的虛擬私有雲內部漏洞，與直接暴露於公網且未設驗證機制的漏洞，兩者的實際風險概廓截然不同。因此，透過理解攻擊者如何取得存取權來精準評估嚴重性，是決定如何優先進行超越人工速度修復的關鍵第一步。

面對全球基礎設施每日超過400兆筆的網路流量，AWS早已在內部營運中導入機器學習與AI，協助強化資安防禦。

羅斯曼說明，AWS內部運行的Sonaris等系統，自2025年以來已在Amazon S3上阻擋逾3億次惡意加密或竄改檔案的企圖。此外，透過AI驅動的日誌分析技術，資安團隊過去需耗時6小時的調查流程，如今已縮短至約7分鐘，效率提升約50倍。

他指出，這項技術能大幅減輕資安工程師準備與分析日誌等繁重且重複的工作，讓團隊將心力投入更具價值的判斷與分析，例如辨識對手的攻擊手法與威脅趨勢。

「識別出威脅後，我們能夠迅速建立偵測機制，並將其整合到全球的服務中。」羅斯曼強調，AWS能夠將保護單一客戶所累積的經驗，轉化為守護所有客戶的防禦能力，這也是自家優勢之一。

### 結合 AI 速度與自動化推理，部署前驗證修補程式正確性

當防禦端開始運用AI生成修補程式碼，也面臨一項核心挑戰：如何確保生成的修補內容正確可靠，不會引發非預期行為？

針對大型語言模型具有機率性的生成特質，AWS的做法是結合自動化推理，透過形式化的數學邏輯驗證修補程式。

羅斯曼解釋，自動化推理源自電腦科學的形式推理領域，透過數學邏輯證明系統行為符合預期，避免系統遭到顛覆，產生意料之外的結果。

AWS投入自動化推理技術已逾十年，並將其應用於IAM存取分析器、VPC可達性分析器等工具，以形式化方法驗證資源是否可達、存取策略是否意外開放權限，以及不同環境是否妥善隔離。

這類驗證並非依賴啟發式分析或經驗評分，而是由演算法得出可證明的結果。目前，AWS安全服務每天處理超過10億次此類數學查詢。

在實務流程中，當AI協助產生修復方案或程式碼修補程式，系統會在部署前透過自動化推理，驗證修補內容是否正確。將AI的生成速度與數學證明的嚴謹性相結合，正是縮短漏洞發現與完成修復之間時間差的關鍵。

在主動防禦與漏洞管理方面，AWS除了在內部以機器速度部署新型偵測機制，阻止運用代理工具發動攻擊的對手，也將內部累積的漏洞管理經驗轉化為對外服務。例如整合漏洞管理服務AWS Continuum、AWS Security Agent與AWS DevOps Agent，協助企業建立完整的資安生命週期。

羅斯曼分享，AWS 還將核心策略技術開源，包括具備邏輯可驗證特性的授權語言與引擎Cedar，以及可針對時間狀態進行形式化推論的引擎 Dogwood。兩者結合能在執行階段為 AI 代理動態推論並授予最低權限，防止代理行為失控。

### AI Agent 缺乏後果概念，安全防護邊界需置於模型外部

除了漏洞修復流程的轉變，如何設計自主 AI 代理的安全架構，也是企業關注的焦點。

隨著企業應用從對話式AI，擴展至能夠調用工具與執行 API 的自主代理，羅斯曼提醒，資安團隊必須辨識 AI Agent 與人類在安全控制上的本質差異。

他分析，人類執行任務時，通常會考量組織政策、法規要求與潛在後果；但AI Agent本質上是「以達成目標為導向」的演算法，無法真正理解行動可能造成的後果。在缺乏後果意識的情況下，Agent 可能為了完成目標，在運算環境允許的範圍內持續推進，甚至採取人類在相同情境下會有所顧忌的操作。

因此，管理AI Agent風險不能依賴模型自我約束，而應將控制措施設置於模型程式碼之外，以確定性機制約束模型的機率性行為。

首先，建立獨立的身分類別。企業系統應區分「人類直接執行」、「Agent代表人類執行」與「Agent代表系統執行」三類操作，並透過Amazon Bedrock AgentCore等工具，掌握完整的呼叫與授權脈絡。

其次，強化基礎設施層級的隔離邊界。單靠容器技術不足以構成完整的安全邊界，防護機制還須延伸至虛擬化與硬體層級。例如，AWS底層運算採用的Nitro系統，以「操作人員零存取」為設計原則，即使AWS人員也無法存取客戶資料，從模型無法觸及的底層架構落實安全防護。

第三，在代理的控制範圍之外建立確定性防護機制。Amazon Bedrock透過身分識別、工作負載隔離與最小權限控管，避免不同代理之間發生上下文洩漏，並限制代理可存取的資源與操作範圍。

在嚴謹的安全架構下，AI Agent也能大幅加快開發進程。

羅斯曼分享，AWS重建Amazon Bedrock推論引擎Mantle時，若採傳統開發模式，預估需由40名工程師耗時一年完成；在導入AI Agent輔助開發並維持相同安全標準後，最終僅由6名工程師花費76天，便完成Mantle的重建與正式部署，展現兼顧安全與開發速度的可能性。

### 金融業強化合規治理，電信業加速AI應用落地

這套結合基礎設施隔離、自動化防禦與合規控管的架構，已經在台灣市場落地。

啟用滿一週年的AWS亞太（台北）區域採多個可用區域（Availability Zones）架構，不僅能降低服務延遲，也能支援資料主權與合規需求，協助金融等高度受監管產業在符合法規與風險控管要求的前提下，加速部署雲端與AI應用。

羅斯曼以國泰金控為例，其與 AWS 專業服務團隊（AWS Professional Services）合作，運用 AWS Control Tower 建立支援多帳戶環境的雲端資料平台。

國泰金控透過集中式團隊統籌管理，結合 Amazon VPC 建立安全網路連線、藉由 AWS Direct Connect 專線強化資料傳輸隱私，並導入 AWS Security Hub 監控資安態勢，與主管機關合作建立符合金融法規要求的持續合規架構。

在電信領域，中華電信也已將生成式AI解決方案導入實際生產環境，並持續探索如何強化應用安全、降低模型產生幻覺的風險，以及培訓內部團隊安全使用生成式AI工具。

羅斯曼指出，這些案例展現雲端共同責任模型如何在實際環境中運作。AWS負責「雲端本身的安全性」，涵蓋底層硬體、實體資料中心、網路與虛擬化架構，並取得超過143項安全標準與合規認證；客戶則負責「雲端內部的安全性」，依據自身業務需求與風險輪廓，保有對資料的完整控制權，並設定相應的存取政策。

### 建立持久安全優勢，兼顧創新速度與數位信任

羅斯曼總結，面對攻擊自動化趨勢，企業與資安領導者若要在AI時代建立長期優勢，必須同步推動技術與營運轉型，讓安全防禦與漏洞修復跟上機器速度。

他指出，企業評估關鍵工作負載的雲端安全時，可聚焦五大核心面向：從產品設計之初便融入安全思維的文化、借助雲端規模掌握廣泛威脅的防禦規模、運用自動化推理驗證系統正確性的數學證明、以機器速度因應新型威脅的修復速度，以及透過底層隔離架構與全球合規認證建立的數位信任。

針對各地市場的法規與合規需求，羅斯曼補充，AWS配置熟悉區域情勢的安全保證專家，並由當地或鄰近地區的專業服務團隊、解決方案架構師與支援團隊，協助客戶因應在地法規與產業特性，做出合適的架構決策。

當漏洞利用窗口從數週縮短至數小時，資安防禦也必須重新思考自動化能力與系統邊界。企業唯有結合情境脈絡、自動化修復與外部邏輯驗證，才能在加速AI創新的同時，建立兼具韌性與可信度的資安防線。
