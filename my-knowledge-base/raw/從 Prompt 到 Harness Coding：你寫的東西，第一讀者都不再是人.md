**TL;DR**  
AI Coding 的下一代不叫「更強的 Prompt」，叫 Harness Coding——為 AI 設計整個運作環境。但這只是更大趨勢的一角：你寫的 prompt、文件、介面、API，第一讀者都正在變成 AI。

**這篇文章適合：**

- 已經在用 Claude Code / Cursor，開始感覺單純寫 prompt 不夠用的 Vibe Coder
- 聽過 Prompt Engineering、Context Engineering，好奇第三代到底是什麼的開發者
- 在做獨立產品或內容創作，想讓 AI 真的幫你跑整條工作流的 indie hacker
- 關注 AI 產業趨勢，想搞懂為 AI 而設計這件事會怎麼影響未來的人

你有沒有發現，最近跟 Claude Code 一起寫 code，感覺越來越不像在寫 code？

## 1\. 你寫的不是 code，是一份越來越厚的員工手冊

你有沒有發現，最近跟 Claude Code 一起寫 code，感覺越來越不像在「寫 code」？

比較像你剛進公司當主管，手上有三四個新進員工——你花的時間不是自己敲鍵盤，而是在想：這個人能碰什麼、不能碰什麼、做錯了要怎麼自己發現、做完要怎麼回報給你。

而且最妙的是：每當員工犯一次錯，你就把那個錯寫進 SOP。下一個來的新員工，這個錯就不會再犯。你的團隊會自己越帶越順。

如果你也有這種感覺，那你已經一隻腳踩進一個新的東西裡，它有一個不怎麼好聽的名字： **Harness Coding** 。

接下來我要帶你看兩件事。一件是 Harness Coding 這個名字到底在講什麼。另一件更大——它只是冰山一角，真正在發生的轉向比它自己還大。

從第一代講起。

## 2\. Prompt → Context → Harness：AI Coding 的三代演進

三代一句話看完：

| 時期 | 名字 | 你在學什麼 |
| --- | --- | --- |
| 2022–2023 | Prompt Engineering | 學會「問」 |
| 2024–2025 | Context Engineering | 學會「餵」 |
| 2026 ~ | Harness Coding | 學會「設計環境」 |

### 2-1. 第一代：Prompt Engineering（2022–2023）——學會「問」

我記得 ChatGPT 剛出來的那陣子，所有人都在背 prompt 模板。

「你是一個資深的 XX 專家，請你用 YY 風格幫我 ZZ。」

我的瀏覽器收藏夾裡，那時候全是「100 個最強 prompt」「ChatGPT 咒語大全」這類東西。大家相信的是：AI 不是不夠聰明，是你沒跟它講清楚。只要 prompt 寫得夠精緻，AI 就能給你想要的答案。

這個階段的核心命題是： **怎麼跟 AI 說話，AI 才聽得懂你。**

### 2-2. 第二代：Context Engineering（2024–2025）——學會「餵」

然後 Cursor 來了、Claude Code 來了。大家發現光會寫 prompt 不夠了。

因為越來越多任務不是「幫我寫一段 code」這種一次性問題——而是「幫我改這個專案的這個 bug」。AI 不是不夠聰明，是 **它不知道你的情況** 。

於是大家開始寫 CLAUDE.md、`.cursorrules` （AI 的規則檔）、把檔案拖進 context、把整個專案餵給 AI。你花的時間從「想怎麼問」變成「想要餵它什麼」。Claude 後來把上下文視窗開到 [百萬 token 規模](https://brickverse.com.tw/blog/claude-200) ，更讓「整份合約、整個 repo 一次塞進去問」變成日常操作——這個階段的工程師，比起寫程式更像在管理一個越來越大的記憶體。

這個階段的核心命題是： **AI 不是不夠聰明，是不夠知道你的情況。**

這就是 [Karpathy 說的 Agentic Engineering](https://brickverse.com.tw/blog/vibe-coding-to-agentic-engineering) 開始成形的階段。工程師的工作重心，從「寫 code」慢慢滑向「決定 AI 眼前放什麼」。

### 2-3. 第三代：Harness Coding（2026 ~）——學會「設計環境」

然後你會發現：光把 context 餵飽還是不夠。

因為 AI 能跑的任務變長了。從一問一答的幾十秒任務，變成要跑好幾小時的長任務。當任務變長，光有好 prompt、好 context 就不夠——AI 跑到一半會偏掉、會忘記自己在幹嘛、會跑進你不希望它去的地方、會把 feedback 搞丟。

你需要的，不是更好的 prompt，不是更完整的 context，而是 **一整個讓 AI 能自己跑、自己修、自己回報的環境** 。

這就是 Harness Coding。

這三代不是彼此取代——它們是疊加。你還是要會寫 prompt，還是要會餵 context，但上面多了一層： **設計 AI 運作的整個賽道** 。

而且如果你仔細看，三代之間有一個共同的底層轉向在悄悄發生—— **設計的對象，從人類變成了 AI** 。從「怎麼跟 AI 說話」、到「怎麼組織它的 context」、到「怎麼設計它運作的整個環境」——你的讀者一直都是 AI，只是你還沒把它當一回事。

**差別在哪裡？** 不是 AI 更聰明了，是你管它的方式變了。從「教它聽懂你」，到「幫它搭好舞台」。而現在——到了「整個劇場都是為它蓋的」這一步。

## 3\. Harness 到底是什麼？就是一間「讓新員工能自己跑完事情」的辦公室

> **Harness Coding 是一種為 AI agent 設計整體運作環境的工程實踐** ，核心包含四件事：它能用什麼工具（Tools）、它不能越過哪條線（Guardrails）、它做錯了怎麼自己發現（Feedback Loops）、你從外面怎麼看它在幹嘛（Observability）。重點不是讓 AI 更聰明，而是讓一個聰明的 AI 能實際把長任務跑完。

### 3-1. Harness 不是 AI 本身，是 AI 工作的「整個辦公室」

「Harness」中文翻譯過來叫「馬具」，聽起來一頭霧水。我沿用前面那個比喻會好懂很多：

**如果 AI 是你剛招進來的新員工，Harness 就是他上工那天，辦公室裡已經備好的一切——權限、工具、SOP、回報流程、主管信箱。**

你不是在改造這個員工。你是在佈置他工作的環境。

員工再聰明，沒有帳號登不進系統；沒有 SOP 不知道哪些事不能碰；沒有驗收流程，做錯了也沒人跟他說；沒有回報管道，你根本不知道他到了下午三點卡在哪裡。

Harness Coding 就是在設計這整間辦公室。你不是在「讓 AI 更聰明」，你是在「設計一個可以讓一個聰明的新員工，實際把事情跑完的工作環境」。

### 3-2. 四個白話元件

Harness 有四個核心元件。我用最白話的方式講一次，每一個都對照回「新員工上工第一天」的情境：

**Tools：他能用哪些系統帳號**

AI 可以動的東西——讀檔、改檔、跑 script、查資料庫、打 API。類比：新員工報到那天給他開的那一疊帳號——Git、資料庫、內部後台、CI。他手上有哪些鑰匙，就決定他能做多少事。

**Guardrails：哪些事情他絕對不能碰**

禁止刪 `.env` （存密碼的檔案）、禁止碰 production、禁止繞過權限檢查、禁止直接敲某些 API。類比：員工手冊裡那幾條用紅字寫的「嚴禁」——不是為了綁手綁腳，是為了讓他放心把其他事做完，不用每一步都回頭問你「這樣可以嗎」。 [Claude Code 的 Auto Mode](https://brickverse.com.tw/blog/claude-code-auto-mode-explained) 就是一種 Guardrail 的設計——它不是限制 AI 能做什麼，而是告訴它「哪些事情可以放手做，哪些事情要先停下來問」。

**Feedback Loops：他做錯了怎麼自己發現、怎麼自己修**

測試有沒有跑過？build（編譯）有沒有失敗？畫面長得對不對？類比：新員工每交一次東西，都有一套驗收流程——不對就自己退回去改，不用你一條一條盯。沒有這個迴圈，AI 會一直拿頭撞同一面牆。 [替 AI 加上「眼睛」的概念](https://brickverse.com.tw/blog/cdp-eyes-ai-vibe-coding) 就是這塊——讓 AI 自己看到自己寫的東西跑起來長什麼樣。

**Observability：你從外面怎麼看他現在在幹嘛**

log、訊息、進度回報、錯誤通知。類比：主管信箱、每日回報、群組裡的進度訊息——你隨時能叫停、能問狀況、能給下一步的指令。沒有這個，你根本不敢放手讓一個新員工自己跑 3 小時。

把這四件事合起來看，就是一份「新員工入職包」：

| 元件 | 對應到新員工 | 沒有會怎樣 |
| --- | --- | --- |
| Tools | 系統帳號、內部工具 | 有手沒鑰匙，寸步難行 |
| Guardrails | 員工手冊裡的紅線 | 隨時可能搞砸正式環境 |
| Feedback Loops | 驗收流程、自檢清單 | 錯了也不知道，一路錯到底 |
| Observability | 主管信箱、每日回報 | 你不敢放他單獨作業 |

**Harness 不是在改造這個員工，是在佈置他上工的整間辦公室。** 而這門學問，最近有一家公司開始認真教了——Anthropic。

## 4\. Anthropic 自己在教大家怎麼設計 Harness

### 4-1. 當 AI 公司自己開始寫「怎麼用好 AI」

Anthropic 官方的 engineering blog 前陣子發了一篇文章，叫 Effective harnesses for long-running agents。

這不是隨便一家公司在蹭新名詞。這是 **造 AI 的公司自己在教大家，怎麼設計 AI 運行的環境** 。

想像一下：福特、豐田寫一本書叫《怎麼蓋一條好賽道》。他們不是在教你怎麼開車，是在教你怎麼鋪路。這件事本身就是個奇怪的訊號——車廠不該關心賽道的事。除非他們發現， **如果賽道蓋不好，再好的車也跑不完全程** 。

Anthropic 就是那家開始關心賽道的車廠。

### 4-2. Anthropic 內部的日常長這樣

Anthropic 自己說的話，比我怎麼寫都有力。他們承認： **公司裡大部分的 code，現在已經是 Claude Code 寫的了** 。

工程師的日常不再是敲鍵盤寫 function。工程師的日常變成了：

- 設計架構（決定這個系統長什麼樣）
- 編排 agent（決定哪些事情交給哪個 AI 跑）
- 審 PR（看 AI 寫出來的 code 對不對）
- 做判斷（當 AI 卡住的時候告訴它下一步往哪走）

幾個具體數字：

- Inference 團隊用 Claude Code 生成單元測試—— **研發時間減少 80%**
- 產品團隊在 auto-accept 模式下，讓 Claude Code **自主寫出 70% 的 Vim mode 程式碼** （Vim mode 是 VS Code 裡一個給資深工程師用的操作模式）
- 非技術的財務團隊，直接用自然語言產 SQL 查詢和 Excel 報表

這些數字漂不漂亮不是重點。重點是： **這不是 demo，不是投影片，不是預測** 。這是一家全球頂尖的 AI 公司，它的日常工作就是這樣。工程師設計環境，AI 跑執行。這就是 Harness Coding 在 production 級的樣子。

而且不只有 Anthropic。 [Cursor 3 的整個改版方向](https://brickverse.com.tw/blog/cursor-3-agent-first) 是同一件事——從「寫程式」變成「管 agent」。所有做 AI 開發工具的公司，都在往同一個方向走。

**他們不是在預言未來，他們就在那個未來裡。**

## 5\. 真正的大趨勢比 Harness 還大——一切都在變成「為 AI 而設計」

講到這裡，我本來要收尾了。但寫著寫著，我發現 Harness Coding 只是一個更大故事的開頭。

這個更大的故事是—— **我們正在設計的東西，第一使用者都變成了 AI** 。Harness Coding 只是第一個赤裸地承認這件事的領域。其他所有設計工作——寫 prompt、寫文件、做 API、做介面——正在悄悄經歷同一個轉向。

只是它們還沒承認而已。

我用四個層次把這件事拆給你看，從最熟悉的走到最反直覺的。

### 5-1. 層次一：你寫的 prompt，第一讀者是 AI

這件事最明顯，但也最容易被忽略。

你寫 prompt 的時候，根本不會去想「這段文字以後人類要看」。你在想的是——「這樣講 AI 會不會懂」「這個詞會不會讓它誤會」「我要不要加個範例」。

這是一種 **全新的寫作** 。讀者不是人，是模型。你判斷「寫得好不好」的標準，不是文筆、不是節奏、不是情感——是 AI 的反應。

我們做這件事做了三年，只是從來沒把它當成一回事。但它其實已經是「為 AI 而設計」最純粹的範例。

### 5-2. 層次二：你寫的文件，第一讀者也變成了 AI

這一層我最有感。

過去我寫 README、寫專案文件，是寫給同事看、寫給半年後回頭找東西的自己看。文筆要好、例子要多、節奏要順——讀者是人，所以你要做故事感、做比喻、做情緒節奏。

但現在我寫的是 CLAUDE.md。讀者是 AI。

這兩種寫作完全不同：

|  | 寫給人看的文件 | 寫給 AI 看的文件 |
| --- | --- | --- |
| 優化方向 | 故事感、比喻、情緒節奏 | 明確、結構化、不留歧義 |
| 句型 | 自然語言 | 規則清單 + 條件判斷 |
| 容錯 | 讀者會自己腦補 | AI 會照字面執行 |
| 目標 | 讀完能記住 | 讀完能執行 |

我一開始很不適應。寫「嚴禁虛構假名」「嚴禁直接呼叫後端 API」「嚴禁使用 emoji」這種句子，感覺很冷、很機械，完全不像我平常的寫作風格。

但有一天我發現： **AI 真的會照做** 。那種「文件真的被讀了」的感覺，比寫給人看的 README 強太多了。寫給人看的 README 很多時候是自欺欺人——你知道同事根本不會讀。但寫給 AI 的 CLAUDE.md 不一樣，你寫了什麼，AI 就會照著做什麼。

這個議題我之前在 [當文章都是 AI 讀的時候，那還要寫文章做什麼？](https://brickverse.com.tw/blog/why-write-in-ai-era) 寫過——但那時候我還沒意識到，這不只是「文章」的事。 **是所有設計工作的事** 。

### 5-3. 層次三：你設計的 API，第一個打電話來的是 AI

過去設計 API，你在想的是「工程師會怎麼寫呼叫程式」。

你會想：欄位名要清楚、錯誤訊息要友善、文件要寫完整——這樣工程師看了就知道怎麼呼叫。

現在不一樣了。現在越來越多 API 的「第一個呼叫者」是 AI agent。你要想的變成：

- AI 能不能猜對欄位名字？
- 錯誤訊息講不講得清楚，讓 AI 知道要怎麼改？
- 回傳結構夠不夠一致，讓 AI 不用每次都重新解析？
- 文件夠不夠「機器友善」，讓 AI 讀一次就懂？

**MCP 就是這個趨勢最純粹的例子** 。從名字開始它就承認自己不是給人用的——它叫 **Model Context Protocol** ，不是 User Context Protocol。這是一個從定義上就承認「我是設計給 AI 用的」的協定。

[MCP 的完整介紹](https://brickverse.com.tw/blog/mcp-model-context-protocol-guide) 我之前寫過。但現在回頭看，MCP 真正的革命性不在技術上——是在哲學上。 **它是第一個大方承認「這個協定的使用者是 AI，不是人」的主流協定** 。

其他 API 還在「半人半 AI」的過渡期，MCP 已經走到對岸了。

### 5-4. 層次四：你做的「使用者介面」，正在變成 AI 代替使用者去操作的東西

想像你在做一個訂票網站。按鈕、表單、驗證訊息，你都很用心設計——顏色漂亮、動畫流暢、錯誤訊息友善。

然後你注意到一件事： **越來越多使用者訂票的方式，是叫 Claude 幫他們訂** 。Claude 用 Computer Use 或 Browser Automation 去點那些按鈕——讀你的 DOM（網頁結構）、點你的按鈕、填你的表單、解析你的錯誤訊息。

問題來了：

- 你設計按鈕的時候，要不要考慮 AI 讀不讀得懂你的 aria-label（無障礙標籤）？
- 你的網頁結構對 AI 友善嗎？還是塞了十層 div 讓 AI 根本不知道哪個是真的按鈕？
- 你的錯誤訊息是給人看的「哎呀，出錯了」，還是給 AI 能解析的「FIELD\_MISSING: email」？
- 你的動畫效果會不會讓 Computer Use 錯過點擊時機？

**第一個要能讀懂你介面的，可能不再是人。**

另一個例子： **Dashboard** 。你花了一週做了超漂亮的圖表，漸層色、動效、tooltip 都做滿。但實際的使用情境變成什麼樣？老闆對他的 AI 助手說：「幫我看上週業績。」AI 打開你的 dashboard，讀資料，產報告給老闆。

老闆從頭到尾沒看過你做的漸層色。

這個情境就是 [AI 怎麼操控網頁](https://brickverse.com.tw/blog/ai-browser-automation-tools-cdp-playwright-guide) 那篇文章在講的那個世界——已經在發生了，而且會越來越普遍。

這不是說 UI 設計師要失業。是說 UI 設計要多一層——「AI 可讀性」這一層。就像網頁從 1995 到 2010 多了 SEO 這層。以前的網頁設計只要給人類看舒服就好；後來多了一個讀者叫「Google 爬蟲」，你得同時服務這兩邊。現在又多了一個讀者叫「AI agent」，而且這個讀者越來越多。

介面還是要給人看——但 **第一個要能讀懂它的，可能不再是人** 。

### 5-5. 連起來看：這是一個比 Harness Coding 還大的故事

把這四個層次連起來看，你會發現一件事——

**Harness Coding 只是這個大趨勢中最赤裸的那一塊。** 它為什麼「最赤裸」？因為它直接承認：「我設計的這個環境，使用者就是 AI，沒有人。」

其他所有領域都還在「半人半 AI」的過渡期——prompt 寫給 AI 看但偶爾有人瞄一眼、文件寫給 AI 看但同事也要能讀、API 給 AI 用但工程師也要能呼叫、介面給 AI 操作但使用者還是會打開看。

但方向都一樣。所有設計工作的讀者構成，都在慢慢從「人為主、機器為輔」變成「AI 為主、人為輔」。

**真正的變化不是 AI Coding，不是 AI 寫 code——是所有「設計」這個動作，都在悄悄換讀者。以前我們設計東西給人用。現在我們設計東西給 AI 用——再讓 AI 服務人。** 中間多了一層翻譯，而這層翻譯，正在變成所有設計工作的新核心。

## 6\. 講個具體的——我自己的課程編輯流水線，就是一個微型 Harness

前面講的都是大公司和大趨勢。講一個我自己做的小東西，對照一下這四個元件。

我最近在做 Brickverse Academy 的課程平台（CourseHub），整條工作流就是一個活生生的 harness 實驗場。

我不再自己動手寫每一章的內容。我的角色變得比較像 **一間編輯部的主編** ——底下有幾個 AI 助理，最核心的那一個叫 course-edit，是課程編輯。我給它大綱，它寫初稿；需要調整版面的時候我再叫 layout-edit 進來處理排版，layout-advisor 負責在旁邊挑剔節奏和視覺層次。

每個助理就是一個 AI Skill。我呼叫它的時候，它就上線工作；沒呼叫，它就不存在。

對照 Harness 的四個元件，長這樣：

**Tools：我能差遣的助理編輯**

course-edit 負責寫內容，layout-edit 負責排版，layout-advisor 負責挑毛病。我不用教它們工具怎麼用，我只要決定—— **什麼時候叫哪一個出來** 。

**Guardrails：寫在 CLAUDE.md 裡的 SOP**

這才是整套系統真正開始變強的地方。

我不是一次就把規矩想清楚的。course-edit 剛上工的前幾週，什麼坑都踩過——章節檔裡自己手刻 Excel 上傳、滾動條套娃三層、心血來潮塞幾個 emoji 當裝飾。

每犯一次錯，我就把那條規矩寫進 CourseHub 的 CLAUDE.md：

- 任何 Excel 上傳下載，不准自己手刻，一律走共用元件
- 滾動容器只能有一層，禁止套娃
- 圖示只能用 Lucide，嚴禁 emoji

這些規則現在變成「新助理第一天上工就會看到的員工手冊」。 **它們再也不會犯同樣的錯了** 。這不是因為 AI 變聰明，是因為我替它寫了一份越來越完整的 SOP。

**Feedback Loops：AI 給 AI 回饋**

layout-advisor 看到 layout-edit 的稿子會給建議——哪裡節奏不對、哪裡視覺層次壞了。這兩個角色會自己來回幾次，通常我只在最後一輪才進去看。

不是我給 AI 回饋，是 **AI 給 AI 回饋** ，我只在它們自己走不下去的時候介入。

**Observability：打開瀏覽器就看得到**

所有章節都能在本地直接預覽；每個 Skill 跑完會給我一份報告，我不用去猜它剛剛做了什麼。

前期不便宜。把 CLAUDE.md 寫到現在這個樣子，坑都是我一個一個踩出來的。但搭好以後的感覺很奇怪——不是「我有一個更快的打字助手」，比較像 **我真的有一個會自己學乖的團隊** 。

而且這個團隊不只用來做課程。你現在讀的這篇文章，背後跑著同一套邏輯。

想了解 Skill 機制本身怎麼運作，可以看 [三大工具的 Skill 機制怎麼選](https://brickverse.com.tw/blog/agent-skill-comparison) ；想從最基礎的規矩開始寫，看 [Claude Code Hooks 教學](https://brickverse.com.tw/blog/claude-code-hooks-guide) 。

**你不用是 Anthropic 才能做 Harness。你只需要一件事——每次 AI 犯錯，不要只是當下糾正它，而是把這個錯寫進你的 SOP。你的團隊就會自己越帶越順。**

## 7\. 結尾：你現在做的這個東西，第一讀者是誰？

回扣開頭的「訓練新員工」——我到這裡才敢把這個比喻說完整。

你在做的事，不是在訓練 **一個** 員工。你是在寫 **一份越來越厚的員工手冊** ——一份未來所有新進 AI 都會第一時間讀到的東西。

- 員工犯錯，你寫進 SOP
- 下一個員工看到 SOP，不會犯同樣的錯
- 你寫的 SOP 是寫給 AI 看的，不是寫給人看的

這件事不只發生在 AI Coding 裡。它正在悄悄發生在所有設計工作裡——prompt、文件、API、介面。設計的第一讀者，正在從人換成 AI。

> 你現在桌上的這個 prompt、這份文件、這個介面、這個 API——
> 
> **它第一個讀者是誰？**

如果你開始常常問這個問題，你就已經在做 Harness Coding 了。不管你自己意不意識到，不管你做的是不是 AI 產品。

不用急著學新東西。先從問這個問題開始。然後——下次你的 AI 同事犯錯， **把它寫進你的 SOP** 。
