## 為什麼選原生掛載？拆解 ASGI 直連與傳統轉換器的差異

市面上其實早就有不少「讀取 OpenAPI 規格書再自動生成 MCP 伺服器」的通用工具，為什麼許多工程師最後還是改用 `fastapi_mcp` 這套專門為 FastAPI 設計的原生套件？

關鍵差異在於通訊層級與身份驗證的整合深度。

一般的 OpenAPI 轉換器運作方式，是在你的 API 伺服器旁邊另外起一個獨立的轉換行程。

當 AI 代理呼叫工具時，請求會先送到轉換器，轉換器再透過網路發送一次 HTTP 請求去打你原本的 API 伺服器，中間平白多了一層網路往返與序列化損耗。

這套原生套件則採用截然不同的設計哲學，它直接建立在 Python 的非同步伺服器介面 ASGI 之上。

所謂 ASGI，是 Python 現代網頁框架用來處理非同步網路請求的底層標準介面，也是 FastAPI 高效能的核心基礎。

因為直接透過 ASGI 在同一個記憶體行程內溝通，工具呼叫不需要繞回外部網路發送 HTTP 請求，不僅延遲大幅降低，也不需要額外維護兩套容器或伺服器連接埠。

這種同行程直連架構在除錯時也特別省事，所有呼叫紀錄與例外錯誤都會直接出現在你原本的 FastAPI 伺服器紀錄裡，不用在兩個服務之間來回對照時間戳記。

更重要的一點，在於它完整保留了 FastAPI 開發者最依賴的三大既有資產。

第一是請求與回應的模型架構。你在程式碼裡用 Pydantic 寫好的欄位型別、數值範圍與必填檢核，會自動對應成為 AI 模型看得懂的工具參數規格。

第二是 Swagger 介面文件。你原本寫在端點函式上的說明文字與註解，都會原封不動傳遞給 AI 代理作為工具用途描述，寫得越清楚，代理選錯工具的機率就越低。

第三則是原生的依賴注入驗證機制。這套套件直接支援 FastAPI 既有的 `Depends` 權限檢查函式，代表你不用為了 AI 代理另外寫一套 API 金鑰驗證系統。

### fastapi\_mcp 原生掛載 vs 通用 OpenAPI 轉換器

| 比較面向 | fastapi\_mcp 原生模式 | 通用 OpenAPI 轉換器 |
| --- | --- | --- |
| 底層通訊方式 | 透過 ASGI 記憶體直連，免去內部 HTTP 呼叫 | 獨立行程運作，需透過網路轉發 HTTP 請求 |
| 權限與驗證整合 | 原生支援 FastAPI `Depends` 依賴注入驗證 | 需額外設定代理層標頭轉發與憑證映射 |
| 部署與維運架構 | 可直接掛載於同一支 FastAPI 服務，免開第二個服務 | 必須額外部署並監控第二個轉接伺服器 |
| 規格與文件保留 | 自動同步 Pydantic 模型與 Swagger 端點說明 | 依賴靜態 JSON 檔案匯出，規格改動易不同步 |
| 適用後端框架 | 專屬於 Python FastAPI 專案 | 不限語言，任何能產出 OpenAPI 規格的服務 |

此外，雖然預設推薦與原本的 API 同機掛載，但若你的團隊基於流量隔離或資安考量，希望把對外開放的 MCP 端點獨立成另一個微服務，官方文件也同樣支援分離部署模式。

## 零配置實戰教學：三步驟把 API 變成 MCP 工具

官方建議的運行環境為 Python 3.10 以上版本，並特別推薦使用 Python 3.12 搭配現代套件管理工具 `uv` 來獲得最佳相容性。

### 第一步：安裝套件

在你的 FastAPI 專案目錄下，開啟終端機並使用 `uv` 安裝 `fastapi_mcp` 套件。

```bash
uv add fastapi-mcp
```

如果你的專案目前還是使用傳統的 `pip` 管理虛擬環境，也可以直接執行以下指令完成安裝。

```bash
pip install fastapi-mcp
```

### 第二步：掛載伺服器到現有應用程式

打開你專案中定義 `app = FastAPI()` 的主程式檔案，只需要匯入 `FastApiMCP` 並加上兩行初始化與掛載程式碼即可。

```python
from fastapi import FastAPI
from fastapi_mcp import FastApiMCP

app = FastAPI()

# 在這裡保留你原本的所有 @app.get 與 @app.post 路由定義

mcp = FastApiMCP(app)

# 將 MCP 伺服器直接掛載到現有的 FastAPI 應用程式上
mcp.mount()
```

執行啟動指令後，你的標準工具服務就會自動出現在應用程式的 `/mcp` 路徑下，例如本機測試網址為 `http://localhost:8000/mcp`，線上正式環境則對應 `https://app.base.url/mcp`。

### 第三步：設定安全權限與客戶端連線

為了避免所有路由一瞬間裸奔暴露給外部代理，建議在定義端點時就養成搭配驗證依賴的習慣，確保請求必須帶著合法授權才能通過。

在開發者端，當伺服器啟動並開放 `/mcp` 端點之後，你就可以在支援遠端或 SSE 傳輸的編輯器或代理工具中填入這個網址進行連線。

連線成功後，AI 編輯器會自動向伺服器請求工具清單，此時你在 FastAPI 裡寫好的每個業務路由、參數名稱與 Swagger 註解，都會立刻出現在代理的可用工具列表裡。

你可以直接在對話框測試用自然語言查詢訂單狀態或建立測試資料，這時後端會直接透過 ASGI 觸發對應函式並把結構化結果送回畫面。

如果團隊想在正式環境進一步控管代理的寫入權限，建議在測試階段先將查詢類端點與寫入類端點分開驗證。

透過檢查工具呼叫日誌，工程師可以清楚觀察 AI 模型每次傳入的參數格式是否符合預期，確認穩定後再逐步開放建立或更新類的操作端點。

如果在公司環境需要把服務部署在獨立容器或後方反向代理伺服器之後，也記得確認代理伺服器不會阻斷長連線串流回應，才能確保工具清單載入與呼叫過程一路順暢。

## 實戰調優技巧：怎麼寫讓 AI 代理更聽話的 FastAPI 路由？

工具成功掛上去只是第一步，很多工程師在實測後會發現，明明端點都出現在清單裡了，為什麼 AI 模型還是常常傳錯參數，或是選錯該呼叫的端點？

這背後通常不是協定的問題，而是原本寫給人類工程師或前端看的文件，對語言模型來說不夠精確。

### 優化端點說明文字與函式命名

語言模型在決定要呼叫哪個工具時，主要依賴工具名稱與說明文字來做語意判斷。

在你的 FastAPI 路由裝飾器中，務必寫清楚簡潔的 `summary` 與詳細的 `description`，明確告知模型什麼時候該呼叫這個端點，以及回傳結果代表什麼意義。

如果你的專案同時有給人類看的文件與給模型用的端點，清晰的 `operation_id` 命名能大幅減少模型在幾十個相似路由之間猶豫不決的情況。

舉例來說，把端點函式命名為 `search_customer_orders_by_email`，遠比命名為 `get_data_v2` 更容易讓模型一次選對工具。

### 善用 Pydantic 欄位描述約束參數格式

與其期待模型自己猜測日期要傳斜線還是減號、金額單位是元還是分，不如直接寫進 Pydantic 請求模型的 `Field` 描述裡。

因為 `fastapi_mcp` 會完整保留所有模型結構，當你在欄位上清楚標註範例值、列舉選項與字數限制時，代理在組裝工具參數時的格式正確率會立刻大幅提升。

如果你有某幾個特定欄位屬於系統內部預設值、不需要模型每次填寫，記得給予明確的預設值設定，這樣模型在生成工具呼叫參數時就不會因為少填欄位而報錯。

### 注意掛載順序避免路由遺漏

在撰寫主程式時，請確保 `FastApiMCP` 的初始化與 `mount` 呼叫放在所有業務路由註冊完成之後再執行。

如果在掛載完成之後才透過 `app.include_router` 動態加入新的路由，剛啟動的工具清單可能無法即時掃描到後方才新增的端點。

## 安全邊界、權限控管與常見踩坑點

「零配置一行掛載」聽起來非常迷人，但在企業級後端服務裡，這同時也是最容易發生資安事故的環節。

當你把整支 `FastAPI` 實例直接交給轉接層時，意味著原本隱藏在管理後台、或只給內部微服務呼叫的路由，都有可能被轉換成 AI 工具端點。

### 必須嚴守的三大安全防線

第一道防線是高風險端點隔離。包含刪除資料表、批量重設使用者密碼、退款與匯出全庫報表等破壞性操作，絕對不能未經篩選就直接開放給 AI 代理自主呼叫。

第二道防線是強制使用 `Depends` 身份驗證。千萬不要在測試階段偷懶拿掉驗證機制，上線後才想起來補，應該從第一天就透過既有權限系統確保代理只能存取該使用者權限範圍內的資料。

第三道防線則是環境隔離與分離部署。對於資安等級較高的金融或醫療系統，不建議把 AI 工具端點直接混在對外營業的主伺服器上，應依照官方提供的分離部署架構，僅將經過白名單審核的唯讀端點獨立掛載出來。

### 實務上最常遇到的兩個坑

第一個常見問題是大型專案的工具數量爆炸。如果一支單體式 FastAPI 專案裡面有上百個路由，全部轉換成 MCP 工具後會瞬間塞滿模型的上下文視窗，不僅每次對話都要白白消耗巨額額度，模型的選用準確率也會跟著暴跌。

遇到這種大型專案時，應該只針對 AI 真正需要的十幾個核心介面進行曝露，或是改用分離部署模式只掛載特定子應用。

第二個常見問題則是執行環境的 Python 版本相容性。雖然官方標註支援 Python 3.10 以上版本，但若專案內混用了過舊的非同步依賴套件，建議優先升級至官方推薦的 Python 3.12 並配合 `uv` 建立乾淨的虛擬環境，能省下大量除錯時間。

## 常見問題

### 這篇 fastapi\_mcp 教學介紹的工具，真的只需要一行程式碼嗎？

核心掛載步驟確實只需建立 `FastApiMCP` 實例並呼叫掛載方法即可啟動。但在正式導入企業專案時，我們強烈建議不要只用預設全開設定，還是要配合路由篩選與權限驗證，才能確保系統安全。

### 我的 FastAPI 端點原本就有 JWT 或 OAuth2 驗證，掛載後還能用嗎？

可以。`fastapi_mcp` 的最大優勢就是專為 FastAPI 原生設計，因此你在路由上透過 `Depends` 實作的 JWT 驗證、API 金鑰檢查或角色權限控管，都會在代理呼叫工具時正常運作並進行攔截。

### 為什麼使用 ASGI 傳輸會比一般 OpenAPI 轉接工具更好？

一般轉接工具需要透過外部網路再打一次你自己的 API，除了增加延遲與網路錯誤點之外，也得額外管理兩套伺服器行程。ASGI 直連則是在同一個 Python 非同步記憶體行程中直接調用路由邏輯，效能更好且部署更簡單。

### 如果我的 FastAPI 專案已經有上百個 API，全部掛上去會發生什麼事？

如果把上百個端點全數暴露給 AI 代理，每次對話開始時光載入所有工具的 Schema 說明就會消耗掉數萬 Tokens，還會讓模型在挑選工具時容易混淆。實務上應該只挑出高頻且安全的少數端點對外暴露，或拆分成專用的輕量級微服務。
