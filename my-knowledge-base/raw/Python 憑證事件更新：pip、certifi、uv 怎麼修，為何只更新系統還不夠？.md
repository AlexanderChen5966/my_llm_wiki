Python 憑證事件提醒我們，電腦更新完成後，下載套件的連線仍可能信任有問題的憑證。原因是同一台機器裡，可能存在不只一份信任清單。

pip 會攜帶自己的憑證資料，所以只修作業系統，未必能把每個開發環境一起處理完。

Python 官方在十月二十日發布 eMudhra 中間憑證事件說明，列出 pip、certifi 與 uv 等工具的更新版本，也要求重新建置容器。

這件事會影響 AI 團隊常用的套件下載與資料連線，但不能直接解讀成 Python 或 PyPI 伺服器已被入侵。

我認為處理重點是先找出實際執行工作的環境，再按官方方法逐一更新。只確認自己終端機裡的一個版本，容易漏掉排程與部署。

要知道哪些地方需要處理，先理解憑證在下載流程中扮演什麼角色。

## Python 憑證事件壞在哪裡，為什麼會影響下載套件？

受影響的是驗證網站身份的信任鏈，攻擊者仍需要能介入連線，才可能利用這個弱點冒充網站。

當程式連到一個使用加密連線的網站，除了加密資料，也要確認對方確實是目標服務。憑證就是這個身份驗證的一部分，背後由憑證機構建立信任關係。

依 [certifi 官方安全公告](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2?ref=aiposthub.com) ，八份 eMudhra 中間憑證的私鑰遭到破壞，並已被撤銷。私鑰是用來簽發身份證明的機密資料。

若某個客戶端仍信任相關鏈，拿到私鑰的攻擊者可能製作看似有效的網站憑證。但這還需要攔截或導向受害者的連線，才能讓程式碰到冒充的服務。

這個條件很重要。它說明為什麼需要更新信任清單，也避免把風險誇大成攻擊者能直接從任何地方登入每台 Python 機器。

Python 官方提到，受影響連線可能包括 python.org 和 pypi.org。前者提供 Python 資源，後者是常用套件發布服務，開發流程因此需要重視這段信任。

但列出這些網域，描述的是可能被冒充的目標，沒有證明網站伺服器已被植入惡意程式。下載通道的身份問題，和發布物本身遭入侵，是不同事件。

API 是供程式呼叫服務的介面，AI 工作也常透過這種方式取得資料。

對 AI 開發者而言，套件下載、資料擷取與服務呼叫可能都使用 Python 網路工具。哪些流程受影響，取決於它實際使用的憑證清單與連線方式。

因此，處理時應回到工具和環境盤點。某個瀏覽器已阻擋問題憑證，不能直接推成同一台電腦上的每個命令列工具都已取得相同更新。

### 版本清單和部署紀錄，應該怎麼對在一起？

更新紀錄應能指向一個實際環境，例如哪台主機、哪個專案或哪份映像。因為同名工具可能存在多份，只記「pip 已更新」無法讓接手者重查。

可以把執行檔路徑、版本查詢時間和對應工作保存在同一列。當排程出現錯誤時，維運者就能沿著工作找到環境，知道它是否包含這次修正。

容器則可以保存建置來源、映像識別與部署時間。這些資訊不必寫進一般讀者介面，但應留在團隊的交付紀錄，避免下次回復舊版時把安全修補一起退回。

如果一項工作暫時不能升級，應記錄阻礙和負責人，再依維護者說明處理。把未涵蓋項目明確列出，比把整批標成完成，更能讓團隊安排後續工作。

對長期沒有重新建置的研究專案，也應確認日後重建使用的來源。因為某次手動更新只改了現有環境，安裝腳本若仍固定舊版本，下一位研究者仍可能重建出相同缺口。

這也有助於區分測試與正式環境。測試機的新版本能運作，是部署前的證據，真正上線之後還要確認服務使用的執行檔和映像，兩者才能接起來。

對由供應商代管環境的團隊，可以向供應商取得處理狀態與適用範圍，再確認自己仍管理的部分。供應商更新底層，不代表專案內固定的套件副本也一定被替換。

當紀錄能回答「哪項工作、在哪個環境、何時取得修正」，完成狀態就比較容易被其他人驗證，也能讓後續新公告沿用同一份盤點。

同一台機器有多份信任清單，正是這次更新容易留下缺口的原因。

## 為什麼只更新作業系統，pip 還可能留下風險？

pip 除了系統信任設定，也會載入自己攜帶的 certifi，所以舊版本可能繼續信任受影響憑證。

certifi 是 Python 生態常用的憑證清單套件。程式可以用它判斷哪些機構值得信任，因此它的版本會影響實際連線驗證。

在 [Python 官方討論串](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576?ref=aiposthub.com) 中，核心開發者特別提醒，pip 會在系統清單之外加入它攜帶的 certifi，更新系統層不足以取代更新 pip。

這也表示，安裝一份新的 certifi 不一定就替 pip 換掉內含副本。團隊需要分別確認套件安裝器和應用程式使用的憑證，而非只看到一個版本號就結案。

虛擬環境讓這個問題更常見。虛擬環境是替單一專案保留獨立套件的空間，目的是避免不同專案互相影響，但也因此可能各自保留舊工具。

例如，一台電腦有三個研究專案，每個都有自己的環境。你在其中一個更新 pip，不代表另外兩個也同步更新，排程仍可能繼續使用舊版本。

容器也有類似情況。它把執行環境包成映像，部署時使用的可能是先前建好的那一份，所以主機更新後，映像裡的憑證仍可能維持舊狀態。

官方因此要求重建容器時停用層快取，以便取得最新系統憑證。快取能加快建置，但在這次處理裡，也可能把需要更新的舊層重新用回去。

不同作業系統發行版可能修改套件安裝器，實際行為應查對應維護者公告。團隊不宜只靠套件名稱推斷所有環境都完全相同，也不應自行關閉驗證來省去處理。

比較可行的做法，是列出開發、建置、排程與正式部署各用哪個 Python，再逐項核對。清單完成後，才能正確套用官方建議的版本。

## pip、certifi 與 uv，要更新到哪些版本？

Python 官方列出的建議最低版本，是 pip 26.2.2、certifi 2026.10.19 與 uv 0.13.4，其他相關工具也有各自更新。

這些數字對應不同程式，不能互相替代。pip 是套件安裝器，certifi 提供憑證資料，uv 則是另一套管理 Python 工具與套件的程式。

官方也列出 sigstore 4.5.1、conda 26.9.4 與 pixi 0.82.1。若團隊使用其中一項，應查看它的對應修復，而非只更新最熟悉的 pip。

certifi 的版本尤其需要分清。安全公告曾提到十月十八日版本移除相關根憑證，Python 公告則建議十月十九日版本，以維持不受影響憑證的相容性。

因此，看到某個較早的安全修正版本時，不應只按日期自行猜測。官方推薦版本同時考慮修補和相容性，按最新說明更新較容易減少額外連線問題。

Python 本身也推出更新。 [十月二十一日發布公告](https://blog.python.org/2026/10/python-3151-3149-31317/?ref=aiposthub.com) 列出 Python 3.15.1、3.14.9 與 3.13.17，內含更新後的 pip 和憑證資料。

這有助於之後建立的新環境，但既有虛擬環境仍要處理。官方在新版公告中再度要求，替所有現有虛擬環境更新 pip 和 uv，顯示兩件工作不能混為一談。

若團隊使用舊版 Python，也應先查工具的支援範圍。直接把不相容的新工具塞進舊執行環境，可能讓安裝流程失敗，應按所用版本的維護者方案處理。

盤點表可以記錄環境名稱、執行檔路徑、安裝器版本與部署位置。這樣後續重跑工作時，才知道修的是實際使用的環境，而非另一個同名指令。

版本確認之後，還有一個自然問題：如果舊下載工具本身受影響，要怎麼確保更新檔沒有在途中被替換。

## 如何安全更新，並把修正帶進虛擬環境和容器？

先依官方指定雜湊核對更新檔，再用修好的安裝器更新相關工具，可以讓更新有獨立的內容檢查。

雜湊可以理解為檔案內容的指紋。官方提供預期值，下載後計算結果若不同，就不應把該檔案當成預期更新執行。

Python 官方公告提供帶有 SHA-256 指紋的直接安裝網址，先安裝指定的 pip 檔案。因為內容必須符合指紋，這能替更新檔增加一層確認。

實際執行時應從官方公告取得完整指令，避免從轉貼重新拼接。網址和雜湊只要少一段，驗證方式就可能不同，所以本文把原文連結保留為操作依據。

更新 pip 之後，再用安全版本更新 certifi、uv 或其他相依工具。這個順序讓後續下載先使用已處理的安裝器，較容易知道每一步的信任來源。

macOS 的 python.org 安裝版本也有額外提醒。官方指出，它包含 certifi 憑證清單，並提供指向特定安裝路徑的更新方式，因此不應只在任意終端機執行一次就假設全部涵蓋。

對虛擬環境，應啟用或明確指向該環境的 Python，再查看 pip 位置與版本。指令顯示成功後，仍要確認專案或排程使用的是同一路徑。

對容器，則需要更新建置來源與相依版本，再依官方建議無快取重建。只在正在跑的容器裡手動修補，下一次重新部署可能又回到舊映像。

同樣地，鎖定檔若仍固定舊版，新的建置也可能把它裝回來。鎖定檔是保存確切套件版本的清單，維持可重現性的同時，也需要跟著安全更新調整。

完成重建後，應從新映像內讀取實際版本，並核對部署服務指向哪個映像。建置成功只證明流程跑完，正式工作仍可能在舊環境執行。

本文沒有替讀者執行任何更新，也沒有聲稱已清查個別系統。操作應按自己的環境和官方文件進行，驗收對象則是最後真正執行工作的那一份。

## AI 團隊如何確認已處理完成，而非只更新了一個終端機？

把所有會下載套件或對外連線的工作環境列出，再確認更新後的版本已進入實際執行流程，才能知道修正範圍。

AI 專案常同時有研究者電腦、建置服務、背景排程和正式部署。每一處都可能使用不同 Python，若只看本機，容易漏掉真正持續處理資料的那台機器。

團隊可以按工作而非按人盤點。先列出每天跑的資料擷取、模型任務和報表，再追到它們使用的環境，通常比只詢問每個人是否更新過更清楚。

對每個環境，保留版本查詢結果與時間，並記錄它如何取得憑證清單。這能幫助維運者分清系統套件、獨立安裝與內嵌環境，避免用同一個處理方法覆蓋所有情況。

修正之後也要查看工作是否仍能連到預期服務。因為移除不可信任的憑證可能改變驗證結果，若遇到連線錯誤，應追查鏈和設定，而不是直接關閉驗證。

關閉驗證會讓程式失去確認網站身份的能力，反而破壞這次修補的目的。遇到內部服務或自簽憑證，應由管理者提供正確信任設定，讓例外有明確來源。

若團隊設定更新冷卻期，也要確認安全版本是否仍被延後。冷卻期是避免剛發布套件立刻進入系統的等待政策，遇到明確修補時，需要按團隊程序處理例外。

這次事件還提醒我們，執行環境包含的不只是模型與程式。安裝器、憑證與建置映像都會影響資料如何被取得，應和其他依賴一起列入管理。

後續若官方公告新增版本或修正範圍，應依盤點表追到受影響工作。清楚的清單能讓更新有起點，也讓完成狀態有證據可查。

Python 官方公布的修補方式已經具體，團隊需要做的是讓它覆蓋到真正使用中的環境。修正能否在下一次部署後繼續保留，比某次更新畫面更能說明工作是否完成。

## Python 憑證事件常見問題 FAQ

### Python 憑證事件代表 PyPI 被駭了嗎？

官方說明的是受影響信任鏈可能被利用冒充網站。這和 PyPI 伺服器或套件發布物已被植入，是不同的主張。

### 更新 certifi 就可以不更新 pip 嗎？

不應這樣推論，pip 攜帶自己的 certifi。Python 官方特別要求更新 pip，並處理每個既有虛擬環境。

### 新裝 Python 後，舊專案也會自動修好嗎？

舊環境、容器和鎖定版本仍可能保留原狀。應逐項核對實際執行路徑與部署映像，確認工作使用更新後版本。

## 結語：把修補落到每一個真正執行工作的環境

這次 Python 憑證事件適合由開發和維運一起處理。單一電腦上可能有多份工具與信任清單，先盤點比只重複一條更新指令更有效。

請從官方公告取得最新版本與驗證方式，確認既有環境、建置和部署都已涵蓋。想持續掌握 AI 開發環境與重要技術更新，歡迎免費訂閱 AI 郵報。
