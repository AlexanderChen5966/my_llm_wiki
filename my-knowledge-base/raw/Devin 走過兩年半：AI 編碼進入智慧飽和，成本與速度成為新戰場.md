> 原始影片： [The misaligned incentives behind AI coding agents](https://www.youtube.com/watch?v=bBUotstDLdk)

Russell Kaplan 是 Cognition 總裁。Cognition 在 2024 年 3 月公開 Devin，當時 Devin 在 SWE-bench 的成績約為 13%，已比此前最佳成績高出數倍。Kaplan 早年曾在 Tesla Autopilot 團隊從事深度學習研究，後來創辦電腦視覺公司 Helia；Helia 被 Scale AI 收購後，他也曾在 Scale 帶領機器學習團隊。

兩年多後，編碼代理面對的問題已有所不同。模型能完成的任務快速增加，SWE-bench 之類的既有評測逐漸失去鑑別力，企業也開始追問大量 token 到底換來多少生產力。這場訪談談的正是這幾個轉折：代理如何從可用走到規模化、Cognition 為何另做 Frontier Code，以及模型路由、專用模型與推理晶片如何壓低成本。

## 從原型走到企業遷移

Devin 公開後，團隊又花了幾個月反覆在內部使用並調整工作流程。2024 年 6 月，Devin 成為自家程式碼庫最大的 commit 貢獻者。Kaplan 把這視為第一個重要里程碑，但當時的非同步雲端代理仍無法處理大多數軟體工程工作。

最早跑通的場景之一是大型遷移與重構。企業可以先花時間把提示、設定與輸入脈絡調準，再把同一套流程套到一萬個模組。它比單純搜尋取代多一點判斷力，卻不必具備通用軟體工程能力，因此很早就能產生投資報酬。

2024 年 12 月，Cognition 開放 Devin 自助註冊，並把 Slack 選為主要介面。整支發布影片反覆示範在 Slack 裡標記 Devin，目的是讓代理像隊友一樣接下完整工作，而非只在編輯器裡提供片段建議。隨著模型、代理框架和雲端基礎設施進步，這類非同步委派才逐漸擴大到更多任務。

## 智慧飽和後，開發者改看速度與成本

Kaplan 認為，近來軟體工程裡愈來愈多工作已進入「智慧飽和」。模型能力跨過可用門檻後，再多一點智慧未必會顯著改善結果，開發者反而更在意延遲與費用。

他也限定了這個說法的範圍。金融交易等對抗性任務仍需要最前沿的能力，因為對手也會持續變強。但許多日常軟體需求有明確門檻，例如替行銷網站做一個註冊頁。當多款模型都能完成，選對模型與控制浪費的價值便迅速上升。

「大家想要快速而正確的答案，不想有任何多餘浪費，也不想每次使用編碼代理時，還得先煩惱該選哪個模型。」

Kaplan 用 Tesla 的經驗說明瓶頸如何移動。2017 年，他在 Autopilot 團隊時最缺的是 GPU 算力；現在他和 Tesla 朋友談起自駕研發，瓶頸已變成評測。自駕系統的人工介入事件太少，必須累積龐大行駛量，才找得到系統堆疊中的問題。軟體工程尚未走到那一步，但可能比預期更早遇上相同限制。

## 資安任務需要精確率與召回率分工

訪談以資安漏洞偵測與修復為例，說明單一模型未必在所有指標上都最好。依 Kaplan 的觀察，Fable 類模型的精確率較強，GPT 5.5 與 5.5 Cyber 的召回率較高。Cognition 的做法是先利用 GPT 系列找出較多候選，再用 Fable 系列過濾。

來自 Datadog 等整合系統的大量資料，也是新模型進步較明顯的地方。這些資料雜訊多，還需要多步推理。Kaplan 認為，Fable 在這類真實資料來源上的表現，反映了背後投入的大量強化學習。

## Frontier Code 評估程式碼是否值得合併

Devin 初次公開時，SWE-bench 的 13% 足以拉開差距。如今這項評測已趨近飽和，Cognition 團隊常覺得某款新模型明顯更好，卻找不到既有測試支持這個直覺。

缺少的指標是「可合併性」。既有測試沒有捕捉程式碼風格、後續可修改性，以及其他模組演進時是否容易出錯。Kaplan 說：

「問題不只在於程式碼有沒有通過測試，還在於你是否真的願意合併它。它會改善程式碼庫的品質嗎？」

Cognition 因此與高標準的開源維護者合作，建立 Frontier Code。維護者先提出自己接受一筆變更所需的條件，研究團隊再把這些判斷轉為測試。部分條件可以直接寫成程式斷言。例如某項改動現在使用 A 或 B 模組都能運作，但維護者知道只有 A 才能承受未來演進，測試便可要求代理必須使用 A。這項判斷仍由人提出，再轉成可重複執行的規則。

Kaplan 特別提到，Cognition 每位研究員都親自貢獻、審閱與評估題目，沒有把資料品質工作交給另一批人或模型處理。每道題都像一個完整工程專案，維護者與研究團隊可能投入數百小時。

Frontier Code 的 Diamond 子集在 Fable 5 推出前只有十幾個百分點，之後提高到三十多個百分點。這項評測何時也會飽和，Kaplan自己也沒有把握。

## Blocking 與 non-blocking 的雙層評分

Frontier Code 先檢查 blocking 條件。測試是否通過、維護者指定的硬性條件是否滿足，都採二元判斷；任何一項沒過，這筆變更便不可合併。

通過硬門檻後，再以線性加權方式計算 non-blocking 分數。模型可能改對目標程式碼，卻順手碰了不相關的檔案。這不影響功能正確性，仍會拉低品質分數。模型評審所使用的啟發式條件也可放入這一層。

Cognition 還加入反向驗證。套用正確 patch 後，測試必須通過；不套用 patch 或換成其他 patch 時，測試則應失敗。這能避免測試本來就會通過，卻被誤認為模型成功解題。

Kaplan 判斷評測是否有效的最後依據，仍是它能否對應實際使用感受：新模型在 Frontier Code 得分較高時，團隊在真實任務裡也應感受到改善。目前各模型在這套評測上的表現仍不理想，表示它尚有鑑別力。

## Devin Fusion：前沿模型帶著 sidekick 並行

企業讓每位工程師任意啟動大量代理後，個人 token 支出可能逼近、甚至超過薪資成本。Cognition 因而在 Devin Fusion 同時使用路由與並行執行。

其核心是一個 sidekick agent。前沿模型在主線上解題，價格較低的模型也同步處理同一任務；前沿模型判斷何時可把工作交給 sidekick。兩者共享大量脈絡，也會頻繁把資訊寫回檔案系統，避免內容超出脈絡視窗。

「前沿模型會判斷，這個任務交給能力較弱的模型也沒問題。這和人的職涯發展很像：往上走時要學會委派，把自己留在槓桿最高的工作上。」

兩個模型並行的用意是讓雙方都保有任務脈絡，若只在需要時才切換，接手者很難立即取得同等理解。

這套做法再配合注意快取的路由決策，使 Devin Fusion 在品質略有提高的同時，價格效能改善約 35%。

## 讓使用者選模型，是雲端代理的 UX 缺陷

Devin Desktop（近期由 Windsurf 更名）與 CLI 仍允許開發者自行選模型，因為本地代理的使用者偏好控制權。雲端 Devin 則只提供價格與能力層級，由 Cognition 決定底層模型。

早期測試若讓雲端使用者直接選模型，常出現兩種抱怨：選了便宜模型後覺得 Devin 變笨，或選了昂貴模型後認為費用太高。Kaplan認為，這是產品把最佳化責任丟給使用者造成的問題。

「人們要的是最好的效能與價格，而且不能犧牲正確性。代理廠商有責任把這些最佳化處理好，不該讓使用者為此操心。」

## 自訓模型的價值，在於短期專精與產品成本

Cognition仍大量投入強化學習與後訓練。Kaplan知道下一代前沿模型終究會更強，但專用模型能在當下交付接近前沿的能力，也能把產品需要的行為直接訓進模型。

Devin Review 是一個例子。它除了提供檢視差異的介面，也在每次程式碼變更上執行輕量靜態分析與模型檢查，尋找錯誤、安全漏洞與 lint 問題。前沿模型可以完成，費用卻太高；便宜的通用模型成本較低，品質又可能不足。專門訓練的模型可在這個狹窄任務上改善價格效能。

Kaplan接受這類模型只有幾個月的半衰期。他認為 AI 新創必須習慣以三到六個月為單位思考：利用當下模型能力做出有差異的產品，等優勢消失後，再訓練下一個專用模型。

Cognition 同時維持的專用模型只有個位數。公司的焦點仍是軟體工程，SWE 1.6 系列可部署到多個位置，不必管理五十或一百個過度細分的模型。Kaplan 表示，SWE 1.6 依 token 使用量計算，是 Devin Desktop 最受歡迎的模型，品質約在 Opus 4.6 的水準。

## Cerebras 每秒約 950 token

SWE 1.6 也用來改善延遲。Kaplan 表示，Cognition 是較早大規模部署 Cerebras 的西方公司之一。測試顯示，自家模型在 Cerebras 上約可達每秒 950 token，比同等規模模型使用 GPU 快數倍，服務成本則略高。

他將這種取捨描述為價格與吞吐量帕累托曲線上的獨特位置。Cerebras 的速度讓 Cognition 得以推出原本難以成立的產品體驗。隨著 Transformer 架構逐漸標準化，晶片設計者也能對工作負載作出更具體的假設，換取更高效率。

Kaplan回憶在 Tesla 與晶片團隊合作時，散熱是設計上限，功耗又有很大一部分花在搬移記憶體。團隊因此逐項檢查哪些功能可拿掉，甚至討論晶片是否需要支援除法。當時的卷積神經網路在推理階段不需要直接除法，批次正規化中的除法也可融合進卷積權重與偏差。

「推理需求會非常龐大，所以我認為專用化程度也會非常高，帶來大幅效能提升。」

## 主動式代理，從 Slack 訊息自行找工作

Kaplan目前最重視的另一層，是代理與組織脈絡的整合。Cognition 把 Devin 接入多個 Slack 頻道，讓它分類訊息，判斷自己是否該加入討論或展開調查。它知道程式碼庫各部分由誰負責，也能把修改建議送給適合的審閱者。

「穩定運作後，公司多數工程工作應預設由代理主動完成。人仍負責決策與新的技術方向，不必再被使用者回饋、錯誤報告和當機調查追著跑。」

主持人問這是否就是「software factory」。Kaplan不喜歡這個詞，因為工廠讓人想到重複生產相同物品，編碼代理的價值卻在於依公司脈絡完成高度客製的工作。他更在意的是，公司能否先投入固定成本，建立一套會依目標、輸入與回饋持續改進的工程系統。

## 一人可以發動全公司的資安修補

漏洞修復是主動式代理成長最快的用途之一。模型同時提高了資安攻擊與防禦能力，大型企業因此急著清理既有漏洞。Cognition 為此推出 Devin Security Swarm。

每個 Devin session 都在獨立的 microVM 執行，因此可以重現潛在漏洞，再驗證修補是否有效。面對無法放進單一模型脈絡視窗的大型程式碼庫，系統先將掃描工作切片，找出脆弱部分，再分派修補、合併結果並驗證。Kaplan將它形容為資安工作的代理式 MapReduce。

這種工作方式讓一名工程師能啟動相當於大量工程人力的全公司修補。人的價值也隨之移向選題、拆解大規模改動，以及留下可持續改進的系統。

## 新進工程師未必處於劣勢

如果入門工作都交給代理，新進工程師如何累積經驗？Kaplan的回答是，所有人使用代理的年資都很短，新的能力階梯才剛開始。真正有效的方法仍是親自嘗試、動手做，並持續重測模型的能力邊界。兩三個月前失敗的做法，現在可能已經可行。

「大家使用代理的經驗都沒幾年。某種意義上，我們站在同一起跑點，眼前是一條新的能力階梯：如何真正把代理用好。」

他甚至認為新進工程師有相對優勢。代理不會嫌問題愚蠢，可以反覆解釋程式碼庫、指出實作位置，讓新人更快熟悉工作。Cognition原本主要服務專業工程師，如今也看到過去不自稱工程師的人開始主導軟體建置。

## 通用代理何時值得做專用產品

Cognition會避免為單一需求過度設計，因為下一版通用 Devin 可能很快就能處理。但公司也扮演獨立代理實驗室，要把底層模型能力做成端到端產品。

Kaplan 認為，產品投資要兼顧兩件事：修掉既有使用摩擦，也追蹤使用者意外找到的高價值用途。資安專用產品就是後者。當團隊發現漏洞修復已是 Devin 最常見的用途之一，便投入專門介面與服務，而非只要求客戶繼續使用通用代理。

## 獨立代理實驗室與前線部署工程師

Cognition 與模型實驗室既合作也競爭。Kaplan認為，獨立代理公司的結構性價值，是讓代理與單一底層模型解耦。

「理想狀態是，不管誰發布了更好的新模型，你每天醒來聽到消息都會很高興。」

Cognition 的前線部署工程師人數已超過其他工程師。這些人深入客戶現場，既處理技術細節，也要理解業務目標。例如客戶必須在年底前完成系統遷移，原排程卻要四年，前線部署團隊便要找出代理可切入的部分並縮短時程。

Kaplan說，具創業經歷的人往往適合這個職位。他們習慣在模糊問題中工作，能兼顧技術與客戶痛點，也較能判斷哪個問題值得先解。當編碼代理幾乎什麼都能嘗試時，選對問題本身就成了重要能力。

## 追高 token 用量的激勵錯位

Kaplan認為，許多 AI 廠商有強烈誘因鼓勵客戶不斷增加 token 用量，把使用量排行當作成功指標。企業帳單升到每年數千萬、數億美元後，管理層終究會問這些支出換到了什麼。

獨立代理公司不必只替特定模型拉高用量，理論上更容易站在客戶一邊，拒絕低價值工作。Cognition早期以人工方式和客戶估算投資報酬，但這無法規模化。團隊後來改測較容易自動判斷的有效工程產出。

第一步是判斷每次 Devin session 是否產生有效工程產出。若 session 建立了 PR 卻從未合併，系統保守地歸為無生產力；合併進正式環境則算有生產力。沒有 PR 的資料分析等任務，則由以客戶共同標註資料訓練的分類器判斷。

第二步是估計有效 session 節省多少工程時數。Cognition透過人工訪談與資料蒐集，估計使用 AI 前後的差異，再把 session 是否有效與省下多少時間兩項結果結合，為個人、團隊與公司提供可比較的分數。

## 1,000 萬美元生產力保證

評估結果顯示，客戶透過 Devin 節省的時間足以讓 Cognition承擔財務風險。公司因此提出最高 1,000 萬美元的生產力保證。

內部曾擔心有人用迴圈不斷呼叫 API，幾百萬美元很快就會燒完。Kaplan的結論是，既然公司承諾補差額，就應在產品裡加入預算上限與算力分配工具，讓管理員決定總預算，也協助判斷誰可使用更多算力、誰還需要較嚴格的限制。

「如果客戶只是空燒用量，沒有得到相應價值，而支付金額又超過省下的工程時數價值，我們就退還差額。這迫使我們和客戶站在同一邊。」

## 儀表板是教練，不是監控器

生產力資料最常用於團隊學習。管理者可以比較不同團隊投入費用後得到多少有效產出。成本偏高通常不是惡意浪費，而是使用方式不同，使用者也未必知道哪個步驟效率差。

Cognition把教練功能放進產品。Devin可以指出提示寫得太簡略，並提出具體改善方式。Kaplan認為，技術變化太快，幾個月前的能力限制可能已消失，依賴人工訓練很難跟上。儀表板的主要用途，是讓團隊與個人看見自己如何提高生產力、降低費用，並逐步掌握與代理協作的新方法。
