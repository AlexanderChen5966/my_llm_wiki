FigCraft 吸引人的地方，是把設計檔放在自己電腦，也讓 AI 能直接修改畫布。因為若代理只回傳一張截圖，設計師後續仍得重做圖層、元件與互動，省下的時間很有限。

2026 年 10 月 24 日，X 上出現這個原生開源設計工具的介紹。原作者公開的專案，以 Rust 開發介面設計與原型功能，並把操作命令開放給程式與代理。

Rust 是一種系統程式語言，但使用者更需要關心的，是它產生什麼文件、哪些功能可用，以及能否保留既有設計的結構。

截至 10 月 24 日查詢，原作者仍把產品標為早期 alpha，Figma 檔案匯入也屬盡力相容。因此可以先拿副本試做，還不適合只憑功能清單就搬走全部客戶專案。

它的離線與開源值得研究，但多人分享會改變資料去向。選擇本機編輯、區域網路協作或線上伺服器，是三種不同的工作方式。

對設計師而言，第一個值得測的問題，是一份設計離開原本平台後，能否繼續用相同的元件與規則維護。

## FigCraft 能保留哪些設計結構？

依 [FigCraft 官方專案](https://github.com/storytold/figcraft?ref=aiposthub.com) ，工具包含畫框、自動排列、元件、變體、樣式、變數與原型。這些結構讓設計可以反覆修改，比單張圖片更接近團隊日常使用的設計文件。

畫框可以整理不同頁面，自動排列則讓物件依規則排版。例如按鈕文字變長時，周圍留白與尺寸可以跟著調整，減少每次改字都要手動拉動圖形的工作。

### 元件與變體為什麼比外觀相似重要？

元件是可以重複使用的設計單位，例如同一套按鈕。變體則保存不同狀態，讓預設、滑過與停用的外觀有共同來源，避免每個畫面各自畫一份而漸漸失去一致性。

因此測試匯入時，不能只看第一眼像不像。若按鈕看起來正確，卻已失去元件關係，日後要改所有頁面的按鈕顏色，就可能重新變成逐頁修改。

變數也有同樣作用。官方範例用一組顏色變數切換明暗主題，設計師可以確認同一個介面在兩種模式下是否仍對應正確的語意，例如背景與文字的關係有沒有被打散。

原型功能則讓畫面之間建立互動關係。若匯入後畫面都還在，連線卻消失，檔案仍然可以看，但用來展示使用流程的價值就會降低，所以應把互動一起納入測試。

### 匯出 React 程式碼能省下多少工作？

README 展示 Dev Mode 的註記與 React 程式碼，其中元件屬性可以轉成程式傳入的設定。這有助於開發者理解設計結構，也讓代理有機會把設計與前端連在一起。

但設計匯出的程式碼仍需要放回產品情境檢查。因為資料來源、登入狀態與錯誤處理不會單靠一張設計稿決定，團隊仍要確認元件是否符合現有專案的規則。

所以可以先拿一張小型介面測交接，觀察匯出的結構是否容易閱讀、修改與重用。若它只能展示外觀，仍可以當作原型參考，卻不應直接視為正式產品的完整程式。

## AI 如何透過 MCP 操作同一份設計？

這個工具的做法，是讓介面、命令列、JSON 控制與 MCP 使用同一套命令。MCP 是讓 AI 串接工具的協定，因此代理可以透過明確的操作要求讀取與修改設計，而不用只猜畫面座標。

原作者說明，命令清單有四百多項，涵蓋選單、工具與拖曳動作。這些是專案自己列出的能力，實際使用時仍應確認當前版本支援的參數與結果。

### 同一套命令有什麼實際意義？

如果人與代理走同一套文件操作，就比較容易把變更對應回設計結構。例如新增一個畫框、設定自動排列，再建立按鈕實例，每一步都能由命令描述，而非只留下完成後的截圖。

這對反覆改版有幫助。因為設計師可以要求代理只調整一個元件的文字與間距，再讀回變更。若結果不合適，也比較容易找到修改範圍，而不用猜代理剛才碰過哪裡。

原作者另提供無視窗執行的命令列工具，可以渲染、匯出或執行設計命令腳本。這讓批次出圖與自動化工作有入口，但是否適合團隊，仍要看字型與渲染結果是否一致。

桌面程式也有只接受本機連線的控制通道，用來檢查狀態、操作與截圖。這裡的本機通道是程式控制方式，與把文件上傳到公開協作服務，是不同功能。

### 代理做得到，也要讓人看得懂

若第一次就讓代理重排整份設計，檢查負擔會很大。比較容易驗收的做法，是挑一張畫面與一個可重用元件，要求完成一項具體變更，再看原始檔、畫面與匯出是否一致。

例如把按鈕文案改長，同時保持左右留白與圖示對齊。這個測試會碰到文字、自動排列與元件設定，比單純新增矩形更能反映工具是否適合真正的設計工作。

測試時也要保存修改前的副本，因為代理操作順利，只能證明該次命令成功，還需要看它有沒有影響其他頁面的實例，才能知道文件關係是否保留。

## 離線與多人分享，資料路徑有什麼不同？

官方 README 說明，本機工作不需要帳號，也沒有遙測，但分享或加入線上文件時，會開始涉及網路服務。因此「可離線」應理解為一種使用模式，不能延伸成所有功能都不傳資料。

以下依原作者的隱私與分享說明，整理三種模式，方便團隊在試用前選擇。

| 模式 | 文件放在哪裡 | 需要理解的條件 |
| --- | --- | --- |
| 本機離線編輯 | 自己的磁碟 | 以本機檔案為主，仍要自行備份 |
| 線上分享 | 選定的協作伺服器 | 預設公開服務會保存文件，管理者可讀取 |
| 區域網路分享 | 由你的應用程式主持連線 | 不經協作伺服器，但連線本身沒有加密 |

這些差異會直接影響客戶資料能不能放進去。團隊應先決定資料允許的去向，再選模式，避免因為產品主打離線，就忽略自己按下分享後的變化。

### 停止分享，不等於伺服器立即刪檔

官方說明中，線上分享會把文件上傳到伺服器，預設為公開協作服務，也可改成其他或自架服務。傳輸使用加密連線，但伺服器儲存的文件沒有端對端加密，所以管理者可以讀取。

停止分享會撤銷分享代碼與中斷其他人的連線，但文件仍可能留在伺服器。依 README，可以另外移除，公開服務也會在三十天無人開啟後清除，因此停止存取與刪除資料需要分開理解。

連結或代碼本身就是存取依據。因為沒有帳號系統，拿到編輯連結的人可以修改，拿到觀看連結的人可以開啟，所以轉貼連結前要先看權限，不能用一般工作群組的習慣隨意散發。

區域網路模式雖然不經中央伺服器，原作者也註明連線沒有加密。因此它適合在可信任網路評估，不能直接當作已符合所有機密協作需求的方案。

### 原作者如何描述多人協作的成熟度？

README 把即時多人協作標為預覽，也說明沒有帳號、團隊或完整雲端體驗。這讓它與成熟雲端設計平台的差距具體可見，團隊不必只從單張協作截圖猜功能深度。

公開服務也沒有承諾備份與可用性，因此即使只是測試，仍應保留本機副本。這種限制會影響它是否適合當唯一工作來源，尤其是多人交付與長期維護的專案。

## 替換 Figma 前，如何測檔案相容與授權？

先挑具有代表性的文件副本，檢查文字、元件、變數與原型，再比較匯出結果。因為原作者明確把 Figma 的.fig 匯入稱為盡力相容，讀得進檔案不能直接推導出所有關係都完整保留。

### 測試應該包含哪些真實內容？

設計檔最好包含中英文混排、不同字重、圖片裁切與自動排列。這些內容容易在換工具後露出差異，所以比一張全是矩形的測試稿，更能看出日常工作會遇到的問題。

接著修改一個共用元件，再看所有實例是否正確更新。如果有些實例失去關聯，就應先了解原因，因為這會影響團隊後續維護成本，與第一次開檔時畫面像不像同樣重要。

官方提供八種起始範本，包括行動介面、著陸頁、儀表板與設計系統。若現有文件太複雜，可以先從範本做一個新專案，評估工具自身的工作方式，再研究搬遷。

截至 10 月 24 日，README 仍以約四成九的自評進度描述取代商業工具的狀態。這是作者估計，沒有統一的外部衡量標準，因此適合當作早期程度的提示，不能當作功能相容率。

### 開源程式與品牌素材的規則一樣嗎？

官方當日說明為 MIT 或 Apache-2.0 雙重授權，可依條件選用，這比第三方 X 介紹只寫 Apache-2.0 更完整。但原作者另外列出素材署名與商標例外，所以不能把程式授權當成品牌使用許可。

如果要重新散布或修改工具，應閱讀 [授權與素材說明](https://github.com/storytold/figcraft/blob/main/ATTRIBUTION.md?ref=aiposthub.com) ，確認保留哪些告示。一般設計師試用時，也可以先保存所用版本，方便之後查回當時的條件。

### 檔案由自己保存，也要規劃版本與交接

原作者說明，文件是保存在磁碟上的.figcraft 封存檔，並提供命令列渲染與匯出。這讓團隊能把原始設計當成自己的工作資產保存，但檔案可取得與備份已完成，仍是不同的事。

如果多人輪流修改，最好在交付時標示版本與修改範圍。因為離線文件不像共用雲端頁面那樣自然指向同一個位置，容易出現兩份名稱相同、內容不同的檔案，造成審閱者看錯版本。

測試匯出時，也可以把同一份設計分別存成向量與點陣格式，再比較文字與透明效果。向量適合繼續調整形狀，點陣圖則便於固定畫面，兩種格式能反映不同的交付需求。

字型也是換工具時的重要依賴。官方說明有配套字型專案，缺少時會回到系統字型，因此團隊應把自己的品牌字型納入測試，避免以預設範例正常就推定所有文件都沒問題。

若某個客戶文件目前無法完整匯入，可以保留原始平台作為權威版本，只把新做的小型設計放進試驗。這樣既能累積工具使用經驗，也不會因為追求一次搬完，而增加既有專案的交付風險。

## 想試開放設計流程，可以先建立小型設計系統

FigCraft 適合拿來探索本機文件與代理共同編輯的工作方式。因為它把元件結構與命令操作放在一起，設計師可以具體檢查 AI 修改的結果，並保留可繼續維護的文件。

若你依賴大量既有 Figma 文件、穩定多人協作或完整組織管理，就先做副本測試。可以從一套按鈕與兩張畫面開始，驗證匯入、修改與匯出，也可免費訂閱 AI 郵報追蹤後續版本。

## FAQ：FigCraft 常見問題

### FigCraft 已經能完全替代 Figma 嗎？

原作者仍標示 alpha，.fig 匯入也屬盡力相容。是否適合替換，需要用自己的文件與協作需求測試。

### 不用帳號是不是代表文件永遠不會上傳？

離線編輯以本機檔案為主，但線上分享會上傳到選定伺服器。分享模式與停止分享後的資料保留，都應另外確認。

### FigCraft 程式只有 Apache-2.0 授權嗎？

截至 2026 年 10 月 24 日查詢，官方 README 列的是 MIT 或 Apache-2.0 雙重授權，商標與個別素材另有條件。
