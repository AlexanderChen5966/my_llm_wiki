GBrain 是 Y Combinator 執行長 Garry Tan 開源的 AI 記憶系統，社群貼文把它稱為他的「第二大腦」。

GitHub 資料顯示，這個專案建立於 2026 年 4 月 5 日，到 11 月 9 日查詢時已有約 3.18 萬個星號，所以它並不是剛冒出來的冷門儲存庫。

但「第二大腦」這個詞很寬，讀者的第一個疑問多半是：它是筆記軟體、聊天機器人，還是別的東西？

依儲存庫的 README，它是替 AI 代理準備的記憶層。AI 代理指能自己呼叫工具、完成任務的 AI 助手。

README 說，記憶以 Markdown 檔為主，放在使用者掌控的資料夾，事實可以更正、撤回，專案也能自己架設。

這點重要，是因為代理的記憶若綁在單一平台，換工具就得從頭教起，而這個專案把記憶放進使用者自己的檔案與資料庫。

我會把它看成給已經在用 AI 代理、也願意自己維護檔案的人的工具，而不是人人都該立刻安裝的筆記替代品。

要判斷貼文的說法有多少站得住腳，得先看這個專案由誰做、做到什麼程度。

## GBrain 是誰做的？貼文與儲存庫各說了什麼

貼文的主角確實是 Garry Tan 的公開儲存庫，但「很多人還不知道」這類說法必須分開看。

這則貼文出自帳號 @imryven，11 月 8 日發出，稱 YC 執行長開源了自己的第二大腦。貼文宣稱列出八個第二大腦儲存庫，第一個就是 Garry Tan 的專案，並形容為「每個事實都保留來源」。

第三方貼文只能當線索，所以得回到儲存庫查證。README 以第一人稱寫明，作者是 Garry Tan，並說明它是自己 AI 代理背後的記憶系統。

GitHub 的儲存庫資料顯示，專案採 MIT 授權，主要語言是 TypeScript。MIT 是寬鬆的開源授權，允許自由使用與修改，所以個人可以自行架設，不必取得額外許可。

截至 11 月 9 日查詢，預設分支有 13,690 筆提交，其中 11,394 筆來自 garrytan 帳號。因此它主要是作者本人持續維護的專案。

最新版本是 v0.60.620.0，發布於 11 月 9 日 UTC 02:29。更新紀錄寫明，這一版讓偏離遠端的受管理 Git 檢出，在啟用 Git 持久化時，重新整理預設會發布本地提交，發布前先掃描是否含有祕密。這屬於維運細節，但可以看出專案仍在密集更新。

### 作者早就公開談過這個專案

因為 Garry Tan 在 X 上的貼文比社群轉述早得多，所以時間線可以直接核對。4 月 15 日他宣布 v0.10.0，說自己的 OpenClaw 設定與記憶庫可以讓別人使用。

OpenClaw 與 Hermes 是 README 提到的兩種代理框架。4 月 30 日，他寫自己每天搭配兩者使用，檔案超過 7.5 萬個。

5 月 16 日，他又說明這是知識系統，不是把 RAG 裝進盒子。RAG 是先檢索資料、再交給模型回答的做法。

從這些公開時間與星數來看，「多數人還不知道」更像貼文的修辭，無法驗證。弄清楚作者與時間線之後，接著要看資料實際存在哪裡。

## 第二大腦怎麼存資料？Markdown 是正本

使用者自己資料夾裡的 Markdown 檔是正本，資料庫裡的索引可以從檔案重建，但少數紀錄只存在資料庫。

依官方的「記憶存放位置」說明，每個檔案開頭有 YAML 格式的欄位資料，檔案放在使用者擁有的資料夾，通常用 Git 管理版本。

系統會把這些檔案索引進 Postgres 資料庫。預設使用內嵌的 PGLite，也能改用 Postgres 加 pgvector，兩者都附帶向量與關鍵字索引。

PGLite 是不必另架伺服器、能在本機內嵌執行的 Postgres。向量索引則是把文字轉成一串數字，讓語意相近的內容能被找出來。

索引壞了，可以從檔案重新建立。但重建有範圍，因為只存在資料庫裡的東西沒有檔案可以還原。

這些內容包括私密頁面、沒有頁面可放的事實、修訂歷史與寫入收據。官方因此說，Markdown 匯出不等於完整備份，資料庫也要另外備份。

新建的記憶庫預設放在使用者家目錄的.gbrain 隱藏資料夾底下，使用者可以改成自己的資料夾。因為是純文字檔，所以能用任何編輯器開，也能放進自己的 Git 儲存庫。

但代價是備份與同步要自己決定，因為自架時沒有人代勞。資料存好之後，才輪到怎麼取回。

## search 與 think 差在哪：回答附來源，也標出不知道的部分

README 把查詢分成兩種：search 回傳頁面，think 則組合出附來源的答案。

search 結合關鍵字與向量排序，再可選擇加上重排序，適合拿原始素材。think 在同樣的檢索之後，寫出帶引用的回答。

README 說，think 的答案還會標出記憶庫缺什麼，例如頁面已過期、說法沒有引用，或兩頁內容互相矛盾。

它的示範用一位虛構的 Alice 當例子：回答先整理未完成事項，最後提醒自上次紀錄後沒有新資料。這是官方示範，不是實際使用者的輸出。

### 知識圖譜與官方自報的測試分數

另外還有一張帶類型的關係圖。README 說，啟用自動連結時，受信任的本機寫入會用模式比對抽出頁面之間的連結，過程不呼叫語言模型。

但官方文件同時提醒，抽出的關聯是待檢查的證據，不等於關係為真。

README 提供了一組內部測試數字。在 BrainBench 的關係類問題上，關係檢索讓正式環境的 R@5 由 0.6626 升到 0.7241。

R@5 指前五筆結果涵蓋正解的比例。README 也註明，0.9791 是用標準答案推算的上限，不是產品分數。這些數字出自作者自己的測試，本文沒有重跑。

官方把整合答案與圖譜都列為選配，其中整合答案需要先設定聊天模型，所以不能把示範輸出當成預設體驗。接著看「保留來源」這個賣點的實際範圍。

## 「每個事實都保留來源」指什麼

保留的是事實與來源頁面的對應，並允許更正，但不保證來源本身正確。

README 開頭就說，系統儲存明確的事實與其來源，支援更正與撤回，並讓不同代理共用同一份記憶。

撤回有邊界。官方說明指出，forget 只是讓某個事實不再出現在回想結果，並沒有刪除原始材料、歷史紀錄或私人備份。

要把文字從運作中的儲存處移除，擁有者必須在記憶庫所在的主機執行清除指令。所以存了敏感內容的人，不能只靠 forget。

自動擷取則要自己開啟。官方寫明，明確要求「記住」可以直接運作，但裝上掛鉤才會啟用對話壓縮與結束時的擷取。

保留來源讓使用者能回頭查證，卻不替內容背書。來源若本身寫錯，記憶庫只會準確地記住那個錯誤。

了解它存什麼之後，就能看實際安裝需要付出什麼。

## 安裝 GBrain 需要什麼？先無金鑰，再逐項加功能

可以從無金鑰的本機模式開始，語意搜尋與背景處理等功能再逐項加入。

README 列出的需求是 Bun 1.4.4 以上，Bun 是 JavaScript 的執行環境。自架時從 GitHub 安裝穩定通道，再執行 `gbrain init --pglite --no-embedding` 建立本機記憶庫。

官方特別警告，npm 上有同名但無關的套件，所以不要用 npm 安裝。這項提醒直接寫在 README 的醒目區塊。

已有筆記的人，可以用官方的匯入指令把資料夾索引進來，再用 search 查詢。本文沒有執行這些指令，以上依官方說明整理。

### 有些功能需要自己的金鑰與主機

無金鑰模式只做關鍵字檢索。要加入語意搜尋、重排序或整合答案，就得設定模型供應商，那是另外的費用。

README 說，24 小時常駐的版本建議跑在記憶體 8 GB 以上的伺服器，並有自己的模型用量。官方也提供付費代管服務 gbrain.io，但那只是選項，不影響自架。

README 引用作者自己的正式環境：155,795 頁、24,589 位人物、5,340 家公司、66 個排程。這是自述規模，所以不代表一般安裝會有同樣內容。

同一個儲存庫的起源文件寫的是撰寫當時的規模，頁數為 17,888，與 README 相差很大，可見這些自述數字會隨時間改變，不是固定規格。

費用之外，還有資料離開機器的問題。

## 隱私與安全邊界：資料會流到哪裡

資料雖然在本機存檔，但設定了雲端模型後，文字仍可能送到外部供應商。

官方的記憶邊界說明寫明，已設定的雲端向量、重排序、抽取與整合供應商都可能收到文字。即使是無金鑰模式，代理使用的模型也看得到被叫回的記憶。

同一份文件提醒，不要把祕密放進記憶頁面。像密碼這類資料，應放在本機設定，不要寫進可被共用的記憶。

作為公司共用記憶時，限制更明確。遠端使用者受來源與操作授權限制，但本機檔案與共用資料庫憑證屬於另一條信任邊界。

README 也寫明，授權測試只涵蓋特定存取路徑，並非「一定不外洩」的保證。所以要分享給團隊前，應先讀官方的分享邊界與公司記憶庫教學。

安裝本身也有信任問題。SECURITY 文件說明，從原始碼安裝與固定標籤安裝，屬於第一次使用時信任的模式。

若要最強的保證，官方建議安裝帶有建置證明的發行版執行檔，並用 `gh attestation verify` 驗證。看完風險，剩下的問題是它適合誰。

## GBrain 常見問題

### 要付費嗎？

軟體本身是 MIT 授權，可以免費自架。官方另有付費的 gbrain.io 代管服務，可選擇。使用模型與向量服務的費用，依自己設定的供應商另計。

### 一定要搭配 OpenClaw 或 Hermes 嗎？

不一定。README 建議的第一種做法，是把它加到既有代理，並提供 Grok Bot、Muse、Codex 與 Claude Code 的指南。沒有代理時，也能用命令列單獨運作。

### 記憶存在哪裡，可以帶走嗎？

正本是你資料夾裡的 Markdown 檔，可用 Git 備份與同步。只存在資料庫的紀錄，如私密頁面與修訂歷史，要另外備份資料庫。若要換電腦，官方的做法是用 Git 同步資料夾，讓另一台機器依檔案重建資料庫。

### 可以匯入現有筆記嗎？

可以。官方指令能把一個 Markdown 資料夾匯入並建立索引。已有公司知識庫的團隊，官方建議先產生匯入計畫，確認後再執行。

## 結語：適合會維護自己資料的 AI 代理使用者

它適合已經每天使用 AI 代理、希望記憶掌握在自己手上，也不介意管理檔案與備份的人。

想研究代理記憶設計的開發者也適合，因為專案把檔案、索引、圖譜與排程的關係寫得相當完整。

不適合只想找即開即用筆記 App 的人，也不適合還沒決定哪些資料可以送給雲端模型的團隊，後者應先讀完隱私邊界再動手，否則可能把不該外送的文字交給模型供應商。

這則貼文提供了入口，但判斷依據應該是 README 與官方文件，因為標題只說了「又一個第二大腦」，沒有說明資料存在哪裡。

我會先用無金鑰模式匯入一小批不敏感的筆記，確認取回的內容與來源是否合用，再決定要不要加入雲端功能。
