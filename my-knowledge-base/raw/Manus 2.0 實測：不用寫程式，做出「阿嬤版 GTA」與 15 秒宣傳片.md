阿嬤騎著機車穿過台灣風格的街區，後座載滿便當。眼前的紅燈要停，送餐還能和朋友比快。這是我用 Manus 2.0 做出的《阿嬤便當快遞》：一款能在瀏覽器操作的 3D 網頁遊戲。我沒有自己寫程式，接著又把遊戲連結交給 Manus，請它做成一支 15 秒的直式宣傳片。

我把它暱稱為「阿嬤版 GTA」，指的是騎車穿梭城市的畫面感。遊戲採用原創角色與虛構店名，玩法是守交通規則送便當，沒有 GTA 的暴力元素。

這次最有感的，是 Manus 做完後還回報了測試與修正。雙人模式曾出現「比較晚送完的人反而獲勝」的問題，它找到原因後調整規則，再重新測試。影片也保留了可編輯的素材與時間軸，我能自己接手剪輯。

不過，能玩到遊戲、拿到影片，和所有功能都已驗收，是兩件事。本文會把製作流程、可複製的提示詞、時間與點數，以及這次沒有測到的地方一起寫清楚。

## 這次做出了什麼？先看成果與用量

《阿嬤便當快遞》的核心玩法，是依導航把便當送到目的地，途中遵守紅燈與兩段式左轉規則。遊戲有單人計時、同一台電腦的雙人分割畫面對戰，也做了排行榜介面與後台。宣傳片則從遊戲錄製畫面，加上標題、特效、配樂與音效。

| 項目 | 本次實測紀錄 |
| --- | --- |
| 遊戲任務 | 任務顯示「已工作 1 小時 27 分」 |
| 宣傳片任務 | 任務記錄為「已工作 47 分 54 秒」 |
| 兩個任務合計 | 約 135 分鐘，使用 6,970 點 |
| 遊戲測試 | Manus 任務回報 40 項自動測試通過，並記錄修正問題 |
| 專案素材 | 資源分頁顯示 339 個素材 |
| 宣傳片 | 15 秒、9:16 直式比例、1080 × 1920，可接手編輯 |

**135 分鐘是兩個任務顯示的工作時間相加，約為 2 小時 15 分。** 這個數字不能當成我的手動操作時間，也不代表從第一次輸入到最後匯出的完整耗時。6,970 點同樣是這次兩個任務的合計，這次沒有分列遊戲與影片各自用了多少點，因此不把它換算成固定單價。

對想試做的人來說，這份用量紀錄比較適合拿來抓初步預算。換一種遊戲、增加修改輪次或調整影片內容，都可能改變工作時間與點數。

## Manus 2.0 的哪些功能用在這次實測？

Manus 是能依照要求拆解並執行工作的 AI 代理工具，例如規劃專案、寫程式、操作瀏覽器與整理素材。依 [Manus 2.0 官方公告](https://manus.im/blog/introducing-manus-2-0?ref=aiposthub.com) ，這一版於 2026 年 9 月 28 日推出。Manus Studio 是桌面工作區，本次使用的是其中的 Game Dev 與 Video Editor，分別負責遊戲開發與影片製作：

- **Game Dev：** Manus Studio 中的遊戲開發環境，用自然語言描述遊戲，再製作、測試與調整可玩的版本。本次遊戲任務使用 Max 模式。

這篇聚焦上述製作流程。新版的其他功能，例如 Cascade 架構、遠端控制與 Cue，沒有在這次阿嬤遊戲任務中做獨立效能比較，因此不把官方宣傳數字當成本次實測成績。

## 第一步：把角色、規則和開發順序寫進 Prompt

我在 Manus 選擇「遊戲開發」，使用 Max 模式。Prompt，也就是交給 AI 的提示詞，要交代它應該完成什麼。這次我除了描述阿嬤與街景，也把製作順序寫進去：先完成能操作、能送達的核心玩法，再加雙人模式與排行榜，最後測試。

這個順序讓需求有清楚的優先次序。做遊戲時，角色能不能順利移動、怎樣才算完成任務，會直接影響後面的對戰與排名。先把這些規則定義好，比只說「幫我做一款很酷的遊戲」更容易檢查結果。

### 本次使用的遊戲 Prompt

> 請幫我製作一款可以直接遊玩的 3D 網頁遊戲。玩家是一位原創台灣阿嬤，騎機車在一座虛構、帶有台灣城市氛圍的街區送便當。玩家需要依照目的地導航完成送餐，紅燈需要停車，並加入適合機車的兩段式左轉／待轉概念。場景可加入騎樓、十字路口與機車停車格，但所有店名與招牌都必須是虛構的。整體風格可愛、幽默、適合大眾，不包含暴力元素。這次請加入多人玩法：支援兩位玩家同場競賽，比誰先把便當送到，並加上送餐時間排行榜，讓玩家可以比較成績。請先完成可以操作與完成任務的核心玩法，再依序加入雙人模式與排行榜，最後測試碰撞、轉向與送達判定。

想換題材，可以先改角色、移動方式與任務目標，保留「核心玩法 → 額外功能 → 測試」的順序。如果希望兩位玩家各用自己的電腦連線，也要直接寫清楚，因為「雙人玩法」可能被做成同一台電腦的分割畫面。

## 第二步：先看遊戲藍圖，再看它怎麼測試與修正

任務開始後，Manus 先讀取網頁開發相關說明，並規劃一份軟體設計文件。這份文件把遊戲玩法與實作方向先列出來，方便確認它理解的送餐規則，再進入開發。

完成後，Manus 的任務結果回報了 40 項自動測試通過。它列出的項目包括左右轉向、低速轉彎、撞牆滑行、兩台機車互撞後分開、紅燈判定、兩段式左轉，以及停穩才算送達。任務也回報用自動操作的方式，在實際網頁跑完單人與雙人各一局，並檢查本機排行榜紀錄。

其中最能看出測試價值的，是雙人勝負判定。原本的規則會讓「比較晚送完，但罰秒較少」的玩家反勝，和 Prompt 要求的「比誰先送到」不一致。Manus 回報把規則改為先送完者獲勝，修正後再重測。

同一輪還回報修正了兩個問題：快速連續重開時，上一局的線上成績可能錯記到下一局，以及第二支手把的玩家對應。這些修正紀錄比一句「遊戲完成」更有用，因為它們指出了具體問題與處理方式。

**40 項通過是 Manus 在本次任務中的測試回報。** 我保留這份紀錄，但它不能替代正式發布環境、實體手把或多人跨裝置連線的驗收。測試涵蓋到哪裡，後面的限制也要一起看。

遊戲主選單提供單人計時挑戰、雙人對戰與送餐時間排行榜。雙人模式的實際畫面是上下分割，兩位玩家在同一台電腦比誰先送完。

![兩位阿嬤騎機車送便當的上下分割畫面，為同一台電腦雙人對戰](https://storage.ghost.io/c/5e/61/5e6189f0-c5e0-49a0-97b4-5eddd3f43c77/content/images/2026/10/manus-grandma-split-screen.jpg)

這個版本適合坐在同一台電腦前一起玩。如果需求是讓朋友從各自的電腦加入，就要另外驗收線上連線。官方的 [Game Dev 說明](https://manus.im/features/game-dev?ref=aiposthub.com) 提供遊戲製作與分享流程，而 2.0 公告中的線上多人功能涉及選擇並購買 Cloud Computer，也就是讓遊戲伺服器持續運作的雲端電腦。本次分割畫面的成果不能直接代表已完成那套連線流程。

排行榜除了介面，也有後台資料表。本次控制台畫面列出了帳號、榜單與每局紀錄等資料，但資料表存在，只能說明後台已建立。正式版登入後是否能送出成績，仍屬於本次沒有驗證的項目。

素材管理也比我原本想像的完整。「資源」（ASSETS）分頁顯示 339 個素材，分成圖片 273 個、音訊 22 個、3D 模型 19 個、影片 22 個與字型 3 個，合計相符。素材再依角色、機車與車輛、店家招牌、街道與建築、交通號誌等分類，3D 模型也有轉台預覽。

這個分頁的價值，是讓後續修改有入口。想調整阿嬤、機車或招牌時，可以先找對應素材，不必只對著遊戲畫面猜要改哪一個檔案。

## 第四步：把遊戲連結交給 Manus，製作 15 秒宣傳片

遊戲完成後，我另外開了一個影片任務，選擇「建立 → 影片」，使用 Video Editor 下的煉金模式。這次沒有先畫分鏡，而是附上遊戲連結，寫明片長、直式比例、開場重點與結尾。

### 本次使用的宣傳片 Prompt

> 用這個遊戲做一支 15 秒、9:16、適合 Reels 的宣傳短片：前 2 秒先放最吸睛的阿嬤騎機車畫面，接著快速帶過玩法（紅燈要停、雙人對戰），最後以成功送達收尾。節奏俐落，自動配上合適的音效與特效，不使用任何第三方品牌素材。

輸入這段提示詞時，再附上要宣傳的遊戲連結。它把一支短片最需要的幾個決定先定下來：前兩秒怎麼吸引人、中間讓觀眾看懂什麼、最後停在哪個畫面。

這次 Manus 接著打開遊戲，以程式操作瀏覽器錄製實機畫面，再生成配樂與音效，包括機車加速、喇叭、轉場、煞車、成功送達及對戰效果，組成一支 1080 × 1920 的直式影片。本次紀錄中的任務工作時間為 47 分 54 秒。

我會把這種做法用在展示玩法、活動預告或產品概念的第一版短片。需求裡先寫出具體畫面與節奏，之後才有依據判斷哪一段需要調整，避免每次只說「再更好看一點」。

## 本次沒有驗證的功能，還有哪些？

如果要把這個遊戲當成可以長期營運的成品，還有幾項檢查必須完成。任務結果直接列出了登入、排行榜與手把的限制，我也把同機雙人玩法和線上連線分開整理：

| 項目 | 本次紀錄與限制 |
| --- | --- |
| 鍵盤操作 | 本次記錄已實測可用 |
| 單人與同機雙人完整流程 | Manus 回報以自動操作各跑完一局 |
| 本機排行榜 | Manus 回報有正確記錄 |
| 正式版登入與線上成績送出 | 本次未在正式發布版完成測試 |
| 實體手把 | 只檢查程式，沒有接實體手把測試 |
| 不同電腦的多人連線 | 本次成果為同機分割畫面，沒有跨裝置實測紀錄 |

其中，「已修正成績錯記」和「正式版成績送出已驗證」要分開理解。前者是任務中的程式修正回報，後者需要在實際發布環境操作登入、完成一局並確認榜單結果。本次紀錄只支持前者。

這些限制不影響它作為遊戲原型的展示價值，卻會影響能不能直接交給大量玩家使用。我會先拿它展示玩法，再依預計開放的功能逐項驗收。

## 想自己試，先把這四件事寫清楚

1. **先定核心玩法。** 角色怎麼移動、要完成什麼、怎樣才算成功，應該比排行榜與裝飾細節更早決定。
2. **把測試情境寫進提示詞。** 本次指定了碰撞、轉向與送達判定。換成其他遊戲，也要列出最容易出問題的操作，並要求回報修正與沒有測到的項目。
3. **讓宣傳片有開頭和收尾。** 片長與尺寸之外，再寫明前兩秒的重點和最後畫面，才能檢查影片有沒有傳達玩法。
4. **把最後一輪留給自己。** 進 Studio 看時間軸，播放匯出檔。AI 先完成一版，你再決定節奏、文字與聲音是否符合用途。

## Manus 2.0 實測常見問題

### 不會寫程式，也能照這個流程做遊戲嗎？

本次的做法，是以提示詞交代需求，由 Manus 規劃、開發並測試，作者沒有自己寫程式。想照做，仍要能描述玩法，並檢查操作與勝負規則。沒有手動寫程式，不等於完全不用驗收。

### 6,970 點是做一款遊戲的固定成本嗎？

這是本次遊戲與宣傳片兩個任務的總用量，沒有個別拆分。修改次數、素材量與任務設定都可能影響點數，不能把它當成每款遊戲的報價。

### 雙人模式已經能讓朋友各自在家連線嗎？

本次展示的是同一台電腦的上下分割畫面。不同電腦的連線需要另外設定與測試，本文沒有提供那項實測結果。

### 可以在網頁產生影片，再到桌面剪輯嗎？

依 [Manus 官方 Video Editor 介紹](https://manus.im/blog/introducing-video-editor?ref=aiposthub.com) ，影片可以從網頁或桌面開始建立，完整時間軸則在 macOS、Windows 的 Manus Studio 桌面版編輯。本次流程也是產生影片後，再進 Studio 接手修改。

## 我的結論：適合先做出能展示的原型

這次實測讓我願意把 Manus 2.0 用在「先把想法做出來」的階段。阿嬤送便當的玩法、雙人畫面、素材庫與宣傳片都有具體成果，而且任務留下了測試與修正紀錄，讓我能接著檢查。

但如果目標是正式營運，我會先完成登入、線上排行、實體手把與需要開放的連線功能驗收。這些測試結果會決定它能從展示原型走到哪一步，也會改變我對交付品質的判斷。

想試做自己的版本，可以從 [Manus 官方 Game Dev](https://manus.im/features/game-dev?ref=aiposthub.com) 開始，先把遊戲規則寫清楚。做完後也歡迎留言：下一站，你想讓阿嬤送便當去哪裡？
