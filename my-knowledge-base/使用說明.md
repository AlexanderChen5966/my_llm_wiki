# 個人知識庫使用說明

> 這份系統的核心邏輯：**你負責輸入，AI 負責整理。**

---

## 一、加入新素材

把任何支援格式的檔案拖進 `raw/` 即可，不需要預先分類或命名。

**支援格式：**

| 格式 | 範例 |
|------|------|
| Markdown 文章 | `.md` — 網路文章、筆記 |
| PDF | `.pdf` — 論文、報告 |
| 截圖 / 圖表 | `.png` `.jpg` `.webp` `.gif` |
| 逐字稿 / 字幕 | `.txt` `.srt` `.vtt` |
| 網頁存檔 | `.html` |
| Jupyter Notebook | `.ipynb` |
| 資料表格 | `.csv` |

> **原則：** 截圖、PDF、逐字稿與 Markdown 文章具有同等的知識地位。格式不影響輸入門檻。

---

## 二、整理素材

### 單篇整理
```
請用 knowledge-organizer 處理這篇：raw/xxx.md
```
產出：一篇 wiki/ 條目（TBRC 格式），並更新 INDEX.md。

### 批次整理（10 篇以上）
```
raw-pipeline
```
三個 Agent 依序執行：摘要 → 分類 → 建立 wiki 條目。

## 三、找資料

| 我想找... | 去哪裡 |
|---------|--------|
| **還有哪些素材沒整理** | **[[raw-待處理清單]]（Dataview 即時清單）** |
| 所有主題總覽 | `wiki/INDEX.md` |
| 特定主題深入內容 | `wiki/[主題].md` |
| **某主題的跨篇整合結論** | **`wiki/synthesis/`（精粹條目，資訊密度最高，想快速掌握一個主題從這裡看）** |
| 跨主題概念框架 | `wiki/concepts/` |
| Sanlong APP 技術文件 | `wiki/sanlong/INDEX.md` |
| B2B Manager 技術文件 | `wiki/b2b-manager/INDEX.md` |
| AI 產出的報告和分析 | `outputs/` |

---

## 四、可用的 Skill

| 指令                      | 做什麼                                                  |
| ----------------------- | ---------------------------------------------------- |
| `knowledge-organizer`   | 處理單篇 raw/ 素材                                         |
| `raw-pipeline`          | 批次處理 raw/（10 篇以上）                                    |
| `daily-brief-generator` | 每日簡報（積壓、wiki 更新、任務狀態）                                |
| `wiki-health-check`     | 每月健康檢查（矛盾、缺口、孤立筆記、精粹過時偵測）                            |
| `knowledge-synthesizer` | 多篇同類型 wiki → 一篇精粹（CAVE 框架）                           |
| `knowledge-elevation`   | 精粹條目三層昇華：E 層加深 / 跨主題 meta-synthesis → wiki/concepts/ |
| `alignment-check`       | 掃描 wiki 補充資料段落是否放錯位置，找出歸屬不對齊的內容並建議搬移                 |

## 五、維護知識庫

**每天：** 把有價值的素材拖進 `raw/`，不需做任何事。

**每週：** 開 [[raw-待處理清單]] 看積壓數量——10 篇以上時跑一次 `raw-pipeline`；每跑完 3 批以上，執行一次 `alignment-check` 確認補充內容歸屬正確。

**每月：** 跑一次 `alignment-check` + `wiki-health-check`，確保內容位置正確後再做整體健檢。

**有需要時：** 同一主題累積 3 篇以上 → 用 `knowledge-synthesizer` 提煉精粹。

> **精粹會過時：** 精粹條目是「快照」，不會自動吸收日後新增的同主題文章。當該主題又長出新條目，`wiki-health-check` 會偵測到（比對 frontmatter 的 `source_count` 與現況）並在月檢報告提醒「🔄 精粹過時」，確認後重跑 `knowledge-synthesizer` 覆蓋即可。

## 六、腦力激盪

直接在對話中描述想法，讓 AI 協助展開：

```
我有個想法：[一句話描述]，幫我展開可能的方向
```

用蘇格拉底式提問幫你釐清模糊需求：
```
用蘇格拉底式提問幫我釐清這個需求：[描述]
```

整理好的想法存到 `ideas/`：
```
把這個想法整理成筆記，存到 ideas/
```

> **進階**：可搭配 [Superpowers](https://github.com/superpowers-ai/superpowers) 工具，提供更完整的 brainstorming → 規格撰寫 → 開發流程支援。

## 七、知識精煉框架

知識庫不只是「存得到、查得到」——這三個框架決定知識如何被**深化、結構化、輸出**。

---

### MAPS — 判斷什麼值得資產化

> 用途：決定一個想法/流程要不要花時間深入整理

四個維度評估：

| 維度 | 問題 |
|------|------|
| **M**indset | 這個知識會改變我的思考方式嗎？ |
| **A**rchitecture | 這個知識能否抽象成可演進的資訊架構藍圖（業務流程、數據流、結構設計）？ |
| **P**rompt | 這個知識能否用結構化指令表達——輸入清晰、輸出明確、AI 可精確執行？ |
| **S**ystems | 如何讓它持續迭代而不是一次性整理？ |

**決策規則：** 頻率 × 耗時 × 複雜度 ≥ 50 分 → 值得建立完整 wiki 條目或 Skill

→ 深入閱讀：`wiki/maps-framework.md`

---

### 5A+ — 知識庫的建設節奏

> 用途：不追求一次完美，用循環方式讓知識庫持續進化

```
AIM      → 定義這個階段要解決的問題
ACQUIRE  → 收集素材（拖進 raw/）
ATTEMPT  → 跑 knowledge-organizer / raw-pipeline 整理
ADJUST   → 根據產出調整 CLAUDE.md 規則或 Skill 設計
APPLY    → 把整理好的知識實際用在工作中
PLUS     → 每週 15 分鐘回顧，每月 wiki-health-check
```

**實際操作：** 不要等到 raw/ 有 100 篇再整理。每週積壓超過 10 篇就跑一次 `raw-pipeline`，保持 ADJUST → APPLY 的節奏。

→ 深入閱讀：`wiki/obsidian-knowledge-base-planning.md`

---

### SCQA — 把知識轉成有說服力的輸出

> 用途：把 wiki 裡整理好的知識，組裝成報告、提案、說明文件

麥肯錫溝通框架，適合任何需要「讓人快速理解問題與答案」的場景：

| 層次 | 問題 | 範例 |
|------|------|------|
| **S**ituation（現況）| 讀者已知的背景是什麼？| 「目前團隊每週花 3 小時整理會議紀錄」|
| **C**omplication（衝突）| 什麼打破了現況？| 「但整理出來的內容 AI 無法直接引用」|
| **Q**uestion（疑問）| 因此引發的核心問題 | 「如何讓會議紀錄變成 AI 可用的知識？」|
| **A**nswer（答案）| 你的解決方案或論點 | 「改用結構化 Markdown 模板 + raw-pipeline 自動整理」|

**在知識庫中的用途：**
- 寫 `outputs/` 報告時用 SCQA 組織結構
- 向他人解釋某個技術決策時用 SCQA 框架說明
- 腦力激盪後把想法整理成提案

**指令範例：**
```
用 SCQA 框架，幫我把這個想法寫成一份說明：[描述]
```

---

### 框架與 Skill 的對應

| 框架       | 用在哪個 Skill                           | 具體作用                                             |
| -------- | ------------------------------------ | ------------------------------------------------ |
| **TBRC** | `knowledge-organizer`、`raw-pipeline` | 每篇 wiki 條目的輸出格式（T 核心論點 / B 適用場景 / R 做法 / C 行動）   |
| **MAPS** | `knowledge-organizer`                | 計算 asset_value 決定素材是否值得建完整條目（頻率 × 耗時 × 複雜度 ≥ 50） |
| **CAVE** | `knowledge-synthesizer`              | 多篇整合的精粹結構（C 共識 / A 獨特視角 / V 知識缺口 / E 精粹論點）       |
| **SCQA** | `daily-brief-generator`              | 結構化「今日建議行動」（S 現況 / C 衝突 / Q 核心問題 / A 行動）         |
| **5A+**  | `wiki-health-check`                  | 健康報告末尾的「階段評估」——判斷知識庫在哪個成長階段，給出下一步方向              |

### 框架使用決策樹

不確定現在該用哪個框架時，用這個決策樹：

```
你現在要做什麼？
├─ 評估要不要整理這份素材  → MAPS asset_value（頻率 × 耗時 × 複雜度 ≥ 50）
├─ 批次整理積壓（10 篇以上）→ raw-pipeline（5A+ ACQUIRE 階段）
├─ 整理單篇成 wiki 條目    → knowledge-organizer（TBRC 格式）
├─ 多篇同主題提煉精粹      → knowledge-synthesizer（CAVE 框架）
├─ 精粹昇華為概念框架      → knowledge-elevation（E 層加深 / 跨主題 meta-synthesis）
├─ 掌握知識庫目前狀態      → daily-brief（SCQA 建議行動）
├─ 月度品質與健康檢查      → wiki-health-check（5A+ 階段評估）
└─ 把想法寫成有說服力的輸出 → SCQA 框架（S 現況 / C 衝突 / Q 問題 / A 答案）
```

### 完整流程圖

```
素材進 raw/
  ↓
knowledge-organizer（MAPS 判值 + TBRC 格式）→ wiki/ 條目
  ↓（同主題 3 篇以上）
knowledge-synthesizer（CAVE 框架）→ wiki/synthesis/ 精粹條目
  ↓（精粹條目 E 層加深 / 同領域 3 篇以上）
knowledge-elevation → wiki/concepts/ 概念框架
  ↓
daily-brief-generator（SCQA）→ 每日建議行動
wiki-health-check（5A+）→ 每月階段評估 + 下一步方向
  ↑（偵測精粹過時：source_count < 現況 → 提醒重跑 synthesizer）
```

## 八、規則提醒

- `raw/` **唯讀**：AI 只讀取，不刪除原始素材，內容一字不改。唯一例外是處理狀態這項流程元資料：
  - **`.md`**：處理完後 AI 會把 frontmatter 的 `status:` 改成 `processed`（**只動這一行**）。所以在 Obsidian 裡直接看 status 就知道整理過沒有
  - **非 `.md`**（PDF / 圖片 / 字幕）：這些檔案沒有 frontmatter 可寫，AI 改為在旁邊放一個同名的 `.processed` 空檔當標記（例：`report.pdf` → `report.pdf.processed`）。`raw/` 裡看到的 `.processed` 檔案不是垃圾，是「這篇已整理過」的紀錄
  - 素材處理完不會被移走，一律留在原地
  - 想知道還有多少沒整理，開 [[raw-待處理清單]] 這頁看即時的 Dataview 清單，或直接問「raw/ 還有幾篇沒處理」（完整判斷邏輯在 `rules/inbox-detection-protocol.md`）
  - ⚠️ 2026-08-13 前 `.md` 曾一度改用旁車標記制，那批舊標記檔還留在 `raw/`，**已不具判斷效力**，一律以 frontmatter 為準
- `wiki/` 由 AI 全權維護：整理、更新、建立連結
- `outputs/` 存放 AI 產出的報告和分析
- `archive/` 歸檔不活躍的筆記（不刪除）
