> 這裡的「研究」指：決定一篇素材是否值得存入知識庫、以什麼深度處理。

## 存入門檻：什麼值得處理

**必要條件（至少符合一個）**：

- 有目前關注領域（輔助程式開發工具 / AI 工具 / Flutter / APP 開發 / PKM）的具體操作內容
- 提出了和現有知識不同的角度或反例
- 有可直接套用的模板、流程、指令

**排除條件（符合任一直接跳過）**：

- 純新聞報導，沒有操作層細節（`asset_value` 趨近 9-15）
- 內容已被現有 wiki 條目完整涵蓋
- 系列文章的「中繼站/回顧篇」，沒有新技術內容
- 只是工具的基礎介紹，沒有深入到可操作的程度

**邊界案例（需要額外判斷）**：

- **輔助工具文章**（Obsidian 插件、生產力工具等）：即使不在主要關注領域，若有可直接套用的操作流程，仍可考慮存入 `ideas/` 暫放
- **個人開發紀錄**：屬於 `my-technical-notes/` 範疇，不走 raw/ → wiki 的知識整理流程，另行處理

---

## 處理深度判斷

**Full TBRC（wiki 條目）**：有可重複查閱的操作框架，asset_value ≥ 60

**輕量 ideas 條目**：觀念有趣但不到可操作、或是暫時存放待進一步整合

**直接標記已處理、不建條目**（標記方式見 [[inbox-detection-protocol]]：`.md` 改 frontmatter `status`，非 md 建 `.processed` 旁車標記）：
- 文章是現有條目的來源補充，內容已被涵蓋
- 圖片、視覺摘要，內容已被文字條目涵蓋

*asset_value 60 的門檻偶爾會出現「應該更高或更低」的邊界案例，屬於正常現象，以當下判斷為準。*

---

## 來源信任度

加權參考（非嚴格規則）：

1. 官方文件 / GitHub README（Anthropic、Google、Microsoft 等）
2. 一手實作經驗（作者親自測試並有數據）
3. 有引用來源的深度分析文章
4. 翻譯或轉述文章（注意是否有資訊失真）
5. 純彙整型媒體報導

**特別注意**：benchmark 數字若由廠商自行公布，要標記「尚未第三方驗證」。

---

## 多篇同主題的處理原則

**合併優先於並列**：3 篇以上講同一件事，整理成 1 個條目，捨棄重複。

**補充優先於新建**：新文章有 20–30% 不同角度 → 更新現有條目；超過 50% 不同 → 考慮建獨立條目。

**命名補充型條目**：用「-deep-dive」「-human-roles」「-practitioner」等後綴區分，明確說明補充哪個基礎條目。

## asset_value 評分參考

| 分數範圍       | 代表特徵                      |
| ---------- | ------------------------- |
| **9–30**   | 重複指標條目、純新聞、系列文中繼站         |
| **40–58**  | 輕量參考工具、基礎概念補充             |
| **60–72**  | 標準 wiki 條目，有操作框架          |
| **75–85**  | 可直接套用的方法論、有實測數據           |
| **88–100** | Synthesis 條目、社群共識框架、跨來源整合 |
